# 可观测架构：分布式故障发生后怎样找到影响链路

> [!summary]- 快速复习卡片（学完再看）
> 可观测架构用日志、链路跟踪和指标关联多个服务的信息，衡量 SLO 并定位影响。

## 出错信息散在十个服务里，为什么只看一条日志不够

一个请求经过网关、订单、库存和支付服务。单条日志只能说明局部发生什么，无法回答整条链路哪里慢、影响谁、最近变更是否相关。

**直接答案是：让上下文和 trace/span 标识在服务间传播，把日志、链路和指标关联起来。**

教材把可观测架构分为 Logging、Tracing、Metrics：日志记录详细信息；链路跟踪记录前端到后端的完整调用；指标提供量化度量。设计时还要定义各组件 SLO，例如并发、耗时、可用时长和容量，才能据此优化 SLA。

## 从“下单变慢”追到具体服务

假设用户反馈促销期间下单卡顿。**下面是解释性排查例子**，演示三类数据怎样分工，不代表某个真实系统或固定产品操作。

1. **先从指标确认异常范围。**看订单接口的请求量、错误率和延迟分布，并对照它的 SLO。例如整体请求的高分位耗时升高，说明问题并非只是一条偶发慢请求；指标适合回答“多大范围、何时开始、是否违反目标”。
2. **挑一个可复现的慢请求看完整 Trace。**Trace 是一次请求经过多个服务的调用记录；每个服务上的局部操作是一个 span。按 trace ID 打开订单请求，沿时间顺序比较网关、订单、库存、支付各 span 的耗时、返回状态和父子关系。若库存 span 等待时间最长，就得到下一步核对的具体位置；若某处没有 span 或上下文断了，应先识别观测链缺口，不能把“没显示”当作“没发生”。
3. **用 Trace/Span 标识关联日志查原因。**在耗时异常的库存 span 上取服务名、操作名、时间和关联标识，查相同请求附近的日志，确认是否有连接池等待、下游超时或错误码等细节。日志提供局部事件和诊断文本；若没有传播 trace ID 等上下文，日志与这次请求的关联可能不可靠。
4. **回到指标验证影响和修复效果。**判断有多少请求走到该库存实例、异常从何时开始，检查相关错误率和延迟是否恢复到 SLO 范围。若只修复一条 Trace 却没有观察整体指标，不能据此断定服务已恢复。

记住三者的关系：**Metrics 发现范围和趋势，Tracing 告诉一次请求经过哪里、耗时在哪，Logging 补充某个局部操作发生了什么。**Trace ID/span ID 及其他上下文需按规范在服务和技术组件间传播，才能关联分析；数据采集本身不能替代 SLO 定义、故障假设和修复验证。

## 自测

1. 从前端到后端还原一次完整调用，主要依靠哪一类可观测数据？

> [!answer]- 第 1 题答案与解析
> **答案**：Tracing。
> **解析**：日志补充细节，指标衡量整体状态；链路追踪负责请求关系。

2. 订单接口延迟指标已经超出 SLO，想确定一次慢请求具体卡在哪个下游服务，应先查看什么？

> [!answer]- 第 2 题答案与解析
> **答案**：查看该请求的 Trace，并比较各服务 span 的耗时和状态。
> **解析**：指标指出总体异常，Trace 展开单次请求路径；定位到可疑 span 后再用关联日志查局部原因。

3. 找到一条 Trace 显示库存服务很慢，能否据此认定所有用户的订单都受影响、问题也已修复？

> [!answer]- 第 3 题答案与解析
> **答案**：不能。
> **解析**：单条 Trace 只代表一次请求；影响范围和恢复情况要回看聚合指标、错误率、延迟及 SLO。
