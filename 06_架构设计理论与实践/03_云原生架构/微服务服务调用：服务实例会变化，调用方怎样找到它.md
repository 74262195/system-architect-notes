# 微服务服务调用：服务实例会变化，调用方怎样找到它

> [!summary]- 快速复习卡片（学完再看）
> 服务发现解决“要调用谁”；调用治理还要处理路由、限流、熔断和安全等通用连接问题。

## 地址会变化时，为什么不能把 IP 写死

微服务会扩缩容、重启或迁移。若订单服务把库存服务的机器地址写进代码，库存服务一变动，调用就可能全部失败。

**直接答案是：服务发现让调用方按服务名称或规则找到当前可用实例，而不是依赖固定机器地址。**

服务网格是教材中的一种治理位置：服务 A 调用服务 B 时，代理可完成服务发现、熔断和限流等策略，策略由控制平面配置。它把连接、安全、流量控制和可观测等通用功能从业务进程中下沉，但不替代服务本身的业务逻辑。

## 从库存服务扩容走完一次服务发现

继续用订单服务调用库存服务说明。**下面的步骤是教学用的通用模型，实际实现会因注册中心、客户端或服务网格而异。**关键目标是：库存实例变化后，订单服务不必把新 IP 写进代码，也不必为每次扩缩容重新发布。

1. **库存实例启动并登记。**新实例把服务标识（如 `inventory`）、可调用地址、端口及必要元数据登记到服务注册中心。实例可能通过定期心跳或健康检查表明自己仍可用；具体登记和健康检测机制取决于实现。
2. **订单侧获得可用实例信息。**订单服务或它使用的代理，按 `inventory` 这个服务标识向注册中心查询可用实例；系统也可以在实例变化时推送更新。教材强调，注册中心应支持依赖服务自动感知发布和扩缩容变化，而不要求重新发布调用方。
3. **从候选实例中选一个发起调用。**得到多个可用地址后，调用侧或代理按负载均衡规则选取一个，通过预先约定的服务接口和远程调用协议发请求。服务发现回答“有哪些实例可找”；负载均衡回答“这次选哪个”；远程调用才实际传送请求与结果。
4. **实例故障或扩缩容时更新列表。**健康状态变化后，注册中心更新或通知可用实例变化；调用侧/代理刷新本地候选列表，后续请求不再发给已知不可用实例，并能使用新加入的实例。已经发出的请求仍可能超时或失败，服务发现不能替代超时、重试、限流和熔断等韧性治理。

可以把这条链记成：**登记实例 → 查询或接收变化 → 选择实例 → 按接口调用 → 状态变化后刷新候选集。**若采用服务网格，应用请求可由代理代办发现与选址；若采用客户端发现，则调用方客户端承担查询和选择。两者的放置位置不同，解决的动态定位问题相同。

**边界：**注册中心保存和传播服务元数据，不等于它执行订单或库存业务；发现到地址不保证服务此刻绝对健康，也不保证调用成功。跨服务身份校验、安全策略、熔断限流和故障恢复分别由相应的安全、治理与韧性机制承担。

## 考试怎样判断

“实例变化、动态找到可用服务” → 服务发现；“代理按策略路由、限流、熔断” → 服务调用治理/服务网格。服务调用并非永远成功，失败时要靠[[微服务韧性：依赖出故障时怎样避免整条链路一起倒下|韧性治理]]控制影响。

## 自测

1. 服务发现主要解决的是业务规则还是服务实例定位？

> [!answer]- 第 1 题答案与解析
> **答案**：服务实例定位。
> **解析**：业务规则仍由业务服务负责。

2. 库存服务从两个实例扩到三个实例后，订单服务必须重新发布才能调用新实例，说明还缺少什么能力？

> [!answer]- 第 2 题答案与解析
> **答案**：服务发现的动态实例信息更新（如注册中心的查询或变化推送）。
> **解析**：依赖方应能按服务标识获知当前实例，而不是把机器地址写死在代码中；实例更新后可刷新候选列表。

3. 注册中心已经返回一个库存实例地址，能否据此保证这次远程调用成功？

> [!answer]- 第 3 题答案与解析
> **答案**：不能。
> **解析**：地址发现只解决实例定位；网络、进程和下游仍可能在返回后发生故障。调用还需要超时、错误处理以及适当的韧性策略。
