# 微服务数据边界：为什么服务拆开后不能随意共用数据库

> [!summary]- 快速复习卡片（学完再看）
> 微服务提倡私有数据源；共享数据库会让数据变化扇出，重新形成服务间耦合。

## 服务拆开了，数据为什么又把它们绑回去

订单和积分服务若直接共用一张核心表，任一字段改动都可能影响另一服务；表面上拆了部署，实际仍被同一数据结构捆住。

**直接答案是：微服务的自治需要数据边界，服务优先管理自己的数据，不把共享数据库当作默认方案。**

教材指出微服务常使用私有数据源；当大粒度业务访问多个服务时会出现分布式事务问题，需要按场景选择处理模式。云环境还推荐把会话和持久数据交给云服务保存，以实现存储计算分离；但远端状态若造成明显性能下降，可用时间日志加快重启后的恢复。

## 沿一笔“下单送积分”看数据边界

教学例：订单服务保存订单，积分服务保存账户积分。用户下单后，两个服务都要更新自己的数据；若订单服务直接改积分库，积分表一变更就会牵动订单服务，服务边界又被数据库结构绑住。

通常让订单服务通过积分服务提供的 API 或业务消息提出“为订单 A102 增加积分”的请求，由积分服务校验并更新自己的数据。此时要明确业务要求：

| 业务要求 | 可以考虑的事务思路 | 关键代价/检查点 |
| --- | --- | --- |
| 必须强一致地一起提交，且是短事务 | XA 等协调式事务 | 教材指出一致性较强，但性能较差；参与者和超时恢复都要考虑 |
| 允许短暂不一致，最终需要收敛 | 基于消息的最终一致性（BASE） | 性能通常较高，但通用性有限；要处理重投、重复消费和失败补偿 |
| 业务可拆为可撤销的步骤 | TCC 或 SAGA | 应用需承担更多流程逻辑；SAGA 为正向步骤配补偿动作，开发维护成本较高 |

例如积分服务暂时不可用时，订单服务可以按业务规则记录“积分待处理”，稍后重试并核对处理结果；若“订单成功”必须依赖积分成功，就不能默默跳过，必须选能满足该一致性要求的事务方案。这个简例说明判断方法，具体事务语义以选用的方案和业务约束为准。

## 考试怎样判断

“服务各自数据源、跨服务一致性” → 数据边界与分布式事务问题；“共享数据库导致数据变更影响多个服务” → 过度拆分后的耦合风险。不要把“私有数据源”误解成任何数据都绝不共享；题目应按一致性、性能和业务边界权衡。

## 自测

1. 微服务共享数据库最直接的架构风险是什么？

> [!answer]- 第 1 题答案与解析
> **答案**：数据变化会扇出到多个服务，形成数据依赖。
> **解析**：这会削弱服务自治。
