# Kubernetes容器编排：谁来让大量容器持续处于目标状态

> [!summary]- 快速复习卡片（学完再看）
> Kubernetes 是容器编排的事实标准，用声明式目标自动部署、调度、修复、发现和扩缩容容器化应用。

## 容器多了以后，谁来盯着每一个是否正常

少量容器可以手工启动；大量容器跨多台机器运行时，节点故障、版本回滚、服务发现和资源不足都会让人工操作不可持续。

**直接答案是：Kubernetes 让你声明应用希望处于什么状态，再由平台持续调度和修复，使实际状态尽量回到目标状态。**

```mermaid
flowchart LR
    A[声明目标状态] --> B[Kubernetes 控制平面]
    B --> C[调度并运行容器]
    C --> D[检查与修复]
    D --> C
```

教材列出 Kubernetes 的核心能力：按 CPU、内存或 GPU 调度资源；自动发布、回滚和配置/存储卷管理；节点或应用故障后的自动修复；基于 Service、DNS 和负载均衡的服务发现；根据负载自动弹性伸缩。控制平面主要包括 API Server、Controller、Scheduler 和 etcd。

它管理的是容器化应用的运行目标，并不替代应用的业务逻辑。不同工作负载可通过 Deployment、StatefulSet、Job 等资源表达，帮助平台理解应用需要的运行方式。

## 节点故障后，平台恢复的是什么

假设订单服务由 Deployment 声明需要运行 3 个副本，其中一个副本所在的节点失联。Kubernetes 的控制器持续比较“期望有 3 个副本”和“目前可用副本数”，发现少了一个后会推动系统补足副本；调度器再把新建的 Pod 安排到有资源且符合约束的健康节点上，节点上的容器运行时启动新的容器。

这通常是**重新创建工作负载实例**，不是把故障节点里的原容器连同内存现场原封不动搬到另一台机器。若应用状态保存在外部数据库或持久卷中，新实例可按应用机制重新连接或恢复；若状态只留在故障容器的内存里，平台补出容器也不能自动找回这些业务状态。因此，平台恢复的是声明中的运行副本目标，数据恢复和业务事务一致性还要由存储、备份与应用设计负责。

同理，“控制命令已提交”不等于新副本已就绪。平台还要等待容器启动并通过就绪检查；Service 等流量入口应只把请求转给符合条件的后端实例。检查配置和应用自身启动行为决定了平台能否及时识别可接流量的副本。

## 自测

1. 节点故障后在健康节点创建替代 Pod，使 Deployment 的副本数恢复到声明值，体现 Kubernetes 的哪项能力？

> [!answer]- 第 1 题答案与解析
> **答案**：自动修复（控制器协调期望状态，并由调度器选择可运行节点）。
> **解析**：这是重新创建并调度工作负载实例，不是把原容器现场原样迁走。资源调度决定放在哪里运行，控制器负责推动副本数回到目标。

2. 新 Pod 已经创建，是否表示原容器内存中的业务状态也已恢复？

> [!answer]- 第 2 题答案与解析
> **答案**：不表示。
> **解析**：平台负责恢复工作负载副本；内存状态恢复、持久数据和未完成业务事务需要应用与存储机制保障。
