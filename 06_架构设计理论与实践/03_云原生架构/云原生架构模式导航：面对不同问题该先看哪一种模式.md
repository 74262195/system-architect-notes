# 云原生架构模式导航：面对不同问题该先看哪一种模式

> [!summary]- 快速复习卡片（学完再看）
> 模式不是产品清单；先问系统卡在哪里，再选服务化、Mesh、Serverless 等对应组织方式。

## 为什么不能把“用了容器”当成全部答案

云原生会同时遇到服务拆分、中间件耦合、资源调度和交付效率等问题。容器只解决其中一部分运行封装问题，不能自动回答所有架构选择。

**直接答案是：云原生架构模式是一组针对不同问题的组织方法，应按问题选用，而不是把每个名词都塞进系统。**

| 系统的主要困难 | 优先理解的模式 |
| --- | --- |
| 模块要独立升级、按需扩缩容 | 服务化架构 |
| 中间件升级不应影响业务进程 | Mesh 化架构 |
| 希望按函数运行、减少运行环境管理 | Serverless / FaaS |
| 计算和数据资源的扩缩容节奏不同 | 存储计算分离 |
| 需要把事件作为系统协作入口 | 事件驱动架构 |

教材的服务化模式用接口契约与标准协议组织模块，让部署关系和代码模块关系分离；但服务拆得越多，若没有自动化和治理，管理成本反而会上升。这个边界正是选型时最重要的判断，而不是“越多模式越先进”。

## 考试怎样判断

先圈出题干的主要矛盾：独立部署看服务化；中间件与业务解耦看 Mesh；运行环境管理负担看 Serverless。后续 Atom 再分别展开每种模式的机制和边界。

## 自测

1. 服务拆分后缺乏自动化与治理，开发运维效率一定会提高吗？

> [!answer]- 第 1 题答案与解析
> **答案**：不一定。
> **解析**：教材指出模块增多而治理能力不足，可能反而降低效率。
