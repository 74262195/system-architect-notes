# 大数据架构索引

> [!summary] 本章主问题
> 综合知识已经回答“大数据是什么”。本章只回答架构层问题：**处理系统为什么要容错/低延迟/可扩展，以及历史重算与实时处理怎样在 Lambda、Kappa 中组织。**

## 学习顺序

1. [[01_大数据处理系统：为什么4V还不等于架构特征]] — 区分数据特征与处理系统架构特征。
2. [[02_Lambda架构：为什么同时保留批处理层和速度层]] — 看批处理层、速度层、服务层怎样协作。
3. [[03_Kappa架构：为什么只保留流处理主链并依靠日志重放]] — 看单一流链怎样通过日志重放承担历史重算，并理解 Kappa 变形解决的问题。
4. [[04_Lambda与Kappa：怎样根据重算和实时需求做选择]] — 用历史重算方式、重放成本和双链路复杂度做架构选择。

## 前置与边界

- 前置概念：[[13_大数据：为什么需要与云协同支撑全局智能]]，负责 4V 与数据处理链，本章不复制第二套定义。
- 本章 stable Atom：`ARCH-BIG-A001 ~ ARCH-BIG-A004`。
- A001 中的 4V/处理链继续复用 FUT-A013；新增正文只承担“容错、低延迟、可扩展”等处理系统架构特征。
- 本章不扩写 Hadoop 组件百科、数据湖/湖仓、厂商产品或与考试范围无关的平台工程细节。

## 一句话关系链

**4V 造成规模、速度与复杂性压力 → 平台必须容错/低延迟/可扩展 → Lambda 用批+流双路径兼顾历史与实时 → Kappa 用可重放日志把逻辑统一到流处理 → 最终根据历史重算方式与工程成本选型。**
