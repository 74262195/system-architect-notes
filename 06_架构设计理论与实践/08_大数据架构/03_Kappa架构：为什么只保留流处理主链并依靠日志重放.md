# Kappa 架构：为什么只保留流处理主链并依靠日志重放

> [!info] 承接
> Lambda 同时维护批处理和速度处理两条链路，能力完整但工程复杂。Kappa 的出发点是：**如果输入事件能长期保存在可重放日志中，能否只维护一套流处理逻辑，正常时处理新事件，需要重算时再重放历史事件？**

> [!summary]- 快速复习卡片（学完再看）
> - **核心结论：** Kappa = 持久事件日志 + 单一流处理主链 + 历史日志重放。
> - **第一动作：** 题干出现“取消独立批处理代码、统一流处理、需要时重放日志”，先识别 Kappa。
> - **易错：** Kappa 不是“不保存历史”，而是把可重放日志作为历史重新计算的基础。
> - **大纲漏点：** 还要会 Kappa 变形——当直接全量重放代价过高时，用额外的历史结果/分段处理等工程手段缩小重算范围；核心目的仍是减少双链路维护成本。

## Kappa 为什么能少一条链路

关键不是“流处理更快”这么简单，而是**输入日志可重放**。

正常运行：

```mermaid
flowchart LR
    A[事件持续写入] --> B[可持久化日志]
    B --> C[流处理程序]
    C --> D[服务结果]
```

当处理逻辑升级或历史结果需要修正时，不必再写一套独立批处理程序，而是从日志中重新读取历史事件，用**同一套或新版本的流处理逻辑**重新计算。

## 日志重放到底解决什么

例如某指标原来计算错误：

1. 原始事件仍保存在日志中；
2. 修正流处理程序；
3. 从指定历史位置重新消费事件；
4. 生成新的结果；
5. 新结果验证完成后替换旧结果。

所以“重放”是 Kappa 能承担历史重算的关键机制。

## Kappa 变形为什么会出现

纯粹从很久以前开始重放全部事件，数据量巨大时可能耗时很长、占用大量资源。工程上因此会出现 Kappa 的变形：保留某些可复用的历史结果、快照或按时间/分区缩小重放范围，再对较新的事件继续流式计算。

这里考试要抓的是**问题与目的**，而不是把所有厂商实现背下来：

> **问题：全量日志重放成本过高。**  
> **变形目的：缩小重算范围、加快恢复/重算，同时尽量保留单一处理逻辑带来的简化优势。**

## Kappa 并不天然优于 Lambda

Kappa 更适合事件天然可日志化、流处理可以表达主要业务逻辑、历史重放成本可接受的场景。

如果业务大量依赖复杂的全量离线计算，或者历史重算无法经济地通过事件重放完成，保留批处理路径仍可能更合适。

## 考前一句话

**Kappa 用“可重放日志 + 一套流处理逻辑”替代 Lambda 的批/流双实现；重算靠日志重放，变形主要解决全量重放成本过高的问题。**
