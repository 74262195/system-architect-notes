# 典型软件架构脆弱性比较：不同结构为什么会暴露不同薄弱点

> [!summary]- 快速复习卡片（学完再看）
> **一句话**：架构把系统“怎么拆、怎么连”固定下来，也会把某些故障传播、通信开销、暴露面和管理复杂性一起固定下来。
> **先抓结构再抓弱点**：分层看层间依赖；C/S 看客户端与直接连接；B/S 看 Web 暴露面；事件驱动看事件顺序与并发；MVC 看分离后的耦合/调用；微内核看 IPC；微服务看分布式通信与服务管理。
> **易错点**：教材这里的“脆弱性”不只指可被黑客利用的安全漏洞，也包含性能、稳定性、可靠性下降等结构性薄弱点。
> **版本边界**：教材对 C/S、B/S、HTTP 的部分比较带有经典考试语境，不能直接当作今天所有真实系统的绝对安全结论。
> **第一反应**：题干先识别“系统怎样拆和怎样通信”，再反推该结构最容易暴露的薄弱点。

前一篇 [[01_综合知识/03_信息安全技术/05_安全架构治理与可信/软件脆弱性分析|软件脆弱性分析]] 解决的是“脆弱性是什么、怎样分析”。

这一篇只回答一个问题：

> **为什么换一种软件架构，系统的薄弱点也会跟着变化？**

因为架构决定了组件怎样划分、彼此怎样依赖、数据怎样传递。优点来自这些结构，薄弱点也通常来自同一个地方。

## 先看总规律：优点的另一面往往就是脆弱点

例如：

- 分层让职责更清晰，但增加层间依赖和调用；
- 事件驱动让组件更解耦，但执行顺序和数据流更难直接控制；
- 微服务让服务可以独立部署，但把单机内调用变成大量跨服务通信。

所以架构脆弱性分析第一步不是背漏洞名，而是：

> **先找这个架构为了获得什么能力而引入了哪些结构和通信关系，再看这些关系在哪些条件下会变成薄弱点。**

## 七类典型架构怎样判断

| 架构 | 结构特征 | 教材强调的主要脆弱点 | 做题第一反应 |
| --- | --- | --- | --- |
| 分层架构 | 表示层、业务层、持久化层、数据库层等逐层协作 | 底层故障可能向上传播；层间通信增加调用与性能开销 | 看到“逐层依赖/层层调用”先想故障传播和通信成本 |
| C/S | 客户端安装专用程序，直接与服务器协作 | 客户端程序可被分析、数据可能被截取；直接连接和客户端数据分布扩大暴露面 | 看到“胖客户端/客户端直连服务器”先看客户端和连接边界 |
| B/S | 浏览器通过 Web/HTTP 访问服务器 | 教材经典语境强调 Web/HTTP 对外开放带来的暴露面 | 看到“浏览器 + Web 服务器”先看 Internet 暴露和 Web 通信边界 |
| 事件驱动 | 组件靠事件异步协作 | 响应者和执行顺序不易直接确定；数据交换、逻辑关系、高并发和循环事件复杂 | 看到“异步事件”先看顺序、并发、事件链和数据传递 |
| MVC | Model、View、Controller 分离 | 结构复杂度增加；视图/控制器仍有联系；频繁获取模型数据可能降低效率；教材还强调调用者验证和数据传输 | 看到“三部分分离”先看分离后的调用关系和控制边界 |
| 微内核 | 小核心 + 外部服务/插件 | 难做整体优化；进程间通信开销和通信损失增加 | 看到“核心很小、功能外移”先想 IPC 与整体优化 |
| 微服务 | 多个独立进程的小服务协作 | 分布式复杂性；服务通信延迟/不可用；大量服务实例管理复杂 | 看到“服务拆得很细”先想网络、局部失败和运维治理 |

## 1. 分层：底层出错为什么可能拖累上层

分层的优势是职责清晰。

但上层通常依赖下层提供能力。如果底层组件返回错误、异常对象或错误数据，而上层没有隔离和处理，问题就会向上扩散。

同时，原本一次直接调用被拆成多层转发，也会增加通信和性能成本。

所以分层架构的考试题眼通常是：

> **层间依赖 + 层间通信。**

## 2. C/S：为什么客户端本身会成为安全边界

C/S 把一部分程序和数据处理能力放到用户终端。

这意味着攻击者可能直接接触、分析客户端程序，甚至观察客户端保存或传递的数据。如果客户端还直接连接后端服务器，服务器暴露边界也会扩大。

因此遇到传统 C/S 场景，先检查：

- 客户端是否保存敏感配置或凭据；
- 客户端与服务器是否直接暴露通信；
- 客户端本地数据是否缺少保护。

## 3. B/S：教材里的结论为什么不能背成“浏览器一定比客户端不安全”

教材在经典语境下把 B/S 的 Web/HTTP 暴露面作为脆弱点。

真正应该记的是：

> **B/S 把访问集中到浏览器和 Web 接口，因此 Web 入口、HTTP/TLS、服务端接口和 Internet 暴露面成为重点控制位置。**

不要把旧教材中的比较扩展成：

> “所有 B/S 系统一定比所有 C/S 系统不安全。”

现实系统安全性还取决于 TLS、身份认证、访问控制、服务端实现、部署边界等大量因素。

考试遇到旧式比较题时按教材口径识别；做现实架构判断时看具体控制。

## 4. 事件驱动：解耦以后为什么反而更难追踪

事件发送者通常不知道最终由哪些组件处理，也不一定直接控制处理顺序。

因此薄弱点会集中在：

- 事件顺序；
- 事件数据传递；
- 多组件逻辑关系；
- 高并发；
- 事件循环或重复触发。

一句话：

> **同步调用容易看见“谁调用谁”，事件驱动则要额外治理“谁会响应、何时响应、响应几次”。**

## 5. MVC：分开以后并不代表完全无耦合

MVC 把模型、视图和控制器分开，但它们仍需要协作。

分离会增加结构和调用路径；视图和控制器仍可能存在紧密联系；视图多次访问模型也可能带来额外开销。

教材还把调用者安全验证和数据传输保护作为 MVC 场景中的安全注意点。

所以不要把 MVC 的优点“职责分离”误解成：

> “三个部分从此互不影响。”

## 6. 微内核：核心变小以后，通信为什么变多

微内核把很多原本在核心中的服务移到外部模块或进程。

优点是核心更精简、扩展更灵活；代价是外部服务之间需要更多进程间通信。

因此薄弱点主要是：

- IPC 开销；
- 通信损失；
- 各独立服务之间难以进行整体优化。

## 7. 微服务：服务越独立，为什么治理反而更复杂

微服务把一个大应用拆成很多独立服务。

原来进程内的方法调用，可能变成跨网络调用；原来一个进程的故障，可能变成多个服务之间的局部失败传播。

因此教材强调：

- 分布式结构复杂；
- 服务间消息可能延迟或不可用；
- 生产环境中的大量服务实例需要统一管理。

这和云原生章节的 [[06_架构设计理论与实践/03_云原生架构/微服务韧性：依赖出故障时怎样避免整条链路一起倒下|微服务韧性]]、[[06_架构设计理论与实践/03_云原生架构/微服务自动化运维：服务变多后为什么更需要自动化交付|微服务自动化运维]] 是同一因果链的不同视角：那里讲怎样解决，这里讲为什么会出现这些薄弱点。

## 考试第一动作

出现“某架构有什么脆弱性”时，不要直接背七张清单。

先做两步：

1. **识别结构**：它是层层依赖、客户端直连、Web 入口、异步事件、三部分分离、小核心+插件，还是大量独立服务？
2. **沿结构找薄弱点**：依赖传播、暴露边界、通信开销、执行顺序、并发、局部失败或管理复杂性。

这样即使忘了教材原句，也能从架构结构反推出主要风险。

## 自测

1. 一个系统采用事件驱动后，组件之间更松耦合，但故障排查时很难确定“谁先处理、谁重复处理了事件”。这属于哪类架构脆弱点？

> [!answer]- 第 1 题答案与解析
> **答案**：事件驱动架构的事件顺序、逻辑关系和事件链复杂性。
> **解析**：解耦降低直接依赖，但也弱化了发送者对响应者和执行顺序的直接控制。

2. 微服务和微内核为什么都会出现“通信成本”问题？

> [!answer]- 第 2 题答案与解析
> **答案**：因为两者都把原本更集中、直接的功能拆成独立单元，单元之间必须通过额外通信协作。
> **解析**：微内核主要体现为进程间通信；微服务更多体现为跨服务网络通信和局部失败。

3. 教材说 B/S 存在 Web/HTTP 暴露面的脆弱性，能否推出“现代 B/S 一定比 C/S 不安全”？

> [!answer]- 第 3 题答案与解析
> **答案**：不能。
> **解析**：教材结论用于经典考试语境；现实安全性还取决于 TLS、认证授权、服务端实现和部署等具体控制。
