# 数据库完整性设计：业务规则怎样变成可执行约束

> [!summary]- 快速复习卡片（学完再看）
> **一句话**：数据库完整性设计就是把“什么数据才算合法”变成 DBMS 或应用程序能够执行的约束。
> **核心对象**：数据的正确性和相容性。
> **设计主线**：需求阶段找业务规则 → 概念阶段建立实体关系 → 逻辑阶段选择 DBMS 约束 → 测试冲突和性能。
> **实现原则**：静态约束优先进入数据库模式；动态规则常需应用程序参与；触发器能做复杂控制但要慎用。
> **第一反应**：题干出现主键、外键、非空、唯一、Check、触发器或“合法用户写入非法数据”，先想到完整性设计。

数据库已经做了登录、授权和审计，为什么还会出现错误数据？

因为**“有权写”只说明这个人可以执行写操作，并不说明他写进去的值一定符合业务规则。**

例如一个有 INSERT 权限的业务系统写入：

- 不存在的客户编号；
- 数量为负数的订单；
- 两条本应唯一的身份证号。

这些都不是“越权”，而是**数据状态不合法**。

所以数据库完整性设计解决的是：

> **把业务规则转成数据库或应用能够自动检查的约束，让数据持续保持正确、相容。**

## 第一步：先决定哪些业务规则必须被守住

教材把数据库完整性定义为数据的**正确性和相容性**。设计不能等到建完表才补几个约束，而应从需求阶段就开始找业务规则。

以“客户—订单”为例：

- 一个订单必须属于某个真实客户；
- 订单号必须唯一；
- 数量不能为负数。

这些规则先在需求阶段被识别，之后才决定放到 DBMS 还是应用程序实现。

## 第二步：静态规则尽量让数据库自己守

教材强调，要根据约束类型选择实现层次。

容易直接描述在数据库模式中的静态规则，通常优先交给 DBMS，例如：

| 业务要求 | 常见实现 |
| --- | --- |
| 某列必须有值 | NOT NULL |
| 某值不能重复 | UNIQUE |
| 一条记录必须能唯一标识 | PRIMARY KEY |
| 引用对象必须真实存在 | FOREIGN KEY / 引用完整性 |
| 某个值必须满足条件 | CHECK |

这样做的价值是：无论数据从哪个应用入口写入，都要经过数据库统一检查，不必要求每个程序员都重复实现同一条规则。

## 第三步：复杂动态规则要在 DBMS 与应用之间做取舍

教材把完整性约束进一步区分为：

- 列级、元组级、关系级；
- 静态约束、动态约束。

组合起来形成六类约束。

考试不必把“六类”理解成六种 SQL 语法。它真正提醒的是：

> **有些规则只看当前数据就能判断，有些规则要结合数据变化过程、事务或业务状态才能判断。**

教材口径下，静态约束应尽量进入数据库模式；动态规则往往需要应用程序参与。

触发器虽然可以表达复杂约束，但要慎用，因为它会带来额外性能开销，多级触发也更难分析和控制。能用清晰的声明式约束解决时，不要为了“高级”而强行使用触发器。

## 完整性设计贯穿数据库设计过程

完整性不是建表后的补丁。教材给出的主线可以压缩为三个阶段：

1. **需求分析**：找出实体、关系和业务规则，并区分哪些规则要作为完整性约束；
2. **概念结构设计**：把业务对象与关系形成 ER 模型，为实体完整性、引用完整性等约束建立基础；
3. **逻辑结构设计**：结合具体 DBMS 的能力，把规则落成主键、外键、唯一、检查等机制，并考虑性能。

完成后还必须测试，因为约束之间可能冲突，也可能对关键性能造成明显影响。

所以题目如果问“什么时候考虑完整性”，不要回答“数据库建好后”。正确思路是：

> **从需求阶段发现规则，并随着概念设计、逻辑设计逐步落地和验证。**

## 与安全访问控制的边界

[[01_综合知识/03_信息安全技术/05_安全架构治理与可信/数据库安全与完整性设计|数据库安全与完整性设计]] 已经建立了“谁能做”与“什么数据合法”的基本区别。

这里进一步把架构动作明确下来：

- **访问控制**：合法主体有没有执行操作的权限；
- **完整性约束**：这个操作产生的数据状态是否合法。

所以“用户有 INSERT 权限，但外键检查失败”完全不矛盾：授权检查通过了，完整性检查仍然可以拒绝这次写入。

## 考试第一动作

看到数据库完整性题，先不要从“黑客篡改”出发，而先问：

> **题目是不是在描述合法程序也不能破坏的业务规则？**

如果是，再按顺序判断：

1. 这是值、记录还是表关系层面的规则？
2. 是当前状态即可判断的静态规则，还是依赖变化过程的动态规则？
3. 能否优先交给 DBMS 的声明式约束？
4. 若需要触发器或应用逻辑，是否同时考虑性能、冲突和绕过风险？

## 自测

1. 用户拥有订单表 INSERT 权限，但插入不存在的客户编号为什么仍应失败？

> [!answer]- 第 1 题答案与解析
> **答案**：因为 INSERT 权限只解决“能不能执行插入”，引用完整性还要保证订单引用的客户真实存在。
> **解析**：授权与数据状态合法性是两条不同控制线。

2. 为什么数据库完整性设计不能等到建表结束以后再统一补？

> [!answer]- 第 2 题答案与解析
> **答案**：因为完整性约束来自业务规则和实体关系，应从需求分析开始识别，并在概念、逻辑设计阶段逐步选择实现方式。
> **解析**：晚补容易遗漏规则，也难以系统评估约束冲突和性能影响。
