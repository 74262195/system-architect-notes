# 安全产品与审计架构：控制措施应该放到系统哪些位置

> [!summary]- 快速复习卡片
> **一句话**：安全产品的价值不在于“产品越多越安全”，而在于把预防、检测、审计、响应和恢复能力放到正确的系统位置并形成闭环。
> **位置**：身份入口、网络边界、主机、应用、数据、日志审计、备份恢复。
> **审计作用**：把分散事件集中起来回答“谁在什么时候对什么做了什么，结果怎样”。
> **易错点**：审计不是访问控制；它主要提供记录、追踪、发现和追责依据，不能替代事前授权。

## 为什么不能按产品名称设计架构

如果方案写成“防火墙 + IDS + WAF + 堡垒机 + 数据库审计”，看起来设备很多，但仍然没有回答三个关键问题：

1. 每个控制要保护什么资产；
2. 它部署在哪个信任边界或数据路径；
3. 发现异常以后由谁处置、怎样恢复。

安全架构更适合先按**控制位置和安全能力**组织，再选择具体产品。

## 常见控制放在哪里

| 位置 | 主要风险 | 典型控制能力 |
| --- | --- | --- |
| 身份入口 | 冒充、账号盗用 | 身份认证、多因素认证、账号生命周期管理 |
| 网络边界/区域之间 | 非法访问、横向移动、异常流量 | 防火墙、隔离、VPN、入侵检测/防御 |
| 主机 | 漏洞、恶意程序、配置错误 | 加固、补丁、主机检测、最小权限 |
| 应用 | 注入、越权、业务接口滥用 | 安全开发、输入校验、应用访问控制、WAF 等 |
| 数据 | 泄露、非法修改 | 数据权限、加密、完整性约束、数据库安全控制 |
| 审计 | 行为不可追踪、异常难关联 | 日志采集、集中审计、关联分析、告警 |
| 恢复 | 故障或攻击后无法恢复 | 备份、恢复验证、容灾与应急流程 |

表中的产品只是能力示例；考试案例题更重要的是说明**为什么放在这里、解决什么风险**。

## 审计为什么要集中

一次越权事件可能同时留下登录日志、应用访问日志、数据库操作日志和网络告警。如果这些记录彼此分散，就很难还原完整路径。

集中审计的基本思路是：

**多源日志 → 统一采集 → 时间/主体/资源等维度关联 → 发现异常 → 告警与调查 → 留存证据。**

它解决的是“发生了什么、由谁做、影响到哪里”，而不是替代认证和访问控制。

## 预防、检测、响应和恢复要能接起来

完整方案至少要能回答：

- **预防**：怎样降低攻击成功概率；
- **检测/审计**：怎样发现控制被绕过或异常已经发生；
- **响应**：怎样隔离账号、主机或网络区域，阻止影响扩大；
- **恢复**：怎样恢复数据和服务并验证安全状态。

这与综合知识中的 WPDRRC 思想一致，但本卡只关注这些能力在系统架构中的落点，不重复背模型定义。

## 考试第一动作

题目给出一串安全产品时，先不要逐个解释定义。先把它们放回：

**身份 → 网络 → 主机 → 应用 → 数据 → 审计 → 恢复**

然后逐项说明“保护对象 + 部署位置 + 解决的风险”，答案就从产品清单变成了安全架构。

## 自测

1. 为什么安全审计不能替代访问控制？

> [!answer]- 第 1 题答案与解析
> **答案**：访问控制负责事前决定主体能否操作资源；审计主要负责记录、发现、追踪和提供事后证据，两者职责不同。

2. 为什么有很多安全产品仍可能不是完整安全架构？

> [!answer]- 第 2 题答案与解析
> **答案**：如果没有根据资产和风险确定控制位置、信任边界以及检测后的响应和恢复关系，产品只是孤立组件，不能形成整体防护闭环。
