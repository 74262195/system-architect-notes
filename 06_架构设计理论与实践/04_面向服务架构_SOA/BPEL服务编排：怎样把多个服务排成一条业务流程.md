# BPEL服务编排：怎样把多个服务排成一条业务流程

> [!summary]- 快速复习卡片（学完再看）
> **BPEL**：使用 Web 服务定义和执行业务流程的语言。
> **编排**：把多个已有服务按业务顺序组合、协调，形成一个新的复合服务。
> **外部效果**：对调用者看起来，这个业务流程仍像一项服务。

## 一次订票为什么常要连续调用多个服务

订票业务可能依次调用查票、锁座、支付和通知服务。单个服务各自能做一件事，但用户真正需要的是“完成订票”这一整条流程。

**BPEL 的直接答案是：用流程把多个已有 Web 服务组合、编排和协调，形成新的复合服务。**

```mermaid
flowchart LR
    A[查票服务] --> B[锁座服务]
    B --> C[支付服务]
    C --> D[通知服务]
    D --> E[对外的订票复合服务]
```

教材将 BPEL 解释为面向 Web 服务的业务流程执行语言：它可将多个 Web 服务组合成一个称为业务流程的复合服务，并把已有服务按要求的业务流程重新组织。

## “编排”不是再写一个大服务

编排关心的是服务之间的顺序、组合与协调；查票、支付等原有服务仍各自保持自己的能力和边界。BPEL 的价值是把跨服务的业务流程明确表达出来，避免调用方自己拼接一长串服务调用。

| 题干对象 | 更接近的理解 |
| --- | --- |
| 单项可被调用的能力 | 服务 |
| 多个服务如何按业务顺序协作 | 编排 / BPEL |
| 编排后对外暴露的整体能力 | 复合服务 |

## 它与工作流的边界

[[06_架构设计理论与实践/02_层次式架构/业务逻辑工作流：怎样让一件事按规则流转|业务逻辑工作流]]关注一个系统内部任务怎样按规则流转；BPEL 在本教材语境中关注 Web 服务怎样被组合成跨服务的业务流程。两者都处理“流程”，但服务编排的重点是服务间协作。

## 长流程失败后，怎样让业务回到可接受状态

沿用订票例：流程先查票、锁座，再请求支付。若支付最终失败，座位不能无限期占用；流程需要识别失败并执行与锁座相配套的补偿动作，例如释放该订单锁定的座位，同时记录流程失败结果供调用方查询。

教材区分短流程与长流程：短流程通常可采用传统两阶段提交；长流程一般采用补偿方法。补偿不是把已经发生的远端动作“时间倒流”，而是再执行一个业务动作，使系统回到业务上可接受的状态。因此每一步都要考虑失败位置、可补偿动作以及补偿本身失败时如何人工/自动恢复。

考试题若出现“跨多个服务、运行较久、中途失败后恢复”，不要只写“重新执行”；应指出流程服务管理顺序与异常恢复，并按长短流程判断事务方案。此处补偿机制说明依据教材 PDF 第 536 页。

## 考试怎样判断

看到“面向 Web 服务的业务流程执行语言”“组合、编排、协调多个 Web 服务”“形成复合服务”，优先选 BPEL。

若题干问的是企业服务如何连接、路由或转换，先想到 ESB；若问的是服务本身怎样定义和调用，先看服务描述、消息交换等后续考点。

## 自测

1. 将支付、库存和物流服务按下单流程组合为一个对外服务，最符合什么概念？

> [!answer]- 第 1 题答案与解析
> **答案**：BPEL 服务编排形成的复合服务。
> **解析**：BPEL 把多个已有 Web 服务按业务流程组合和协调。

2. 编排后，原有支付服务是否必须失去独立性？

> [!answer]- 第 2 题答案与解析
> **答案**：不必须。
> **解析**：编排组织的是服务间协作；单项服务仍可保持自身能力和边界。
