# TOGAF与ADM：怎样按步骤开发企业架构

> [!summary]- 快速复习卡片（学完再看）
> **TOGAF 是什么**：开放式企业架构框架标准。  
> **ADM 是什么**：TOGAF 的核心开发方法，用一组迭代阶段把“想做什么”推进到“怎么实施、怎么治理、怎么持续变更”。  
> **阶段主链**：预备 → A 架构愿景 → B 业务架构 → C 信息系统架构 → D 技术架构 → E 机会与解决方案 → F 迁移规划 → G 实施治理 → H 架构变更管理。  
> **贯穿全程**：需求管理。  
> **第一反应**：题目问某阶段“主要干什么”，先按“愿景 → 业务 → 数据/应用 → 技术 → 方案 → 迁移 → 实施 → 变更”定位。

上一站 [[企业信息系统总体框架：为什么不能只画应用系统]] 已经知道企业架构不是只画几套软件，而是要同时考虑战略、业务、应用和基础设施。

接下来会遇到一个很现实的问题：

> 知道“要看哪些东西”以后，真正做企业架构时应该先做什么、后做什么？

**TOGAF 提供企业架构的框架，ADM 则提供一套按阶段推进架构开发的方法。**

## 先把 TOGAF 和 ADM 的关系讲清楚

初学时最容易把两个词当成同义词。

不是。

- **TOGAF**：一个企业架构框架标准，提供方法、内容、参考模型、能力等整体框架；
- **ADM（Architecture Development Method）**：TOGAF 中最核心的架构开发方法，负责告诉你架构工作怎样一步步推进。

可以把它理解成：

> **TOGAF 是整套工具箱，ADM 是其中负责“怎么做架构开发”的主流程。**

考试如果问“TOGAF 的核心是什么”，优先想到 ADM；如果问“ADM 属于什么”，回答它是 TOGAF 的核心开发方法，而不是另一个独立企业架构标准。

## 为什么 ADM 不是一条做完就结束的直线

企业不会永远停在同一个业务环境里。

今天的目标架构做完，明年业务战略、法规、技术、组织都可能变化。因此架构开发不可能“一次设计，永久不动”。

**ADM 本质上是一个迭代过程。**

教材强调三层迭代：

1. 整个 ADM 周期可以反复执行；
2. 不同阶段之间可以回退、重做；
3. 一个阶段内部也可以多次迭代。

所以看到 ADM 环形模型时，不要把它背成“只能 A 做完才能永久进入 B”。

它表达的是：

> **有主顺序，但允许根据需求和反馈反复校正。**

## 先抓住整条主线

把每个阶段先翻译成人话：

| 阶段 | 先问自己什么 | 核心动作 |
| --- | --- | --- |
| 预备阶段 | 我们有没有能力开始做架构？ | 定组织、原则、框架、工具和治理准备 |
| A 架构愿景 | 这次到底要做什么、范围多大？ | 定范围、干系人、约束、愿景并获得认可 |
| B 业务架构 | 企业业务应该怎样运转？ | 建基线/目标业务架构并做差距分析 |
| C 信息系统架构 | 需要什么数据和应用来支撑业务？ | 设计数据架构、应用架构并做差距分析 |
| D 技术架构 | 这些应用靠什么技术底座实现？ | 设计硬件、软件、通信等技术架构 |
| E 机会与解决方案 | 怎么把差距变成可实施项目？ | 组合工作包、识别方案和过渡架构 |
| F 迁移规划 | 先做什么、后做什么？ | 排优先级，形成详细实施与迁移计划 |
| G 实施治理 | 实施时怎样保证不跑偏？ | 监督项目符合架构要求 |
| H 架构变更管理 | 业务变了以后怎么办？ | 持续监测、管理架构变化 |

还有一个不能漏：

**需求管理贯穿整个 ADM 周期。**

它不是“阶段 I”，而是持续接收、维护、协调各阶段需求。

## 预备阶段：先确认“有没有条件做架构”

很多人第一次看 ADM 会直接从 A 开始背。

但在 A 之前还有**预备阶段**。

它解决的问题是：

> 组织有没有准备好以统一方式开展企业架构？

常见动作包括：

- 明确负责架构的组织和角色；
- 确定架构原则；
- 选择或定制框架；
- 准备工具与治理机制。

因此题目如果描述“建立架构能力、确定原则和组织方式”，不要选 A 架构愿景，优先想到预备阶段。

## A：架构愿景——先把这次架构工作的边界说清楚

**A 阶段的重点是确定范围、约束、干系人和高层目标，形成共同愿景并获得认可。**

例如集团准备统一会员体系。

A 阶段先解决：

- 这次只改会员体系，还是同时改订单和营销？
- 哪些部门受影响？
- 核心业务目标是什么？
- 有哪些限制条件？
- 谁需要批准？

这一阶段还不是详细画数据库和服务器。

它先回答：

> **这次架构工作为什么做、做到哪里、大家是否同意。**

## B、C、D：从业务一路落到技术

这三段是 ADM 的核心设计主链。

### B：业务架构

回答：

> 企业为了实现目标，业务能力、组织、流程和服务应该怎样安排？

核心动作通常都围绕：

**基线架构 → 目标架构 → 差距分析**

### C：信息系统架构

C 又包含两个主要部分：

- **数据架构**：需要哪些数据、数据之间是什么关系；
- **应用架构**：需要哪些应用、应用之间怎样协作。

所以题目出现“数据实体、数据关系、应用系统及应用交互”，优先定位 C。

### D：技术架构

回答：

> 应用和数据最终依赖什么硬件、软件、网络和技术平台？

如果题目强调技术平台、通信、硬件和软件基础设施，优先定位 D。

可以压成一条：

> **B 业务做什么 → C 用什么数据和应用支撑 → D 用什么技术承载。**

## E、F：从“架构图”走向“实施计划”

做到 D 为止，目标架构已经比较清楚，但企业不能一次性把所有旧系统推倒重来。

因此接下来要把设计转换成可执行变化。

### E：机会与解决方案

重点是把前面发现的差距整理成：

- 工作包；
- 实施项目；
- 解决方案；
- 过渡架构。

所以 E 解决：

> **有哪些实施机会，应该组合成哪些项目和阶段性方案？**

### F：迁移规划

有了项目还不够，还要排序。

F 重点考虑：

- 业务价值；
- 成本；
- 风险；
- 依赖；
- 时间与资源。

最终形成更详细的实施和迁移计划。

最简单区分：

- **E：形成“做哪些项目”**
- **F：决定“这些项目怎么排、什么时候做”**

## G、H：实施不跑偏，架构还能继续演化

### G：实施治理

项目开始落地后，架构师不能退出。

G 的任务是监督实施是否符合已经批准的架构，例如：

- 约束实施项目；
- 做架构监督；
- 检查是否偏离设计。

### H：架构变更管理

系统上线也不是终点。

当业务、法规或技术变化时，需要：

- 持续监测；
- 判断变化是否需要触发新一轮架构工作；
- 管理架构演进。

所以：

> **G 管“这次实施别跑偏”，H 管“以后变化怎么继续演进”。**

## 需求管理为什么放在中间

企业架构每个阶段都会产生和修改需求。

例如：

- A 发现范围变了；
- B 发现业务流程需要调整；
- C 发现应用整合要求；
- D 发现技术约束；
- E/F 又会产生实施依赖。

因此需求不能只在最开始收集一次。

**需求管理贯穿 ADM，用来识别、维护、协调和反馈需求。**

考试看到“贯穿各阶段”“持续管理需求”，第一反应就是需求管理。

## 一道题先怎么做

遇到 ADM 阶段题，不要先背字母，先找题干动作：

| 题干动作 | 第一判断 |
| --- | --- |
| 建架构组织、原则、能力 | 预备阶段 |
| 定范围、愿景、干系人 | A |
| 业务流程、组织和能力 | B |
| 数据或应用 | C |
| 硬件、软件、网络平台 | D |
| 工作包、方案、过渡架构 | E |
| 排实施优先级、迁移计划 | F |
| 监督实施符合架构 | G |
| 持续变更与演进 | H |
| 全过程处理需求 | 需求管理 |

先按“动作”定位，再回忆阶段字母，比单纯背 A～H 更稳。

## 自测

1. 某企业正在确定本轮企业架构工作的范围、关键干系人和高层目标，应优先定位哪个阶段？

> [!answer]- 第 1 题答案与解析
> **答案**：A，架构愿景。
> **解析**：题干重点是范围、干系人和高层愿景，不是详细业务或技术设计。

2. 已经明确目标架构，现在要把多个差距整理成实施项目和过渡架构，这更接近 E 还是 F？

> [!answer]- 第 2 题答案与解析
> **答案**：E，机会与解决方案。
> **解析**：E 先形成工作包、项目和过渡架构；F 再对这些项目进行优先级和详细迁移规划。

3. 为什么“需求管理”不能简单记成 A～H 中的某一个阶段？

> [!answer]- 第 3 题答案与解析
> **答案**：因为需求会在整个 ADM 周期持续被识别、调整和反馈，所以它贯穿所有阶段。
> **解析**：它是持续活动，不是按顺序执行一次后结束的阶段。
