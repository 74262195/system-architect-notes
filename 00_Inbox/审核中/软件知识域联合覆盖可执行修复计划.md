# 软件知识域联合覆盖可执行修复计划

> 基线：远端 `main` = `2fe7986e62f7000568b24257056869d6cc23671f`
>
> 本文件只定义后续修复机制、批次、验收条件与提交边界。本轮不修改任何正文，不修改提示词，不批量生成原子卡。
>
> 本轮已读取：`AGENTS.md`、`prompts/00-全局写作规范.md`、`prompts/10-原子考点卡生成.md`、`prompts/20-章节检查与重构.md`、`prompts/65-教材证据与笔记校验.md`、`prompts/66-章节三轮审查.md`、`00_Inbox/审核中/软件知识域联合覆盖审查与提示词优化建议.md`。

## 1. 先给结论：当前真正缺的不是“再强调一次大纲 → 真题 → 教材”

现有规则对**单篇笔记怎么写完整**已经较强：`prompts/00` 明确了来源优先级与教学闭环，`prompts/10` 也有样稿门禁、原子化和生成流程。

真正导致 UML、SC、业务流程图、架构生命周期、ADL 等漏项的，是**章节级覆盖没有形成可验收的硬闭环**。

当前缺口不是一句“执行不严格”能够解释，而是规则层面仍存在以下结构性问题：

| 机制缺口 | 当前表现 | 为什么会产生漏项 | 后续主修提示词 |
|---|---|---|---|
| 没有强制生成“大纲原子项全集” | 章节审核可以直接从现有目录/正文开始 | 只要现有主线看起来完整，未进入目录的 UML、SC、业务流程图就不会进入审核视野 | `20`、`66` |
| 没有稳定的大纲原子项 ID | 大纲项靠自然语言临时描述 | 同一知识点在不同聊天、不同章节中难以追踪，容易重复或漏掉 | `20` |
| 没有“原子项 → 正文具体落点”的强制矩阵 | 常以“章节已有某主题”“有某文件”判断覆盖 | 《建模语言与 UML》存在，会造成“UML 已覆盖”的错觉，但不代表 UML 图、用途、判图考法真正覆盖 | `20`、`65`、`66` |
| 没有 `未映射原子项 = 0` 的硬门禁 | 第一轮审核可以用“主线完整”“基本覆盖”通过 | 上位章节名可以掩盖下位缺项 | `66` |
| 没有正文集合的反向检查 | 主要是“大纲 → 当前笔记”正向看 | 无法发现正文孤岛、重复主事实源，也无法验证每个正文落点是否真的承担了某个原子项 | `20`、`66` |
| “已覆盖”的定义过宽 | 目录、frontmatter、一句话定义、占位卡都可能被视为存在 | “出现过”被误判为“已经形成考试闭环” | `20`、`65`、`66` |
| 跨章节知识没有唯一主事实源 | 同一知识可能在语言、软件工程、架构章节各讲一点 | 一个章节看到另一个章节“提过”，就可能停止补齐；同时又容易重复造卡 | `20`、`66` |
| `65` 主要按“笔记”而不是“原子项落点”核验证据 | 教材证据可以证明整篇大致正确 | 不能保证某个大纲原子项已解释到考试所需深度 | `65` |
| `66` 第二、三轮主要审现有正文 | 第一轮若没发现缺项，后两轮不会凭空发现它 | 漏项会在后续轮次永久隐身 | `66` |
| `10` 的样稿门禁保护了写作质量，但没有约束“样稿从哪里来” | 可能从当前目录或主线选样稿 | 如果候选集合本身漏了 UML/SC，样稿质量再高也无法补覆盖 | `10` |

因此后续要建立两个互补闭环：

### 1.1 单篇教学闭环

每个承担主事实源的正文落点必须能够回答：

1. 承接与定位：它接着什么问题来，为什么现在学；
2. 具体问题：本篇到底只解决什么；
3. 直接答案：先把结论说清楚；
4. 核心机制：为什么、怎么工作、怎么区分；
5. 考试动作：题目出现什么信号时应该做什么判断；
6. 收口与下一站：本篇解决到哪里，下一篇为什么顺着来。

这部分继续以 `prompts/00`、`prompts/10` 为主，不需要另造一套平行规则。

### 1.2 章节覆盖闭环

每章必须完成：

`大纲全集 → 大纲原子项拆分 → 每项唯一正文落点 → 教材核验解释深度 → 真题核验实际考法 → 跨章节主事实源检查 → 正向/反向核验 → 未映射项归零`

只有这条链闭合，才能说“章节覆盖完成”。

## 2. 建立统一的“章节覆盖契约”

后续第一阶段修改提示词时，不增加“别漏 UML”这类知识点特例，而是加入所有章节通用的强制产物和验收条件。

## 2.1 大纲原子项必须有稳定唯一 ID

建议按知识域使用稳定前缀，例如：

- `CS-SW-A001`：`01_计算机系统基础知识/04_计算机软件与语言`
- `SE-A001`：`04_软件工程基础知识`
- `ARCH-A001`：`06_软件架构设计`

规则：

- ID 来源是**最新大纲的原子化结果**，不是当前目录；
- 一个大纲条目若包含多个可独立出题、需要不同考试动作的内容，应拆成多个原子项；
- 不因现有文件合并/拆分而随意更换 ID；
- 后续发现遗漏时追加原子项，不通过重排旧 ID 掩盖变化；
- 一个正文文件可以承载多个相关原子项，但每个原子项都必须指向**正文中的具体标题/段落落点**，不能只映射到文件名。

## 2.2 每章必须生成强制覆盖矩阵

矩阵至少包含：

| 字段 | 含义 |
|---|---|
| Atom ID | 大纲原子项唯一 ID |
| 大纲原文 | 保留大纲依据，防止改写后失真 |
| 原子项 | 可独立核验的最小考试知识单元 |
| 最小考试闭环 | 这项至少要会到什么程度 |
| 主事实源章节 | 该知识真正由哪一章负责讲完整 |
| 正文文件 | 实际承载文件 |
| 正文具体落点 | 二级/三级标题或明确锚点，不能只写文件名 |
| 教材证据 | 用于确认定义、边界、机制和解释深度 |
| 真题证据 | 用于确认实际考法、辨析点与优先级 |
| 覆盖状态 | `unmapped / partial / covered / link_only` |
| 修复动作 | 补强原卡 / 新增原子卡 / 建立链接 / 无需修改 |
| 跨章链接 | 非主事实源章节如何承接到主事实源 |

覆盖状态必须统一定义：

- `unmapped`：没有可验证的实质正文落点；
- `partial`：已有实质正文，但解释深度、机制、边界或考试动作不足；
- `covered`：已有实质落点，且达到该原子项最小考试闭环；
- `link_only`：该章不是主事实源，本地只负责解释“它在这里为什么出现”，并链接到另一个已 `covered` 的主事实源。

## 2.3 以下情况一律不得计为“已覆盖”

以后统一禁止以下“假覆盖”：

- 目录存在；
- README/索引存在；
- 文件名存在；
- frontmatter、tag、alias 中出现关键词；
- 只有一句定义；
- 只有 TODO、占位卡、空壳卡；
- 只有上位章节名，例如“面向对象分析与设计”存在就推断 UML 已覆盖；
- 只有“本章主线完整”“内容基本齐全”这类主观结论；
- 跨章节只有一个失效链接，或链接目标自身也只是占位；
- 仅在别章提到术语，但没有确定唯一主事实源。

## 2.4 第一轮审核必须有硬门禁

`prompts/66` 第一轮后只有满足以下条件才能判通过：

- 大纲原子项全集已建立；
- 每个原子项都有稳定 ID；
- 每项都指向正文具体落点或明确标记待修；
- `unmapped = 0`；
- 不存在以上“假覆盖”被计作 `covered`；
- 已完成正文集合反向检查；
- 跨章节主事实源冲突 = 0；
- 所有 `link_only` 都能指向真实、有效且已覆盖的主事实源。

章节最终通过时再额外要求：

- `partial = 0`；
- 主事实源落点通过教材解释深度核验；
- 真题考法已映射；
- 单篇六要素教学闭环成立；
- 反向检查无无法解释的正文孤岛和重复主事实源。

## 2.5 必须同时做正向与反向检查

**正向检查：**

`大纲原子项 → 主事实源 → 正文文件 → 正文具体落点 → 教材/真题 → 状态`

用于发现漏项。

**反向检查：**

`正文集合 → 每一个承担知识教学的实质段落/卡片 → 对应 Atom ID 或“补充内容”理由`

用于发现：

- 正文孤岛；
- 无大纲/真题依据却无限扩写的枝节；
- 同一知识在多个章节重复讲完整；
- 文件名看似覆盖但正文实际上没有承担该原子项。

## 2.6 跨章节知识只允许一个主事实源

原则：**同一个事实和机制只在最合适的章节讲完整，其他章节只做本地定位 + 链接承接。**

本轮已知应采用的方向：

- UML 的图、用途、关系、判图与考试动作：主事实源应落在 `04_软件工程基础知识/03_分析与设计`；
- `01_计算机系统基础知识/04_计算机软件与语言/02_建模语言与UML：从“语言分类”到“软件设计表达”的桥梁.md` 只保留“UML 为什么属于建模语言、它解决什么表达问题”的桥梁定位，再链接到软件工程 UML 主事实源；
- 软件架构章节出现 UML / Use Case 时，只解释它们在架构活动中的位置，再链接到 UML/用例主事实源，不复制整套 UML 语义；
- ADL、IEEE 1471 与架构视图/描述的事实源优先留在软件架构章节；
- `04_软件工程基础知识/03_分析与设计/10_形式化方法：用数学规约消除系统歧义.md` 已存在，后续“形式化方法开发过程”默认优先补强原卡，而不是另建重复卡，除非大纲/真题证明它有独立考试闭环。

# 第一阶段：提示词机制修复

## 3. 修改顺序与职责边界

这一步必须先于任何内容修复。否则后续补完 UML 后，新的章节仍会以同样机制继续漏别的知识点。

## 3.1 先改 `prompts/20-章节检查与重构.md`

### 要加入

1. 在现有章节盘点前增加“阶段 A0：大纲原子化与覆盖矩阵”；
2. 强制建立 Atom ID；
3. 强制输出“原子项 → 正文具体落点”矩阵；
4. 明确四种覆盖状态；
5. 加入假覆盖排除规则；
6. 加入正向 + 反向检查；
7. 加入跨章节唯一主事实源登记；
8. 章节重构的修复任务必须来自矩阵中的 `unmapped / partial`，不能凭当前目录自由发挥。

### 为什么它先改

`20` 是章节级诊断/重构入口，应当负责“**先证明缺什么**”，而不是等 `66` 最后审核时才发现。

## 3.2 再改 `prompts/65-教材证据与笔记校验.md`

### 要加入

1. 教材证据记录从“整篇笔记级”下沉到“Atom ID + 正文具体落点”；
2. 明确区分“教材提到了”与“正文已经解释到考试所需深度”；
3. 每个 `covered` 原子项必须核验定义、边界、机制、条件中实际需要的部分；
4. 教材只负责事实、定义、边界和机制深度，**不能单独决定考试频率和优先级**；
5. 若教材证据证明当前正文只是一句话定义，应把状态退回 `partial`，不能继续标 `covered`。

### 为什么第二个改

先由 `20` 生成原子矩阵，`65` 才有稳定对象可核验；否则教材审查仍会停留在“整篇大致没错”。

## 3.3 再改 `prompts/66-章节三轮审查.md`

### 第一轮改成真正的覆盖门禁

第一轮必须检查：

- 原子项全集是否存在；
- `unmapped` 是否归零；
- 主事实源是否唯一；
- 假覆盖是否为 0；
- 是否做过反向检查。

不满足任何一项，第一轮直接失败，不允许进入“内容基本完整”的结论。

### 第二轮改成逐 Atom ID / 落点审事实

不能只遍历“现有卡片”。要遍历矩阵中的每一行，核验：

- 正文落点是否真存在；
- 教材证据是否支持；
- 解释深度是否足够；
- 真题是否要求额外辨析/动作。

### 第三轮改成逐主事实源检查教学闭环

每个承担 `covered` 的主事实源落点都要检查：

`承接定位 → 具体问题 → 直接答案 → 核心机制 → 考试动作 → 收口/下一站`

最终要求 `partial = 0`。

### 为什么第三个改

`66` 应负责“**能不能宣布章节通过**”，而不应重复 `20` 的诊断逻辑。

## 3.4 最后改 `prompts/10-原子考点卡生成.md`

### 要加入

1. 新卡候选必须来自已完成原子化矩阵中的 `unmapped`，或确需拆卡的 `partial`；
2. 如果已有其他章节的 `covered` 主事实源，禁止重复造卡，改成 `link_only`；
3. 每张新卡生成后必须回填对应 Atom ID 和实际正文落点；
4. 样稿门禁继续保留，但“样稿候选集合”必须来自矩阵，而不是当前目录或模型主观挑选；
5. 若某章本轮只有 1 张真正需要新增的卡，不为了凑“2 张样稿”制造第二张假卡：唯一新卡作为样稿交付，先停下来审核；
6. 不跨章节拼凑两张样稿以绕过门禁。

### `prompts/10` 样稿门禁如何影响后续

- **修改提示词本身**：不受样稿门禁限制；
- **补强已有卡**：不属于“新增原子卡”，不触发 `10` 的新卡样稿门禁；
- **只建立跨章节链接**：不触发新卡门禁；
- **新增原子卡**：必须先样稿，通常先 2 张；样稿通过后才允许同章继续 5–8 张一批；
- 不因“这一批很明确”跳过样稿。

## 3.5 本阶段暂不修改的文件

### `prompts/00-全局写作规范.md`

暂不修改。它已经承担单篇六要素教学闭环与来源优先级，再把章节覆盖门禁塞进去会造成职责重复。

### `AGENTS.md`

暂不修改。只有第一阶段完成后发现任务路由仍无法明确把“章节覆盖矩阵”导向 `20/65/66` 时，才单独补路由说明；本阶段不预设必须修改。

## 3.6 第一阶段验收条件

用一个**虚拟漏项**做机制回归测试：

- 即使某章目录、README、frontmatter、上位主题都出现该词，只要没有正文实质落点，必须判 `unmapped`；
- 第一轮审核必须因此失败；
- 一个跨章节知识若已有主事实源，本章建立正确定位和链接后可以判 `link_only`，不能要求复制正文；
- 反向检查必须能发现重复主事实源；
- 规则正文不得出现“UML 不能漏”这类特例，证明机制可复用于任何章节。

`prompts: enforce atom-level chapter coverage gates`

# 第二阶段：P0 内容修复

所有 P0 修复都必须在第一阶段提示词机制落地后执行，并先建立对应 Atom ID 与矩阵状态。

## 4. 批次 2：UML 知识组

### 目标目录

`01_综合知识/04_软件工程基础知识/03_分析与设计/`

当前已有结构化分析、DFD、数据字典、结构化设计、结构图、面向对象分析/设计、形式化方法等卡，但缺独立 UML 知识组。

### 修复原则

**必须新增 UML 主事实源，但不能机械拆成 13 张“每种图一张卡”。**

先依据：

`大纲原子项 → 教材解释结构 → 真题实际考法`

确定“最小考试闭环”。可考虑的候选闭环只是分组方向，不是预先钉死文件数量，例如：

- UML 总体定位、结构图/行为图怎么分、题目如何先判断图种；
- Use Case 建模：参与者、用例、关系和典型判题；
- 类图/对象图等静态结构表达中真正有考法的部分；
- 顺序图/通信图等交互表达中真正需要区分的部分；
- 状态机图/活动图等行为表达中真正需要区分的部分；
- 构件/部署等实现视角中真题实际要求的部分。

若多个图在真题中只要求“识别用途”，应合并到同一考试闭环；只有当某图有独立关系、符号、推断动作时才独立拆卡。

### 同时补强但不重复造正文

现有：

`01_综合知识/01_计算机系统基础知识/04_计算机软件与语言/02_建模语言与UML：从“语言分类”到“软件设计表达”的桥梁.md`

后续只补：

- UML 在语言分类中的定位；
- 为什么从编程语言过渡到建模语言；
- 指向软件工程 UML 主事实源的链接。

不在这张桥梁卡复制 13 种图、关系和判题逻辑。

### 样稿门禁

UML 涉及新增卡：**受 `prompts/10` 样稿门禁限制**。

先从矩阵选最有代表性的 2 个 UML 原子闭环做样稿；审核通过后，余下新卡才可 5–8 张一批继续。

### 验收

- UML 相关 Atom ID 全部有正文具体落点；
- `unmapped = 0`、`partial = 0`；
