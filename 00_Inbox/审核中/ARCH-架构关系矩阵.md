# ARCH 架构关系矩阵

> [!important] 这张矩阵解决“为什么下一站出现”
> 它描述的是**教学依赖、架构问题演化和边界关系**，不是宣称所有架构严格按时间顺序互相替代。

## 一、主认知链

`ARCH-IS-A001/A002 信息系统架构与模型`
→ `ARCH-LAY-A001 层次式架构`
→ `ARCH-SOA-A001 SOA`
→ `ARCH-CN-A003 微服务`
→ `ARCH-CN-A004 容器运行与交付`
→ `ARCH-CN-A001/A002 云原生原则与模式`
→ `ARCH-CN-A005/A006/A009/A010 Mesh / Serverless / 可观测 / 事件驱动`

每一跳都必须回答：

1. 前一方案解决了什么；
2. 又留下什么复杂性；
3. 后一方案为什么出现；
4. 两者是替代、细化、支撑还是可以并存；
5. 什么场景下旧方案仍然更合适。

## 二、跨域稳定关系

| 上一节点 | 下一节点 | 关系 | 唯一主事实源约束 |
| --- | --- | --- | --- |
| ARCH-SOA-A007 | ARCH-CN-A003 | SOA 的服务化思想向更小自治单元、独立部署继续细化 | **微服务完整事实只放 ARCH-CN-A003**；SOA 侧只解释演化与边界 |

| 03 信息安全技术 | ARCH-SEC-A005/A010 | 既有安全技术被组合成分层安全架构，并分析不同架构的脆弱性 | 安全技术主事实源不复制 |
| FUT-A013 大数据基础 | ARCH-BIG-A002/A003/A004 | 从“数据问题是什么”进入 Lambda/Kappa 组织方式与设计选择 | 大数据基础与大数据架构分离 |

## 三、必须显式区分的等同误区

- 云原生 ≠ Kubernetes；
- 容器 ≠ 云原生；
- 微服务 ≠ 云原生；
- Kubernetes ≠ 微服务；
- Service Mesh ≠ 微服务本身；
- Serverless ≠ 没有服务器；
- SOA ≠ 微服务，但微服务延续并强化服务化的一部分思想；
- 分层 ≠ 三层，三层只是常见分层实现；
- MVC ≠ 分层架构本身；
- C/S、B/S 描述客户端与服务端分布/交互，不等于分层；
- 大数据 ≠ Lambda/Kappa；Lambda/Kappa 是大数据处理系统的架构组织方式。

## 四、八域之间的前置关系

| 域 | 主要前置 | 向后交付 |
| --- | --- | --- |
| 信息系统架构 | 信息系统基础、软件架构基础 | 总体框架、ADM、常用模型，为后续具体架构域建立“如何看整体系统” |
| 层次式架构 | 架构风格、数据库/软件工程基础 | 职责分离与层边界，为 SOA/微服务比较提供基线 |
| 云原生架构 | 云计算、分布式/质量属性、SOA/微服务 | 面向动态云环境的模式、运行与治理能力 |
| SOA | EAI、面向服务方法、架构风格 | 服务化、契约、编排、ESB 与微服务演化入口 |
| 嵌入式 | 计算机系统、OS、实时/可靠性、ABSD | 资源受限/实时系统中的架构方法 |
| 通信系统 | 计算机网络、可靠性、安全 | 网络技术如何组合成可用、可扩展、安全的通信架构 |
| 安全架构 | 信息安全技术、质量属性 | 从零散控制进入整体安全组织与架构脆弱性判断 |
| 大数据架构 | 大数据基础、数据库/分布式基础 | Lambda/Kappa 与处理路径选型 |
