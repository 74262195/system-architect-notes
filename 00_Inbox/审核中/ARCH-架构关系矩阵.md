# ARCH 架构关系矩阵

> [!important] 这张矩阵解决“为什么下一站出现”
> 它描述的是**教学依赖、架构问题演化和边界关系**，不是宣称所有架构严格按时间顺序互相替代。零基础可视化入口见 [[架构设计总览与八域学习路线]]。

## 一、主认知链

零基础主线统一为：

`架构基础 → 分层 → 分布式问题 → SOA → 微服务 → 云原生`

其中“分布式问题”是问题空间桥梁，不是第九域。落到 stable Atom 时，核心映射为：

`ARCH-IS-A001/A002 信息系统架构与模型`
→ `ARCH-LAY-A001 层次式架构`
→ `分布式问题桥梁`
→ `ARCH-SOA-A001 SOA`
→ `ARCH-CN-A003 微服务`
→ `ARCH-CN-A004/A016 容器与 Kubernetes`
→ `ARCH-CN-A001/A002 云原生原则与模式`
→ `ARCH-CN-A005/A006/A009/A010 Mesh / Serverless / 可观测 / 事件驱动`

每一跳都必须回答：

1. 前一方案解决了什么；
2. 又留下什么复杂性；
3. 后一方案为什么出现；
4. 两者是替代、细化、支撑还是可以并存；
5. 什么场景下旧方案仍然更合适。

## 四、概念层级约束

| 层级 | 概念 | 关系约束 |
| --- | --- | --- |
| 架构范式/组织方式 | 分层、SOA、微服务、云原生 | 可形成主学习线；不与具体工具并列 |
| 设计思想 | DDD | 可帮助服务边界设计，不等于微服务 |
| 通信方式 | REST、RPC、消息 | 服务间交互手段，不决定整体架构 |
| 运行机制 | 容器、Kubernetes、服务发现、配置管理、Service Mesh、可观测性 | 支撑分布式/云原生运行，不是新的顶级架构域 |
| 工程实践 | CI/CD、DevOps、Infrastructure as Code | 支撑持续交付与运维，不等于运行时机制或架构范式 |

## 五、必须显式区分的等同误区

- 云原生 ≠ Kubernetes；
- 容器 ≠ 云原生；
- 微服务 ≠ 云原生；
- Kubernetes ≠ 微服务；
- Service Mesh ≠ 微服务本身；
- DDD ≠ 微服务；
- REST / RPC / 消息 ≠ SOA 或微服务本身；
- CI/CD / DevOps / IaC ≠ 云原生定义；
- Serverless ≠ 没有服务器；
- SOA ≠ 微服务，但微服务延续并强化服务化的一部分思想；
- 分层 ≠ 三层，三层只是常见分层实现；
- MVC ≠ 分层架构本身；
- C/S、B/S 描述客户端与服务端分布/交互，不等于分层；
- 大数据 ≠ Lambda/Kappa；Lambda/Kappa 是大数据处理系统的架构组织方式。
