# 一、先给结论

这次联合审查确认：此前“软件工程主线完整”的结论过于乐观。

问题不是第四章整体失效，而是现有覆盖审查主要按“大纲章节/主题 → 当前卡片”做映射，没有严格做到：

> **大纲每一个原子项目符号 → 唯一承接位置 → 正文真实落点 → 做题判断动作 → 跨章节链接。**

因此出现了典型的“目录幻觉”：

- 文件存在，不等于知识已经讲完；
- 上位主题有卡，不等于下位原子项都有正文；
- 某个知识点在其他章节被提到，不等于当前章节已经完成承接；
- 一个章节有几十张卡，也可能漏掉大纲明确点名的项目。

### 计算机语言

- UML 关系；
- UML 五种视图。

### 软件工程分析与设计

大纲把 UML 与以下设计/分析表达工具并列：

- DFD；
- SC；
- 业务流图；
- 流程图；
- PAD；
- NS；
- PDL；
- UML。

### 软件架构设计与生命周期

大纲明确列：

- Use Case 图；
- ADL；
- 4+1 模型；
- UML；
- IEEE 1471-2000。

证据入口：

- [[官方教材/AI教材库/原始文本/系统架构第二版 大纲/p0049-p0060]]
- 计算机语言与软件工程对应大纲原始文本块，执行下轮时重新按最新 `main` 检索。

## 2.2 当前 UML 卡过浅

当前：

- [[建模语言与UML]]

已有：

- UML 是标准建模语言，不是开发方法；
- 四类事物；
- 五种视图。

但明显缺少：

- 依赖；
- 关联；
- 聚合/组合；
- 泛化；
- 实现；
- 多重度；
- 用例图；
- Actor；
- 系统边界；
- `include`；
- `extend`；
- 类图；
- 序列图；
- 通信图；
- 活动图；
- 状态机图；
- 构件图；
- 部署图；
- “题干描述 → 应选哪类 UML 图”的判断能力。

主教材在 UML 正文中实际展开了：

- UML 基本构造块；
- 4 种基本关系；
- UML 2.0 的 13 种图；
- 用例图的参与者、系统边界、include、extend、泛化；
- 五种视图及其常用图。

主教材入口：

- [[官方教材/AI教材库/原始文本/系统架构设计师教程第二版可搜索/p0097-p0108]]

## 2.3 UML 的建议拆法

不要按 13 种图拆成 13 张卡，避免知识膨胀。

建议形成一个紧凑 UML 学习组：

1. **UML 总览：事物、关系、图、五视图**
2. **类图与 UML 基本关系：关联、聚合/组合、泛化、实现、依赖、多重度**
3. **用例图：Actor、系统边界、include、extend、泛化**
4. **序列图与通信图：对象之间怎样交互**
5. **活动图与状态机图：流程变化 vs 对象状态变化**
6. **构件图与部署图：软件构件组织 vs 软件到硬件节点映射**
7. **题干 → UML 图第一反应**（可作为总结卡，不必长）

学习链建议改为：

> OOA → OOD → UML 建模 → OOP

软件工程只负责说明“为什么这里需要 UML”，完整 UML 正文应只保留一个事实源，其他章节使用 wikilink 承接，避免复制。

# 三、计算机软件与语言：总体可用，但存在 4 类明确缺口

## 3.1 软件分类：通用软件 / 专用软件承接太薄

当前 [[计算机软件分类]] 已经解释：

- 系统软件；
- 应用软件。

但“应用软件还可分通用软件与专用软件”只是一句带过。

主教材明确按“开发方式与适用范围”区分：

- **通用软件**：面向一类普遍需求；
- **专用软件**：面向某个组织、行业或特定业务需求。

修复方式：**补现有卡，不新拆大卡。**

## 3.2 机器语言：教学很通俗，但考试覆盖不够

当前 [[计算机语言-编译与解释]] 很擅长解释：

> `if / for → 比较、跳转 → 机器指令 → CPU 执行`

这部分教学保留。

但大纲/教材还要求：

- 指令格式；
- 操作码；
- 地址码；
- 三地址、二地址、单地址、零地址；
- 基本寻址定位。

修复方式：**在现有语言卡中补“机器指令长什么样、地址数表示什么”最小考试深度。**

## 3.3 汇编语言：伪指令等大纲内容缺失

大纲/教材要求：

- 指令语句；
- 伪指令语句；
- 宏指令语句；
- 汇编语句基本字段；
- 伪指令与机器指令的区别。

当前卡只有 ADD/MOV 等助记符定位。

修复方式：**补现有语言卡，不扩成汇编课程。**

## 3.4 形式化语言：主体已有，缺形式化开发过程

当前 [[形式化语言与规格说明]] 已覆盖：

- 公理方法；
- 集合论/谓词演算；
- 代数规格；
- CSP/CCS；
- Z 语言。

但教材还明确给出形式化方法贯穿软件生命周期：

> 可行性分析 → 需求分析 → 体系结构设计 → 详细设计 → 编码 → 测试发布

当前没有真正承接。

修复方式：**在原卡增加一个短小过程小节。**

# 四、软件工程：主体完整，但“主线完整”必须改成“主体完整”

第四章已经建设的大量正文仍然有价值，不推翻重做。

以下部分本次检查后仍可认为主体承接较好：

- 过程模型；

- 测试主线；
- 风险管理；
- 净室软件工程；
- CBSE；

## 4.1 重大缺口：UML

OO 当前主线：

> 面向对象方法 → OOA → OOD → 实体/边界/控制 → OOP → ORM

问题：

- OOA 已讲对象、类、关联、整体/部分；
- OOD 已讲类职责、接口、协作、关系；
- 但没有正式告诉学习者如何使用 UML 表达这些分析/设计结果。

这构成教学断链。

修复方式：

> 在 OOA/OOD 学习链中明确插入 UML 主入口，不复制整套 UML 正文。

## 4.2 中等缺口：SC 系统结构图 / 业务流图

当前 [[结构化详细设计工具]] 已出现：

> “模块调用层次看 SC”

但没有真正解释 SC 是什么。

[[结构化分析与设计分工]] 只把系统结构图写成概要设计产物，也没有继续讲判断方法。

业务流图承接更弱。

修复深度：

- SC：知道它表达模块调用/层次关系；
- 业务流图：知道它表达业务活动/业务流转，与 DFD 的“数据流”区分；
- 不需要扩成大篇。

## 4.3 P0 缺口：CMMI 不应只背五级

当前 [[CMMI成熟度等级]] 的五级已经讲清：

> 初始 → 已管理 → 已定义 → 量化管理 → 优化

但大纲还明确要求：

- 关键过程域；
- 过程目标。

当前卡因版本敏感，选择不背关键过程域数量，这是正确的。

但不能因此把“过程域是什么、过程目标是什么、它们与成熟度等级的关系”整个删掉。

建议补：

- 过程域是什么；
- 过程目标是什么；
- 为什么不同成熟度等级会对应不同过程能力要求；
- 不强背未经当前考试指定版本核验的数量表。

## 4.4 净室：无重大缺口

当前：

- [[净室软件工程]]
- [[净室盒子结构]]

已覆盖：

- 正确性验证；
- 受控增量；
- 函数理论；
- 抽样理论；
- 统计测试；
- 黑盒/状态盒/明盒；
- 局限。

仅需低优先级补：

- 软件认证；
- 应用场景/发展背景最小定位。

无需新拆很多卡。

# 七、为什么按现有提示词生成，仍然会出现这些问题

这次问题不是因为提示词“完全没有覆盖规则”。恰恰相反，当前提示词已经写了很多正确原则。

真正原因是：

> **原则写得够多，但缺少可机械验收的覆盖产物。**

## 原因 1：覆盖检查粒度还是太粗

`prompts/66-章节三轮审查.md` 已要求：

> 把大纲条目映射到现有原子卡。

但执行时“大纲条目”容易被理解成：

> 4.3 分析与设计 → 已有 DFD、OOA/OOD、形式化方法 → 完成。

而不是继续拆成：

- 4.3.1.1 ……
- 4.3.1.2 DFD
- 4.3.1.3 SC
- 4.3.1.4 业务流图
- 4.3.1.5 UML
- ……

最终 UML、SC、业务流图被上位主题吞掉。

## 原因 2：缺少“未映射数必须为 0”的硬门禁

当前规则要求做映射，但没有要求输出类似：

| 原子 ID | 大纲原文项目 | 承接卡 | 正文落点 | 状态 |
| --- | --- | --- | --- | --- |
| 4.3-UML | UML | — | — | ❌ 未映射 |

也没有明确规定：

> **章节第一轮审查通过前，`未映射原子项 = 0`。**

没有这个硬数字，就容易凭整体感觉写“主线完整”。

## 原因 3：单篇原子性很强，但章节级兜底不足

`prompts/10` 强调“一卡一主问题”，这是正确的。

但它依赖一个前提：

> **章节覆盖清单本身必须完整。**

如果覆盖清单漏了 UML，那么原子卡生成器会忠实地把已有卡写得很好，却永远不会主动发现“还有一张 UML 主卡根本没建”。

所以问题不在原子性，而在原子性上层缺少完整覆盖清单门禁。

## 原因 4：优先级校准有时掩盖了“知识本体是否存在”

旧软件工程审核里已经注意到：

> “OO/UML 是上位 P0，但不能把 OOA/OOD/OOP 全部机械升级为 P0。”

这个判断本身正确。

但审查随后集中在“下位卡该 P0/P1/P2”上，没有再反向检查：

> **UML 这个上位主题本身有没有完整正文？**

于是出现：

- 上位主题被真题雷达识别成 P0；
- 下位 OOA/OOD/OOP 被正常分级；
- 但 UML 本体没有真正建成。

## 原因 5：旧审核报告是“发现了什么问题”，不是“证明没有漏项”

旧报告主要列：

- 新增构件组装；
- 补 OOD/OOP；
- 补逆向工程；
- 补形式化方法；
- 补 V&V；
- 等等。

这些都是有效修复。

但这种报告只能证明：

> **发现的问题修了。**

不能证明：

> **大纲所有项目都已经逐项检查完。**

缺少“全集 → 映射 → 差集”的过程。

## 原因 6：跨章节知识没有“唯一主事实源”规则

UML、4+1、形式化方法这类知识横跨多个大纲章节。

当前提示词强调不要重复，但没有强制为跨章节主题记录：

- 主承接章节；
- 主事实源卡；
- 次级章节只负责什么；
- 哪些地方必须反向链接。

因此容易出现两种坏结果：

1. 多处重复写；
2. 大家都认为“别的章节会讲”，最终没人真正讲。

UML 这次更接近第二种。

## 原因 7：教学质量和覆盖质量被放在同一个“完成感”里

有些卡正文确实很好，例如：

- ABSD；
- 系统测试；
- 风险管理；
- 网络近期大量重写卡。

这些高质量正文会让人产生“这一章已经比较成熟”的整体感觉。

但：

> **单篇写得好 ≠ 章节覆盖完整。**

因此以后必须把这两个验收维度彻底分开。

# 八、“教学闭环”必须保留，而且应升级为两层闭环

“教学闭环”这个词非常重要，不应该因为本次发现覆盖问题而删掉。

目前 `prompts/00` 和 `prompts/10` 已经建立了很好的**单篇教学闭环**思想：

> 承接与定位 → 具体问题 → 讲懂机制 → 落到考试 → 收口与下一站

这是当前笔记从“教材摘要”转向“零基础能学懂”的核心原因，应保留并继续强化。

本次真正缺的是第二层：**章节覆盖闭环**。

## 8.1 第一层：单篇教学闭环

每张原子卡必须闭环回答：

1. **我为什么现在学这个？**
2. **它解决什么具体问题？**
3. **机制到底怎么走？**
4. **考试题里怎么认、第一步怎么做？**
5. **我学完得到什么，下一站为什么出现？**

一句话：

> **一张卡不能只是“把知识放进来”，而要让学习者从不知道走到会理解、会判断。**

## 8.2 第二层：章节覆盖闭环

每个章节必须闭环回答：

1. **大纲要求的全集是什么？**
2. **每一个原子要求由哪张卡负责？**
3. **这张卡是真正文还是占位/一句话？**
4. **教材要求的必要下位机制有没有被承接？**
5. **真题真正考过的判断动作有没有进入正文？**
6. **跨章节知识是否有唯一主事实源和双向链接？**
7. **未映射原子项是否为 0？**
8. **待生成 P0/P1/P2 是否为 0？**

一句话：

> **单篇教学闭环保证“这一张学得懂”，章节覆盖闭环保证“该学的没有漏”。**

以后所有章节完成必须同时满足这两层闭环。
