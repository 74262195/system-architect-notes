# 全库覆盖审计矩阵

> [!important] 本表不是“全章已经审核完”的证明
> 本表是 G0-3 的**全库控制矩阵**：把 `[[全库综合知识大纲Atom母表]]` 的官方范围与仓库当前真实承接状态对齐，决定后续先做迁移复核、在途收口、章级 Atom 审计，还是新建知识域。
>
> `covered / partial / unmapped / link_only` 仍只能由各知识域的稳定 Atom 矩阵逐行证明；本表不越权用目录或关键词替代章节覆盖契约。

## 一、G0-3 的反向检查方法

本轮同时使用三类证据：

1. **真实目录/文件树**：确认综合知识实际有哪些章节与学习入口；
2. **已有审核、交接和 Atom 矩阵**：只承认当前可追溯的在途/完成证据；
3. **反向关键词检索**：重点检索官方大纲 8～13 的“软件可靠性、架构演化、数字孪生、知识产权、标准化、图论、概率统计、运筹、专业英语”等主题，判断是否已经散落为可复用正文。

### 检索结果怎样解释

GitHub 私有仓库代码搜索可能存在索引延迟或漏召回，因此：

- **0 搜索结果不能单独证明“仓库绝对没有”**；
- 完整 tree 中没有同名/近义学习文件，只能提高“未发现独立主事实源”的可信度；
- 教材原始文本、提示词、审核报告、索引中出现关键词，**不计为综合知识正文覆盖**；
- 案例/论文素材中即使出现同一主题，也只能作为后续复用候选，不能自动替代综合知识主事实源；
- 只有可独立学习的正文 + 明确主事实源 + 后续 Atom 证据，才允许最终标 `covered`。

因此对 8～13，本轮使用“未发现可独立主事实源 / 可能有散点承接 / 待章级 Atom 审计”等措辞，不制造虚假的绝对结论。

## 五、8～13 的建章判定门禁

“无同名顶层目录”不等于立即创建目录。每个候选新知识域必须先经过一个**只审计、不写正文**的范围批次，完成：

1. 回看官方大纲原 PDF，确认章节/子项；
2. 按 `20` 原子化为稳定 Atom；
3. 搜索全库正文，确定已有主事实源、可复用散点和重复风险；
4. 按 `65` 锁主教材解释深度；
5. 按可靠真题确认优先级/做题动作；
6. 决定是否需要新顶层章、哪些 Atom 应 `link_only`、哪些才是真 `unmapped`；
7. 只有完成上述步骤才进入样稿门禁。

特别是：

- **8 软件可靠性**与 7 质量属性、4 软件测试有交叉，必须先定主源；
- **9 架构演化与维护**与 6.2 ABSD 的“演化”有交叉，不能重复写；
- **10 未来信息技术**控制深度，不能扩成 AI/云原生百科；
- **11 标准化与知识产权**需警惕法规/标准版本口径；
- **12 应用数学**需要以考试动作决定拆卡，不以教材目录机械拆；
- **13 专业英语**优先考虑“术语 + 阅读识别 + 真题词汇链”的轻量入口，不默认做大章百科。

## 六、G0-3 形成的任务类型

全库后续只允许从以下五类任务进入：

1. `MIGRATE`：旧完成章节迁移到当前 Atom 规则；
2. `CLOSE`：已有当前 Atom 矩阵的在途章节清零 `unmapped/partial`；
3. `AUDIT`：有章但没有当前完整覆盖契约，先建立 Atom 矩阵；
4. `NEW-DOMAIN-AUDIT`：8～13 候选缺章先做范围/主事实源审计；
5. `REVIEW-DEBT`：已有新正文但尚未经过独立三轮审核，例如当前网络任务。

不得出现第六类“看目录觉得缺什么就直接写什么”。
