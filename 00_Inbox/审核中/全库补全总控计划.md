# 全库补全总控计划

> [!important] 本文件的角色
> 本文件是本次“补全 GitHub 笔记”的**执行控制面**。它不替代章节知识索引，也不替代各知识域 Atom 矩阵。
>
> 固定关系：
>
> `[[全库综合知识大纲Atom母表]]` 定全局范围  
> → `[[全库覆盖审计矩阵]]` 定当前处置类型  
> → 本文件定批次、模型、门禁和换聊天节点  
> → 各知识域稳定 Atom 矩阵定具体正文任务  
> → `66` 三轮审核决定是否真的完成。

## 一、总目标

最终建立一条可追溯链：

> **官方大纲 → 稳定 Atom → 唯一主事实源 → 零基础教学正文 → 真题/考试动作 → 案例分析 → 论文素材 → 真题反向验收**

本工程不以“文件数量多”为完成标准。

完成必须同时满足：

- 大纲范围无漏项；
- 所有保留 Atom 最终只有 `covered / 合法 link_only`；
- `unmapped = 0`；
- `partial = 0`；
- 假覆盖 = 0；
- 重复主事实源冲突 = 0；
- P0/P1/P2 均有可独立学习正文；
- 三轮独立审核全部通过；
- 索引、学习路线、正文、优先级和矩阵一致；
- 真题能反向落到 Atom/正文，不能出现“大纲内有效题无主事实源”。

## 二、并发仓库协议

用户当前同时运行多个聊天修改仓库，所以每个批次都执行：

1. **写入前重新获取远端最新 `main`**，不使用本文件记录的历史 SHA 当固定起点；
2. 重新读取最新 `AGENTS.md`；
3. 按路由读取本批 prompts；
4. 读取本计划、G0 矩阵、本批知识域矩阵/交接；
5. 读取目标正文和直接相邻正文；
6. 若其他会话已经修改本批目标文件，重新读取并合并，不覆盖；
7. 不顺手改其他在途任务线；
8. 不 force push；
9. 一个逻辑批次原则上形成一个可追溯提交；
10. 工具支持时运行 `node scripts/check-vault.mjs` 与 `git diff --check`；不支持时明确记录，不能假装通过。

### 当前并发隔离

信息安全仍由其他会话推进。在其正式交接前：

- 本计划不修改信息安全正文；
- 不抢写其 Atom 矩阵/审核报告；
- 只在总控中保留“并发在途”；
- 收到交接后进入 G2 迁移/收口判断。

## 三、正文 95 分启动门禁

正文不能因为“已经知道主题”就开始写。每个新增/大幅重写任务先评分：

| 项目 | 分值 | 达标条件 |
| --- | ---: | --- |
| 大纲 Atom 与所属范围已确定 | 15 | 有稳定 Atom/明确范围，不从目录猜 |
| 主教材证据已定位 | 15 | 定义、机制、边界有可靠教材页/块 |
| 真题证据已核验 | 10 | 有可靠考法，或明确记录“当前无可靠真题” |
| 唯一主事实源已确定 | 10 | 不与别章重复讲完整机制 |
| 当前正文/占位状态已读 | 10 | 知道是新增、补强还是链接 |
| 上一站与下一站已读 | 10 | 能解释为什么现在学、下一步去哪 |
| 唯一主问题可一句话表达 | 10 | 无第二个独立主问题 |
| 零基础具体场景可建立 | 10 | 能先让读者看见对象/问题，再给术语 |
| 考试动作已确定 | 5 | 能给题干信号与第一步动作 |
| 无证据硬阻断 | 5 | OCR/版本/术语/层级无关键疑问 |
| **合计** | **100** | **≥95 才可进入正文** |

### 即使分数达到 95，以下任一存在也必须停止

- 大纲归属有实质争议；
- 主教材关键定义/表格只剩不可靠 OCR；
- 两个章节都可能成为完整主事实源，尚未裁决；
- Atom 是否应该拆分仍无法确定；
- 版本、标准、教材术语存在未解决冲突。

处理方式：记录 `blocked: evidence` / `blocked: source-of-truth`，继续证据任务，不用正文试错。

## 四、一个正文批次到底多大

模型上下文窗口不是批量上限。上限由“能否逐篇独立验收”决定。

| 任务类型 | 默认每批上限 |
| --- | ---: |
| P0 复杂机制/计算/体系 | 1 篇 |
| 普通 P0/P1 原子卡 | 1～2 篇 |
| P2 简单定位型 | 最多 3 篇 |
| 跨章节主事实源迁移 | 1 个知识组 |
| 章级 Atom/覆盖审计 | 1 个知识域 |
| 三轮审核 | **1 轮 = 1 个独立批次** |

### 批量样稿门禁

一次计划新增/大幅重写 **3 篇及以上**，或首次进入一个新知识域：

1. 从真实 `unmapped / partial` 选 1 篇代表样稿；
2. 完成 95 分门禁；
3. 只生成这一篇；
4. 按 `10` 验收并回填 Atom；
5. **交用户确认**；
6. 用户确认后才继续后续正文。

不得用“矩阵已经明确”绕过样稿确认。

## 五、模型与工具分工

以下是本工程的默认配置；若产品当前可选名称发生变化，使用同等级最强推理配置替代，不降低正文门禁。

| 工作 | 默认配置 | 原因 |
| --- | --- | --- |
| 全库/章级范围审计 | GPT-5.6 Sol High | 跨大纲、教材、真题、仓库综合推理 |
| Atom 拆分与主事实源裁决 | GPT-5.6 Sol High | 边界错误会导致全章重复或漏项 |
| 教材/真题证据核验 | GPT-5.6 Sol High | 事实与版本错误代价高 |
| P0/P1 代表样稿 | GPT-5.6 Sol High | 零基础教学质量门槛最高 |
| 正式正文生成/大改 | GPT-5.6 Sol High | 不为省额度降低正文质量 |
| 三轮独立审核 | GPT-5.6 Sol High，**新聊天** | 避免生成上下文自我确认 |
| 多文件同步、索引、Git 收口 | Codex Sol / 高推理 | 更适合仓库级一致性操作 |
| frontmatter、死链、机械格式 | Codex Terra 等较轻配置 | 低风险机械任务不占最高推理 |
| Luna | 不用于正式正文/事实审核 | 仅考虑低风险机械工作 |

原则：**写懂内容**和**把多文件准确落库**是两个职责，可以由不同配置完成。

# 十二、G6：论文素材

> **论文主题 → 可复用论点 → 项目场景 → 技术措施 → 质量属性/风险 → 结果 → 对应综合知识 Atom**

禁止杜撰真实项目数据。教学示例必须明确是示例。

# 十三、G7：真题反向漏洞扫描与全库终审

最终用标准化真题/可靠回忆题反向检查：

`真题 → 考点动作 → Atom → 主事实源正文`

出现大纲内有效题找不到 Atom/正文时：

- 重新打开相应知识域；
- 判断是 Atom 漏建、正文缺口、主事实源错误还是链接失效；
- 修复后重新执行受影响的审核轮。

最后检查：

- 全库孤岛正文；
- 重复主事实源；
- 失效 `link_only`；
- 学习路线断链；
- 索引/正文状态不一致；
- P0/P1/P2 空占位；
- 真题无法落点。

# 十四、换聊天规则

为了保证上下文干净和独立审核，以下节点必须/建议换聊天。

## 必须新开聊天

1. **G0 完成后 → 开始 G1 / SW-06A**；
2. 每个知识域的第 1、2、3 轮独立审核分别使用新聊天；
3. 一个新大知识域从 `NEW-DOMAIN-AUDIT` 进入正式施工时，建议新聊天起步；
4. 前一聊天已经完成一个完整逻辑批次且上下文包含大量生成细节，下一批涉及新的证据链时，新开聊天。

## 可以留在同一聊天

- 同一个证据审计批次内部；
- 代表样稿生成后等待用户反馈；
- 用户对样稿提出直接修改时；
- 纯链接/frontmatter/索引机械收口且不需要独立审查。

助手必须主动提醒：

> **“这里应该新开聊天，下一聊天执行 XXX。”**

不能让用户自己猜什么时候需要换。
