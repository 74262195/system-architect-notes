# 全库补全总控计划

> [!important] 本文件的角色
> 本文件是“补全 GitHub 笔记”的执行控制面，不替代章节知识索引，也不替代各知识域 Atom 矩阵。
>
> 固定关系：
>
> `[[全库综合知识大纲Atom母表]]` 定全局范围  
> → `[[全库覆盖审计矩阵]]` 定当前处置类型  
> → 本文件定批次、模型、门禁和换聊天节点  
> → 各知识域稳定 Atom 矩阵定具体正文任务  
> → `66` 三轮审核决定是否真的完成。

## 一、总目标

最终建立一条可追溯链：

> **官方大纲 → 稳定 Atom → 唯一主事实源 → 零基础教学正文 → 真题/考试动作 → 案例分析 → 论文素材 → 真题反向验收**

本工程不以文件数量为完成标准。完成必须同时满足：

- 大纲范围无漏项；
- 所有保留 Atom 最终只有 `covered / 合法 link_only`；
- `unmapped = 0`；
- `partial = 0`；
- 假覆盖 = 0；
- 重复主事实源冲突 = 0；
- P0/P1/P2 均有可独立学习正文；
- 三轮独立审核全部通过；
- 索引、学习路线、正文、优先级和矩阵一致；
- 真题能反向落到 Atom/正文，不能出现“大纲内有效题无主事实源”。

## 二、并发仓库协议

每个批次都必须执行：

1. **写入前重新获取远端最新 `main`**，不能把本文件记录的历史 SHA 当固定起点；
2. 重新读取最新 `AGENTS.md`；
3. 按路由读取本批 prompts；
4. 读取本计划、全库矩阵、本批知识域矩阵/交接；
5. 涉及正文时读取目标正文和直接相邻正文；
6. 若其他会话已修改本批目标文件，重新读取并合并，不覆盖；
7. 不顺手改其他在途任务线；
8. 不 force push；
9. 一个逻辑批次原则上形成一个可追溯提交；
10. 工具支持时运行 `node scripts/check-vault.mjs` 与 `git diff --check`；不支持时明确记录“未执行”，不能假装通过。

## 三、正文 95 分启动门禁

正文不能因为“已经知道主题”就开始写。每个新增/大幅重写任务先评分：

| 项目 | 分值 | 达标条件 |
| --- | ---: | --- |
| 大纲 Atom 与所属范围已确定 | 15 | 有稳定 Atom/明确范围，不从目录猜 |
| 主教材证据已定位 | 15 | 定义、机制、边界有可靠教材页/块 |
| 真题证据已核验 | 10 | 有可靠考法，或明确记录当前无可靠真题 |
| 唯一主事实源已确定 | 10 | 不与别章重复讲完整机制 |
| 当前正文/占位状态已读 | 10 | 知道是新增、补强还是链接 |
| 上一站与下一站已读 | 10 | 能解释为什么现在学、下一步去哪 |
| 唯一主问题可一句话表达 | 10 | 无第二个独立主问题 |
| 零基础具体场景可建立 | 10 | 能先让读者看见对象/问题，再给术语 |
| 考试动作已确定 | 5 | 能给题干信号与第一步动作 |
| 无证据硬阻断 | 5 | OCR/版本/术语/层级无关键疑问 |
| **合计** | **100** | **≥95 才可进入正文** |

即使达到 95，以下任一存在仍停止正文：

- 大纲归属有实质争议；
- 主教材关键定义/表格只剩不可靠 OCR；
- 两个章节都可能成为完整主事实源，尚未裁决；
- Atom 是否应该拆分仍无法确定；
- 版本、标准、教材术语存在未解决冲突。

处理方式：记录 `blocked: evidence` / `blocked: source-of-truth`，继续证据任务，不用正文试错。

## 四、一个正文批次到底多大

| 任务类型 | 默认每批上限 |
| --- | ---: |
| P0 复杂机制/计算/体系 | 1 篇 |
| 普通 P0/P1 原子卡 | 1～2 篇 |
| P2 简单定位型 | 最多 3 篇 |
| 跨章节主事实源迁移 | 1 个知识组 |
| 章级 Atom/覆盖审计 | 1 个知识域 |
| 三轮审核 | **1 轮 = 1 个独立批次** |

### 批量样稿门禁

一次计划新增/大幅重写 3 篇及以上，或首次进入一个新知识域：

1. 从真实 `unmapped / partial` 选 1 篇代表样稿；
2. 完成 95 分门禁；
3. 只生成这一篇；
4. 按 `10` 验收并回填 Atom；
5. 交用户确认；
6. 用户确认后才继续后续正文。

不得用“矩阵已经明确”绕过样稿确认。

## 五、模型与工具分工

| 工作 | 默认配置 | 原因 |
| --- | --- | --- |
| 全库/章级范围审计 | GPT-5.6 Sol High | 跨大纲、教材、真题、仓库综合推理 |
| Atom 拆分与主事实源裁决 | GPT-5.6 Sol High | 边界错误会导致重复或漏项 |
| 教材/真题证据核验 | GPT-5.6 Sol High | 事实与版本错误代价高 |
| P0/P1 代表样稿 | GPT-5.6 Sol High | 零基础教学质量门槛最高 |
| 正式正文生成/大改 | GPT-5.6 Sol High | 不为省额度降低正文质量 |
| 三轮独立审核 | GPT-5.6 Sol High，**新聊天** | 避免生成上下文自我确认 |
| 多文件同步、索引、Git 收口 | Codex Sol / 高推理 | 仓库级一致性操作 |
| frontmatter、死链、机械格式 | 较轻高可靠配置 | 低风险机械工作 |
| Luna | 不用于正式正文/事实审核 | 仅考虑低风险机械工作 |

原则：**写懂内容**和**把多文件准确落库**可以分工，但都必须服从同一事实源和门禁。

1. 独立审核的第 1、2、3 轮分别使用新聊天；
2. 新大知识域从 `NEW-DOMAIN-AUDIT` 进入正式施工时建议新聊天；
3. 前一聊天完成完整逻辑批次、下一批需要新证据链时新开聊天。

## 可以留在同一聊天

- 同一个证据审计批次内部；
- 代表样稿生成后等待用户反馈；
- 用户对样稿提出直接修改；
- 纯链接/frontmatter/索引机械收口且不需要独立审查。

# 十五、每个新聊天固定启动顺序

1. 远端最新 `main`；
2. 最新 `AGENTS.md`；
3. 任务路由 prompts；
4. `[[全库补全总控计划]]`；
5. `[[全库覆盖审计矩阵]]`；
6. 本知识域覆盖矩阵/交接；
7. 本批目标 Atom；
8. 目标正文 + 上一站/下一站；
9. 证据；
10. 执行或记录阻断；
11. 回填矩阵、索引；
12. 检查并提交。

通用原则：本批只执行一个可独立验收范围，写入前再次确认最新 `main`，不得覆盖并发会话修改；能运行仓库命令则运行，不能运行必须明确说明。
