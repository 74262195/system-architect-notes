# 敏捷方法（Agile Methods）

## 零基础先抓住

> [!question] 为什么要学这个
> 项目可以线性推进、反复迭代，也可以风险驱动。这里重点看“开发步骤按什么节奏和反馈方式推进”。

> [!important] 考试怎么认
> 看到与“**敏捷开发模型**”相关的阶段、方法或关键术语时，先判断它解决什么问题、适用什么场景，再做选择。


> **软考定位**：现代主流方法，关键词 **“以人为核心、迭代、拥抱变化”**。

---

## 一、一句话定义

**敏捷方法** 是一组开发方法的统称（包括 XP、Scrum、Crystal 等），其核心是 **“以人为核心、快速迭代、拥抱变化”**。

> **核心思想**：**“与其花半年写完美需求文档，不如花2周做出可用的东西给用户看，再根据反馈改。”**

---

## 二、敏捷 vs 传统（瀑布）核心对比（必考！）

| 对比维度 | **瀑布模型（传统）** | **敏捷方法** |
| :--- | :--- | :--- |
| **核心理念** | **“计划驱动”** | **“价值驱动”** |
| **需求变化** | 抵制变化（变更代价大） | **拥抱变化**（响应变化高于遵循计划） |
| **交付节奏** | 项目末期一次性交付 | **频繁交付**（每2~4周一个可用版本） |
| **团队结构** | 层级分工明确 | **自组织团队**，跨职能 |
| **文档要求** | 大量文档 | **“可工作的软件高于详尽的文档”** |
| **用户参与** | 只在开始和结束参与 | **业务人员和开发人员** 一起工作 |
| **规模适用** | 大规模、稳定团队 | **小到中型团队**（不超过几十人） |

---

## 三、敏捷的四大价值观（敏捷宣言）

> 记住这 4 条对比，选择题秒杀！

| 敏捷价值观 | 传统做法 |
| :--- | :--- |
| **个体与互动** 高于 流程与工具 | 流程工具优先，忽视团队沟通 |
| **可工作的软件** 高于 详尽的文档 | 过度文档化，忽视实际交付 |
| **客户合作** 高于 合同谈判 | 僵化合同，缺乏灵活性 |
| **响应变化** 高于 遵循计划 | 严格按计划执行，拒绝变更 |

---

## 四、常见敏捷方法（只需认识名字）

| 方法 | 简称 | 一句话特点 |
| :--- | :--- | :--- |
| **极限编程** | **XP** | 重视 **技术实践**（结对编程、测试驱动开发 TDD） |
| **Scrum** | **Scrum** | 重视 **项目管理**（Sprint冲刺、每日站会） |
| **水晶法** | **Crystal** | 强调 **团队规模**，方法轻量灵活 |
| **自适应软件开发** | **ASD** | 强调 **自适应性**，边做边调整 |

---

## 五、适用场景

| ✅ 适合 | ❌ 不适合 |
| :--- | :--- |
| 需求**不稳定、变化快** | 需求**非常明确且固定**（没必要用敏捷） |
| 互联网产品、创业项目 | 大型政府、银行核心系统（有合规/文档要求） |
| **小到中型团队**（10人以内效果最佳） | 超大型团队（上百人的项目不好协调） |
| 用户**可以紧密参与** | 用户无法频繁反馈 |

---

## 六、一句话总结

> **“瀑布怕变化，敏捷爱变化。”** 互联网公司用敏捷，银行核心系统用瀑布——没有谁绝对好，只看场景对不对。
