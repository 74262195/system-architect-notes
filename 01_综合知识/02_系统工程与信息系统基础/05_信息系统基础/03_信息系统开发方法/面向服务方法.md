# 面向服务方法（Service-Oriented Method）

> **软考定位**：从面向对象“升级”而来，关键词 **“粗粒度、松散耦合”**。

---

## 一、一句话定义

面向服务方法将系统功能封装成一个个 **“服务”** ，每个服务通过 **标准接口** 对外提供能力，服务之间 **松散耦合**，可以独立开发、部署、升级。

> **大白话**：**“每个功能都是一个‘标准插座’，谁想用谁就插上去，不用管里面怎么接线的。”**

---

## 二、三大特征（必考！）

| 特征 | 大白话 |
| :--- | :--- |
| **粗粒度** | 服务比对象“大”——一个服务可能包含多个对象（如“订单服务”包含订单对象、商品对象、支付对象） |
| **松散耦合** | 服务之间依赖最少——订单服务挂了，用户服务还能正常跑 |
| **基于标准接口** | 服务通过标准协议（如 HTTP/REST、SOAP）通信，不关心对方用什么语言写的 |

---

## 三、三层抽象级别

| 层次 | 内容 | 举例 |
| :--- | :--- | :--- |
| **操作（Operation）** | 最底层，单个方法/函数 | `createOrder()` |
| **服务（Service）** | 中间层，一组操作的集合 | “订单服务”——包含创建、查询、取消订单等操作 |
| **业务流程（Business Process）** | 最高层，多个服务的编排 | “下单流程”——调用订单服务 + 库存服务 + 支付服务 |

---

## 四、技术实现方式

| 技术 | 特点 |
| :--- | :--- |
| **Web Service（SOAP）** | 基于 XML，协议复杂，企业级应用 |
| **RESTful API** | 基于 HTTP，轻量简单，互联网应用 |
| **微服务（Microservices）** | 面向服务的极端实现，每个服务独立部署 |

---

## 五、面向对象 vs 面向服务（考场对比！）

| 对比维度 | **面向对象方法** | **面向服务方法** |
| :--- | :--- | :--- |
| **粒度** | **细粒度**（类/对象） | **粗粒度**（服务） |
| **耦合度** | 类之间有一定耦合 | **松散耦合** |
| **复用单元** | 类 | 服务 |
| **通信方式** | 方法调用（进程内） | 网络调用（HTTP/消息） |
| **部署方式** | 打包在一起部署 | **独立部署** |
| **适用场景** | 单体应用 | **分布式系统、跨系统集成** |

---

## 六、适用场景

| ✅ 适合 | ❌ 不适合 |
| :--- | :--- |
| **跨系统集成**（ERP + CRM 对接） | 简单的单体应用（用面向对象就够了） |
| 企业应用集成（EAI） | 对**网络延迟**敏感的系统 |
| 需要**灵活扩展**的系统 | 团队**缺乏分布式系统经验** |
| **微服务架构** | 小型创业项目（成本高） |
