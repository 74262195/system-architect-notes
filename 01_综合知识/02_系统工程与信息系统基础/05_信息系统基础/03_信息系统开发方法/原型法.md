# 原型法（Prototyping）

## 零基础先抓住

> [!question] 为什么要学这个
> 进入开发阶段后，还要选择分析、设计和实现系统的方法论。这里重点区分各种方法的题干关键词和适用场景。

> [!important] 考试怎么认
> 看到与“**原型法**”相关的阶段、方法、系统类型或关键术语时，先判断它解决什么问题、面向什么对象，再做选择。


> **软考定位**：专门对付 **“需求说不清楚”** 的项目。

---

## 一、一句话定义

原型法是 **在需求尚不明确的情况下，快速构建一个可运行的“样品”（原型）**，让用户试用、体验、提反馈，反复修改直到用户满意，再正式开发。

> **大白话**：**“先做个样子给用户看，用户说‘对了，就是这个感觉！’，再正式开始做。”**

---

## 二、原型法的分类（必考！）

### 按功能划分

| 类型 | 特点 | 目的 |
| :--- | :--- | :--- |
| **水平原型**（行为原型） | 只做**界面**，不实现功能，点按钮不会真处理数据 | 确认**界面布局和操作流程** |
| **垂直原型**（结构化原型） | 实现**部分核心功能**，可以真实操作 | 验证**关键技术或复杂算法** |

### 按结果划分

| 类型 | 特点 | 用途 |
| :--- | :--- | :--- |
| **抛弃式原型**（探索式） | 原型用完即扔，不进入最终系统 | 用于**搞清楚需求**，需求明确了就扔掉重写 |
| **演化式原型** | 原型逐步完善，最终成为正式系统的一部分 | 适用于**Web项目**，边用边改边成长 |

---

## 三、原型法的工作流程

需求初步了解 → 快速设计原型 → 用户试用 → 收集反馈 → 修改原型 → 用户再试用 → ...（循环）→ 用户满意 → 正式开发/交付

**关键**：这是一个 **“反复迭代”** 的过程，不是一次性搞定。

---

## 四、优缺点

| 优点 | 缺点 |
| :--- | :--- |
| 1. 能快速确认需求，减少返工 | 1. 如果技术**非常复杂**，原型做不出来 |
| 2. 用户全程参与，满意度高 | 2. 用户可能把原型当成品，产生不切实际的期望 |
| 3. 适合需求不明确的项目 | 3. 可能掩盖系统架构问题（只顾界面好看） |

---

## 五、适用场景

| ✅ 适合 | ❌ 不适合 |
| :--- | :--- |
| 需求**不明确、说不清楚** | 需求**非常明确**（直接用结构化即可） |
| 用户界面为主、交互复杂的系统 | 技术**实现难度极高**的系统（如实时交易系统） |
| 用户能**紧密配合**、频繁反馈 | 用户无法参与、只能远程沟通 |
