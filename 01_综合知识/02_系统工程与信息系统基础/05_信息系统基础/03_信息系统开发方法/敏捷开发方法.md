# 敏捷方法（Agile）——开发方法篇

## 零基础先抓住

> [!question] 为什么要学这个
> 进入开发阶段后，还要选择分析、设计和实现系统的方法论。这里重点区分各种方法的题干关键词和适用场景。

> [!important] 考试怎么认
> 看到与“**敏捷开发方法**”相关的阶段、方法、系统类型或关键术语时，先判断它解决什么问题、面向什么对象，再做选择。


> [!important] 核心理解
> 敏捷是一套**应对需求变化**的开发理念和流程框架：**小步快跑、拥抱变化、以人为中心、轻文档重交付**。记住 **敏捷宣言 4 价值观** + 主流实践（Scrum/XP/看板）即可拿分。
>
> ⚠️ 别和生命周期方法里的 [[生命周期方法速览|敏捷]] 搞混：**生命周期方法里的敏捷**（迭代+增量）回答"项目怎么组织节奏"；**本笔记的开发方法敏捷**回答"用什么流程范式干活"，是同一理念在开发环节的具体落地（Scrum 等）。

---

## 一、敏捷宣言：4 大价值观（⭐必背）

| 左（更看重） | 右（但仍然有价值） |
| :--- | :--- |
| **个体和互动** | 流程和工具 |
| **可工作的软件** | 详尽的文档 |
| **客户合作** | 合同谈判 |
| **响应变化** | 遵循计划 |

> **考场考法**：给一句话判断是否属于敏捷价值观。如"文档详尽优于可工作软件"→ ❌ 违背敏捷。

---

## 二、敏捷 12 原则（记核心 5 条即可）

1. **尽早、持续交付**有价值的软件，让客户满意
2. **欢迎需求变化**（后期变化也欢迎，变化是竞争力）
3. 频繁交付可运行软件（几周~几个月，越短越好）
4. 业务人员与开发人员**每天一起工作**
5. 面对面沟通是最高效的传递方式
6. 团队自组织、定期反思改进
7. 可持续的开发节奏（不加班透支）
8. 简单是根本（最大化"不做的艺术"）

## 三、主流实践框架（考场辨析）

### Scrum（最常考）
| 角色 | 事件 | 工件 |
| :--- | :--- | :--- |
| **产品负责人（PO）**：管需求优先级 | **Sprint（冲刺）**：1~4 周一个迭代 | **产品待办列表（Product Backlog）** |
| **Scrum Master**：服务团队、清障碍 | 每日站会（15 分钟） | **冲刺待办列表（Sprint Backlog）** |
| **开发团队**：自组织 | 冲刺评审（给客户演示） | **燃尽图（Burndown Chart）** |
| | 冲刺回顾（团队复盘） | 增量（可交付软件） |

### XP（极限编程）
- **结对编程**、**测试驱动开发 TDD**（先写测试再写代码）、**持续集成 CI**、**简单设计**、重构
- 考场关键词："结对编程""TDD""持续集成" → XP

### 看板（Kanban）
- **可视化任务流**、限制在制品（WIP）、拉式生产
- 考场关键词："看板""WIP 限制""任务可视化" → 看板

## 四、敏捷 vs 瀑布（必考对比）

| 对比维度 | **瀑布模型** | **敏捷方法** |
| :--- | :--- | :--- |
| 需求 | **前期一次性确定** | **持续变化、动态调整** |
| 交付 | 最后一次性交付 | **小步高频交付**（每个迭代都可运行） |
| 文档 | **文档驱动**（重） | **轻文档**，重可运行软件 |
| 沟通 | 阶段式、书面 | **面对面、高频** |
| 用户参与 | 开始和结束 | **全程参与** |
| 适用场景 | 需求稳定（政府/银行） | 需求多变、快速迭代（互联网产品） |

## 五、考场秒杀表

| 题干关键词 | 秒选 |
| :--- | :--- |
| "拥抱变化""小步快跑""响应变化优于遵循计划" | **敏捷** |
| "Scrum""Sprint""每日站会""产品待办列表" | **敏捷（Scrum）** |
| "结对编程""TDD""持续集成" | **敏捷（XP）** |
| "看板""WIP 限制""可视化任务" | **敏捷（看板）** |
| "个体和互动优于流程和工具" | **敏捷宣言** |
| "严格按阶段、文档详尽、需求冻结" | ❌ 那是瀑布 |

---

## 六、一句话总结

> **瀑布是"图纸画完再开工"，敏捷是"边开工边改图纸、两周一版给用户看"。** 互联网项目用敏捷，稳定项目用瀑布。
