# 结构化方法（Structured Method）

> **软考定位**：经典传统方法，关键词 **“自顶向下、逐步求精”**。

---

## 一、一句话定义

结构化方法是一种 **“自顶向下、逐步分解”** 的开发方法，将系统按功能逐层拆解，直到每个模块足够简单、可直接编码。

> **大白话**：**“把一个大问题，像切西瓜一样，切成小块，再一块一块解决。”**

---

## 二、三大组成部分（必记！）

| 组成部分 | 全称 | 核心任务 |
| :--- | :--- | :--- |
| **SA** | 结构化分析 | 搞清楚 **“做什么”**（需求分析） |
| **SD** | 结构化设计 | 规划 **“怎么做”**（模块划分、接口设计） |
| **SP** | 结构化程序设计 | 用 **顺序、选择、循环** 三种结构写代码 |

---

## 三、核心特点

| 特点 | 大白话 |
| :--- | :--- |
| **自顶向下** | 从全局到局部，先整体后细节 |
| **逐步求精** | 一层一层细化，直到可编码 |
| **严格分阶段** | 每个阶段有明确任务和交付物 |
| **文档驱动** | 每个阶段都要写文档，文档是重要产出物 |
| **用户至上** | 用户参与需求分析，确认系统边界 |

---

## 四、优缺点

| 优点 | 缺点 |
| :--- | :--- |
| 1. 阶段清晰，便于管理和分工 | 1. **怕变化**——需求变更代价极大 |
| 2. 文档齐全，有利于团队协作 | 2. 开发周期长，用户迟迟看不到成果 |
| 3. 适合大型、稳定的项目 | 3. **不适合需求不明确**的项目 |

---

## 五、适用场景

| ✅ 适合 | ❌ 不适合 |
| :--- | :--- |
| 需求**明确、稳定**的项目 | 需求**不明确或变化频繁** |
| 政府/银行/大型企业管理系统 | 互联网快速迭代产品 |
| 技术方案成熟、团队经验丰富 | 探索型、创新型项目 |

---

## 六、结构化 vs 面向对象（考场必考对比！）

| 对比维度 | **结构化方法** | **面向对象方法** |
| :--- | :--- | :--- |
| **分解方式** | 按**功能**分解 | 按**对象**分解 |
| **数据与操作** | 分离（数据 + 函数） | 封装在一起（对象） |
| **复用性** | 差（函数复用有限） | 好（类可继承、组合） |
| **需求变化应对** | 差 | 好 |
| **思维习惯** | 偏向机器思维（流程） | 偏向人类思维（现实世界） |
