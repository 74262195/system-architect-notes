# 质量属性：为什么“功能做对了”还不代表系统真的好

> [!summary]- 快速复习卡片
> **作用/定位**：质量属性描述系统“做得怎么样”，不是“有没有这个功能”。
> **核心结论**：开发期更关注好不好理解、修改、测试、复用和迁移；运行期更关注快不快、稳不稳、安全不安全、能否持续服务。
> **题干怎么认**：题目把“性能、可用性、可修改性、可测试性”等分类或辨析时，先判断它主要在开发阶段还是运行阶段体现。
> **易错点**：分类只是主要关注阶段，不代表某属性只在一个阶段发生作用；“面向架构评估的属性集合”和“六类重点质量属性场景”也不是同一张表。

一个系统能正确完成下单、支付、查询，却仍可能高峰很慢、故障恢复很久、改一个需求牵动很多模块。这些都属于质量属性问题。

主教材把软件系统质量概括为：软件与明确和隐含需求相一致的程度。质量属性则是**可测量或可测试的系统属性**，用来说明系统满足利益相关者需求的程度。

## 按生命周期理解

| 时期 | 典型质量属性 | 关注的问题 |
| --- | --- | --- |
| 开发期 | 易理解性、可扩展性、可重用性、可测试性、可维护性、可移植性 | 好不好开发、修改、测试、迁移 |
| 运行期 | 性能、安全性、可伸缩性、互操作性、可靠性、可用性、鲁棒性 | 跑起来后快不快、稳不稳、安全不安全 |

GB/T 16260.1 的质量模型还从功能性、可靠性、易用性、效率、维护性、可移植性等维度描述软件质量。考试遇到不同分类口径时，先看题目问的是“质量模型分类”“生命周期分类”，还是“架构评估重点属性”。

## 面向架构评估时，还要认出这 8 类属性

官方大纲 7.1.2 单独要求“面向架构评估的质量属性”。这里的集合不要和上面的生命周期分类混在一起。

| 属性 | 一句话判断 |
| --- | --- |
| 性能 | 系统多快响应、单位时间能处理多少事件 |
| 可靠性 | 在规定条件和时间内持续完成规定功能 |
| 可用性 | 需要提供服务时，系统有多大程度处于可服务状态 |
| 安全性 | 向合法用户提供服务，同时阻止未授权使用 |
| 可修改性 | 变更系统时，影响范围、时间和成本有多大 |
| 功能性 | 系统能否完成期望的工作 |
| 可变性 | 架构能否按预定义规则扩充或变更成相关的新架构，产品线场景尤其常见 |
| 互操作性 | 本系统与其他系统交换数据、调用服务和协同工作的难易程度 |

> [!important] 两张表不要混
> 主教材随后详细展开的**六类质量属性场景**是：可用性、可修改性、性能、可测试性、易用性、安全性。
> 这不表示可靠性、功能性、可变性、互操作性“不是质量属性”；只是教材选择六类场景做详细描述。

## 质量属性会互相牵动

质量属性不是互不相干的独立开关。一个架构决策可能改善一个目标，却让另一个目标变差。例如提高加密强度通常有利于安全性，却可能增加处理时间；增加冗余有利于可用性，却会增加资源和一致性复杂度。

因此后续架构评估不会只问“某个属性好不好”，还会继续找：

- 哪个架构决策对某个质量目标特别敏感；
- 哪个决策同时影响多个质量目标；
- 哪个决策可能导致质量目标无法满足。

这些分别会进入 [[敏感点与权衡点]] 中的敏感点、权衡点和风险点判断。

## 历年考法落点

仓库既有题库把质量属性分类列为 P0。考试常把多个属性混在一起，让你判断“题干真正描述的是哪种质量问题”。做题不要背整张列表，先抓动作：**修改/测试/迁移 → 开发期倾向；响应/故障/攻击/服务在线 → 运行期倾向。**

如果题目直接给出“功能性、可变性、互操作性”等词，并问架构评估关注什么，不要因为它们不在“六类重点场景”中就排除。

## 易混

- **可靠性**：规定条件和时间内持续正确工作的能力。
- **可用性**：需要服务时处于可服务状态的程度。
- **功能性**：能不能完成期望的工作，不等于“做得快、稳、安全”。
- **可变性**：架构向相关新架构变化的能力，不等同于一般可修改性。
- **互操作性**：系统间交换数据和调用服务的能力，不等同于单纯网络连通。
- **鲁棒性**：异常输入或不利条件下仍保持受控行为。

## 自测
1. 为什么功能全部正确，架构仍可能失败？
2. 可测试性为什么更偏开发期？
3. 可用性和可靠性分别看什么？
4. “系统能完成目标业务”和“系统能与外部系统交换数据”分别是什么属性？
5. 为什么“六类重点质量属性场景”不能替代“面向架构评估的八类质量属性”？

> [!answer]- 答案与解析
> 1. 功能正确不代表性能、可用性、安全性等质量目标也达标；架构仍可能因这些约束失败。
> 2. 可测试性关注开发和验证时能否控制、观察与定位问题。
> 3. 可用性看系统可服务的程度；可靠性看持续正确运行、少发生故障的能力。
> 4. 分别是功能性与互操作性。
> 5. 两套分类服务于不同的分析语境，不能把场景练习中的重点六类当作架构评估分类的完整替代。
