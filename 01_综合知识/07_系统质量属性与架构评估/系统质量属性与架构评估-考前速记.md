# 系统质量属性与架构评估 · 考前速记

## 一眼看全章

1. **先有功能**：系统能不能完成期望工作。
2. **再看质量**：同一个功能可以快/慢、稳/不稳、安全/不安全、好改/难改。
3. **把模糊要求场景化**：用六要素把“要快、要稳定”改成可以分析和验收的要求。
4. **架构决策会牵动质量属性**：因此要找敏感点、权衡点、风险和非风险。
5. **架构评估提前暴露问题**：不要等系统全部实现甚至上线后才发现质量目标不达标。
6. **SAAM / ATAM / CBAM**：分别抓场景与可修改性、多质量属性权衡、成本收益决策。

## 功能 vs 质量：先判断题目在问哪一层

| 题干 | 第一反应 |
| --- | --- |
| “用户可以登录/系统可以完成某项业务” | **功能**：系统做什么 |
| “登录 2 秒内返回/服务不能轻易中断/身份信息要安全/以后容易修改” | **质量**：系统做得怎么样 |

[[质量属性-开发期与运行期|总入口]]中还要认出：

- **功能性**：能否完成期望工作；
- **可变性**：架构能否按预定义规则扩充或变化成相关新架构；
- **互操作性**：不同系统之间能否交换数据、调用服务并协同工作。它不是单纯网络连通；与可移植性相比，后者更关注系统迁移到不同平台/环境。

## 属性秒杀：看到题眼先想什么

| 题眼 | 第一反应 | 易混 |
| --- | --- | --- |
| 多久完成、响应时间、每秒多少请求、高负载 | [[性能质量属性场景|性能]] | 并发数本身不是完整性能目标，还要有度量 |
| 规定时间内持续无故障 | [[可靠性与可用性|可靠性]] | 不等于恢复一定快 |
| 需要服务时能用、MTTR、快速恢复 | [[可靠性与可用性|可用性]] | 不等于“从不故障” |
| 越权、篡改、泄露、检测、恢复 | [[安全性质量属性场景|安全性]] | 安全产品是手段，不是质量场景本身 |
| 变化范围、受影响构件、修改时间/成本 | [[可修改性质量属性场景|可修改性]] | 可变性更强调按规则演化成相关新架构 |
| 可观察、可控制、测试时间/成本 | [[可测试性质量属性场景|可测试性]] | 不等于普通“容易维护” |
| 任务时间、用户错误、学习成本、满意度 | [[易用性质量属性场景|易用性]] | 看使用者完成任务的质量 |
| 系统之间交换并使用数据/服务 | [[质量属性-开发期与运行期|互操作性]] | 不等于可移植性 |

## 质量属性场景六要素

**刺激源 → 刺激 → 环境 → 制品 → 响应 → 响应度量**

人话顺序：**谁触发 → 发生什么 → 当时什么环境 → 作用到哪里 → 系统怎么做 → 做到什么程度。**

看到“高峰期 1000 个并发用户发起查询，95% 请求在 2 秒内返回”时，至少要能立即认出：
- “高峰期”是**环境**；
- “发起查询”是**刺激**；
- “返回查询结果”是**响应**；
- “95% 请求在 2 秒内返回”是**响应度量**。

入口：[[质量属性场景六要素]]。

## 敏感点 / 权衡点 / 风险 / 非风险

| 题干在问什么 | 先判什么 |
| --- | --- |
| 某个架构决策一变化，某一个质量属性就明显变化 | **敏感点** |
| 同一决策同时影响多个质量属性，而且需要取舍 | **权衡点** |
| 某个决策可能导致重要质量目标无法满足 | **风险** |
| 当前场景和证据支持相应质量目标能够满足，未暴露对应风险 | **非风险** |

一个决策可以同时是敏感点、权衡点和风险来源；这几个概念不是互斥标签。入口：[[敏感点与权衡点]]。

## 架构评估：为什么设计完还要评估

架构是对未来系统的重要设计决策。很多性能、可用性、可修改性问题在系统完全实现前不会自动暴露；如果等上线后才发现，返工成本很高。因此要把利益相关者关心的质量目标变成场景，在架构阶段提前分析关键决策和风险。

三类方法第一判断：

| 关键词 | 选什么 |
| --- | --- |
| 专家经验、逐项检查 | 调查问卷/检查表 |
| 具体质量场景 | 基于场景；SAAM、ATAM 属于此类 |
| 指标、模型、计算/推导 | 基于度量 |

入口：[[架构评估-问卷场景与度量]]。

### ATAM 到底干什么

**通过业务驱动因素、质量属性场景和关键架构决策，识别风险、非风险、敏感点和权衡点。**

它不是自动选择唯一“最佳架构”的算法。

### ATAM 实践四阶段（官方大纲）

**演示 → 调查和分析 → 测试 → 报告**

题目问“四个基本阶段”时，用这一条，不要拿 7 步去凑四阶段。

### ATAM 7 步分析链（主教材）

1. 收集场景；
2. 收集需求、约束和环境；
3. 描述架构视图；
4. 将场景映射/落实到架构；
5. 针对特定质量属性分析；
6. 识别敏感点；
7. 识别权衡点。

做顺序题时抓住因果：**先有场景和约束 → 再看架构 → 把场景压到架构上 → 做属性分析 → 最后找敏感点和权衡点。**

### Utility Tree

典型四层：**效用 → 质量属性 → 属性细化 → 质量属性场景**。叶子是具体质量属性场景，不是组件。入口：[[ATAM效用树]]。

## 最容易错

1. **功能性 ≠ 质量属性“做得怎么样”**：功能先回答“能不能做这件事”。
2. **可修改性 ≠ 可变性**：前者看修改影响和代价，后者强调架构按规则演化成相关新架构。
3. **互操作性 ≠ 可移植性**：前者看系统间协同，后者更偏迁移平台/环境。
4. **可靠性 ≠ 可用性**：少故障和故障后能快速恢复/持续服务不是一回事。
5. **权衡点不是任何敏感点**：必须是同一决策牵动多个质量属性并需要取舍。
6. **风险不是“已经发生故障”**：它是某决策可能让质量目标无法满足。
7. **SAAM 和 ATAM 都用场景**：不能看到“场景”就自动选 SAAM。
8. **ATAM 四阶段 ≠ 7 步分析链**：题目问哪一层，就用哪一层。
9. **效用树叶子是质量属性场景**，不是构件或模块。
10. **CBAM 不替代 ATAM**：它在质量分析基础上继续加入经济决策。
