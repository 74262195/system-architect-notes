# SAAM：怎么用一组场景检查架构到底好不好改

> [!summary]- 快速复习卡片
> **作用/定位**：用场景分析架构，经典重点是可修改性。
> **核心结论**：开发场景 → 描述架构 → 单场景评估 → 场景交互 → 总体评估。
> **题干怎么认**：场景技术、可修改性、场景交互、多个场景修改同一构件。
> **易错点**：SAAM 不是 ATAM；前者经典重点偏可修改性，后者强调多质量属性的敏感与权衡。

通知系统先后收到两个变化：增加短信渠道、把邮件模板改为多语言。两个需求单独看都能做，但如果每次都要改同一个通知路由器，未来维护就会越来越麻烦。评估时需要把场景逐一放到架构上，看哪些能直接支持、哪些要修改，以及多个场景会不会挤到同一处。**SAAM 就是用场景检查架构及其可修改性的一种方法。**

SAAM（Software Architecture Analysis Method，软件架构分析方法）属于基于场景的架构评估方法。

```mermaid
flowchart LR
    A[开发场景] --> B[描述架构]
    B --> C[单场景评估]
    C --> D[场景交互]
    D --> E[总体评估]
```

单场景评估看现有架构能否直接支持场景，还是必须修改；场景交互则关注多个场景是否反复影响同一构件，这往往意味着变化热点。

### 场景交互怎样暴露修改热点

教学例子：通知系统先后收到“增加短信渠道”和“把邮件模板改为多语言”两个变化场景。评估者逐一映射到架构：前者需要改通知路由器和渠道配置，后者也需要改通知路由器中的模板判断。单独看两个场景都能实现；合起来发现路由器成了共同修改点，后续每加渠道或语言都可能碰它，这就是场景交互提示的修改热点。SAAM 在这里不是直接宣布架构失败，而是把影响重叠显出来，供团队评估是否拆分职责。

## 历年考法落点

题目出现“场景交互”或强调“可修改性场景”时，SAAM 是强识别词。若题目继续强调性能、安全、可用性之间的折中，则更可能转向 ATAM。

## 自测
1. SAAM 中为什么要专门分析场景交互？
2. SAAM 与 ATAM 的第一判断入口分别是什么？

> [!answer]- 答案与解析
> 1. 多个场景若修改同一构件或相互影响，架构支持一个场景的代价会影响其他场景，需要据此判断可修改性风险。
> 2. SAAM 先看场景及其交互，尤其是可修改性；ATAM 先看多质量属性之间的权衡、敏感点和风险。
