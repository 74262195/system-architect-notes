# 系统质量属性与架构评估 · 学习路线

> [!important] 为什么按这个顺序学
> 先有“系统能做什么”的功能，再问“做得怎么样”的质量；质量要求如果只写“快、稳、安全”无法验收，所以要变成质量属性场景；而架构决策会同时影响多个质量属性，因此还要找敏感点、权衡点和风险，并通过架构评估在系统完全实现前尽早暴露问题。ATAM 就是把这条链系统化的一种核心方法。

## 第一段：先分清“功能正确”和“质量做好”

[[质量属性-开发期与运行期]]

先做到三件事：
- “用户可以登录”这类描述回答**系统做什么**，属于功能；
- “2 秒内完成登录、服务不中断、身份信息安全、以后容易修改”回答**做得怎么样**，属于质量要求；
- 同一张总览里同时认识功能性、可变性、互操作性，以及开发期/运行期属性分类，避免把“六类重点场景”误当成全部质量属性。

## 第二段：把模糊质量要求变成能分析的场景

[[质量属性场景六要素]]
→ [[性能质量属性场景]]
→ [[可靠性与可用性]]
→ [[安全性质量属性场景]]
→ [[可修改性质量属性场景]]
→ [[可测试性质量属性场景]]
→ [[易用性质量属性场景]]

这一段的核心不是背属性名，而是学会把“要快、要稳定、要安全、要好改”落成：**谁/什么事件 → 什么环境 → 作用到什么对象 → 系统如何响应 → 怎样度量响应。**

其中高价值辨析：
- 可靠性看“规定条件和时间内持续正确工作”，可用性看“需要服务时是否处于可服务状态”；
- 可修改性看变化的影响范围、时间和成本；可变性则强调架构按规则扩充或变成相关新架构；
- 互操作性看不同系统之间能否正确交换数据、调用服务并协同工作，不等于单纯网络连通或平台迁移。

## 第三段：为什么已经有架构设计，还要评估

[[架构评估-问卷场景与度量]]
→ [[敏感点与权衡点]]
→ [[SAAM架构评估]]
→ [[ATAM架构权衡分析]]
→ [[ATAM效用树]]
→ [[CBAM成本效益分析]]

架构决定了很多后续很难低成本改变的结构和策略。如果等系统上线后才发现性能、可用性或可修改性达不到目标，返工代价会很高。因此要在架构阶段把利益相关者关心的质量目标转成场景，分析关键决策：

- 只要某个决策一变，一个质量属性就明显变化：先想**敏感点**；
- 同一决策同时牵动多个质量属性并需要取舍：先想**权衡点**；
- 某个决策可能导致重要质量目标无法满足：属于**风险**；
- 当前证据支持目标能够满足且没有暴露对应风险：属于**非风险**。

## 第四段：把 ATAM 学成“会判断顺序”，不是只会背缩写

在 [[ATAM架构权衡分析]] 中重点抓三层：

1. **目的**：用业务驱动、质量属性场景和架构决策识别风险、非风险、敏感点和权衡点；
2. **官方大纲四阶段**：演示 → 调查和分析 → 测试 → 报告；
3. **主教材 7 步分析链**：收集场景 → 收集需求/约束/环境 → 描述架构视图 → 场景映射到架构 → 属性分析 → 识别敏感点 → 识别权衡点。

[[ATAM效用树]]负责把大量质量场景组织并排序；[[CBAM成本效益分析]]再把成本、收益和预算带入架构策略选择。

## 通关标准
- [ ] 能用一句话区分“功能做什么”和“质量做得怎么样”。
- [ ] 能识别功能性、可变性、互操作性。
- [ ] 能闭卷写出质量属性场景六要素，并从一句场景中找出环境、响应和响应度量。
- [ ] 能区分可靠性与可用性。
- [ ] 能从“变化范围/修改成本”识别可修改性。
- [ ] 能区分敏感点、权衡点、风险和非风险。
- [ ] 能说出为什么要在实现完成前做架构评估。
- [ ] 能说出 SAAM 五步主线及其经典可修改性定位。
- [ ] 能解释 ATAM 的目的，并区分“四阶段”和“7 步分析链”。
- [ ] 能画出效用树四层并说明叶子为什么是质量属性场景。
- [ ] 能说明 CBAM 为什么在 ATAM 之后继续考虑 ROI/成本收益。
