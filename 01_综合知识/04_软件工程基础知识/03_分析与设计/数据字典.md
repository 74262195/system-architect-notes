# 数据字典：DFD 已经画了“告警信息”，为什么还必须把这个名字继续定义清楚

> [!summary]- 快速复习卡片（学完再看）
> **定位**：数据字典是结构化分析工具，用来给 DFD 中的数据和处理元素补充统一定义。  
> **主要对象**：数据项、数据结构、数据流、数据存储、处理过程。  
> **核心价值**：消除“同名不同义、同义不同名、范围不一致”等歧义。  
> **第一动作**：图上只看到名称但不知道组成、类型、范围、来源、去向、存取方式 → 查数据字典。  
> **易错点**：这里的数据字典不是数据库产品自动维护的系统目录，而是需求/分析阶段的定义工具。

上一站 [[数据流图DFD]] 已经画出了：

> 设备 → “告警信息” → 校验 → 分级 → 告警库 / 通知

看上去很清楚。

但开发人员问：

> “告警信息”里到底有哪些字段？

测试人员问：

> “告警级别允许哪些值？”

运维人员又说：

> “设备编号是主机名还是资产 ID？”

这说明：

> **DFD 把关系画清楚了，但名称的精确定义仍然可能含糊。**

数据字典就是用来补这层细节的。

> [!tip] 先记住建立顺序
> **从 DFD 盘点名称 → 按五类建条目 → 先定义组合再定义原子项 → 与 DFD 双向核对 → 随模型变更同步维护。**

## 数据字典和 DFD 是怎么配套的

可以把它们理解成：

> **DFD 负责画关系；数据字典负责解释图里的名词。**

例如 DFD 里只有：

> “原始告警”

数据字典可以继续定义：

- 包含：设备编号、发生时间、级别、告警内容；
- 设备编号的数据类型和长度；
- 级别允许哪些取值；
- 这条数据流从哪里来、到哪里去；
- 平均/高峰流量是多少。

这样不同人看到同一个名称，才不会各自脑补。

## 数据字典主要定义哪五类对象

### 1. 数据项：最小的数据单位

例如：

> 告警级别

需要说明：

- 名称；
- 含义；
- 类型；
- 长度；
- 取值范围；
- 不同取值的意义；
- 与其他数据项的约束关系。

如果一个模块把：

> 1 = 最高级

另一个模块却理解成：

> 1 = 最低级

系统一定会出错。

所以数据字典首先解决的是：

> **同一个数据项到底是什么意思。**

### 2. 数据结构：多个数据项怎样组合

例如：

> 告警信息 = 设备编号 + 发生时间 + 级别 + 内容

这就是一个数据结构。

它回答：

> **一份完整数据由哪些部分组成。**

### 3. 数据流：这份数据从哪里来、到哪里去

例如：

> 原始告警：由监控设备产生，流向告警接入加工。

除了组成，还可能记录：

- 来源；
- 去向；
- 平均流量；
- 高峰流量。

所以“数据流”不仅是一个名字，也有业务含义和传输特征。

### 4. 数据存储：存的是什么，怎样存取

例如“告警记录库”可以说明：

- 保存哪些数据结构；
- 大致数据量；
- 由哪些数据流写入/读出；
- 查询还是更新；
- 顺序还是随机存取等。

注意：

> **数据字典描述存储的逻辑含义，不等于已经决定具体数据库表设计。**

### 5. 处理过程：这个加工做什么

例如“告警校验”：

- 输入：原始告警；
- 输出：合格告警 / 错误信息；
- 功能：检查必要字段与合法性；
- 处理要求：可能包含频度、响应时间等要求。

这里的重点仍是：

> **它做什么、有哪些输入输出和要求。**

不是在数据字典里把详细代码算法全部写出来。

## 为什么它能改善沟通

假设产品经理说：

> “负责人”。

开发理解为：

> 当前告警处理人。

运维理解为：

> 这台主机的资产负责人。

如果数据字典没有统一定义：

> 同一个词在不同文档中就会漂移。

数据字典的价值因此不仅是“补字段表”，而是：

> **建立一套分析阶段共享的语言。**

这对分析人员和用户沟通尤其重要。

## 怎样从刚才的 DFD 建立数据字典

继续使用 [[数据流图DFD]] 的告警平台。不要脱离 DFD 凭空整理字段，而是顺着图上的元素建立。

### 第 1 步：把 DFD 上需要解释的名称盘点出来

先从顶层图和第一层图抄出名称，并保留编号：

- 数据流：原始告警、合格告警、告警记录、待通知告警、通知；
- 数据存储：`D1 告警库`；
- 处理：`P1 校验告警`、`P2 分级并保存`、`P3 生成通知`；
- 数据流内部还会出现不可再分的数据项，如告警编号、设备编号、级别。

这一步的产物不是一堆新名词，而是一份**与 DFD 同名、可逐项勾选的登记清单**。

### 第 2 步：按五类分别建条目

五类对象的字段不同，不能只做一张“字段名—类型”表就结束。

| 条目类型 | 至少回答什么 |
| --- | --- |
| 数据项 | 名称、含义、类型、长度、取值范围与约束 |
| 数据结构 | 由哪些数据项或子结构组成 |
| 数据流 | 从哪里来、到哪里去、由什么组成、流量要求 |
| 数据存储 | 编号、流入/流出、组成、数据量和存取方式 |
| 处理过程 | 输入、输出、功能和处理要求 |

### 第 3 步：先写出一份完整数据，再向下定义原子项

以下是**教学示例**，字段和取值用于演示建立方法，不冒充真实项目数据。

**数据结构条目：告警记录**

> 告警记录 = 告警编号 + 设备编号 + 发生时间 + 告警级别 + 状态 + 告警内容

这个等式只说明组成，还要继续定义其中不可再分的数据项。例如：

| 数据项 | 含义 | 类型/长度 | 取值范围及含义 | 约束 |
| --- | --- | --- | --- | --- |
| 告警级别 | 表示告警紧急程度 | 字符型，2 位 | `P1`、`P2`、`P3`；本例约定 P1 最紧急 | 必填，只能取枚举值 |
| 状态 | 表示告警当前处理状态 | 字符型 | `待确认`、`已确认`、`已关闭` | 已关闭后不得回到待确认 |

如果“告警级别”的真实取值尚未由业务方确认，应写成“待业务核验”，不能由分析人员自行编造后当成正式规则。

### 第 4 步：把 DFD 上的流、存储和处理补成可检查条目

**数据流条目：原始告警**

| 字段 | 定义 |
| --- | --- |
| 说明 | 监控设备提交、尚未完成合法性校验的告警数据 |
| 来源 | 外部实体“监控设备” |
| 去向 | `P1 校验告警` |
| 组成 | 告警编号 + 设备编号 + 发生时间 + 告警级别 + 告警内容 |
| 平均/高峰流量 | 待业务方根据实际监控规模核验 |

**数据存储条目：D1 告警库**

| 字段 | 定义 |
| --- | --- |
| 说明 | 保存已分级的告警记录 |
| 流入 | `P2 分级并保存` 输出的“告警记录” |
| 流出 | 提供给 `P3 生成通知` 的“待通知告警” |
| 组成 | 告警记录 |
| 数据量/存取方式 | 待业务量核验；逻辑上需要新增、按状态读取和更新 |

**处理过程条目：P1 校验告警**

| 字段 | 定义 |
| --- | --- |
| 输入 | 原始告警 |
| 输出 | 合格告警 |
| 功能 | 检查必填字段、标识格式及告警级别是否合法 |
| 处理要求 | 非法数据的处置方式、响应时间和处理频度待需求确认 |

注意：处理过程条目写“做什么”和约束，不在这里展开代码级算法。

### 第 5 步：与 DFD 双向核对并持续维护

完成后至少检查五件事：

1. DFD 上每个数据流、数据存储和处理，字典里是否都有同名条目；
2. 字典中登记的来源、去向，是否与箭头方向一致；
3. 数据流的组成，是否都能向下追到数据结构和数据项；
4. 同一个词是否只有一种含义，别名是否已显式登记；
5. DFD 新增、改名或删除元素时，字典是否同步更新。

例如 DFD 把“原始告警”改成“设备告警”，字典仍保留旧名，就会形成两个事实版本。数据字典不是画完图后一次性补的附件，而是与 DFD 同步演化的分析成果。

## 数据字典和数据库字典不是一回事

在数据库产品中，也会出现“数据字典”这个词，表示数据库元数据目录。

但本章结构化分析里的核心考法是：

> **给 DFD 中的数据项、数据结构、数据流、数据存储、处理过程做定义说明。**

考试要看语境。

如果题目正在讨论 DFD 和结构化分析：

> 优先按这里的需求分析工具理解。

## 为什么下一站开始从“分析”转向“设计”

到这里，结构化分析已经有两张核心成果：

> **DFD：功能和数据流逻辑。**  
> **数据字典：把图中元素定义清楚。**

但分析回答的仍然是：

> **系统逻辑上要做什么。**

接下来系统设计要决定：

> **软件怎样拆成相对独立的模块，模块对外暴露什么、内部细节怎么隔离。**

因此下一站进入 [[模块信息隐藏]]。

## 考试第一动作

遇到题干：

- “DFD 上某数据流包含哪些数据项”；
- “数据项类型/取值范围是什么”；
- “某数据存储有哪些内容和存取方式”；
- “给 DFD 元素做定义和说明”；

→ 优先想到 **数据字典**。

## 自测

1. DFD 已经画出“告警信息”，为什么还要数据字典？

> [!answer]- 第 1 题答案与解析
> **答案：DFD 主要显示关系和流向，数据字典负责定义“告警信息”的组成、含义、类型、范围等细节。**

2. “告警级别只能取 P1/P2/P3”主要属于数据字典里的哪一层？

> [!answer]- 第 2 题答案与解析
> **答案：数据项定义。**
> **解析：**它在定义一个最小数据项的允许取值及含义。

3. 建立数据字典时，为什么应先盘点 DFD 名称并在完成后反向核对？

> [!answer]- 第 3 题答案与解析
> **答案：为了保证 DFD 与数据字典使用同一套元素、名称、来源和去向，避免遗漏及两个版本不一致。**

4. 数据字典里的“处理过程”是否等于把模块内部算法代码完整写出来？

> [!answer]- 第 4 题答案与解析
> **答案：不是。**
> **解析：**它主要说明处理做什么、输入输出及处理要求；详细实现属于后续设计。
