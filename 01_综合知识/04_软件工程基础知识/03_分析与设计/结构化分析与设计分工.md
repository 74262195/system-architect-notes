# 结构化分析与设计分工：业务流图、DFD、SC 和程序流程图分别画什么

> [!summary]- 快速复习卡片（学完再看）
> **核心结论**：业务流图看业务处理怎样流转；DFD 看数据怎样被加工和传递；SC 看软件模块怎样组织和调用；程序流程图 / NS / PAD / PDL 看单个模块内部怎样执行。  
> **阶段判断**：系统分析先把问题和逻辑说清；系统设计再形成模块结构和实现细节。  
> **题干信号 → 第一反应**：业务活动/处理环节 → 业务流图；数据流/加工/存储 → DFD；模块层次/调用 → SC；顺序/判断/循环 → 详细设计工具。  
> **易错点**：这几种图不是同一张图的不同画法；DFD 不是程序控制流程，SC 也不是“更细的 DFD”。

上一站 [[需求双向追踪矩阵]] 已经解决了一个问题：每项需求都应该能追到后续设计、代码和测试。但“需求有出处”还不等于“已经知道系统该怎样分析和设计”。

假设现在要做一个告警系统：设备产生告警，值班人员核实，系统记录告警并按规则分级，必要时派单维修，最后关单。

面对同一个系统，你可能会看到业务流图、DFD、SC、程序流程图。看起来都在“画流程”，为什么要画这么多？

**直接答案：因为它们的主角不同。业务流图看业务处理怎样流转，DFD 看数据怎样流动和被加工，SC 看软件拆成哪些模块以及模块怎样联系，程序流程图等详细设计工具看一个模块内部怎样执行。**

> [!note] 术语与证据边界
> 联合覆盖矩阵将 `SE-A023` 命名为“业务流程图”；最新版大纲 OCR 与主教材本节文字层出现“业务流图”。本卡把它们作为同一个考试落点处理，重点训练“它表达什么、和其他图怎样区分”。当前证据没有锁定一套需要背诵的统一业务流图符号，因此不自行补符号表。

## 先分清系统分析和系统设计：先把问题说清，再形成实现蓝图

**系统分析先回答“这个系统究竟要解决什么、应当表现出什么逻辑”；系统设计再回答“怎样把分析结果组织成可以实现的软件”。**

主教材把两者的边界说得很清楚：系统分析建立在充分理解用户需求的基础上，把对新系统的理解形成需求规格；系统设计则依据分析结果形成系统蓝图，再展开概要设计和详细设计。

| 层次 | 主要回答什么 | 结构化方法中的典型结果 |
| --- | --- | --- |
| SA 结构化分析 | 系统要处理什么信息和功能逻辑 | DFD、数据字典、加工说明 |
| SD 概要设计 | 软件由哪些模块组成，模块怎样联系 | SC 系统结构图、接口说明 |
| SD 详细设计 | 每个模块内部怎样实现 | 程序流程图、NS、PAD、PDL 等 |
| SP 结构化编程 | 怎样把设计写成结构清晰的程序 | 顺序、选择、循环组成的代码 |

为了第一次学习更容易，可以把几类图按“关注对象越来越接近程序实现”排成一条理解链：

```mermaid
flowchart LR
    B["业务处理怎样流转<br/>业务流图"] --> D["数据怎样被处理<br/>DFD"]
    D --> S["模块怎样组织和调用<br/>SC"]
    S --> P["模块内部怎样执行<br/>程序流程图 / NS / PAD / PDL"]
```

> [!warning] 这不是教材规定的严格作图顺序
> 这张图只是帮助区分四类表达对象。教材把业务流图列在结构化设计的图形工具语境中，所以不能把上图机械背成“项目必须先画业务流图，再按箭头依次画完”的固定流程。

## 业务流图：主角是“业务处理怎样流转”

**业务流图关注业务活动或处理环节怎样前后衔接，先让人看清一项业务是怎样办下去的。**

仍用告警系统举例：告警出现后，需要核实、分级、派单、维修、关单。业务流图关心的是这些业务处理怎样衔接，而不是先把“告警记录中有哪些字段”画出来，也不是说明软件内部哪个模块调用哪个模块。

所以看到题干强调“业务环节、处理过程、业务怎样从一个环节转到下一个环节”，先想到**业务流图**。

这里最重要的边界是：

- 业务流图的主角是**业务处理和业务流转**；
- DFD 的主角是**数据以及数据的加工、存储和传递**。

两张图可能描述同一项业务，但回答的问题不同。

## DFD：主角换成“数据从哪里来，经过什么加工，到哪里去”

**DFD（数据流图）不是在画人员办理顺序，而是在建立系统的功能/数据流逻辑模型。**

例如同一个告警系统，DFD 会关心：告警数据从设备进入哪个加工，分级结果是否写入存储，通知数据最终送给谁。

这时题干如果出现“外部项、加工、数据流、数据存储、父子图平衡”等信号，就已经进入 [[数据流图DFD]] 的范围。四种元素、分层和平衡规则由那张主事实源卡完整讲解，本篇只负责把它放回正确层次，不复制第二套 DFD 正文。

## SC 系统结构图：从“数据怎么处理”走到“软件模块怎么组织”

**SC（Structure Chart，系统结构图/模块结构图）属于概要设计，它关注模块的层次、联系和调用，而不是数据流本身。**

假设分析阶段已经确认告警需要“接收、分级、记录、通知”。进入设计阶段后，设计者要决定这些能力由哪些软件模块承担，哪些模块调用哪些模块，接口怎样衔接。这就是 SC 要回答的问题。

主教材明确说明：结构化分析阶段可以得到 DFD、数据字典和加工说明等逻辑模型；进入系统设计后，可以按一定规则从 DFD 导出初始 SC。

这里很容易犯一个错误：

> **“可以从 DFD 导出初始 SC”不等于“DFD 的每个加工框原样改名成一个模块”。**

DFD 描述的是逻辑上的数据加工，SC 描述的是实现层面的模块结构。一个是在回答“系统逻辑上做什么”，另一个是在回答“软件怎样拆开来做”。

因此题干出现“模块层次、模块调用、接口、总体软件结构”，第一反应应是 **SC**，而不是 DFD。

## 程序流程图等详细设计工具：最后看一个模块内部怎样执行

概要设计已经决定“有哪些模块、谁调用谁”后，还要继续回答：**某个模块内部到底先做什么、遇到条件怎样分支、什么时候循环？**

这属于详细设计。教材把程序流程图、NS、PAD、PDL 等作为表达模块内部实现逻辑的工具；其中程序流程图重点描述处理步骤、逻辑条件和控制流。

例如“通知模块”内部可能需要：先判断告警级别，再判断是否已确认，满足条件才发送通知。这里的主角已经不是模块之间的结构，而是**一个模块内部的执行控制**。

各详细设计工具怎样选，继续看 [[结构化详细设计工具]]；本篇只负责建立它们和 SC、DFD 之间的层次边界。

## 一眼判断：题目到底在问哪一层

| 题干主要在说什么 | 优先想到 | 先问自己什么 |
| --- | --- | --- |
| 业务活动、处理环节、业务如何流转 | 业务流图 | 题目是不是在看“业务怎么办下去”？ |
| 数据从哪里来、怎样加工、存到哪里、送给谁 | DFD | 主角是不是数据和功能逻辑？ |
| 模块层次、模块调用、接口、总体软件结构 | SC | 题目是不是在看“软件怎样拆成模块”？ |
| 单个模块内部的顺序、判断、循环和算法 | 程序流程图 / NS / PAD / PDL | 题目是不是已经进入模块内部？ |

再加一个阶段判断：

- “理解需求、形成逻辑模型” → **系统分析 / SA**；
- “模块和接口怎样组织” → **概要设计 / SD**；
- “模块内部算法怎样实现” → **详细设计 / SD**；
- “按结构化控制写成程序” → **SP**。

考试时不要先背图名，先找题干的**主角**。主角一旦确定，干扰项通常就会少很多。

## 自测

1. 题目要求表示“告警核实后转维修处理，维修完成后关单”这一业务处理如何衔接，第一反应是什么？

> [!answer]- 第 1 题答案与解析
> **答案**：优先想到业务流图。
> **解析**：题目的主角是业务处理环节怎样流转，并没有要求描述数据加工、存储或模块调用。

2. 题目要求表示“告警数据进入分级加工，结果写入告警库，再产生通知数据”，应该优先用什么？

> [!answer]- 第 2 题答案与解析
> **答案**：DFD。
> **解析**：题目正在描述数据从哪里来、经过什么加工、存到哪里和流向哪里，这是数据流图的核心对象。

3. 题目要求表示“接收模块调用分级模块，分级模块再调用通知模块”，应该优先想到什么？为什么不是 DFD？

> [!answer]- 第 3 题答案与解析
> **答案**：SC 系统结构图。
> **解析**：这里关心模块层次和调用关系，属于概要设计；DFD 关心的是逻辑数据加工和数据流，不承担模块调用结构的主事实。

4. 已经确定了“通知模块”后，还要描述“高等级且未确认时发送通知，否则结束”，这时进入哪一层？

> [!answer]- 第 4 题答案与解析
> **答案**：详细设计，使用程序流程图、NS、PAD、PDL 等工具表达模块内部控制逻辑。
> **解析**：问题已经从“模块之间怎么组织”进入“一个模块内部具体怎么执行”。
