# 对象持久化与ORM

> [!summary]- 快速复习卡片（学完再看）
> - **核心结论**：持久化保存对象状态；ORM 建立对象与关系数据的映射，持久层隔离业务和存储细节。
> - **角色判断**：SQL 是数据库操作语言；JDBC 是 Java 访问关系数据库的 API；ORM 是对象—关系映射机制；JDO 是对象持久化规范/API。
> - **做题入口**：先看题目问“数据库命令、访问接口、对象表映射，还是透明持久化规范”，不要把几个层次混成同一个工具。

**持久化**是把内存中的对象状态保存到可长期保留的介质。进程退出后内存对象消失，已经确认的告警不能因此恢复成未确认状态。

保存时把告警标识、时间和状态映射为数据库记录，提交成功后数据保留；重新查询时读取记录并重建对象。读取、更新、失败处理都要有明确结果，调用保存函数不等于存储一定成功。

**ORM（对象关系映射）**负责对象与关系数据库表示之间的对应。持久层将这类工作从业务流程中分离，业务代码不用处处处理存储细节。

## SQL、JDBC、ORM、Hibernate、iBatis、JDO 分别站在哪一层

这些名字经常一起出现，但职责并不相同。

| 名称 | 本质角色 | 先抓什么边界 |
| --- | --- | --- |
| SQL | 面向关系数据库的数据定义、查询和更新语言 | 它描述“要对关系数据做什么”，不是 Java 的数据库访问 API，也不是 ORM 框架 |
| JDBC | Java 访问关系数据库的 API | Java 程序可通过它建立连接、发送 SQL、读取结果；它解决“怎样访问关系数据库” |
| ORM | 对象模型与关系表之间的映射机制 | 解决“对象怎样对应表、字段和关系”；ORM 不等于数据库，也不等于 JDBC |
| Hibernate | 以 ORM 为核心的持久化框架 | 教材语境下对 JDBC 做封装，并可根据对象映射生成、执行 SQL |
| iBatis | 对象与手写 SQL 的参数/结果映射框架 | SQL 仍主要由开发者编写，框架负责参数和结果映射 |
| JDO | Java 对象持久化规范/API | 强调透明对象存储；按教材语境可面向关系库之外的多种持久化底层 |

可以把它们放到一条链上理解：

> **业务对象 → 持久层/ORM 或 JDO 等持久化机制 → JDBC 等数据库访问接口 → 关系数据库；需要直接表达关系数据库操作时使用 SQL。**

这是一条帮助理解职责的教学链，不表示所有框架都必须严格按同一内部实现路线工作。

按教材历史技术语境：Hibernate、iBatis、JDO 是当时用于说明对象持久化的代表技术。这里学习的是**角色和边界**，不是当前产品选型建议。

ORM 不自动消除事务、并发控制或数据一致性问题；JDBC 也不负责把对象模型自动变成合理的关系模型。

> [!tip] 考试动作
> - 题干强调“Java 访问关系数据库的标准接口/API” → 先想到 **JDBC**；
> - 强调“对象属性与表列、对象关系与表关系怎样对应” → 先想到 **ORM**；
> - 强调“开发者手写 SQL，再映射参数和结果” → 更接近 **iBatis** 的教材角色；
> - 强调“透明保存 Java 对象、持久化规范/API” → 先想到 **JDO**。

## 自测

> [!question] 自测
> 1. 程序重启后重新查出对象，是原来的内存对象一直存在吗？
>
> > [!answer]- 第 1 题答案与解析
> > **答案**：不是，持久化的是状态，程序从存储读取数据后重新建立对象。
>
> 2. “JDBC”和“ORM”可以直接画等号吗？
>
> > [!answer]- 第 2 题答案与解析
> > **答案**：不能。JDBC 是 Java 访问关系数据库的 API；ORM 解决对象模型与关系数据之间的映射。二者可能配合使用，但职责不同。
