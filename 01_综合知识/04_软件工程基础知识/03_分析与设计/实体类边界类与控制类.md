# 实体类、边界类、控制类：一次“确认告警”到底应该由谁存数据、谁接用户、谁协调流程

> [!summary]- 快速复习卡片（学完再看）
> **实体类**：保存长期有意义的业务信息，如告警、设备、课程。  
> **边界类**：位于系统与外部环境交接处，如页面、外部接口、通信协议接口。  
> **控制类**：协调一个或几个用例的处理流程。  
> **第一动作**：业务状态 → 实体；人/外部系统交互 → 边界；一次用例的流程协调 → 控制。  
> **易错点**：边界不只等于 GUI；教材对属性/方法的“通常”描述不要扩成语言级绝对禁令。

上一站 [[UML构件图与部署图]] 已经把 UML 核心图走完。

现在回到 [[面向对象设计OOD]] 的核心任务：

> **设计类的职责。**

假设值班人员点击：

> “确认告警”。

如果一个类同时负责：

- 接收页面请求；
- 保存告警业务状态；
- 判断确认流程；
- 返回界面结果；

它就把三种不同变化揉在了一起。

OOD 常用“实体 / 边界 / 控制”三类职责把它们分开。

## 先看一次“确认告警”怎样流过去

可以先形成这个画面：

~~~mermaid
flowchart LR
    U["值班人员"] --> B["边界类<br/>确认告警页面/API"]
    B --> C["控制类<br/>告警确认控制器"]
    C --> E["实体类<br/>告警"]
    E --> C
    C --> B
~~~

这不是要求你把所有项目都强制设计成这一张图，而是帮助区分三类职责。

## 实体类：业务信息本身

实体类最接近：

> **系统长期需要认识和保存的业务对象。**

例如：

- 告警；
- 设备；
- 用户；
- 课程。

“告警”对象可能长期保存：

- 告警编号；
- 状态；
- 级别；
- 发生时间。

教材强调实体类通常和需要持久保存的信息关系紧密。

所以题干出现：

> 业务领域名词、长期状态、需要持久保存的信息

→ 优先想到**实体类**。

## 边界类：系统和外界的交接处

边界类负责：

> **把系统内部和外部角色/系统连接起来。**

例如：

- 确认告警页面；
- REST/API 接口；
- 与外部监控系统通信的协议接口；
- 报表；
- 终端/传感器接口。

所以“边界类 = 页面”是不完整的。

更准确地说：

> **只要位于系统与外部环境的交互边界，都可能属于边界类。**

它的重要价值是隔离外部变化。

例如页面从 Web 改成移动端，不希望业务实体和流程协调代码全部一起变化。

## 控制类：把一个用例的步骤协调起来

控制类通常不负责长期保存核心业务数据。

它更像：

> **一次用例的流程协调者。**

例如“确认告警”可能需要：

1. 查找告警；
2. 检查当前状态；
3. 调用告警完成确认；
4. 记录结果；
5. 通知边界返回成功。

这些步骤由控制对象协调。

所以题干出现：

> 用例流程、协调多个对象、组织一次业务处理

→ 优先想到**控制类**。

## 三类为什么不能只靠“类名”判断

例如：

> 告警服务

这个名字本身不能保证它一定是控制类。

要看它实际上承担什么职责。

考试和设计判断都优先问：

> **这个类负责的数据/行为属于哪一层？**

- 业务核心状态 → 实体；
- 内外交互 → 边界；
- 用例协调 → 控制。

## 教材里的“通常”不要背成绝对禁令

教材会描述一些典型特征：

- 实体类通常有属性；
- 控制类通常偏方法和协调；
- 边界类可以有属性和方法。

这些是建模识别经验。

不要错误扩成：

> “控制类绝对不能有属性。”

考试若按教材典型特征问，可以据此判断；实际编程语言层面不要把它当不可违反的语法规则。
