# 结构化详细设计工具：怎样把一个模块的规则写成可执行逻辑

> [!summary]- 快速复习卡片（学完再看）
> - **核心结论**：详细设计说明模块内部算法与局部数据结构；流程图、NS、PAD、判定表和 PDL 是不同表达工具。
> - **建立主线**：确定输入输出 → 找对应数据 → 导出程序结构 → 放入操作和条件 → 写伪码并走查。
> - **做题入口**：模块调用层次看 SC；模块内部控制过程看详细设计工具；数据流向看 DFD。

概要设计确定模块和接口后，开发者仍要知道每个模块内部怎样运行。**详细设计工具**用图、表或语言表达这些逻辑。

## 详细设计不是“挑一种图就画”

教材给出的基本步骤是：

```mermaid
flowchart LR
    A[分析输入/输出的逻辑结构] --> B[找输入输出的对应数据]
    B --> C[导出程序结构]
    C --> D[放入基本操作与条件]
    D --> E[用伪码写出并检查]
```

先把逻辑推出来，再选择最能表达它的工具。图、表和语言是不同视角，不是互相排斥的开发阶段。

## 用告警通知模块完整建立一次

模块需求如下：

> 输入一条已经保存的告警。若告警级别为 P1 且尚未确认，则发送通知；其他情况只记录本次检查结果。输出通知结果和检查记录。

### 第 1 步：确定输入、输出和局部数据

| 类别 | 本例内容 |
| --- | --- |
| 输入 | 告警级别、确认状态、接收人 |
| 输出 | 是否发送、发送结果、检查记录 |
| 局部数据 | `needNotify`，表示是否需要通知 |

这一步先确认模块边界，不讨论整个告警平台的模块调用层次。

### 第 2 步：列出条件、动作及对应关系

条件有两个：是否 P1、是否已确认。动作有两个：发送通知、记录检查结果。

当条件组合容易漏项时，先建立判定表：

| 条件/动作 | 规则 1 | 规则 2 | 规则 3 |
| --- | --- | --- | --- |
| 是否 P1 | 是 | 是 | 否 |
| 是否已确认 | 否 | 是 | — |
| 发送通知 | 执行 | 不执行 | 不执行 |
| 记录检查结果 | 执行 | 执行 | 执行 |

`—` 表示该条件对本规则无关：既然不是 P1，是否确认都不发送。这样两种非 P1 情况可合并，而不是遗漏。

建立判定表时依次做四件事：

1. 把所有条件写成条件行；
2. 把可能动作写成动作行；
3. 展开有意义的条件组合，能合并的用“—”；
4. 为每列规则勾选动作，再检查是否存在无动作或互相矛盾的列。

### 第 3 步：导出顺序、选择和循环结构

本例没有批量处理，因此只需要“顺序 + 选择”：

1. 读取输入；
2. 判断“P1 且未确认”；
3. 满足时发送通知；
4. 无论是否发送都记录检查结果；
5. 返回输出。

如果需求改成“逐条处理待通知告警列表”，才在外层增加循环。不能为了展示工具而凭空增加控制结构。

### 第 4 步：用 PDL 落成可交流的算法

> [!example] PDL 示例
> **PROCEDURE 处理告警通知（告警）**
>
> `needNotify ← （告警.级别 = P1）AND（告警.状态 = 待确认）`
>
> **IF** `needNotify` **THEN**
> - 发送通知（告警.接收人，告警）
>
> **END IF**
>
> 记录检查结果（告警.编号，`needNotify`）  
> **RETURN** 通知结果与检查记录  
> **END PROCEDURE**

PDL 外层的 `IF`、`RETURN` 等控制结构较确定；“发送通知”内部怎样调用短信或应用消息，可以根据设计层次继续逐步求精。

### 第 5 步：走查是否逻辑正确、表达清楚

至少代入三组数据：P1/未确认、P1/已确认、非 P1。检查：

- 每一列判定表是否都能走到一个明确结果；
- PDL 是否与判定表一致；
- 所有路径是否都会记录检查结果；
- 输入输出是否仍符合概要设计规定的模块接口；
- 是否出现任意跳转，破坏单入口、单出口的结构化控制。

至此才形成“规则 → 条件组合 → 程序结构 → 伪码 → 测试走查”的完整详细设计产物。

| 工具 | 最该抓住的识别点 |
| --- | --- |
| 程序流程图 | 方框表示处理、菱形表示条件、箭头表示控制流；能描述执行过程，但不擅长描述数据 |
| NS 图 | 盒状嵌套的结构化图；控制不能任意跳转，适合看嵌套与作用域 |
| PAD 图 | 比流程图更直观、结构更清晰；能体现自顶向下的细化过程，也可描绘数据结构 |
| 判定表 | 将各种条件组合与对应动作列成表，适合查条件组合有没有漏项或冲突 |
| PDL | 用结构化伪码说明模块内部算法；外层控制结构确定，内层业务操作可按实际情况灵活写 |

教材的 PDL 外层控制语法较确定，内层具体操作可按业务灵活描述。它不是必须编译运行的程序语言。结构化程序主要用顺序、选择和循环组合，强调自顶向下、逐步求精和清晰表达。

> [!tip] 一句话选工具
> 问“模块怎样被调用”选 **SC**；问“数据如何流动”选 **DFD**；问“模块内部如何执行”才在本卡的流程图、NS、PAD、判定表、PDL 中判断。

## 自测

1. 选择判定表最主要是为了展示什么？

> [!answer]- 第 1 题答案与解析
> **答案**：条件组合与动作的对应关系。
> **解析**：判定表适合把多种条件组合逐列展开，从而检查动作是否遗漏、冲突或不一致；它不是模块调用层次图，也不以描绘控制流为主。

2. 为什么不能看到“模块内部逻辑”就立即画程序流程图？

> [!answer]- 第 2 题答案与解析
> **答案**：应先确定输入输出、数据对应、基本操作和条件，再选择能清楚表达该逻辑的图形、表格或语言工具。

3. 本例判定表中“非 P1”规则下，“是否已确认”为什么可以写“—”？

> [!answer]- 第 3 题答案与解析
> **答案**：因为只要不是 P1，无论是否确认都不发送通知，该条件不会改变动作结果。
