# 架构可维护性度量：六个指标在看什么

> [!summary]- 快速复习卡片（学完再看）
> **核心结论**：教材用 CCN、FFC、CBO、RFC、TCC、LCC 六个子指标从复杂度、耦合、响应和内聚等方面观察架构可维护性。
> **题干信号 → 第一反应**：组件图 + 六个结构指标 + 可维护性 → 架构可维护性度量。
> **第一动作**：先辨认指标是在看复杂度、依赖/耦合、响应还是内聚，不必把它们当可靠性指标。
> **易错边界**：单个指标不能替代完整演化评估；它们只是观察架构可维护性的结构度量维度。

## 为什么“代码还能跑”不代表架构健康

多轮演化以后，系统功能可能全部正常，但依赖越来越多、模块越来越纠缠、修改波及越来越大。此时需要从组件图等架构表示里观察可维护性。

大纲明确列出六个指标：

| 指标 | 主要在看什么 |
| --- | --- |
| CCN | 圈复杂度，结构路径/复杂程度 |
| FFC | 扇入扇出相关度量，组件依赖进入与发散情况 |
| CBO | 模块/对象间耦合程度 |
| RFC | 模块响应，收到请求后可能触发的响应范围 |
| TCC | 紧内聚度，内部元素直接紧密关联程度 |
| LCC | 松内聚度，考虑间接关系后的内聚程度 |

首轮学习目标不是背复杂公式，而是知道它们共同回答：**这个架构版本是否越来越复杂、越来越耦合、越来越难局部修改？**

## 和 07 章“可修改性”怎么分

07 章的可修改性质量属性场景告诉你“希望一次变化在什么代价和范围内完成”；本篇用架构结构指标观察“当前架构是否具有有利于维护的结构特征”。一个偏质量目标/场景，一个偏演化后的结构度量。

## 考试动作

若题干把 CCN/CBO/TCC 等描述成“软件可靠性失效数据指标”，先排除；它们在本节用于架构可维护性度量。看到“组件图解析后计算六个子指标”，优先定位 9.7.4。
