# 架构演化到底改变哪些元素

> [!summary]- 快速复习卡片（学完再看）
> **核心结论**：在 `SA = {components, connectors, constraints}` 这个定义下，演化就是对组件、连接件、约束进行增加、删除或修改，并分析直接影响与波及影响。
> **题干信号 → 第一反应**：模块/服务变化 → component；交互/调用变化 → connector；拓扑/配置/规则变化 → constraint。
> **第一动作**：找“第一处变化”后继续追依赖，不能只看被直接修改的元素。
> **易错边界**：组件变化常会带动连接件变化；三类元素不是彼此隔离的三个盒子。

## 为什么架构定义会决定“演化看什么”

“架构演化”很抽象，所以教材先给了一个可操作的定义：

`SA = {components, connectors, constraints}`

也就是把架构看成**组件、连接件、约束**三类核心信息。定义一旦确定，演化就能落到具体对象上。

| 元素 | 大白话 | 常见变化 |
| --- | --- | --- |
| Component 组件 | 做事或存数据的主要结构单元 | 新增、删除、替换、拆分、合并模块/服务 |
| Connector 连接件 | 组件之间怎样交互 | 增删调用、消息、接口关系，改变交互顺序或方向 |
| Constraint 约束 | 组件和连接件必须遵守的拓扑、配置或规则 | 新增、删除、修改配置参数、约束条件 |

## 为什么改一个地方会“牵一发动全身”

假设订单系统把“库存扣减”从订单服务里拆成独立库存服务：

```mermaid
flowchart LR
    A[拆出库存组件] --> B[新增订单到库存的连接]
    B --> C[新增超时/重试/一致性约束]
    C --> D[影响调用链和故障范围]
    D --> E[需要重新评估相关质量属性]
```

第一步只是 component 变化，但它会带出 connector 和 constraint 的变化。这就是**波及效应**。

教材因此把演化后的元素分成三类理解最清楚：

- **直接变更元素**：这次修改直接动到的对象；
- **受波及元素**：因为依赖、交互或约束而被迫跟着调整；
- **未受影响元素**：可以保持不变。

## 与 07 质量属性的边界

07 章回答“系统希望保持什么能力”，例如性能、可靠性、可修改性、安全性；本篇回答“变化从哪个结构元素开始，又会波及哪里”。质量属性是**目标/观察维度**，组件—连接件—约束是**演化对象**。

## 考试动作

看到“新增模块”不要只勾“组件变化”就结束；如果题目继续问架构影响，应检查交互消息和约束是否也需要改变。看到“调用顺序改变”优先想到连接件层；看到“部署拓扑/配置条件改变”优先想到约束层。

## 自测

1. 订单服务拆出独立库存服务后，新增了调用关系，又增加超时重试规则。分别属于哪三类架构元素的变化？还应继续检查什么？

> [!answer]- 第 1 题答案与解析
> **答案**：拆服务是组件变化；新增调用是连接件变化；超时重试规则是约束变化；还要追踪直接变更产生的波及影响。
> **解析**：在 `SA = {components, connectors, constraints}` 下，三类元素相互牵动；不能看到一个组件变化就停止影响分析。
