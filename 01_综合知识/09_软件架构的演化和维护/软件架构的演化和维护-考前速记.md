# 软件架构的演化和维护 · 考前速记

> [!summary] 5～10 分钟主线
> **当前架构满足要求 ≠ 永远不需要变。变化驱动 → 找到架构级影响 → 选择演化时机/方式 → 控制波及 → 评估结果 → 维护知识、修改和版本。**

## 1. 为什么会演化

看到下面信号，先想到“架构需要持续适配”，不要直接降成改代码：

- 新需求或业务规则变化；
- 用户规模、部署和运行环境变化；
- 技术替换；
- 安全、可靠性、性能、可维护性等质量目标变化。

**第一动作**：先问变化是否影响系统整体结构、组件/连接件/约束及质量能力。

## 2. 演化 vs 维护

| 概念 | 更关注什么 | 题干第一反应 |
| --- | --- | --- |
| 架构演化 | 架构随需求/技术/环境变化而发生结构与决策改变 | “为什么变、改什么、何时/怎样变、变完怎样评估” |
| 架构维护 | 在持续变化中管理已有架构资产，使其可理解、可追踪、可继续修改 | “决策知识、修改波及、版本基线、可维护性” |

**陷阱**：架构维护不是简单等于“修改代码”。

## 3. 四个演化时期

- **设计时**：编译前。
- **运行前**：编译后、执行前。
- **有限制运行时**：系统运行中，但必须进入设计时预先规定的安全条件。
- **运行时**：系统运行中按需求动态调整结构。

分类：**静态演化 = 设计时 + 运行前；动态演化 = 有限制运行时 + 运行时。**

第一动作：**先判断系统是否正在运行，再判断变化条件是不是预先规定。**

## 4. 可持续演化与评估

- 可持续原则的作用不是背口号，而是给持续变化加护栏，避免局部修改无限扩散。
- 评估题先看：当前演化过程是否已知、证据是什么、演化后结构/质量能力是否仍满足目标。
- 演化会影响可靠性、性能、可修改性等质量属性，但这些质量属性的完整定义仍回 07，不在本章复制。

## 5. 架构维护四个入口

| 题干信号 | 第一反应 |
| --- | --- |
| 人员流动后只剩架构图，不知道为什么这么设计 | **架构知识管理** |
| 一次变化可能影响很多组件，需要限制波及 | **架构修改管理** |
| 需要追踪不同架构版本、保留演化基线 | **架构版本管理** |
| CCN / FFC / CBO / RFC / TCC / LCC | **架构可维护性度量** |

## 6. 当前稳定契约的边界

当前稳定契约是 `EVO-A001 ~ EVO-A016`。它覆盖演化驱动/对象、OO 演化、演化时期与静态/动态方式、可持续原则、演化评估、大型网站演化、架构知识/修改/版本/可维护性管理。

“架构漂移/腐化/侵蚀、架构恢复、重构、再工程”等并未作为本章当前 stable Atom 的独立主事实源，因此本轮不凭模型记忆扩写第二套术语课；若题目后续证明需要，再按教材证据进入专项维护。
