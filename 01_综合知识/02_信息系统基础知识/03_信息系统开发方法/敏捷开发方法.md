# 敏捷开发方法：需求会变时，团队怎样缩短反馈回路

> [!summary] 快速复习卡片
> **定位**：用短周期交付和反馈应对需求变化。
> **题干怎么认**：Sprint 与产品待办列表看 Scrum；测试驱动与结对编程看 XP。
> **核心动作**：选择本轮目标，设计开发测试，交付可用增量，用反馈调整下一轮。
> **易错点**：敏捷更重视可工作软件和互动，不等于不要计划、文档与流程。

## 先定位：本卡只讲具体开发方法

[[敏捷开发模型]] 已说明系统工程生命周期中的敏捷原则。本卡只补充软件开发中常见的 Scrum、XP 等落地方式，避免重复背两遍“拥抱变化”。

## 四项价值观怎样理解

敏捷宣言更重视：

| 更重视 | 同样有价值 |
| --- | --- |
| 个体和互动 | 流程和工具 |
| 可工作的软件 | 详尽的文档 |
| 客户合作 | 合同谈判 |
| 响应变化 | 遵循计划 |

“更重视”不等于右侧不要。敏捷仍需要必要流程、文档、合同和计划，只是用短周期反馈及时修正它们。

## 一轮迭代怎样闭环

~~~mermaid
flowchart LR
    A[排序需求] --> B[选择本轮目标]
    B --> C[设计开发测试]
    C --> D[交付可用增量]
    D --> E[评审与反馈]
    E --> A
~~~

每轮从高价值需求中选取可完成范围，开发与测试并行推进，产出可工作的增量，再用用户和团队反馈调整下一轮。重点是**小批量交付 + 快速验证假设**，不是边做边随意改。

## 用一张设备报修单看需求怎样变成迭代增量

下面是虚构的教学例子，重点看 Scrum 式待办/迭代和反馈闭环，不代表某个真实项目。

| 迭代环节 | 本例中的记录 |
| --- | --- |
| 产品待办项 | “作为办公室员工，我要提交设备故障报修，以便维修人员接单处理。” |
| 本轮目标与验收 | 本轮只做提交和查看：员工填写设备编号、故障描述后可提交；提交成功会生成工单号；维修人员能看到新工单。用员工和维修人员测试账号走通完整路径。 |
| 可工作增量 | 测试环境里可以创建工单、生成工单号并在维修列表中查看；本轮不包含派单、状态流转和消息通知。 |
| 评审反馈 | 员工指出“故障描述”不足以表达紧急程度；维修人员希望先看到影响多个办公室的报修。 |
| 下一轮待办调整 | 新增“影响范围/紧急程度”字段及排序需求，并让维修人员评审排序是否符合实际处理需要；对应补充字段校验和列表排序验收。 |

可见，敏捷开发不是把所有要求都塞进第一轮，而是先承诺一个可完成目标，交付用户能操作的增量，再把反馈变成下一轮可验收的待办。Scrum 的角色和迭代框架可以组织这个过程；若题干出现测试驱动、结对编程等工程实践，则识别为 XP 题眼。

## 常见方法怎么区分

| 方法 | 核心题眼 | 不要混成 |
| --- | --- | --- |
| Scrum | 产品待办列表、Sprint、产品负责人、Scrum Master、评审与回顾 | 具体工程实践清单 |
| XP | 测试驱动、结对编程、持续集成、重构、简单设计 | 项目管理角色框架 |
| 水晶系列 | 团队规模和关键性不同，方法也应调整 | 单一固定流程 |
| FDD | 以特征为中心进行短周期设计与构建 | 看板 |
| Kanban | 可视化工作流、限制在制品、拉动 | 教材所有版本都列为同一组时才按题干作答 |

## 适用边界

敏捷适合需求变化较多、需要频繁反馈、团队能够持续协作的环境。稳定或强监管项目也能采用敏捷实践，但需加强文档、追踪和合规控制；不能按“政府/银行必瀑布、互联网必敏捷”机械判断。

## 考试怎么认

- “适应型、面向人、欢迎变化” → 敏捷方法。
- “测试先行/结对编程” → XP。
- “Sprint/产品待办列表” → Scrum。
- 题目若按指定教材列举敏捷方法，以题干口径为准，不把所有现代实践都强塞进官方清单。

## 自测

1. 敏捷宣言写着“可工作的软件 重于 详尽的文档”，是否说明敏捷项目可以不写文档、不做计划？

> [!answer]- 第 1 题答案与解析
> **答案**：不能这样理解。
> **解析**：“更重视”不等于右侧不要；敏捷仍然需要必要的流程、文档、合同和计划，只是用短周期反馈及时修正它们。

2. 一轮迭代从排序需求开始，交付增量后经过评审反馈又回到排序需求，这个闭环为什么能应对需求变化？

> [!answer]- 第 2 题答案与解析
> **答案**：它靠小批量交付 + 快速验证假设，用真实反馈调整下一轮。
> **解析**：每轮只从高价值需求中选取当前可完成的范围，产出可工作的增量再接受评审，反馈变成下一轮待办；这不是边做边随意改。

3. 题干出现“测试驱动、结对编程、持续集成”，以及出现“Sprint、产品待办列表”，分别对应哪种方法？

> [!answer]- 第 3 题答案与解析
> **答案**：前者是 XP，后者是 Scrum。
> **解析**：XP 的题眼是工程实践（测试驱动、结对编程、持续集成、重构、简单设计）；Scrum 的题眼是产品待办列表、Sprint、产品负责人、Scrum Master、评审与回顾。题目若按指定教材列举敏捷方法，以题干口径为准。

4. “政府或银行项目必须用瀑布、互联网项目必须用敏捷”这个判断成立吗？

> [!answer]- 第 4 题答案与解析
> **答案**：不成立，不能这样机械判断。
> **解析**：敏捷适合需求变化较多、需要频繁反馈、团队能够持续协作的环境；稳定或强监管项目也能采用敏捷实践，但需加强文档、追踪和合规控制。
