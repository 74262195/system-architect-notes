# 软件可靠性技术 · 考前速记

> [!summary] 5～10 分钟主线
> **07 把可靠性识别为质量属性 → 08 把它工程化：定义 → 度量 → 目标 → 建模/管理 → 设计 → 测试 → 评价。**

## 1. 先判题目在问什么

| 题干信号 | 第一反应 |
| --- | --- |
| 规定条件、规定时间、完成规定功能、不失效 | **软件可靠性** |
| 不失效概率、`R(t)` | **可靠度**；先确认时间口径 |
| 平均多久才失效 | **MTTF** |
| 平均多久恢复 | **MTTR**，重点已转向恢复/可用性 |
| 真实用户使用概率、运行剖面、失效统计 | **可靠性测试** |
| 模型选择、失效数据、是否达标/停止测试/发布 | **可靠性评价** |

## 2. 可靠性 vs 可用性

- **可靠性**：重点是“这段时间内尽量不要失效”。
- **可用性**：还要看“需要服务时是否可用、故障后恢复多快”。
- 看到 MTTR、恢复时间、服务可用比例时，不要只停在可靠性。
- 完整边界继续回 [[可靠性与可用性]]，本章不复制 07 的定义课程。

## 3. 最小公式入口

- `R(t)`：运行到时间 `t` 仍未失效的概率。
- 若 `F(t)` 是到 `t` 前已失效概率，则 `R(t)=1-F(t)`。
- 做计算前第一步：**先看题目采用自然时间、运行时间还是执行时间，避免把不同时间口径直接混算。**

## 4. 设计 / 测试 / 评价怎么区分

| 环节 | 它解决什么 | 常见误区 |
| --- | --- | --- |
| 可靠性设计 | 在设计阶段通过容错、检错、降低复杂度、系统配置等降低失效风险 | 不是“后期多测几遍” |
| 可靠性测试 | 按预期使用方式运行并取得可统计的失效数据 | 不只是找 bug |
| 可靠性评价 | 用模型和统计方法分析数据，判断当前/未来可靠性及是否达标 | “一次没出错”不等于可靠度 1 |

一条链记住：**目标 → 设计 → 运行剖面/测试 → 失效数据 → 模型评价 → 与目标比较。**

## 5. 容错 / 检错 / 降复杂度

- **容错**：局部故障发生后，仍尽量继续正确服务。
- **检错**：尽快发现故障并进入处理，不等于已经具备容错能力。
- **降复杂度**：从设计源头减少缺陷产生和隐藏的机会。

## 6. 三个高频陷阱

1. “软件连续运行很久没出错，所以一定可靠” → **错**，必须带规定条件、时间、功能和使用分布。
2. “普通功能测试发现很多 bug，就能直接推出上线失效概率” → **错**，可靠性评价还需要能代表真实使用的统计数据。
3. “有限测试一次失效都没有，所以可靠度就是 1” → **错**，只能说明这批样本中未观察到失效。
