# 可靠性管理：为什么要贯穿软件生命周期

> [!summary]- 快速复习卡片（学完再看）
> **核心结论**：可靠性管理是软件工程管理的一部分，管理对象是贯穿生命周期的可靠性目标、计划、活动、数据和纠正措施。
> **题干信号 → 第一反应**：看到“各开发阶段安排可靠性活动” → 想可靠性管理，而不是只想到测试。
> **易错边界**：可靠性不是测试人员在交付前单独负责的一项末端活动。
> **第一动作**：先判断题干处于需求、设计、编码、测试还是实施阶段。

## 为什么“最后多测几轮”救不了所有问题

教学情境：一个在线预约系统准备上线时，团队才发现业务方从未说明“预约提交失败能接受多少次”，架构也没有考虑短信服务故障时如何处理。此时再加测只能暴露问题，未必能低成本补回缺失的目标和设计。

如果需求阶段根本没定义可靠性目标，设计阶段没考虑故障处理，等系统完成后才要求“达到很高可靠性”，往往只能付出更高的返工成本。可靠性管理因此不是交付前临时加测，而是让各阶段的目标、活动、数据和纠正措施接得起来。

因此可靠性管理要把活动分散到整个生命周期：

```mermaid
flowchart LR
    A[需求：目标与验收标准] --> B[设计：度量与可靠性设计]
    B --> C[编码：测试 排错 数据]
    C --> D[测试：建模 评价 调整]
    D --> E[实施：运行数据 再评价]
```

## 每个阶段在解决什么

- **需求阶段**：先把可靠性目标、验收标准、数据规范定下来。
- **设计阶段**：确定度量，落实可靠性设计，并预测当前方案可能达到的水平。
- **编码阶段**：结合单元级活动发现问题、排错并持续收集数据。
- **测试阶段**：可靠性测试、建模、评价同时发生，根据结果调整计划。
- **实施阶段**：继续收集真实运行数据，必要时调整模型并重新评价。

管理的核心不是“每阶段都做同一件事”，而是保证目标、设计、测试、数据、评价之间不断链。

## 考试动作

题干问“软件可靠性管理属于什么” → 软件工程管理的一部分；问“何时开展” → 贯穿软件生命周期；问需求阶段重点 → 可靠性目标/验收标准通常优先。

## 自测

1. 可靠性活动只放在交付前测试阶段，是否符合可靠性管理？

> [!answer]- 答案与解析
> **不符合。**可靠性目标、设计控制、测试数据和运行再评价都应贯穿生命周期；末端测试无法低成本补回前期遗漏。
