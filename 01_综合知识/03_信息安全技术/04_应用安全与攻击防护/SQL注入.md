# SQL 注入：为什么“用户输入”会变成数据库指令

> [!summary]- 快速复习卡片（学完再看）
> **作用/定位**：识别输入数据越过边界、改变 SQL 语句结构的攻击。
> **核心结论**：首要防线是参数化查询/正确使用预编译接口，让数据与 SQL 结构分离；最小权限等做纵深防护。
> **题干怎么认**：拼接 SQL、登录绕过、异常查询、数据库数据泄露。
> **易错点**：黑名单过滤和 WAF 都不能替代正确参数绑定。

## 登录框里的文字，为什么会改掉数据库指令

用户在登录框输入用户名和密码，本来只是给程序提供两份数据。如果程序把这些文字直接拼进 SQL 查询，攻击者就可能在输入中夹带 SQL 语法，让数据库执行另一条意思完全不同的指令。**SQL 注入就是用户输入越过了“数据”的边界，变成数据库指令的一部分。**

正确做法是用参数化查询把指令结构和用户数据分开，并给数据库账号最小权限。WAF（Web 应用防火墙）和字符黑名单只能补充防护，不能代替代码层修复。下一篇会看同类边界问题怎样发生在浏览器中。

## 为什么输入会改变数据库指令

程序把不可信输入直接拼入 SQL 字符串，数据库解析时无法区分“原本的 SQL 结构”和“用户带入的恶意语法”。

```sql
SELECT * FROM users WHERE name = ? AND password_hash = ?;
```

参数化接口把 SQL 结构先固定，再把输入作为参数传入，从机制上显著降低注入风险。

### 同一段输入，拼接与参数绑定会怎样解释

假设页面只按用户名查询记录，输入下面这个**仅用于理解语法的无破坏性示例**：`x' OR '1'='1`。

```sql
-- 不安全：把输入直接拼进 SQL
SELECT id FROM users WHERE name = 'x' OR '1'='1';
```

拼接后，输入中的单引号结束了原本的用户名字符串，`OR '1'='1'` 成为 SQL 条件的一部分；该条件恒为真，因此查询可能返回超出预期的记录。问题发生在**输入被拼进 SQL 后，由数据库解析器重新当作语法解释**的那一步。

```sql
-- 安全接口示意：先固定语句，再单独绑定 name 参数
SELECT id FROM users WHERE name = ?;
```

调用参数化接口时，把整个 `x' OR '1'='1` 作为 `name` 的一个字符串值绑定。数据库仍按固定结构执行“name 等于这个完整字符串”的查询，不会把其中的引号和 `OR` 重新解释为 SQL 语法。`?` 是常见占位符示意，具体占位符写法取决于语言和数据库驱动；关键是使用真正的参数绑定接口，不是先拼出完整 SQL 再转义。

输入格式校验和最小数据库权限仍有价值，但职责不同：白名单校验拒绝不合业务格式的值，最小权限限制成功注入后的损害范围；防止数据被解析成 SQL 指令，首选参数化查询。详见 [OWASP SQL Injection Prevention Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/SQL_Injection_Prevention_Cheat_Sheet.html)。

## 防御优先级

1. 参数化查询 / 安全 ORM（对象关系映射，负责把程序对象转换为数据库操作）参数绑定；
2. 对输入做业务白名单校验；
3. 数据库账号最小权限；
4. 错误信息收敛、日志审计；
5. WAF（Web 应用防火墙，用规则检查和拦截 Web 请求）等作为补充防线。

## 自测

1. 为什么参数化查询比“过滤单引号”更可靠？

> [!answer]- 第 1 题答案与解析
> **答案**：参数化查询先固定 SQL 结构，再把输入按数据参数传递，不依赖猜全所有危险字符和绕过方式。
> **解析**：过滤是补充校验；数据与指令边界不清才是注入根因。

2. 最小数据库权限为什么不能替代参数化查询，但仍然值得做？

> [!answer]- 第 2 题答案与解析
> **答案**：它不能阻止注入发生，但可限制注入成功后数据库账号能读取或修改的范围。
> **解析**：这是典型纵深防御：根因修复在前，损害限制在后。

3. 为什么 `x' OR '1'='1` 在拼接查询中可能改变结果，而绑定参数时只会作为用户名文本查找？

> [!answer]- 第 3 题答案与解析
> **答案**：拼接会把输入并入 SQL 字符串并由数据库当语法解析；参数绑定让数据库先按固定 SQL 结构解析，再把整段输入作为一个值处理。
> **解析**：防护关键是代码与数据分离，不是猜测并删除某几个危险字符。

4. `?` 占位符能不能直接放进最终 SQL 字符串、再把整条字符串执行？

> [!answer]- 第 4 题答案与解析
> **答案**：不能；要通过数据库驱动或安全 ORM 的参数绑定接口单独传值。
> **解析**：如果应用又把值拼回完整 SQL，代码与数据的边界仍未建立。不同语言/驱动的占位符形式可能不同。
