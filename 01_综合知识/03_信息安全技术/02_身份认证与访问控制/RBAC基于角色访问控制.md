# RBAC：为什么把权限给“岗位角色”比逐个人配置更好管理

> [!summary]- 快速复习卡片（学完再看）
> **作用/定位**：在用户与权限之间增加角色层，适合按岗位职责统一授权。
> **核心结论**：用户被分配角色，角色关联权限；最小权限和职责分离可以借助角色设计实现。
> **题干怎么认**：岗位、角色、用户—角色—权限、职责分离、互斥角色。
> **易错点**：RBAC 是常见方案，不是任何权限案例的“默认唯一答案”；应按题目组织模型和约束选择。

```mermaid
flowchart LR
    U[用户 User] --> R[角色 Role]
    R --> P[权限 Permission]
```

## 它在访问控制主线中负责什么

当人员经常入职、转岗、离职时，逐个给用户配置权限会变得难以维护。**RBAC 在用户和权限之间增加“角色”这一层，把权限先交给岗位角色，再把角色分配给用户。**

| 定位 | RBAC 在这里的答案 |
| --- | --- |
| 要防的风险 | 人员变动导致逐用户授权遗漏、权限膨胀或职责冲突 |
| 主要交付 | 按岗位职责统一管理权限，并支持最小权限和职责分离 |
| 依赖/边界 | 依赖角色设计、分配和回收流程正确；不自动替代认证，也不天然适合所有细粒度动态规则 |
| 在主线中的位置 | 它是 DAC/MAC 的并列策略模型；访问控制到这里解决“权限依据什么规则分配”，下一模块继续解决请求经过网络时怎样被控制、检测和保护 |

## 为什么企业系统常用 RBAC

人员会变动，但岗位职责相对稳定。把权限绑定在角色上，员工入职、转岗、离职时主要调整其角色关系，减少逐用户维护成本。

RBAC 还能表达：

- 角色层次；
- 互斥角色/职责分离；
- 用户或角色的基数等约束。

关于“父角色/子角色谁继承谁”的说法容易因教材或实现定义不同而混淆，考试时应按题目给出的角色层次方向判断，不死背“子继承父”一句话。

## 考试怎么认

- 属主决定 → DAC；
- 标签强制 → MAC；
- 岗位角色承载权限 → RBAC。

## 为什么访问控制之后还不能停

认证与访问控制已经能回答：**“你是谁”和“你能对哪个资源做什么”。** 但一次真实请求在到达资源之前，还可能穿过互联网、内部网段、不同信任域和网络设备。权限配置完全正确，也不能自动阻止不该进入的流量、发现混在正常连接中的攻击，或防止通信内容在不可信链路上被窃听和篡改。

所以接下来不是换一种授权模型，而是切换问题层次：**从“主体与资源之间的权限关系”进入“请求在通信路径上怎样被控制、检测和保护”。** 先读 [[网络安全-从漏洞威胁到安全措施]] 建立网络模块入口，再进入 [[防火墙]] 等具体机制。

> [!question] 自测
> 1. 为什么组织频繁换人时 RBAC 通常比逐用户授权更易维护？
>
> > [!answer]- 第 1 题答案与解析
> > **答案**：权限绑定在相对稳定的角色上，人员变化时主要调整用户与角色的关系。
> > **解析**：这减少了逐用户逐权限修改的数量和遗漏风险。
>
> 2. 职责分离为什么可以通过互斥角色表达？
>
> > [!answer]- 第 2 题答案与解析
> > **答案**：把存在利益冲突的职责设计为不能同时分配给同一用户的角色。
> > **解析**：例如申请与审批可设置为互斥角色，避免同一人独立完成相互制约的操作。
