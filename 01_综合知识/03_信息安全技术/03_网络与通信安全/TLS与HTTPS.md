# TLS 与 HTTPS：浏览器怎样建立可信的加密通道

> [!summary]- 快速复习卡片（学完再看）
> **作用/定位**：HTTPS 用 TLS 为 HTTP 建立受保护的通信通道。
> **核心结论**：证书用于验证服务器身份，握手协商参数并导出会话密钥，后续数据通常用对称加密高效保护。
> **题干怎么认**：证书链、主机名校验、握手、会话密钥、443。
> **易错点**：HTTPS 不等于网站业务一定可信；现代 TLS 也不等于“永远用服务器公钥直接加密会话密钥”。

## 打开网站时，怎样确认对方身份并保护通信

小林在浏览器中打开银行网站时，首先要确认连接的确实是银行服务器；登录密码和转账内容在途中还不能被旁人看见或偷偷修改。

**HTTPS 用 TLS 先验证服务器身份，再为浏览器和网站建立一条加密且能检查篡改的通信通道。**这依赖浏览器正确验证证书，也依赖服务器妥善配置协议和密钥。地址栏显示 HTTPS，只能说明这段通信受到保护，不能证明网站业务一定合法或应用代码没有漏洞；通道建好后，应用仍要防 SQL 注入、XSS 等攻击。

## HTTPS 是 HTTP 运行在 TLS 保护之上

传输层安全协议（Transport Layer Security，TLS）为应用通信提供机密性、完整性，并在常见 HTTPS 场景中认证服务器身份。客户端证书是可选机制，不是所有 HTTPS 连接都进行双向认证。

## 先用五步看懂浏览器怎样建立安全通道

先不记报文名和算法。假设小林在浏览器中打开银行网站，一条 HTTPS 连接可以先理解为下面五步：

1. **浏览器先打招呼**：它告诉服务器自己支持哪些安全方案，并提供建立新连接所需的信息。
2. **服务器亮出身份证明**：服务器返回选择结果和数字证书，证明“这个公钥对应当前网站”。
3. **浏览器核验证明**：浏览器检查证书是否来自信任的签发链、网站名称是否匹配、证书是否仍在有效期内；核验失败就不应把对方当成目标网站。
4. **双方算出本次连接专用的会话密钥**：双方依据协商信息分别得到相同的临时密钥，同时确认前面的握手内容没有被替换。
5. **再传真正的网页数据**：后续 HTTP 请求和响应使用会话密钥进行高效保护，窃听者难以读懂内容，篡改也能被发现。

所以，HTTPS 不是“拿证书直接加密整段网页”。**证书主要帮助浏览器确认服务器身份，握手负责协商并导出会话密钥，会话密钥再保护大量 HTTP 数据。**下面的正式术语只是把这五步写得更精确。

## 参与对象

- 客户端与服务器：协商协议参数和临时会话密钥。
- 服务器证书与证书颁发机构（Certificate Authority，CA）信任链：把服务器身份和公钥绑定起来。
- 握手协议：协商版本、算法、密钥并验证握手。
- 记录协议：使用会话密钥保护后续应用数据。

## 现代握手的共同逻辑

~~~mermaid
sequenceDiagram
    participant C as 客户端
    participant S as 服务器
    C->>S: ClientHello：版本、算法、密钥协商参数
    S->>C: ServerHello：选择结果、证书、协商参数与签名
    C->>C: 验证信任链、主机名、有效期和签名
    C->>S: 完成密钥协商并验证握手
    C<->>S: 使用会话密钥保护 HTTP 数据
~~~

1. 双方交换能力和密钥协商参数。
2. 服务器发送证书，并用对应私钥证明身份。
3. 客户端验证证书链、域名、有效期和撤销/策略等条件。
4. 双方由密钥协商结果导出会话密钥，并验证握手消息未被篡改。
5. 后续记录使用高效的对称认证加密保护。

> [!note] 版本边界
> 早期 TLS 可使用 RSA 密钥交换，即客户端用服务器公钥保护预主密钥；现代 TLS 尤其 TLS 1.3 通常使用 (EC)DHE，证书公钥主要用于身份认证和签名。考试若明确给出经典 RSA 流程，再按题干作答。

## TLS 能与不能

- 能降低被动窃听和传输中篡改风险。
- 正确验证证书可抵御冒充服务器的中间人。
- 不能保证网站业务本身可信、服务器没有漏洞或用户不会被钓鱼。
- HTTPS 默认端口通常为 443，但端口号本身不提供安全性。

## 为什么 HTTPS 安全了，应用仍可能被攻击

TLS 保护的是**请求和响应在通信路径上的传输过程**，它不会判断服务器收到的业务输入是否安全。即使整条 HTTPS 连接完全正常：

- 应用把恶意输入拼进 SQL，仍可能发生 [[SQL注入]]；
- 应用把不可信内容放进浏览器可执行上下文，仍可能发生 [[XSS跨站脚本]]；
- 服务端不能区分合法交互与借用用户身份发出的伪造请求，仍可能发生 [[CSRF跨站请求伪造]]。

所以要牢牢记住：**通信通道安全 ≠ 应用代码安全。** VPN 与 TLS 也不是谁替代谁：VPN 更偏受保护的网络/逻辑通道，TLS/HTTPS 更直接保护具体应用连接。

## 考试怎么认

- 证书 → 认证服务器身份和公钥。
- 握手 → 协商参数、密钥并验证双方握手状态。
- 大量业务数据 → 对称会话密钥。
- “TLS 永远用服务器公钥加密会话密钥”是过时的绝对说法。

## 自测

1. HTTPS 为什么不直接用服务器公钥加密全部 HTTP 数据？

> [!answer]- 第 1 题答案与解析
> **答案**：公钥密码计算成本较高；握手完成后通常导出高效的对称会话密钥保护大量业务数据。
> **解析**：证书/公钥主要解决身份认证和密钥协商相关问题，对称密钥负责数据面高效保护。

2. 客户端验证服务器证书时，为什么不能只检查“签名有效”？

> [!answer]- 第 2 题答案与解析
> **答案**：还要检查信任链、主机名/身份、有效期、用途和必要的状态信息。
> **解析**：签名有效不等于该证书适合当前网站和当前时间。

3. HTTPS 能否保证网站业务本身可信？

> [!answer]- 第 3 题答案与解析
> **答案**：不能。它保护通信通道和身份验证条件，不保证服务器没有业务漏洞、内容不欺诈或用户不会被钓鱼。
> **解析**：通道安全与业务安全是不同层面的目标。
