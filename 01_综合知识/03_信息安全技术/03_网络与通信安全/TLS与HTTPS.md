# TLS 与 HTTPS：浏览器怎样建立可信的加密通道

## 先定位：HTTPS 是 HTTP 运行在 TLS 保护之上

TLS 为应用通信提供机密性、完整性，并在常见 HTTPS 场景中认证服务器身份。客户端证书是可选机制，不是所有 HTTPS 连接都进行双向认证。

## 参与对象

- 客户端与服务器：协商协议参数和临时会话密钥。
- 服务器证书与 CA 信任链：把服务器身份和公钥绑定起来。
- 握手协议：协商版本、算法、密钥并验证握手。
- 记录协议：使用会话密钥保护后续应用数据。

## 现代握手的共同逻辑

~~~mermaid
sequenceDiagram
    participant C as 客户端
    participant S as 服务器
    C->>S: ClientHello：版本、算法、密钥协商参数
    S->>C: ServerHello：选择结果、证书、协商参数与签名
    C->>C: 验证信任链、主机名、有效期和签名
    C->>S: 完成密钥协商并验证握手
    C<->>S: 使用会话密钥保护 HTTP 数据
~~~

1. 双方交换能力和密钥协商参数。
2. 服务器发送证书，并用对应私钥证明身份。
3. 客户端验证证书链、域名、有效期和撤销/策略等条件。
4. 双方由密钥协商结果导出会话密钥，并验证握手消息未被篡改。
5. 后续记录使用高效的对称认证加密保护。

> [!note] 版本边界
> 早期 TLS 可使用 RSA 密钥交换，即客户端用服务器公钥保护预主密钥；现代 TLS 尤其 TLS 1.3 通常使用 (EC)DHE，证书公钥主要用于身份认证和签名。考试若明确给出经典 RSA 流程，再按题干作答。

## TLS 能与不能

- 能降低被动窃听和传输中篡改风险。
- 正确验证证书可抵御冒充服务器的中间人。
- 不能保证网站业务本身可信、服务器没有漏洞或用户不会被钓鱼。
- HTTPS 默认端口通常为 443，但端口号本身不提供安全性。

## 考试怎么认

- 证书 → 认证服务器身份和公钥。
- 握手 → 协商参数、密钥并验证双方握手状态。
- 大量业务数据 → 对称会话密钥。
- “TLS 永远用服务器公钥加密会话密钥”是过时的绝对说法。
