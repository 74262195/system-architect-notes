# 数字证书与 PKI：拿到一个公钥，凭什么相信它真属于对方

> [!summary]- 快速复习卡片（学完再看）
> **作用/定位**：数字证书把主体身份与公钥绑定，并由受信任的 CA 签名；PKI 管理证书的申请、签发、验证和失效。
> **核心结论**：CA 用私钥签证书，验证方用 CA 公钥验证签名；但“信任 CA”只是验证链的一部分。
> **题干怎么认**：CA、RA、X.509、证书链、CRL/OCSP、HTTPS 服务器身份。
> **易错点**：证书签名正确 ≠ 一定可以信任当前站点；还要检查链、有效期、名称/身份、用途等条件。

## 它在信息安全主线中负责什么

数字签名能证明“某把私钥产生了这个签名”，但验证者还有一个更早的问题：**手里的公钥究竟属于谁？** 数字证书与 PKI 负责建立和管理“身份 ↔ 公钥”的可信绑定，使签名、加密和 HTTPS 等机制有可信的公钥可用。

| 定位 | 数字证书与 PKI 在这里的答案 |
| --- | --- |
| 要防的风险 | 攻击者用自己的公钥冒充服务器或用户 |
| 主要交付 | 身份与公钥的可验证绑定，以及证书签发、验证、撤销等管理机制 |
| 依赖/边界 | 验证方必须信任相应信任锚并检查证书条件；证书本身不加密业务数据，也不替代权限控制 |
| 在主线中的位置 | 它让签名和公钥加密“知道该相信谁”；下一步的密钥管理处理密钥整个生命周期怎样受控 |

## 拿到一个公钥，为什么仍然不够

公钥本身可以公开，但攻击者也可以发给你一把自己的公钥并谎称“这是服务器的”。数字证书就是给公钥附上一份**可验证的身份证明**。

典型证书包含主体身份、公钥、有效期、颁发者、用途约束以及 CA 的数字签名。

## PKI 中常见角色

- **CA（认证机构）**：签发证书并维护证书状态相关机制。
- **RA（注册机构）**：常负责身份核验和申请受理，具体部署可以有差异。
- **证书库/目录**：发布或保存证书。
- **CRL / OCSP 等状态机制**：帮助判断证书是否已被撤销或失效。

## 验证证书不是只做一步

以 HTTPS 服务器证书为例，验证方通常要考虑：

1. 证书签名能否沿证书链验证到本地信任锚；
2. 证书是否在有效期内；
3. 证书标识是否与正在访问的主机名/身份匹配；
4. Key Usage / Extended Key Usage 等用途是否允许当前用途；
5. 在策略要求时检查撤销/状态信息。

因此：**信任某个根 CA，不代表无条件信任它签名链下的任意证书用于任意站点。**

## 考试怎么认

- “谁签发证书” → CA；“谁先审核身份” → 常见口径是 RA。
- “CA 用哪把钥匙签名” → CA 私钥；验证其签名使用 CA 公钥。
- “证书的核心价值” → 证明“某身份与某公钥”的可信绑定。

> [!question] 自测
> 1. 为什么拿到服务器公钥还不够，还需要数字证书？
>
> > [!answer]- 第 1 题答案与解析
> > **答案**：公钥可以公开，也可以被攻击者替换；证书通过 CA 的签名把公钥与主体身份绑定，供验证方检查。
> > **解析**：证书解决的是“公钥属于谁”，不是“用哪种算法加密数据”。
> 2. CA 签名验证通过后，为什么仍要做主机名和有效期检查？
>
> > [!answer]- 第 2 题答案与解析
> > **答案**：签名有效只说明证书内容未被篡改且由该 CA 签发；它未必适用于当前站点或当前时间。
> > **解析**：证书链、有效期、名称/身份和用途共同构成验证条件。
> 3. CA 和 RA 的常见分工是什么？
>
> > [!answer]- 第 3 题答案与解析
> > **答案**：CA 负责签发证书并维护相关状态机制；RA 常负责身份核验和申请受理。
> > **解析**：具体部署可有差异，做题时按“签发 → CA、审核/受理 → RA”识别。
