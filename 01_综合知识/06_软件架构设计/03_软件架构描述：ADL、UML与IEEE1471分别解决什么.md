# 软件架构描述：ADL、UML 与 IEEE 1471 分别解决什么

> [!summary]- 快速复习卡片（学完再看）
> **ADL**：专门描述软件架构，核心抓 **构件 + 连接子 + 配置**；特别重视连接子。  
> **UML**：通用建模语言，可以表达架构，但它不是专门的架构方法，也不等于 ADL。  
> **4+1 / 多视图**：同一架构从不同关注角度分别表达。  
> **IEEE 1471-2000**：软件密集型系统架构描述的推荐实践/标准语境，强调用多视图回应不同相关方关注。  
> **题干信号 → 第一反应**：构件+连接子+配置 → ADL；通用建模/类图部署图 → UML；逻辑/进程/开发/物理/+1 → 4+1；软件密集型系统架构描述标准 → IEEE 1471。

上一站 [[02_软件架构生命周期：为什么架构工作从需求一直持续到上线后]] 已经知道：设计阶段不仅要“想出架构”，还要把架构模型描述清楚，让后续实现、部署和维护都能理解它。

但“描述架构”不是简单画一张图。

还是看网上商城。假设我们已经决定系统里有：

- 订单服务；
- 库存服务；
- 支付服务；
- 消息中间件。

如果文档只列出这四个名字，别人仍然不知道：

- 订单服务怎样通知库存服务？
- 是直接调用，还是通过消息？
- 哪些构件通过哪种交互机制连接？
- 开发人员、运维人员、业务人员各自要看哪部分？

所以真正的问题是：

> **怎样把“系统有什么、它们怎么连接、不同人分别关心什么”描述清楚？**

教材在这里引出 ADL、多视图、UML 和 IEEE 1471 等不同层次的表达手段。

## 先抓最容易考的 ADL：不只画“零件”，还把“怎么连”当成一等公民

假设商城只有两个构件：

- 订单服务；
- 支付服务。

光知道有这两个“软件块”还不够，因为它们可能：

- 直接调用；
- 通过消息队列通信；
- 通过远程过程调用；
- 通过其他协议交换数据。

也就是说：

> **构件是谁，只回答了一半；构件之间靠什么机制互动，同样属于架构本身。**

这就是 ADL 特别强调“连接子”的原因。

**ADL（Architecture Description Language，体系结构描述语言）**，可以先理解成：

> **专门拿来描述软件架构的一类语言。**

教材给出的核心结构是：

> **ADL 描述 = 构件（Component）+ 连接子（Connector）+ 配置（Configuration）。**

### 构件：系统里的主要软件部分

例如：

- 订单服务；
- 支付服务；
- 库存服务。

它们负责真正的计算、数据处理或业务能力。

### 连接子：这些构件到底“怎么交流”

连接子不是简单的一根线。

它表达的是构件之间的交互机制，例如：

- 过程调用；
- 消息通信；
- 管道；
- 数据访问；
- 事件通知。

所以看到题目强调：

> **ADL 与其他一般建模语言相比，特别重视什么？**

第一反应就是：

> **连接子。**

因为 ADL 不把“构件怎么互联”只当成图上的普通线，而把连接机制本身当成需要明确描述的架构实体。

### 配置：把构件和连接子真正组织成一套架构

只有“订单服务”“支付服务”和“消息通信”这些孤立名字还不是完整系统。

还要说明：

> 哪个构件通过哪个连接子连接到哪个构件，最终整体怎样组织起来。

这就是**配置（Configuration）**。

所以三者可以大白话记成：

> **构件 = 有哪些软件块；连接子 = 它们怎么交流；配置 = 这些块和连接方式最终怎么拼成系统。**

## UML 为什么也会出现在架构描述里

[[UML总览]] 已经学过：UML 是一套通用的软件建模语言。

它可以画：

- 类图；
- 构件图；
- 部署图；
- 序列图；
- 其他结构和行为图。

所以架构设计当然可以借 UML 表达某些结构、交互和部署信息。

但一定要分清：

> **UML = 通用建模语言。**  
> **软件架构 = 要被表达的系统级结构和关系。**

因此：

- UML 可以用来画架构；
- 但“会 UML”不等于“已经完成架构设计”；
- UML 也不等于专门强调“构件 + 连接子 + 配置”的 ADL。

完整 UML 仍回软件工程主事实源：[[UML总览]]、[[UML构件图与部署图]]。本章只解释它为什么出现在架构描述语境里。

## 为什么有了 ADL / UML，还要“多视图”

因为一个大型系统不可能让所有人都看同一种信息。

例如商城：

- 开发人员可能关心模块和代码组织；
- 并发设计人员关心进程、线程和同步；
- 运维人员关心软件部署到哪些结点；
- 业务相关方关心场景能否被系统支持。

所以多视图的核心不是“再发明一套架构”，而是：

> **同一套架构，按不同关注点分别看。**

具体 4+1 的逻辑视图、进程视图、开发视图、物理视图和 +1 场景，放在 [[04_软件架构视图：为什么同一系统需要多个观察视角]]，这里不重复。

## IEEE 1471-2000 又是什么层次

前面几个概念很容易被混成同一类：

- ADL 是一种**架构描述语言类别**；
- UML 是一种**通用建模语言**；
- 4+1 是一种**多视图组织模型**；
- IEEE 1471-2000 则处在**软件密集型系统架构描述的推荐实践/标准**语境。

主教材把 IEEE 1471-2000 放在工业界的多视图架构描述标准中。

大白话理解：

> **它关心的不是“这条线怎么画”，而是“面对不同相关方的不同关注点，怎样组织架构描述，才能把系统说明白”。**

所以做题时如果题干出现：

- IEEE 1471-2000；
- 软件密集型系统；
- 体系结构描述推荐实践；
- 多视图/不同相关方关注；

就不要把它误选成某一种具体 UML 图或某一种 ADL 名称。

## 四个名字到底放在哪一层

| 名称 | 先用大白话记 | 主要解决什么 |
| --- | --- | --- |
| **ADL** | 专门描述架构的语言 | 构件、连接子、配置怎样表达 |
| **UML** | 软件系统通用画图/建模语言 | 用统一图形表达结构和行为，可用于架构，也可用于详细设计 |
| **4+1** | 同一架构分几个角度看 | 多个视图怎样分工并由场景贯穿 |
| **IEEE 1471-2000** | 架构描述的标准/推荐实践语境 | 不同相关方关注怎样通过规范化架构描述得到承接 |

不要背成“四种架构语言”。它们根本不在同一层。

## 考试怎么判断

1. **构件 + 连接子 + 配置** → ADL；
2. 问 ADL 与其他一般建模语言的重要区别 → **特别重视连接子**；
3. 类图、构件图、部署图等通用建模图 → UML；
4. 逻辑/进程/开发/物理/+1 场景 → 4+1；
5. “软件密集型系统体系结构描述推荐实践” → IEEE 1471-2000；
6. 看见 UML 不要直接判断“这是架构方法”；UML 只是表达工具；
7. 看见多视图不要判断“有多套架构”；它们是同一架构的不同观察角度。

## 一句话记住

> **ADL 重点说清“软件块怎样连接”，UML 提供通用建模图，4+1 把同一架构分角度看，IEEE 1471-2000 则站在架构描述标准的层面组织这些关注。**

## 自测

1. 某语言能显式描述构件、连接子以及它们的配置，而且特别强调连接机制，它最符合什么？

> [!answer]- 第 1 题答案与解析
> **答案**：ADL。
> **解析**：构件、连接子、配置是 ADL 的核心描述对象，对连接子的重视还是其重要识别点。

2. “部署图”属于 ADL、UML、4+1 还是 IEEE 1471？

> [!answer]- 第 2 题答案与解析
> **答案**：UML 图。
> **解析**：部署图是 UML 的具体图类型；它可以用于表达架构部署信息，但不等于架构方法或 IEEE 标准。

3. “逻辑视图、进程视图、开发视图、物理视图，并用场景贯穿”对应什么？

> [!answer]- 第 3 题答案与解析
> **答案**：4+1 多视图模型。
> **解析**：这是多视图组织方式，不是 ADL 的三要素。
