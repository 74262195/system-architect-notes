# 软件架构生命周期：为什么架构工作从需求一直持续到上线后

> [!summary]- 快速复习卡片（学完再看）
> **六阶段**：需求 → 设计 → 实现 → 构件组装 → 部署 → 后开发。  
> **核心结论**：架构不是设计阶段画一次图，而是每个阶段都要用架构做不同的事。  
> **需求阶段**：从需求模型走向架构模型，并保持可追踪；Use Case 可作为需求表达入口。  
> **部署阶段**：不仅看软件，还要看结点、硬件拓扑、CPU/内存等资源与质量目标。  
> **易错点**：这六阶段 ≠ ABSD 六子过程；一个讲“架构在哪些生命周期阶段工作”，一个讲“以架构为中心具体怎样开发”。

上一站 [[01_软件架构是什么：为什么需要架构视角]] 已经知道：软件架构解决的是系统主要构件怎样组织、连接和协作的问题。

还是看网上商城。设计阶段已经画好订单、库存、支付服务的协作图，项目却没有停在这张图上：

- 需求变化时，原来的构件划分还成立吗？
- 写代码时，怎样保证实现没有偷偷偏离架构？
- 组装已有构件时，它们的接口和交互方式能不能接上？
- 上线时，这些服务放到哪些结点、需要多少资源？
- 上线后系统扩容、演化、重构时，原有架构怎样继续维护？

这时再问“架构是不是在设计阶段画完图就结束了”，答案就清楚了：**那张图只是当时的方案；从需求到上线后的维护与演化，各阶段都还要用架构处理不同的问题。** 这整段持续工作的历程，就是软件架构生命周期。

大纲把它分成六个阶段：

> **需求阶段 → 设计阶段 → 实现阶段 → 构件组装阶段 → 部署阶段 → 后开发阶段。**

## 1. 需求阶段：先把“要什么”变成“系统准备怎么组织”

需求阶段首先面对的是用户和业务问题，例如：

> 用户要能下单、支付、取消订单；支付结果必须可追踪。

但架构最终要回答的是：

> 这些需求由哪些主要构件承担，它们之间怎样协作？

所以需求阶段的一个核心问题是：**怎样从需求模型走向架构模型，同时还能追得回“这个架构决定到底对应哪条需求”。**

这就是教材强调的“可转换性”和“可追踪性”。

### Use Case 为什么会在这里出现

[[UML用例图]] 很适合先从系统外面表达：

- 谁在使用系统；
- 系统要提供什么功能；
- 系统边界在哪里。

架构阶段并不是重新学习一套 Use Case 语法，而是把它当成一种**需求入口**：先把外部需求说清楚，再逐步映射到架构模型中的构件和关系。

因此这里记住的是：

> **Use Case 负责帮助描述“外部要什么”，架构模型继续回答“内部主要结构怎样承接这些需求”。**

完整用例图知识仍以软件工程里的 [[UML用例图]] 为唯一主事实源。

## 2. 设计阶段：真正把架构结构想清楚、描述清楚

到了设计阶段，重点才集中到：

- 架构模型由哪些元素组成；
- 构件之间怎样连接；
- 怎样描述和分析架构；
- 怎样从不同关注角度组织多个视图；
- 怎样复用已有架构经验。

比如商城已经决定有“订单服务、库存服务、支付服务”，还必须说明：

> 它们到底通过直接调用、消息、管道还是其他机制交互？

这也是为什么后面会学习 [[03_软件架构描述：ADL、UML与IEEE1471分别解决什么]] 和 [[04_软件架构视图：为什么同一系统需要多个观察视角]]。

## 3. 实现阶段：把高层架构真正落成代码，但不能“写着写着变样”

架构模型通常比代码抽象得多。

例如架构里只有一句：

> 订单服务通过消息机制把“订单已创建”通知库存服务。

真正实现时还要决定具体中间件、消息格式、异常处理、配置管理等。

所以实现阶段要解决的是：

> **怎样把高层架构逐步映射、细化成真正可运行的实现，同时保持架构约束。**

教材还把基于架构的开发过程、配置管理、模型转换、构件组装、中间件支持和测试等放在这一阶段讨论。

## 4. 构件组装阶段：已有零件不等于插上就能用

假设商城不从零写支付，而是接入一个已有支付构件。

这时真正的问题不是“有没有这个构件”，而是：

- 它和订单服务怎样互联？
- 它要求的调用协议与系统现有方式一致吗？
- 数据格式、交互假设能不能对上？

所以构件组装阶段，架构模型会继续指导：

1. **构件怎样通过连接子互联**；
2. **怎样发现并处理架构失配。**

这里先知道“连接子”很重要，下一张 [[03_软件架构描述：ADL、UML与IEEE1471分别解决什么]] 会专门解释它。

## 5. 部署阶段：软件已经写好了，还要决定“放哪里跑”

一个分布式系统能运行，不代表随便部署都一样。

比如：

- 订单服务和数据库放得太远，延迟可能变大；
- 某结点 CPU、内存不足，性能会受影响；
- 某个单点部署可能影响可靠性。

因此部署阶段要同时考虑：

- 待部署软件构件之间的互联；
- 硬件拓扑；
- CPU、内存等资源；
- 性能、可靠性等质量目标。

所以架构在部署阶段会提供高层软硬件视图，并帮助比较部署方案。

这里如果需要具体 UML 表达，可以回到 [[UML构件图与部署图]]；但 UML 只是表达工具，不是部署方案本身。

## 6. 后开发阶段：上线了，架构仍然没有退休

系统部署之后，还会发生：

- 维护；
- 功能扩展；
- 架构演化；
- 架构恢复与重建；
- 对已有架构和构件的复用。

例如商城从单体演化到多个服务，或者需要根据现有代码重新恢复系统架构，这些都属于上线后的架构问题。

因此：

> **后开发阶段 = 系统已经运行以后，继续维护、演化、恢复和复用架构。**

## 最容易混：生命周期六阶段和 ABSD 六子过程不是一回事

两套都是“六个”，但问的问题完全不同。

| 比较 | 软件架构生命周期六阶段 | ABSD 六子过程 |
| --- | --- | --- |
| 它在回答什么 | **架构在哪些软件生命周期阶段持续发挥作用？** | **采用基于架构的软件开发方法时，具体怎样推进？** |
| 主线 | 需求→设计→实现→组装→部署→后开发 | 架构需求→架构设计→文档化→复审→实现→演化 |
| 观察角度 | 生命周期阶段 | 开发方法步骤 |
| 能否互相替代 | 不能 | 不能 |

所以看到题目先问：

> **它是在问“整个软件生命周期分到哪里”，还是在问“ABSD 这套方法怎么走”？**

完整 ABSD 放在 [[05_ABSD：如何从架构需求逐步形成可交付架构]]，本卡不重复。

## 考试怎么判断

1. 题目问“软件架构贯穿哪些阶段” → 六阶段：**需求、设计、实现、构件组装、部署、后开发**；
2. 强调需求模型向架构模型转换、可追踪 → **需求阶段**；
3. 强调 ADL、多视图、架构模型设计分析 → **设计阶段**；
4. 强调高层架构向代码/实现映射 → **实现阶段**；
5. 强调构件互联、连接子实现、架构失配 → **构件组装阶段**；
6. 强调软硬件映射、结点、资源、部署质量 → **部署阶段**；
7. 强调维护、演化、恢复、重建 → **后开发阶段**；
8. 如果选项出现“架构需求→设计→文档→复审……” → 那是在考 **ABSD**，不要和生命周期混。

## 一句话记住

> **架构不是设计阶段的一张图，而是一条从需求、设计、实现、组装、部署一直延续到上线后演化的系统级主线。**

## 自测

1. “从 Use Case 等需求模型继续建立架构模型，并保持需求到架构的可追踪性”更偏哪个阶段？

> [!answer]- 第 1 题答案与解析
> **答案**：需求阶段。
> **解析**：这里仍在解决需求模型与架构模型的转换和追踪关系。

2. “根据服务器拓扑、CPU/内存和可靠性比较两个上线方案”属于哪个阶段？

> [!answer]- 第 2 题答案与解析
> **答案**：部署阶段。
> **解析**：重点已经是软件构件如何映射到实际运行环境以及部署质量。

3. “架构需求→架构设计→文档化→复审→实现→演化”是不是软件架构生命周期六阶段？

> [!answer]- 第 3 题答案与解析
> **答案**：不是。
> **解析**：这是 ABSD 六子过程。生命周期六阶段是需求、设计、实现、构件组装、部署、后开发。
