# 软件架构复用：为什么复用不只是复制代码

> [!summary]- 快速复习卡片（学完再看）
> **复用不是复制旧代码**，而是把已经验证过的需求、架构、测试和工程经验等资产，在新系统中再次选择、定制和使用。  
> **机会复用**：开发过程中发现可用资产再复用；**系统复用**：开发前就规划复用。  
> **基本过程**：构造/获取资产 → 管理资产 → 选择、定制、组装使用。  
> **做题第一动作**：先判断题目问“何时决定复用”“复用什么”，还是“处于复用过程哪一步”。

上一站 [[04_软件架构风格：如何用构件与连接件识别典型结构]] 已经知道，很多系统会反复出现稳定的组织方式。接下来很自然会问：

> **既然一些需求、架构和工程经验已经验证过，为什么每个新项目还要从零开始？**

软件架构复用就是把这些成熟成果变成**可管理、可检索、可定制、可再次使用的资产**。

## 机会复用和系统复用

区别只看“什么时候决定复用”：

- **机会复用**：项目已经在做，碰到合适资产就拿来用；
- **系统复用**：项目开始前就规划哪些需求、架构、构件、测试等要复用。

不要按“复用多少”来区分。

## 能复用什么：远不止代码

主教材列出 10 类可复用资产，考试不必逐段背解释，但要知道范围：

| 资产 | 大白话 |
| --- | --- |
| 需求 | 以前已经验证过的需求 |
| 架构设计 | 已验证的整体结构 |
| 元素 | 构件、类、接口等 |
| 建模与分析 | 性能分析、容错方案、负载均衡模型等 |
| 测试 | 用例、数据、工具、计划、过程 |
| 项目规划 | 成本、预算、进度、团队经验 |
| 过程/方法/工具 | 规范、标准、开发方法和工具环境 |
| 人员 | 熟悉产品线和领域的人才经验 |
| 样本系统 | 已投产系统作为演示或工程原型 |
| 缺陷消除 | 已知缺陷及其处理经验 |

所以“复制一个代码仓库”只是复用的一小部分。

## 三阶段：资产怎样真正进入新系统

**构造 / 获取**：先形成可靠、可广泛使用、易理解、易修改的资产。

**管理**：把资产放进可维护的资产库。这里最关键的是**分类和检索**——有资产但找不到，等于没有形成有效复用能力。

**使用**：根据新需求检索资产，再进行选择、修改、扩展、配置和组装集成。复用不要求原封不动照搬。

一句话：

> **先有好资产 → 再让人找得到 → 最后按新需求改一改、拼起来。**

## 为什么值得复用

教材强调的价值包括：减少开发工作和时间、降低成本、提高生产率与质量、改善互操作性，并让维护更容易。

考试如果只问“为什么复用”，不要把答案缩成“少写代码”。

## 最容易错的两个点

**系统复用 ≠ 不允许修改。** 规划复用后仍然可以定制、扩展和配置。

**资产库 ≠ 只负责存文件。** 管理阶段还必须支持分类、检索、浏览和维护。

## 自测

> [!question] 自测
> 1. 项目开发到一半才发现已有性能分析模型可以直接利用，属于机会复用还是系统复用？
>
> > [!answer]- 第 1 题答案与解析
> > **机会复用。** 决定复用发生在开发过程中。
>
> 2. 企业已经积累大量构件，但开发人员经常“不知道有什么，也搜不到”，首先是哪一阶段没做好？
>
> > [!answer]- 第 2 题答案与解析
> > **管理可复用资产。** 关键缺口是分类和检索。
>
> 3. 找到旧构件后修改接口、调整配置再集成，还算复用吗？
>
> > [!answer]- 第 3 题答案与解析
> > **算。** 使用阶段本来就包含选择、定制和组装。
