# NoSQL 体系框架与适用场景

> [!summary] 快速复习卡片
> **作用/定位**：在知道 NoSQL 有哪些类型后，再看一套 NoSQL 系统从底层存储到上层接口怎样分层。
> **核心结论**：教材框架自下而上为**数据持久层 → 数据分布层 → 数据逻辑模型层 → 接口层**。
> **题干怎么认**：问四层次序先找最底层“数据怎么持久化”，最上层“应用怎样访问”。
> **易错点**：NoSQL 适用场景取决于数据与访问模式，不是“数据量大就一定应该换 NoSQL”。

教材用四层框架帮助理解 NoSQL 系统：

1. **数据持久层**：数据最终怎样保存在内存、磁盘或其他介质中。
2. **数据分布层**：数据如何跨节点分布、复制或组织。
3. **数据逻辑模型层**：对上层呈现键值、文档、列、图等逻辑模型。
4. **接口层**：向应用提供访问入口。

这条链可以记成：**先存得下 → 再分得开 → 再组织成模型 → 最后给程序接口。**

## 什么场景更可能考虑 NoSQL

当系统更看重以下需求时，可以评估 NoSQL：
- 数据结构变化快，不适合固定关系模式；
- 数据规模和访问吞吐需要水平扩展；
- 数据天然是文档、图、键值等模型；
- 对分布式、高可用有强需求，且业务允许相应一致性/事务模型权衡。

如果业务强依赖复杂关系查询、严格事务约束和成熟 SQL 生态，关系数据库仍可能更合适。架构选择应从需求出发，而不是追求技术标签。

## 自测

1. NoSQL 四层框架里，直接面向应用程序的一般是哪一层？

> [!answer]- 第 1 题答案与解析
> **答案**：接口层。
> **解析**：接口层向应用提供访问入口；底层持久化、分布和逻辑模型由它向下屏蔽。

2. 一个业务数据量很大，但强依赖复杂关系查询、严格事务约束和成熟 SQL 工具链，能只凭“量大”就选 NoSQL 吗？

> [!answer]- 第 2 题答案与解析
> **答案**：不能。
> **解析**：NoSQL 选择要看数据模型、访问模式、扩展和一致性权衡；题干中的约束反而可能使关系数据库更合适。

本章收口：先按数据模型识别 NoSQL 类型，再按访问和一致性需求判断是否适用，不能把“高并发/大数据”当作唯一条件。
