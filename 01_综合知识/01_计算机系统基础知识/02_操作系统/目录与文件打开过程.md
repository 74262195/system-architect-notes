# 目录与文件打开：open 怎样从路径得到文件描述符

> [!summary] 快速复习卡片
> **作用/定位**：`open()` 把磁盘上“按路径命名的文件”，转换成进程可以反复使用的文件描述符。
> **核心链路**：解析路径 → 找到 inode → 建立打开文件记录 → 写入进程文件描述符表 → 返回 fd。
> **三个层次**：inode 描述文件本身；打开文件记录描述这一次打开；fd 是进程描述符表中的编号。
> **易错点**：fd 不直接等于 inode；当前偏移属于打开记录，而不是文件唯一的永久属性。

## 为什么找到 inode 后还不能直接读

前一站 [[FCB与inode]] 已经解决了：

> 怎样根据文件名找到 inode，并由 inode 找到文件的数据块？

但是，程序打开文件时还需要保存**这一次怎样使用文件**，例如：

- 以只读还是读写方式打开；
- 当前已经读到什么位置；
- 有多少运行时引用正在使用这次打开。

这些信息不适合写入 inode。因为 inode 描述的是文件本身，而同一个文件可以被多个进程同时打开，每次打开的方式和读取位置可能不同。

因此，找到 inode 后，内核还必须建立一层**打开文件记录**，然后才能给进程返回文件描述符。

## 参与对象

| 对象 | 负责什么 |
| --- | --- |
| 目录项 | 在目录中保存“文件名 → inode 号” |
| inode | 保存文件属性和数据块定位信息 |
| 打开文件记录 | 保存本次打开的方式、当前偏移以及对 inode 的引用 |
| 进程文件描述符表 | 保存“fd → 打开文件记录”的对应关系 |
| 文件描述符 fd | 进程描述符表中的一个编号 |

## 一次 open 完整发生了什么

假设程序执行 **int fd = open("report.txt", O_RDONLY);**

其中，`report.txt` 是路径，`O_RDONLY` 表示只读；`fd` 是调用成功后内核返回的结果。

~~~mermaid
flowchart LR
    A["调用 open"] --> B["解析路径"]
    B --> C["找到 inode"]
    C --> D["建立打开记录"]
    D --> E["登记并返回 fd"]
~~~

### 1. 解析路径，找到 inode

内核从当前目录开始查找 `report.txt`。它在当前目录的数据中找到相应目录项，例如：

`report.txt → inode 105`

随后，内核根据 inode 号取得 inode 105 的元数据。

如果路径是 `/home/yan/report.txt`，内核会从根目录开始，依次查找 `home`、`yan`、`report.txt`，并检查沿途目录是否允许搜索。

### 2. 检查这次打开是否合法

内核结合 inode 和 `open()` 传入的打开标志，检查：

- 目标是否为可按此方式打开的文件类型；
- 当前进程是否具有相应权限；
- 只读、只写、追加等打开方式是否允许。

检查失败，`open()` 返回错误，不会得到可用的 fd。

### 3. 建立打开文件记录——这是最容易漏掉的一步

检查通过后，内核为**这一次打开**建立打开文件记录。可以把它简化为：

| 打开文件记录中的信息 | 本例 |
| --- | --- |
| 指向的文件 | inode 105 |
| 打开方式 | 只读 |
| 当前偏移 | 0 |
| 引用计数 | 1 |

这一步把“磁盘上长期存在的 inode”转换成了“进程运行期间的一次打开状态”。

> [!important] inode 与打开记录的区别
> inode 说明“这是哪个文件、数据在哪里”；打开文件记录说明“这一次怎样打开、现在读到哪里”。

### 4. 在进程文件描述符表中登记

每个进程都有自己的文件描述符表。假设表项 0、1、2 已经被标准输入、标准输出和标准错误占用，内核找到空闲的第 3 项：

| fd | 指向 |
| ---: | --- |
| 0 | 标准输入的打开记录 |
| 1 | 标准输出的打开记录 |
| 2 | 标准错误的打开记录 |
| 3 | `report.txt` 的打开记录 |

于是，内核把表项编号 **3** 返回给程序，也就是 **fd = 3**。

所以 fd 不是 inode 号，也不是磁盘地址，而是：

> **当前进程文件描述符表中的表项编号。**

## read 为什么只需要 fd

程序随后执行 **read(3, buffer, 100)**，表示最多读取 100 字节，并放入 `buffer`。

~~~mermaid
flowchart LR
    A["fd 3"] --> B["描述符表"]
    B --> C["打开文件记录"]
    C --> D["inode"]
    D --> E["数据块"]
~~~

内核会：

1. 用 fd 3 查当前进程的文件描述符表；
2. 找到对应的打开文件记录；
3. 读取其中的当前偏移和打开方式；
4. 经由 inode 的块映射找到相应数据块；
5. 把数据复制到程序提供的 `buffer`；
6. 将打开文件记录中的当前偏移向后推进。

这就是为什么第一次需要用路径执行 `open()`，后续 `read()` 不必重复解析路径。

## close 关闭的是什么

执行 `close(3)` 时，内核先清除当前进程描述符表中的第 3 项，并减少打开文件记录的引用计数。

当没有引用继续使用该打开记录时，内核可以释放这条运行时记录；但文件的目录项、inode 和数据块仍然存在。关闭文件不等于删除文件。

> [!note] 关于“共享打开记录”
> 普通地再次调用 `open()`，通常会形成新的打开实例，因而可以有独立的当前偏移。`dup()`、`fork()` 等情况则可能让多个 fd 共享同一打开文件记录和当前偏移。理解基本三层关系即可，不必在本卡深挖系统实现。

## 考试只需抓住的层次

| 题目问什么 | 对应对象 |
| --- | --- |
| 文件名怎样关联文件 | 目录项 |
| 文件属性、数据块位置 | FCB / inode |
| 本次打开方式、当前偏移 | 打开文件记录 |
| 进程拿什么调用 read/write | 文件描述符或句柄 |

## 一句话记住

> **open 先用路径找到 inode，再为这次打开建立打开记录，最后让进程的一个 fd 指向该记录并把 fd 返回。**

## 自测

### 1. 找到 inode 后，为什么不能立即把 inode 号当作 fd 返回？

> [!answer]- 答案与解析
> inode 描述文件本身；内核还要建立本次打开的方式、当前偏移等运行时状态，并在当前进程的文件描述符表登记一项。返回给进程的 fd 是这项打开记录的入口，不是 inode 号。

### 2. 当前读取偏移保存在 inode 中还是打开文件记录中？

> [!answer]- 答案与解析
> 保存在本次打开对应的打开文件记录中。相同文件可以有多个打开实例，各自维护偏移；`dup()`、`fork()` 等特定情况可能共享同一打开记录，正文已单独标出。

### 3. `read(fd, ...)` 怎样最终找到磁盘数据块？

> [!answer]- 答案与解析
> 内核从 fd 查进程描述符表，找到打开文件记录；再由该记录关联的 inode 和文件块映射找到数据块，读取内容并复制给程序。
