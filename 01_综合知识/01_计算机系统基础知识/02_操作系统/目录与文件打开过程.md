# 目录与文件打开：从路径 /work/report.txt 到真正的数据块，中间发生了什么

## 先定位：目录不是“装文件内容的盒子”，而是帮助按名字定位文件

用户输入：

> /work/report.txt

系统不能直接把这个字符串交给磁盘。

它必须一层层解析目录，找到这个名字对应的文件控制信息。

## 路径解决什么

- **绝对路径**：从根目录开始定位；
- **相对路径**：从当前工作目录开始定位。

不管哪一种，本质都是：

> **沿目录层次把名字逐级解析到目标文件。**

## 目录项大致做什么

在经典模型中，目录项保存：

> **名称 → 文件标识/控制结构位置**

例如 Unix 风格可以理解成：

> 文件名 → inode 号。

然后 inode 再告诉系统文件元数据和数据块如何定位。

## 为什么 open 以后还要返回一个“句柄”

系统成功找到文件后，应用通常不会每次 read 都重新从完整路径查一遍。

open 会建立一次“已打开文件”的运行时状态，并给进程一个较短的引用，例如文件描述符/句柄。

后续：

- read；
- write；
- seek；

都可以通过这个引用找到已打开文件状态。

## 当前读写位置为什么是运行时状态

同一个文件可以被不同进程同时打开。

A 可能已经读到第 1000 字节，B 可能刚开始。

因此“当前读到哪里”不是文件永久内容本身，而是：

> **某次打开/访问过程的状态。**

## 整条链

```mermaid
flowchart LR
    A["路径"] --> B["逐级查询目录"]
    B --> C["找到 FCB / inode"]
    C --> D["建立打开文件状态"]
    D --> E["返回句柄 / 文件描述符"]
    E --> F["read / write"]
    F --> G["定位实际数据块"]
```

## 一句话记住

> **路径帮你找到文件；open 把这次访问变成运行时对象；后续读写通过句柄继续，不必每次重新解析完整路径。**
