# 进程三态：没在运行时，为什么还要分就绪与阻塞

> [!summary] 快速复习卡片
> **作用/定位**：进程三态描述“现在有没有 CPU、如果没有是在等 CPU 还是等事件”，是理解调度和阻塞的基础。
> **核心结论**：就绪=只差 CPU；运行=正在占用 CPU；阻塞=还在等 I/O/资源/事件，即使此刻给 CPU 也不能继续。
> **经典题型怎么做 / 题干怎么认**：时间片到/被抢占：运行→就绪；等 I/O：运行→阻塞；I/O 完成：阻塞→就绪；调度选中：就绪→运行。
> **易错点 / 考试重点**：阻塞解除后通常先回就绪态，不是直接跳到运行态。

## 先定位：三态模型按“能否运行、是否占有 CPU”分类

| 状态 | 是否具备运行条件 | 是否占有 CPU | 典型场景 |
| --- | --- | --- | --- |
| 运行 | 是 | 是 | 正在执行指令 |
| 就绪 | 是 | 否 | 只等调度获得 CPU |
| 阻塞/等待 | 否 | 否 | 等 I/O、锁、消息或事件 |

核心判断：**就绪只缺 CPU；阻塞即使立即给 CPU 也无法继续。**

## 状态转换由什么触发

~~~mermaid
stateDiagram-v2
    [*] --> 就绪
    就绪 --> 运行: 调度
    运行 --> 就绪: 时间片到或被抢占
    运行 --> 阻塞: 等待事件
    阻塞 --> 就绪: 事件完成
    运行 --> [*]: 结束
~~~

- 就绪 → 运行：调度器选中并分配 CPU。
- 运行 → 就绪：时间片用完或被更高优先级任务抢占，进程仍具备运行条件。
- 运行 → 阻塞：进程主动等待尚未满足的条件。
- 阻塞 → 就绪：条件满足，只是重新获得竞争 CPU 的资格。
- 运行 → 结束：正常退出或被终止。

> [!warning] 经典陷阱
> I/O 完成通常使“阻塞 → 就绪”，不是直接进入运行；是否马上运行还取决于调度。三态是简化模型，现实系统还可能有创建、终止、挂起等状态。

## 与调度、PCB 的关系

状态保存在 [[进程控制块PCB]] 中，状态变化伴随队列迁移。[[进程调度]] 从就绪队列选择下一运行者；阻塞队列中的进程尚不参加 CPU 竞争。

## 自测

1. 等待磁盘数据的进程为什么不是就绪态？
2. 时间片到后为什么是运行 → 就绪？
3. 事件完成后为什么通常不是阻塞 → 运行？
