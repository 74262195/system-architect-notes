# TCP 可靠传输：底层会丢包、乱序，接收方为什么仍能得到有序字节流

## 先定位：可靠不是网络不出错

TCP 属于传输层，向应用提供**可靠、有序、无重复的字节流**。IP 仍可能丢包、重复、乱序或损坏；TCP 的作用是让通信两端发现这些问题并恢复。

可靠性不是某一个字段单独完成的，而是一条闭环：

> **编号 → 检测 → 确认 → 未确认时重传 → 按序交付。**

## 五个参与机制

| 机制 | 负责什么 |
| --- | --- |
| 校验和 | 检测报文段在传输中是否损坏 |
| 序号 | 标明数据位于字节流的什么位置 |
| 确认号 ACK | 告诉发送端下一个期望收到的字节 |
| 重传 | 超时或出现丢失迹象时再次发送 |
| 滑动窗口 | 允许多段数据连续在途，提高链路利用率 |

TCP 序号按**字节位置**编号，不是简单的“第几个包”。

## 用一段数据走完整过程

假设发送端要发送序号 1001～1500 的 500 字节：

1. 发送端保存这段未确认数据并启动重传计时；
2. 接收端检查校验和，确认数据无误；
3. 若 1001～1500 已连续收到，接收端返回 ACK=1501；
4. ACK=1501 表示“下一字节希望从 1501 开始”，也意味着此前连续字节已确认；
5. 发送端收到有效 ACK 后，从重传队列移除相应数据，窗口向前滑动。

~~~mermaid

    participant S as 发送端
    participant R as 接收端
    S->>R: 字节 1001～1500
    R-->>S: ACK=1501
    Note over S: 移除已确认数据<br/>窗口向前滑动
~~~

## 中间丢了一段会怎样

假设发送端连续发出三段，第二段丢失，第三段先到：

- 接收端发现中间有缺口，不能把后面的字节当成“已经连续收到”；
- 经典累计确认模型会继续确认缺口起点；
- 发送端可能因重传计时器超时而重发；
- 连续收到多个重复 ACK 时，也可能触发快速重传；
- 缺失数据补齐后，接收端才能把连续字节流向上交付，确认号继续前进。

是否缓存乱序段、是否使用选择确认等属于实现和选项机制；考试没有额外条件时，先按累计确认的经典模型判断。

## 滑动窗口为什么重要

“停等”做法每发一段就等待 ACK，往返时间较大时链路会长时间空闲。

滑动窗口允许发送端在许可范围内保留多份未确认数据。ACK 返回后，窗口边界向前移动，新的字节获得发送资格。

> **窗口解决效率，序号和 ACK 让窗口移动仍然不会失去可靠性。**

## 易错点

- ACK=1501 不是“已收到 1501”，而是“下一步期望 1501”；
- 校验和只能帮助发现差错，不能独自完成纠错和重传；
- TCP 保证的是有序字节流，不保留应用每次写入的消息边界；
- 收到重复 ACK 不等于 ACK 机制失效，它可能是在报告中间仍有缺口。

## 一句话记住

> **序号定位字节，ACK 推进窗口，计时与重复 ACK 暴露丢失，重传补齐缺口，最后才按序交给应用。**
