# TCP 与 UDP：同样把数据交给应用，为什么还要两种传输方式

> [!summary] 快速复习卡片
> **TCP**：面向连接，向应用提供可靠、有序的**字节流**；靠确认、重传、排序等机制处理底层丢失和乱序。
> **UDP**：无连接，以**数据报**为单位；协议本身不提供 TCP 同等级别的确认、重传和按序保证。
> **题干判断**：强调可靠、完整、顺序 → 先想 TCP；强调简单、低控制开销、应用自己处理丢失 → 先想 UDP。
> **易错点**：不要背成“TCP 一定慢、UDP 一定快”；这是可能的效果，不是定义。
> **边界**：TCP 不保留应用每次写入的消息边界；UDP 保留数据报边界。

## 先看同一台主机上的两种业务需求

上一站 [[IPv6与IPv4过渡]] 已经把数据送到目标主机。

现在有两个应用：

- 下载程序安装包：少一段、顺序错了都可能损坏文件；
- 实时语音：某一小段晚了几秒，再补回来可能已经没价值。

这两个业务都要“传数据”，但要求明显不同：

> **一个更在意完整和顺序，一个更在意简单、及时，并愿意自己决定丢失后怎么办。**

因此传输层提供两种典型服务风格：**TCP** 和 **UDP**。

## TCP：底层会丢会乱，但尽量给应用一条可靠有序的字节流

TCP 的“可靠”不是说网络从此不会丢包，而是 TCP 自己会做额外工作，例如：

1. 建立通信状态；
2. 对数据进行顺序管理；
3. 接收方确认已收到的数据；
4. 必要时重传；
5. 最终按正确顺序把字节交给应用。

所以做题时看到“可靠、有序、面向连接、字节流”，优先想到 TCP。

当前减负到这里即可，不继续展开三次握手、四次挥手、TIME_WAIT 和具体拥塞控制算法。

## UDP：把一份份数据报交给 IP，更多取舍留给应用

UDP 不建立 TCP 那样的连接状态，也不在协议本身提供同等级别的确认、重传和排序。

应用交给 UDP 一个数据报，UDP 就按一个独立数据报交给 IP。

这并不等于“用了 UDP 的应用一定不可靠”。应用完全可以自己增加重试、确认等逻辑，只是这些不是 UDP 协议本身提供的保证。

## 一张表做题足够

| 判断点 | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接 | 无连接 |
| 可靠有序 | 协议提供 | 协议本身不提供同等级保证 |
| 数据形式 | 字节流 | 数据报 |
| 控制机制 | 较多 | 较简单 |

“某应用常用 TCP/UDP”是典型使用方式，不要把应用协议和传输协议绑死成绝对规则。

## 一句话收口

**TCP 用更多控制换取可靠、有序的字节流；UDP 保持简单的数据报传输，把更多可靠性和时效性取舍留给应用。**
