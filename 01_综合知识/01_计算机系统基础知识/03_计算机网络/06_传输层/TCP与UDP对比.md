# TCP 与 UDP：数据已经送到目标主机，为什么传输层还要提供两种完全不同的方式

> [!summary] 快速复习卡片
> **TCP**：面向连接，提供可靠、有序的字节流；传输层会承担确认、重传、流量控制等更多工作。
> **UDP**：无连接，以一个个数据报为单位发送；协议本身不提供 TCP 同等级别的可靠、有序保证，控制更简单。
> **不要死背“TCP 慢、UDP 快”**：这是可能出现的效果，不是定义。真正区别是连接、可靠机制和数据形式。
> **边界**：TCP 不保留应用每次写入的消息边界；UDP 保留数据报边界。

## 网络层已经把数据送到服务器，为什么还没结束

上一站 [[IPv6与IPv4过渡]] 把网络层收口了。

现在假设主机 A 已经能通过 IP 把数据送到服务器 S。

但不同应用对“怎么送”有完全不同的要求。

先看两个场景。

### 场景一：下载一个程序安装包

假设文件有 100 MB。

如果中间丢了几 KB，或者数据顺序乱了，这个文件可能直接损坏。

应用希望传输层帮它保证：

- 缺了的数据能发现并补回来；
- 接收端得到的数据顺序正确；
- 双方建立明确的通信状态；
- 接收方来不及处理时，发送方不要无限猛灌。

这类需求自然适合 **TCP**。

### 场景二：实时语音正在播放

假设某一小块语音已经迟到了 3 秒。

这时“费很大劲把三秒前那一小块补回来”可能已经没有多大价值，因为实时播放早就往后进行了。

某些实时或简单查询场景更愿意让传输层保持简单，把“是否重试、过期数据还要不要、怎么容错”交给应用自己决定。

这类服务风格就是 **UDP** 更典型的使用场景。

所以 TCP 和 UDP 不是“好协议 vs 坏协议”，而是：

> **应用对可靠性、时效性和控制方式的需求不同，传输层提供两种典型服务风格。**

## TCP 的“可靠”到底不是一句口号

TCP 要提供可靠、有序传输，意味着它需要做额外工作。

你现在只跟住最核心的动作，不展开三次握手和拥塞算法：

1. 双方先建立连接状态；
2. 发送的数据带有顺序相关信息；
3. 接收方对收到的数据进行确认；
4. 应该到但没确认的数据可以重传；
5. 接收端按正确顺序把字节交给应用；
6. 还有流量控制等机制避免接收方被淹没。

所以所谓“可靠”不是网络从此绝不丢包，而是：

> **底层即使可能丢、乱，TCP 会用确认、重传、排序等机制尽量向应用提供可靠有序的字节流。**

## UDP 为什么简单

UDP 不先建立 TCP 那样的连接状态，也不在协议本身提供同等级别的：

- 确认；
- 重传；
- 按序恢复；
- 流量控制。

应用交给 UDP 一个数据报，UDP 就按数据报形式交给 IP 去发送。

所以它更像：

> **“我负责把这一份数据报交给网络，至于丢没丢、要不要补、晚到了还值不值得要，由上层需求自己决定。”**

这不等于使用 UDP 的应用一定“不可靠”。

应用完全可以在 UDP 之上自己实现确认、重试或其他机制，只是这些不是 UDP 协议本身提供的 TCP 式保证。

## “字节流”和“数据报”为什么值得单独理解

假设应用连续调用三次发送：

- 第一次写入“AAA”；
- 第二次写入“BBB”；
- 第三次写入“CCC”。

### TCP

TCP 把数据看成连续的字节流。

接收方最终看到的是有序字节序列，但不能假设“发送端调用三次写入，接收端就一定刚好三次分别读到 AAA、BBB、CCC”。

所以：

> **TCP 保证字节顺序，不保留应用写入时的消息边界。**

### UDP

每次 UDP 发送形成一个独立数据报。

接收方按一个个数据报接收，数据报边界保留。

所以：

> **UDP 是数据报服务。**

这是考试概念题很容易混的地方。

## 为什么不能只背“TCP 慢，UDP 快”

TCP 的确认、重传、连接状态等确实带来额外控制开销；UDP 协议本身更简单。

但真实应用性能还受到：

- 网络质量；
- 应用实现；
- 数据量；
- 丢包率；
- 应用在 UDP 上自己做了多少可靠控制

等因素影响。

所以考试里最稳的判断不是“谁绝对更快”，而是：

| 对比 | TCP | UDP |
| --- | --- | --- |
| 连接 | 面向连接 | 无连接 |
| 可靠有序 | 协议提供 | 协议本身不提供同等级保证 |
| 数据形式 | 字节流 | 数据报 |
| 控制机制 | 较多 | 较简单 |

## 应用名和 TCP/UDP 为什么也不能死绑

例如 DNS 常见查询大量使用 UDP，但某些场景也会使用 TCP。

所以：

> **“某协议常用 TCP/UDP”是常见映射，不等于技术上永远只能用一种。**

系统架构设计师第一轮先掌握典型默认关系，避免把应用协议和传输协议混为同一层。

## 这一篇解决了什么，还剩什么没解决

现在我们已经知道：

- 需要可靠、有序字节流时想到 TCP；
- 需要简单数据报传输时想到 UDP。

但主机 S 上可能同时运行：

- Web 服务；
- DNS；
- 邮件；
- SSH；
- 数据库。

IP 只把数据送到**这台主机**，TCP/UDP 只决定**用哪种传输方式**。

还差最后一个问题：

> **这份数据到底交给主机上的哪个网络程序？**

这就是下一站 [[端口与进程通信]]。

## 一句话总结

**TCP 和 UDP 是两种传输服务风格：TCP 用更多控制换取可靠、有序的字节流；UDP 保持简单的数据报传输，把更多取舍留给应用。**
