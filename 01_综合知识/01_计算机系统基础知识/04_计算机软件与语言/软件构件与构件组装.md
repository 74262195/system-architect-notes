# 软件构件与构件组装：怎样像搭积木一样复用软件

> [!summary]- 快速复习卡片（学完再看）
> **核心结论**：构件是自包容、可复用的程序集，外部只能经统一接口访问；构件组装按“设计组装 → 建构件库 → 构建应用 → 测试发布”推进。
> **题干信号**：统一接口、自包容、复用、第三方构件库 → 构件；CORBA、J2EE、DNA → 商用构件规范。

把整个系统从零写起，会反复开发相同能力。**软件构件**（组件）是一组程序的集合，可表现为源代码或二进制代码；它对外提供统一访问接口，内部实现不能被直接操作。最关键的两项特性是 **自包容** 与 **可重用**。

先由需求确定功能并设计构件及其关系；再选择自研、复用或第三方构件建立构件库；构件通过接口协作组装为应用，最后测试发布。这里的关键不是“有很多代码模块”，而是模块之间能依靠约定接口独立协作。

| 优点 | 代价与边界 |
| --- | --- |
| 易扩展、易复用，降低开发成本 | 构件设计需要经验；设计差会降低复用价值 |
| 构件粒度较小，可分团队并行开发 | 为复用可能牺牲部分性能，研发人员要学习构件 |
| 可选用第三方构件 | 第三方构件库质量会影响整体质量，且不易完全控制 |

### 走一遍构件库选择、组装和测试

下面是虚构的教学例子。订单服务需要在扣库存前检查订单格式，因此团队决定复用一个“订单校验构件”。

| 项目 | 本例约定 |
| --- | --- |
| 构件与版本 | `OrderValidator v1.2`，从团队构件库选择 |
| 接口输入 | `validate(order)`；订单含非空订单号和一项或多项商品行，每行含 SKU 与数量 |
| 前置条件 | 订单号非空；至少有一项商品；每项数量为正整数 |
| 返回结果 | `valid=true`，或 `valid=false` 并带可显示的校验错误 |
| 副作用边界 | 只检查订单数据，不扣库存、不创建订单记录 |
| 组装位置 | 订单服务先调用校验构件；校验通过后才调用库存构件 |

选择入库时先检查构件版本、接口和已有测试记录是否满足订单服务的约定。集成测试再检查两个构件的调用顺序：

- 输入订单号 `A17`、商品 `P9` 数量 2：校验构件返回 `valid=true`，订单服务随后调用库存构件；测试通过。
- 将数量改为 0：校验构件返回 `valid=false` 和错误信息，订单服务不得调用库存构件；测试通过。

如果要换成 `OrderValidator v2`，只有当它继续接受同样的输入、返回兼容结果，并保留“只校验、不扣库存”的行为约定时，订单服务才可能直接替换；接口或错误语义不同，就要修改调用方或增加适配。**可复用的关键是契约兼容，不是名字相似。**

教材列举的商用构件标准规范包括 **CORBA、J2EE、DNA**；它们在本篇只需做名称与“构件规范”定位，不展开产品细节。

1. 构件为什么不能被其他模块直接改内部实现？

> [!answer]- 第 1 题答案与解析
> **答案**：构件对外以统一接口提供服务，外部只能通过接口访问；这使实现可被封装和替换。
> **解析**：调用方依赖接口契约而不是内部代码，构件才能独立维护或在契约兼容时替换。

2. 使用第三方构件库一定只会降低成本吗？

> [!answer]- 第 2 题答案与解析
> **答案**：不一定。复用可降低开发成本，但第三方库质量会影响整体质量，且团队还需承担学习和集成成本。
> **解析**：还需核查版本、接口、质量和集成适配；“复用”本身不保证低成本或高质量。
