# 建模语言与 UML：系统还没写成代码，怎样先把结构和行为说清楚

> [!summary]- 快速复习卡片（学完再看）
> **大白话**：UML 就是一套“软件系统统一画图规则”，让大家用相同画法说明系统。  
> **正式定位**：UML 是标准建模语言，不是规定项目开发步骤的方法。  
> **组成**：基本构造块（事物、关系） + 图 + 公用机制。  
> **四类事物**：结构、行为、分组、注释。  
> **题干信号 → 第一反应**：问 UML“由什么组成”先答三部分；问“是不是方法”直接判断不是。  
> **易错点**：UML 图 ≠ UML 视图；UML 也 ≠ 4+1 架构视图模型。

上一站 [[计算机语言-编译与解释]] 已经说明：程序最后要经过编译、解释或汇编，变成机器能够执行的形式。

但程序真正开始写之前，还有一个更早的问题。

## 为什么需要 UML：光靠嘴说，大家脑子里的系统可能根本不是一个样子

假设我们现在要做一个**网上商城**。

程序还没开始写，大家已经要讨论很多东西：

- 用户可以做什么？——登录、下单、付款；
- 系统里有哪些东西？——用户、商品、订单；
- 它们是什么关系？——一个用户可以有多个订单；
- 下单时谁先做什么？——用户提交订单，系统检查库存，再生成订单；
- 订单会经历哪些状态？——待付款、已付款、已发货；
- 程序最后跑在哪里？——哪些服务部署在哪些服务器上。

如果这些内容全部靠嘴说，或者每个人自己随便画，很容易出现一个问题：

> **你脑子里的“商城”，和我脑子里的“商城”，可能根本不是同一个样子。**

所以大家需要一套约定好的画法。

**UML 就可以先理解成：软件系统的一套统一画图规则。**

它让大家看到同一种符号、同一种图时，基本知道这张图想说明什么。

比如还是这个商城：

| 现在想说明什么 | 可以想到的 UML 图 |
| --- | --- |
| 用户能使用系统哪些功能 | **用例图** |
| 用户、商品、订单之间是什么关系 | **类图** |
| 下单时用户、订单服务、库存服务谁先调用谁 | **序列图** |
| 订单怎样从待付款变成已付款、已发货 | **状态图** |
| 哪个服务部署在哪台服务器上 | **部署图** |

看到这里，先不用背完整定义，只先抓住一句：

> **UML = 用统一画法把软件系统“画明白”，让大家讨论的是同一个东西。**

正式一点说，**UML（Unified Modeling Language，统一建模语言）是一种标准建模语言**，用于统一表达系统的结构和行为。

### UML 为什么“不是开发方法”

因为 UML 只负责：

> **这个系统该怎么画、怎么表达。**

它不负责规定：

> 第一天做需求，第二天做设计，还是先做原型再迭代；团队到底按什么步骤开发。

所以可以把两者分开：

- **UML**：告诉你“图怎么画、模型怎么表达”；
- **开发方法/开发过程**：告诉你“项目按什么步骤推进”。

因此考试如果问“UML 是不是一种开发方法”，答案是：**不是。它是建模语言。**

## UML 到底由哪三部分组成

现在再看教材里的正式结构就容易多了。

刚才商城例子里，我们既要画“用户、订单这些东西”，又要画“它们之间的线”，最后还要把这些东西组合成不同的图。

教材把 UML 的组成概括为三部分：

| 组成 | 先用大白话理解 | 这一层解决什么 |
| --- | --- | --- |
| **基本构造块** | 图里能画哪些“东西”，以及这些东西能怎样连起来 | 模型的基本词汇 |
| **图** | 把这些“东西”和“关系”按某个问题组织成一张具体图 | 从一个角度把系统画出来 |
| **公用机制** | 各种 UML 图共同遵守的一些表达规则 | 让不同图的表达保持一致 |

最容易漏掉的是第一项内部还包含两部分：

> **基本构造块 = 事物 + 关系。**

所以不能把“UML 由四类事物组成”当成完整答案。四类事物只是“基本构造块”里面的一部分。

## 四类事物：模型里到底有哪些“东西”

UML 把模型中的事物分为四类。这里先抓“它在模型中扮演什么角色”，不背完整元素清单。

| 类别 | 大白话 | 典型例子 |
| --- | --- | --- |
| **结构事物** | 模型里的“名词”，描述比较静态的东西 | 类、接口、构件、结点 |
| **行为事物** | 模型里的“动作/变化”，描述系统怎样动起来 | 交互、状态机、活动 |
| **分组事物** | 把一批模型元素整理到一起 | 包 |
| **注释事物** | 给模型补解释、说明或约束 | 注解 |

继续用商城理解：

- “订单类”是一个结构事物；
- “订单从待支付变成已支付”体现行为；
- 把订单相关元素放进一个包是在分组；
- 在图旁边补一句限制说明属于注释。

做题时如果题目问“四类事物”，第一步不是想某张具体图，而是先判断题干描述的是：**结构、行为、组织还是说明。**

## 关系先知道它解决什么，细节不要塞进总览

只有“用户、订单、商品”这些东西还不够，因为它们不是互相孤立的。

比如：

- 用户和订单有联系；
- 某个类可能依赖另一个类；
- 子类可能继承父类；
- 一个类可能实现某个接口。

UML 就需要用“关系”把这些情况表达出来。

教材给出的四种基本关系是：

- **依赖**；
- **关联**；
- **泛化**；
- **实现**。

其中关联还会继续出现聚合、多重度等细节。

这四种关系可以独立出题，而且需要分别理解“谁依赖谁、谁和谁连接、谁是父子一般化、谁实现契约”。因此本总览只先把它们放回 UML 组成结构中，**不在这一篇抢讲完整关系语义和画法**；关系细节应由后续原子卡单独承担。

## UML 有 13 种图，是不是 13 种都要在这里背完

**不是。** 本篇只建立地图，避免第一次学 UML 就被 13 个名字淹没。

主教材按 UML 2.0 列出 13 种图。为了先看出它们在回答什么问题，可以压成三组：

| 先按问题看 | 代表图 | 主要在回答什么 |
| --- | --- | --- |
| **结构类表达** | 类图、对象图、构件图、部署图、包图、组合结构图 | 系统“有什么、怎样组织” |
| **一般行为表达** | 用例图、活动图、状态图 | 系统“要做什么、状态/流程怎样变化” |
| **交互行为表达** | 序列图、通信图、交互概览图、计时图 | 多个对象“怎样交互” |

其中序列图、通信图、交互概览图和计时图又属于教材所说的**交互图**。

这一层只需要先建立地图。后续学习重点应该按“题干在描述什么 → 该用哪类图”展开，而不是机械按 13 个名字顺序背百科。

## 五种视图是在比较什么

这里特别容易把“图”和“视图”混成同一个概念。

先继续用商城理解：

- 如果你只想看“用户需要哪些功能”，是在看系统的一个关注角度；
- 如果你只想看“程序最终部署在哪些服务器”，又是在看另一个关注角度。

**视图（View）就是：你现在站在哪个角度看同一个系统。**

而**图（Diagram）就是：你真正画出来的那张图。**

所以一个视图可以用合适的 UML 图来表达，但“某一种 UML 图”并不天然等于“某一个视图”。

教材给出的 UML 五种视图可以先这样记：

| 视图 | 主要关注 |
| --- | --- |
| **用例视图** | 系统对外提供什么行为，参与者需要系统做什么 |
| **逻辑视图** | 系统的关键抽象、类及其关系 |
| **进程视图** | 运行时并发、通信和同步等动态问题 |
| **实现视图** | 构件、文件等实现组织 |
| **部署视图** | 软件怎样映射到结点和硬件环境 |

### 为什么“UML 五视图”和“架构 4+1”不能直接画等号

它们确实有很多相近关注点，但不是同一个分类表。

- UML 是**建模语言**，五视图是在 UML 语境下从不同关注点组织模型；
- [[02_软件架构视图：为什么同一系统需要多个观察视角|4+1 架构视图]] 是一种**软件架构多视图模型**，重点组织逻辑、进程、开发、物理视图并用场景贯穿。

所以考试看到“视图”两个字，先看题干究竟在问 **UML 模型表达**，还是在问 **软件架构 4+1**，不要只按名字相似硬套。

## UML 和软件工程、软件架构到底是什么关系

### 在软件工程里：UML 是表达工具，不是 OOA/OOD 本身

[[面向对象分析OOA]]、[[面向对象设计OOD]] 是分析和设计活动；UML 可以把这些活动形成的对象、关系、交互等模型画出来。

因此先大白话记：

> **OOA/OOD 负责想清楚“系统里有什么、应该怎么设计”；UML 负责把你想清楚的东西按统一规则画出来。**

看到“采用 UML”不能反推项目一定使用某一种固定开发方法。

### 在软件架构里：UML 可以描述架构，但 UML 图不等于架构

架构关心的是主要构件、外部可见属性和构件关系等系统级结构。UML 可以拿来画这些内容，但一张 UML 类图也可能只是画某个很小的局部设计。

所以判断“是不是架构”，关键仍然看**这张图在讨论整个系统的关键结构，还是某个局部细节**，而不是看到 UML 图就自动选“软件架构”。

## 考试怎么认

遇到 UML 题，先按下面顺序拆题：

1. **问“UML 是什么”** → 先想“软件系统统一画图规则”，正式答案是标准建模语言，不是开发方法；
2. **问“UML 由什么组成”** → 基本构造块 + 图 + 公用机制；
3. **问基本构造块** → 继续拆成事物 + 关系；
4. **问四类事物** → 结构 / 行为 / 分组 / 注释；
5. **问四种基本关系** → 依赖 / 关联 / 泛化 / 实现；具体辨析留到关系原子卡；
6. **问图还是视图** → 图是具体画出来的东西；视图是观察系统的角度；
7. **问软件工程/架构里的 UML** → 先记住它是表达工具，不能把“语言、方法、架构视图”混为一层。

## 一句话记住

> **UML 就是软件系统的统一画图语言：大家按相同规则把“有什么、什么关系、怎么交互、怎么变化、部署在哪”画出来，这样讨论的是同一个系统。**

## 自测

> [!question] 自测
> 1. 为什么一个团队不能简单理解成“大家自己随便画系统图也行”？UML 解决的核心问题是什么？
>
> > [!answer]- 第 1 题答案与解析
> > **答案**：因为每个人随便画，符号和含义可能不同，容易产生理解偏差。UML 提供统一的建模表达规则，让团队用共同语言描述系统。
> > **解析**：先理解“统一画法”这个问题，再记正式术语“标准建模语言”。
>
> 2. “UML 由结构事物、行为事物、分组事物和注释事物组成”为什么不是完整的 UML 组成答案？
>
> > [!answer]- 第 2 题答案与解析
> > **答案**：因为四类事物只属于 UML“基本构造块”中的事物部分。
> > **解析**：完整的上位组成是“基本构造块（事物、关系）+ 图 + 公用机制”。
>
> 3. UML 是不是一种规定项目开发步骤的方法学？
>
> > [!answer]- 第 3 题答案与解析
> > **答案**：不是。
> > **解析**：UML 负责统一表达模型，可以配合不同开发方法使用；“语言”和“方法”不是同一层概念。
>
> 4. 一张部署图和“部署视图”是不是完全同义？
>
> > [!answer]- 第 4 题答案与解析
> > **答案**：不能直接画等号。
> > **解析**：部署图是一种具体 UML 图；部署视图是围绕部署关注点观察系统，可能使用部署图等合适表达来呈现。
