# 敏捷开发：需求会变时，为什么要缩短反馈周期而不是死守最初计划

## 先定位：这是教材 2.8.3 的四种生命周期方法之一

本节主线是：

[[计划驱动方法]] → [[渐进迭代式开发]] → [[精益开发]] → **敏捷开发**

这里讲的是系统工程语境下的敏捷思想，不是要求你把 Scrum、XP 的所有实践都背下来。

## 敏捷在解决什么

传统方法如果把很长时间都花在按照最初计划开发，用户直到很晚才看到结果，一旦需求变化，前面的假设可能大量失效。

敏捷因此把重点放在：

- 尽早、持续交付有价值的可用成果；
- 接受并利用需求变化；
- 业务人员和开发人员持续协作；
- 用可工作的成果衡量进展；
- 保持简单，并持续反思和调整工作方式。

核心不是“不要计划”，而是：

> **让计划能够随着真实反馈及时调整。**

## 用一次门诊预约需求看短周期反馈

下面是虚构的教学情境。患者希望在线预约门诊号，但第一轮不试图一次做完所有功能。

| 短周期环节 | 本例中的内容 |
| --- | --- |
| 本轮目标 | 患者能按科室查看可预约时段并提交预约 |
| 可运行交付与验收 | 测试环境中从科室选择到预约成功的最小流程可运行；用测试账号完成预约后，系统显示预约日期和时段 |
| 用户/业务反馈 | 患者能完成预约，但不清楚如何取消；门诊人员指出取消后名额需要及时释放给其他患者 |
| 下一轮调整 | 将“取消预约并释放名额”加入下一轮优先待办，同时补充取消后状态提示；再用患者和门诊人员共同验收 |

第一轮交付不是最终系统，而是能让用户实际操作并指出问题的增量。反馈改变了下一轮的优先顺序，但团队仍然有本轮目标、待办和验收条件。因此敏捷的“响应变化”是持续协作、交付和调整，不是放弃计划。

## 和前面三种方法怎么区分

| 方法 | 最先抓住的核心 |
| --- | --- |
| 计划驱动 | 用规定流程、文档和追溯保证大型协作可控 |
| 渐进迭代 | 先提供能力，再通过多轮评估逐步演进 |
| 精益 | 围绕价值持续消除浪费 |
| 敏捷 | 缩短反馈周期，持续交付并响应变化 |

现实项目可以组合使用这些思想，考试分类时按题干强调的核心判断。

## 一句话记住

> **敏捷不是“不要计划”，而是用短反馈、持续交付和协作，让计划跟得上变化。**

## 自测

1. 为什么敏捷强调“可工作的成果”？

> [!answer]- 第 1 题答案与解析
> **答案**：因为可工作的成果能尽早交付价值，也能让利益攸关者基于真实结果提供反馈。
> **解析**：敏捷用可运行、可验证的成果衡量进展，避免长期只按文档或计划推测完成度。

2. “响应变化”是否等于完全不做计划？

> [!answer]- 第 2 题答案与解析
> **答案**：不等于。敏捷仍然需要计划，只是让计划能根据反馈及时调整。
> **解析**：敏捷反对的是在条件已变化时仍机械固守最初计划，而不是取消目标、安排和协调。

3. 精益和敏捷最主要的关注点有什么不同？

> [!answer]- 第 3 题答案与解析
> **答案**：精益主要围绕价值消除浪费；敏捷主要通过短反馈、持续交付和协作响应变化。
> **解析**：两者可以组合使用，考试分类时应按题干强调的核心判断。
