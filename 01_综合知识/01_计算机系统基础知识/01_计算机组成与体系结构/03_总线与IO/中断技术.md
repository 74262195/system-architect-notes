# 中断技术：设备准备好了，怎么把 CPU 叫回来

## 先接上上一站：中断首先解决的不是“搬数据”，而是“CPU 要不要一直等”

在 [[IO控制技术]] 中，最早的一种办法是**程序查询方式**。

例如 CPU 让磁盘读取一份数据以后，磁盘不会瞬间完成。  
如果采用程序查询，CPU 就要不断读取 I/O 接口的状态：

> 好了吗？  
> 好了吗？  
> 现在好了吗？

设备还没准备好，CPU 就继续问。

问题很明显：

> **CPU 很快，外设很慢。CPU 大量时间浪费在“等设备、查状态”上。**

中断方式换了一个思路：

> **CPU 发出 I/O 命令以后先去执行别的程序；等设备真的准备好了，再主动通知 CPU。**

所以中断首先解决的是：

> **怎样让 CPU 不必一直轮询设备。**

这也是为什么在 I/O 控制技术中，中断方式会排在程序查询方式后面学习。

---

## “设备通知 CPU”到底是谁在通知

这里不要想成磁盘、键盘直接跑到 CPU 面前说话。

前面 [[IO接口]] 已经学过：

> 外设和 CPU 之间通常隔着 **I/O 接口 / 设备控制器**。

以输入为例，可以先建立这条链：

**外设 → I/O 接口 → CPU / 主存**

外设完成一部分工作后，I/O 接口会记录：

- 数据已经准备好；
- 当前状态是就绪还是出错；
- 必要时向 CPU 发出**中断请求**。

所以经典 I/O 场景中，更准确的理解是：

> **设备控制器 / I/O 接口通过中断请求告诉 CPU：“我这里有事情需要你处理了。”**

---

## 中断改变了什么，又没有改变什么

这一点非常重要。

在经典的**中断驱动 I/O**模型中：

### 改变的是

CPU **不用一直等设备**。

设备没准备好时：

> CPU 可以先执行别的程序。

### 没有完全改变的是

设备准备好以后，CPU 仍然要执行中断服务程序来处理它。

如果题目采用经典输入模型，数据搬运仍可以理解成：

> **I/O 接口的数据寄存器 → CPU → 主存**

也就是说：

> **中断主要把“什么时候来处理设备”从 CPU 轮询，改成设备主动通知。**

它并不等于 DMA，也不代表 CPU 从此完全不参与数据搬运。

---

# 一次中断到底怎么走

假设 CPU 已经命令某个输入设备读取数据。

~~~mermaid
flowchart LR
    A[CPU启动I/O] --> B[CPU先做别的事]
    B --> C[I/O接口准备好并发出中断]
    C --> D[CPU转去执行中断服务程序]
    D --> E[处理完成后回原程序]
~~~

下面把这 5 步拆开。

## 第 1 步：CPU 先启动 I/O

CPU 通过 I/O 接口告诉设备：

> 开始读取数据。

设备开始工作。

因为设备比较慢，CPU 没必要站在那里等。

---

## 第 2 步：CPU 去执行别的程序

这就是中断相比程序查询最直接的收益。

程序查询：

> CPU 一直问设备好了没有。

中断：

> CPU 先走，设备准备好再叫 CPU。

---

## 第 3 步：设备准备好，I/O 接口发出中断请求

当设备完成操作或数据已经到达接口后，I/O 接口向 CPU 提出：

> **中断请求。**

这里的“请求”很重要。

它不是说：

> 一发中断，CPU 无论正在干什么都必须瞬间停下。

而是：

> **请求 CPU 在合适的时机转去处理这件事。**

---

## 第 4 步：CPU 决定是否响应

CPU 通常会在当前指令执行到合适的检查点后查看中断请求。

如果：

- 当前允许中断；
- 该请求没有被屏蔽；
- 优先级等条件允许；

CPU 才会真正**响应中断**。

因此：

> **中断请求 ≠ CPU 已经开始处理中断。**

“设备提出请求”和“CPU 接受请求”是两个动作。

---

## 第 5 步：CPU 要先记住“自己原来做到哪里”

CPU 原本正在运行程序 A。

现在突然要转去处理设备。

那处理完设备以后怎么办？

必须还能回来继续执行程序 A。

所以在离开原程序前，要保存能够返回所需的信息。

最重要的是：

> **原程序下一步应该从哪里继续。**

这类返回位置信息通常称为**断点**。

你可以把它理解成看书时夹的一张书签：

> 先去处理别的事情，回来以后还能找到刚才读到哪。

---

## 第 6 步：CPU 怎么知道应该去执行哪段处理程序

不同设备发生中断，需要处理的事情不一样。

例如：

- 键盘有输入；
- 网卡收到数据；
- 定时器到点；

CPU 不能所有中断都跑到同一段程序里乱处理。

所以系统需要知道：

> **这个中断对应哪一个处理入口。**

用于处理某类中断的程序叫：

> **中断服务程序（Interrupt Service Routine，ISR）**

而帮助 CPU 找到相应中断服务程序入口的机制，常涉及：

> **中断向量 / 中断向量表**

先把它理解成：

> **“发生了哪类中断 → 应该跳到哪段处理程序”的入口映射。**

不需要一上来背硬件实现细节。

---

## 第 7 步：中断服务程序真正处理事情

CPU 进入 ISR 后，才开始真正处理这个事件。

以经典输入设备为例，可能包括：

1. 查看 I/O 接口状态；
2. 从接口的数据寄存器读取数据；
3. 把数据写入主存中的目标位置；
4. 处理完成状态；
5. 清除或确认本次中断请求。

最后一步很重要。

如果设备的中断状态一直没有清除，CPU 返回后可能继续认为：

> “这个设备还在请求中断。”

于是可能再次进入中断处理。

---

## 第 8 步：恢复原来的程序，继续执行

设备事件处理完后：

> CPU 恢复之前保存的运行状态，然后回到刚才被打断的程序继续执行。

所以完整过程其实就是：

> **原程序运行 → 设备发请求 → CPU 暂时离开 → 执行 ISR → 回到原程序。**

中断不是把原程序“丢掉”。

而是：

> **临时插入一段更需要及时处理的工作，做完再回来。**

---

# 现在再看“断点”和“现场”，就不容易混了

前面已经知道 CPU 为什么必须保存信息，现在再给术语。

## 断点

主要解决：

> **处理完中断以后，回到哪里继续执行？**

最核心的是返回地址。

## 现场

解决：

> **除了执行位置，原程序当时的运行状态还要不要恢复？**

例如某些寄存器、处理器状态等。

因此可以先记：

> **断点偏向“回哪里”，现场偏向“回来以后恢复成什么状态”。**

具体哪些信息由硬件自动保存、哪些由软件保存，取决于体系结构。

经典软考题若问“断点信息一般保存在哪里”，常见考试口径是**栈**；不要把它扩大成所有体系结构都绝对如此。

---

# 为什么还会出现屏蔽、优先级和嵌套

现在再增加一个现实问题：

> 如果 CPU 正在运行，同时来了好几个中断怎么办？

这才需要下面三个概念。

| 概念 | 它回答的问题 |
| --- | --- |
| **屏蔽** | 这个中断现在接不接？ |
| **优先级** | 多个中断同时来，先处理谁？ |
| **嵌套** | 正在处理中断时，能不能被更高优先级中断再次打断？ |

所以它们不是凭空出现的新术语。

它们都是在解决：

> **多个中断请求竞争 CPU 时怎么安排。**

---

# 中断方式和 DMA 到底差在哪里

这是 I/O 控制技术里最容易一起考的地方。

| 方式 | CPU 等不等设备 | 数据主要谁搬 |
| --- | --- | --- |
| 程序查询 | CPU 一直查询、容易忙等 | CPU |
| 中断方式 | CPU 可以先做别的，设备好了再通知 | 经典模型中仍由 CPU / ISR 参与 |
| DMA | CPU 可以先做别的 | DMA 控制器在设备与主存之间成块传输 |

所以不要把中断理解成：

> “有了中断，CPU 就不用搬数据了。”

真正进一步把**批量数据搬运**从 CPU 手中拿走的，是 [[IO控制技术|DMA]]。

---

# 中断和异常为什么有时会放在一起

学完中断主流程后，再看这个边界就简单很多。

它们都可能让 CPU：

> 暂时停止当前正常执行流程 → 转去执行专门处理程序 → 之后再决定如何继续。

但**触发来源不同**。

| 情况 | 从哪里来 | 例子 |
| --- | --- | --- |
| 外部中断 | CPU 外部事件 | I/O 完成、定时器 |
| 异常 | 当前指令执行过程中发现问题 | 除零、非法指令、缺页 |
| 主动陷入 | 程序主动执行专门指令 | 系统调用、trap |

本卡学习主线是 **I/O 中断**。

考试题如果专门问“中断、异常、陷入的分类”，再按题干和教材口径判断；不要在刚学中断时把三者混成一件事。

# 考试怎么认

看到：

> **CPU 不需要不断查询设备，设备准备好后主动通知**

优先想到：

> **中断方式**

看到：

> **设备与主存之间成块直接传输，CPU 不逐个搬运**

优先想到：

> **DMA**

看到：

> **CPU 处理中断后要回到原程序**

就要想到：

> **保存断点 / 现场 → 执行 ISR → 恢复并返回**

看到：

> **多个中断同时到来**

再考虑：

> **屏蔽、优先级、嵌套**

# 一句话串起来

> **CPU 启动 I/O 后先去做别的事；I/O 接口准备好后发出中断请求；CPU 在合适时机保存原程序状态，进入对应的中断服务程序处理设备，最后恢复现场并回到原程序。**

再缩成最关键的一句：

> **中断解决的是“设备什么时候把 CPU 叫回来”，DMA 进一步解决的是“数据还要不要 CPU 亲自搬”。**

---

## 自测

### 1. 中断方式相比程序查询，最先解决了什么问题？

CPU 不需要一直轮询并等待慢速设备，可以先执行其他工作，设备准备好后再通知 CPU。

### 2. 在经典中断驱动输入模型中，CPU 从哪里取得设备数据？

从 **I/O 接口 / 设备控制器的数据寄存器**取得，再由 CPU 指令写入主存。

### 3. 中断请求和中断响应为什么不是一回事？

中断请求是设备提出“需要处理”；中断响应是 CPU 判断允许后真正接受请求并转去处理中断。

### 4. 为什么处理中断前要保存断点？

因为中断处理完成后还要回到原程序继续执行，CPU 必须知道原来执行到哪里。

### 5. 中断和 DMA 最核心的区别是什么？

中断方式让 CPU 不必一直等待，但经典模型中 CPU 仍参与数据处理或搬运；DMA 则进一步让 DMA 控制器负责设备与主存之间的成块数据传输。
