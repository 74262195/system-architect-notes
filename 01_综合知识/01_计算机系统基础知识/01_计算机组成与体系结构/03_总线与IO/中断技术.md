# 中断技术：设备准备好了，怎么把 CPU 叫回来

## 先接上上一站：中断先解决“CPU 要不要一直等”

在 [[IO控制技术]] 中，程序查询方式是：

> CPU 启动设备以后，不断去查设备状态：好了没有？好了没有？

因为 CPU 很快、外设很慢，这会让 CPU 大量时间浪费在等待和轮询上。

中断方式换了一个思路：

> **CPU 启动 I/O 后先去做别的事；设备真的准备好以后，再通知 CPU 回来处理。**

所以中断最先解决的是：

> **CPU 不必一直轮询慢速设备。**

注意：这里解决的是“什么时候回来处理”，还不是“谁来搬数据”。  
“谁搬数据”要继续和 DMA 区分。

---

## 先统一一个名词：后文都叫 I/O 接口

前面 [[IO接口]] 已经学过，CPU 和外设之间通常不会直接硬接，中间有一层接口控制硬件。

在很多教材和题目里，你会看到：

- I/O 接口；
- 设备控制器；
- 接口控制器。

它们的使用范围并不总是完全相同，但在本章当前的经典 I/O 模型里，可以先把它们理解成**同一层中间控制硬件**。

> **本笔记后文统一写“I/O 接口”，不再和“设备控制器”来回换名字。**

它负责：

- 接收 CPU 的控制命令；
- 保存设备状态；
- 暂存输入/输出数据；
- 必要时向 CPU 发出中断请求。

---

## 先看清数据从哪里走

以“输入设备把数据交给程序”为例。

在经典的**中断驱动 I/O**中，可以先理解成：

~~~mermaid
flowchart LR
    DEV[外设] --> IO[I/O 接口]
    IO --> CPU[CPU]
    CPU --> MEM[主存]
~~~

也就是：

> **外设 → I/O 接口 → CPU → 主存**

设备先把数据交给 I/O 接口。  
I/O 接口准备好后通知 CPU。  
CPU 进入中断服务程序，再从接口的数据寄存器读取数据并写入主存。

所以：

> **中断方式没有把 CPU 从数据搬运中完全拿掉。**

真正让设备和主存之间进行成块传输、减少 CPU 逐次搬运的是后面的 DMA。

---

# 一次 I/O 中断到底怎么走

假设 CPU 已经让某个输入设备开始读取数据。

~~~mermaid
flowchart LR
    A[CPU启动I/O] --> B[CPU继续做别的事]
    B --> C[I/O接口发出中断请求]
    C --> D[CPU响应并保存返回信息]
    D --> E[执行中断服务程序]
    E --> F[恢复原程序继续运行]
~~~

下面把这条主流程拆开。

## 第 1 步：CPU 启动 I/O

CPU 通过 I/O 接口告诉设备：

> 开始工作。

设备开始读取或接收数据。

---

## 第 2 步：CPU 不再原地等

设备需要时间。

采用中断方式时，CPU 不需要不停读取状态寄存器，而是：

> **先去执行其他指令。**

这就是中断相比程序查询方式最直接的收益。

---

## 第 3 步：I/O 接口准备好后发出中断请求

当设备完成操作，或者输入数据已经到达 I/O 接口时，接口向 CPU 发出：

> **中断请求。**

这里一定要分清：

> **中断请求 = I/O 接口说“我这里需要你处理”。**

它还不代表 CPU 已经停止当前程序。

---

## 第 4 步：CPU 判断现在能不能响应

CPU 会在体系结构规定的合适时机检查中断请求。

如果：

- 当前允许中断；
- 这个请求没有被屏蔽；
- 优先级等条件允许；

CPU 才真正接受这个请求。

因此：

> **中断请求 ≠ 中断响应。**

- 请求：接口提出；
- 响应：CPU 接受并准备转去处理。

---

## 第 5 步：CPU 先记住“原程序做到哪里”

CPU 原本正在运行程序 A。

现在要临时离开它去处理设备，处理完还得回来。

因此 CPU 必须保存返回所需的信息。

最重要的是：

> **原程序之后应该从哪里继续执行。**

这类返回位置信息通常称为**断点**。

可以把断点理解成书签：

> 先去处理一件急事，回来还能找到刚才看到哪一页。

---

## 第 6 步：CPU 找到对应的中断服务程序

键盘、网卡、定时器等发生中断时，需要执行的处理程序并不一样。

专门处理某类中断的程序叫：

> **中断服务程序（ISR，Interrupt Service Routine）**

CPU 还必须知道：

> “这次中断应该跳到哪个 ISR？”

这就会用到**中断向量**一类入口定位机制。

先只需要理解：

> **中断来源 → 对应处理程序入口**

不必现在深挖具体硬件实现。

---

## 第 7 步：ISR 真正处理设备

以经典输入设备为例，ISR 可能做：

1. 查看 I/O 接口状态；
2. 从接口的数据寄存器读取数据；
3. 将数据写入主存中的目标位置；
4. 更新处理状态；
5. 确认或清除本次中断请求。

所以前面“CPU 从哪里搬数据”的答案，在这里就落地了：

> **CPU 从 I/O 接口的数据寄存器取数据，再写入主存。**

如果中断状态没有正确清除，CPU 返回后可能仍然认为设备在请求中断。

---

## 第 8 步：恢复原程序继续执行

ISR 完成后，CPU 恢复之前保存的运行状态，然后回到原程序继续执行。

因此完整过程是：

> **原程序运行 → I/O 接口请求中断 → CPU 暂时离开 → 执行 ISR → 回原程序。**

中断不是把原程序丢掉，而是：

> **临时插入一项需要及时处理的工作。**

---

# 断点和现场到底有什么区别

现在再看这两个术语。

## 断点

主要回答：

> **处理完中断以后，回到哪里？**

核心是返回地址。

## 现场

主要回答：

> **回来以后，要恢复成原来什么运行状态？**

例如部分寄存器、处理器状态等。

所以可以先记：

> **断点解决“回哪里”，现场解决“恢复成什么样”。**

具体哪些信息由硬件自动保存、哪些由软件保存，取决于体系结构。

经典软考题若问“断点信息一般保存在哪里”，常见考试口径是**栈**；不要扩大成所有体系结构都绝对如此。

---

# 为什么会有屏蔽、优先级和嵌套

如果多个设备都向 CPU 请求中断，就需要解决三个新问题：

| 概念 | 回答的问题 |
| --- | --- |
| **屏蔽** | 这个中断现在接不接？ |
| **优先级** | 多个请求同时来，先处理谁？ |
| **嵌套** | 正在处理中断时，能不能被更高优先级中断再次打断？ |

所以这三个概念的共同背景是：

> **多个中断请求竞争 CPU 时怎么安排。**

---

# 中断和 DMA 最容易混在哪里

| 方式 | CPU 是否一直等设备 | 数据主要由谁搬 |
| --- | --- | --- |
| 程序查询 | 容易忙等、反复轮询 | CPU |
| 中断方式 | 不一直等，设备好了再通知 | 经典模型中仍由 CPU / ISR 参与 |
| DMA | 不一直等 | DMA 控制器在设备与主存间成块传输 |

最容易记错的是：

> **有了中断 ≠ CPU 不搬数据。**

中断主要改变：

> **CPU 什么时候回来处理设备。**

DMA 才进一步改变：

> **设备与主存之间的大量数据还要不要 CPU 逐次搬运。**

---

# 易混边界：中断和异常不是同一个来源

有些教材会把中断、异常、陷入放在相近章节，因为它们都会让 CPU 暂时改变正常控制流。

但本卡主线只学 **I/O 中断**。

先做最小区分即可：

- **I/O 中断**：来自 CPU 外部设备或控制器的事件；
- **异常**：当前指令执行过程中发现的问题，例如除零、非法指令；
- **主动陷入**：程序主动执行专用指令，例如系统调用。

不要在刚学 I/O 中断时把三者混成一件事。

# 一句话串起来

> **CPU 启动 I/O 后先做别的事；I/O 接口准备好后发出中断请求；CPU 在合适时机保存返回信息，进入对应的 ISR 处理设备，最后恢复原程序继续运行。**

再缩成一句：

> **中断解决“什么时候把 CPU 叫回来”，DMA进一步解决“数据还要不要 CPU 亲自搬”。**

## 自测

### 1. 中断方式相比程序查询，首先解决了什么？

CPU 不必一直轮询等待慢速设备，可以先执行其他工作，设备准备好后再通知 CPU。

### 2. 在经典中断驱动输入模型中，CPU 从哪里取得设备数据？

从 **I/O 接口的数据寄存器**取得，再由 CPU 指令写入主存。

### 3. 中断请求和中断响应有什么区别？

中断请求是 I/O 接口提出“需要处理”；中断响应是 CPU 判断条件允许后真正接受请求并转去处理。

### 4. 为什么处理中断前要保存断点？

因为处理完成以后还要回到原程序继续执行，CPU 必须知道原来执行到哪里。

### 5. 中断和 DMA 最核心的区别是什么？

中断让 CPU 不必一直等待设备，但经典模型中 CPU 仍参与数据处理或搬运；DMA 则进一步让 DMA 控制器负责设备与主存之间的成块数据传输。
