# 共享内存与消息传递：多个处理器怎么交换结果

## 先定位：Flynn 分类完“怎么算”，这里开始讲“怎么交流”

上一站 [[Flynn分类法]] 是从**指令流和数据流**的角度给并行计算机分类，例如 SIMD、MIMD。它回答的是：

> **这些处理单元在执行什么样的指令和数据？**

但即使已经知道一个系统属于 MIMD，还没回答另一个问题：

> 多个处理器或多个核心一起计算时，**一个核心算出来的数据，另一个核心怎么拿到？**

这就是本卡的主题：**并行计算的通信方式**。

- **Flynn 分类**：看“怎么并行计算”。
- **共享内存 / 消息传递**：看“并行单元怎么交换数据”。

因此它们不是同一套分类。一个 MIMD 系统既可以采用共享内存，也可以采用消息传递。

---

## 先解决一个容易混淆的问题：不是已经有片内总线了吗？

有。

多个 CPU 核心之间确实需要依靠**片内总线或其他片内互连**传输数据。

但这里要分清两个层次：

> **片内总线 / 片内互连解决“数据从哪条硬件通路走”。**

> **共享内存 / 消息传递解决“多个计算单元用什么方式协作和交换数据”。**

它们不是二选一，而是**上下层关系**。

~~~mermaid
flowchart TD
    A[多个核心一起计算] --> B[需要交换数据]
    B --> C{采用什么通信方式}
    C --> D[共享内存]
    C --> E[消息传递]
    D --> F[底层仍要依靠硬件互连传输]
    E --> F
    F --> G[片内总线 / Ring / Mesh / NoC 等]
~~~

可以把它理解成：

- **共享内存 / 消息传递**：决定“大家怎么交流”；
- **片内总线 / 片内互连**：负责“这些数据实际上怎么送过去”。

所以：

> **共享内存讲的是通信模型，片内总线讲的是硬件传输通路。**

### 一个多核 CPU 的例子

假设 Core 0 算出一个结果，Core 1 接下来要使用它。

从程序和体系结构模型上看：

> Core 0 把结果写到共享地址空间，Core 1 再读取 —— 这是**共享内存通信**。

但从硬件上看，数据真正到达 Core 1 时，可能经过：

~~~mermaid
flowchart LR
    C0[Core 0] --> I[片内互连]
    I --> Cache[共享 Cache / 缓存一致性系统]
    Cache --> C1[Core 1]
    I --> MC[内存控制器]
    MC --> MEM[主存]
~~~

也就是说，**共享内存并没有替代片内总线**。

它只是规定：

> “两个核心通过共同的地址空间交换数据。”

至于数据最后经过总线、环形互连、Mesh 还是 NoC，是更底层的硬件实现问题。

> 软考阶段把它记成：**多核之间通过片内互连传数据；共享内存和消息传递描述多核或多处理器之间的通信方式。**

## 多个核心一起算，结果怎么交给别人

并行计算不只是“多个人同时干活”。

A 算出的中间结果，B 往往还要继续使用。

因此真正的问题是：

> **处理单元之间用什么方式交换结果？**

主要有两种思路：

1. **共享内存**
2. **消息传递**

---

## 共享内存：大家看同一块白板

多个处理器或核心共享一个地址空间。

一个处理器把结果写入共享内存，另一个处理器直接读取。

~~~mermaid
flowchart LR
    P1[处理器 / Core 1] <--> M[共享地址空间]
    P2[处理器 / Core 2] <--> M
~~~

这里的“共享内存”重点不是说：

> 两个核心一定直接连在同一颗 RAM 上。

而是说：

> **它们看到的是共同的地址空间，可以通过读写同一个地址来交换数据。**

实际硬件中，数据可能暂时存在各级 Cache 中，并通过缓存一致性机制保证多个核心看到的数据尽量一致。

### 为什么共享内存需要同步

“共享”只解决了：

> **大家都能访问同一份数据。**

却没有规定：

> **大家以什么顺序修改这份数据。**

假设共享变量 `count = 10`，两个线程都要做 `count = count + 1`。

这个看起来像一步的动作，实际通常至少包含：

1. 读出旧值；
2. 加 1；
3. 写回。

如果两个线程都先读到 10：

~~~mermaid
sequenceDiagram
    participant A as Core A
    participant M as 共享数据 count
    participant B as Core B

    A->>M: 读取 10
    B->>M: 读取 10
    A->>M: 写回 11
    B->>M: 写回 11
~~~

最终可能仍然是 11，而不是预期的 12。

因此多个执行单元并发修改共享数据时，需要锁、信号量、原子操作等同步机制。

> **共享内存解决“数据放在哪里共同访问”，同步解决“大家什么时候能修改这份数据”。**

---

## 消息传递：各自有本子，需要时发消息

另一种思路是：

> 各处理单元拥有相对独立的数据空间，需要通过**发送 / 接收消息**显式交换结果。

~~~mermaid
flowchart LR
    A[处理单元 A<br/>自己的数据] -->|发送消息| I[互连]
    I -->|接收消息| B[处理单元 B<br/>自己的数据]
~~~

注意：

> **消息传递同样需要底层硬件互连。**

如果是同一芯片内部，可以经过片内互连；

如果是多台服务器组成的集群，则通常经过网络。

所以“消息传递”和“片内总线”也不是竞争关系。

---

## 为什么消息传递特别适合集群

集群通常由多台独立计算机组成。

每台机器都有自己的物理内存：

~~~mermaid
flowchart LR
    A[服务器 A<br/>CPU + 自己的内存] --> N[网络]
    N --> B[服务器 B<br/>CPU + 自己的内存]
~~~

A 机器不能像访问自己的 RAM 一样，直接使用普通内存地址读取 B 机器的 RAM。

因此最自然的方式就是：

> **把任务、数据或计算结果封装成消息，通过网络发送给另一台机器。**

所以消息传递并不是“比共享内存更高级”，而是特别适合：

> **各节点物理内存彼此独立的系统。**

常见的集群和分布式并行通常采用这种思路。

---

## 两种通信方式怎么区分

| 对比 | 共享内存 | 消息传递 |
| --- | --- | --- |
| 核心思路 | 大家访问同一地址空间 | 各自保存数据，需要时互发消息 |
| 数据交换 | 读写共享数据 | 显式发送 / 接收 |
| 常见问题 | 同步、锁、缓存一致性 | 通信延迟、消息组织 |
| 常见场景 | 多核、共享内存多处理器 | 集群、分布式并行 |
| 底层是否需要互连 | 需要 | 需要 |

最容易考混的一点：

> **片内总线 / 片内互连不是第三种并行通信方式。**

它属于更底层的**硬件连接机制**。

---

## 把这一组概念串起来

~~~mermaid
flowchart LR
    A[多核 / 多处理器] --> B[一起并行计算]
    B --> C[需要交换中间结果]
    C --> D{通信模型}
    D --> E[共享内存<br/>读写共同地址空间]
    D --> F[消息传递<br/>发送 / 接收]
    E --> G[硬件负责真正搬运数据]
    F --> G
    G --> H[片内总线 / 片内互连 / 网络]
~~~

因此整条知识链是：

> **多核 / 多处理器 → 并行计算 → 需要通信 → 选择共享内存或消息传递 → 底层再依靠片内互连或网络完成实际传输。**

---

## 一句话记住

> **共享内存和消息传递讲“怎么交流”，片内总线讲“数据怎么走”。**

再加一句：

> **共享内存是在同一块白板上协作；消息传递是各写各的本子，需要时互相发消息。**

2023 年回忆资料中出现过“并行计算通信方式，共享内存和消息传递”的近年信号。
