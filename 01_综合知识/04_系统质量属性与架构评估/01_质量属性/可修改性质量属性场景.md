# 可修改性质量属性场景：改一个需求，为什么有的系统只动一处，有的全身都要改

任何软件理论上都能改。架构师真正关心的是：

> 改一个功能时，需要改多少位置、花多少人力、会不会连带破坏其他功能。

| 要素 | 典型内容 |
| --- | --- |
| 刺激源 | 用户、开发人员、管理员 |
| 刺激 | 增加/删除/修改功能、质量属性或容量 |
| 环境 | 设计、编译、构建或运行时 |
| 制品 | UI、平台、环境或交互系统 |
| 响应 | 定位修改点、完成修改、测试并部署 |
| 响应度量 | 影响元素数量、工作量、费用、对其他功能/属性的影响 |

相关概念：
- 可维护性：修缺陷、实施修改是否容易；
- 可扩展性：增加新特性是否容易；
- 结构重组：重新组织构件和关系是否容易；
- 可移植性：迁移运行环境是否容易。

题干出现“修改影响范围、修改成本、受影响构件数量”，优先想到可修改性。
