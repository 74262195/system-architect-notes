# SAAM：怎么用一组场景检查架构到底好不好改

只说“这个架构可修改性很好”没有验证依据。

SAAM 的核心思路是：

> **把质量属性具体化成场景，再看架构为了支持这些场景需要付出什么变化。**

教材指出 SAAM 最初重点分析**可修改性**，后来可用于其他质量属性。

## 五步主线

~~~mermaid
flowchart LR
    A[开发场景] --> B[描述架构]
    B --> C[单场景评估]
    C --> D[场景交互]
    D --> E[总体评估]
~~~

1. **场景开发**：利益相关者提出系统必须支持的活动。
2. **架构描述**：让参与者理解构件、数据和控制关系。
3. **单场景评估**：判断场景是否被现有架构直接支持，还是需要修改。
4. **场景交互**：多个场景若都改同一构件，该处可能是变化热点。
5. **总体评估**：综合场景和交互，比较方案、识别风险。

## 题眼
“场景技术、可修改性、单场景评估、场景交互” → SAAM。
