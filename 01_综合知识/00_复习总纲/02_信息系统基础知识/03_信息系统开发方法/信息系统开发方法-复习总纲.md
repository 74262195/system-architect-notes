# 信息系统开发方法 · 复习总纲

> 预计 12 分钟。先闭卷做两次分流：**需求稳不稳**、**按什么单位组织问题域**；卡住再点原子卡。本模块是本篇篇幅最大的原因在口径，不在记忆量。

## 一、大纲边界与优先级

大纲在本章只列出**四种教材内开发方法**：结构化方法、原型法、面向对象方法、面向服务方法。它们各自回答“需求状态不同时，用什么方式组织开发”这个层次的问题。

敏捷与 V 模型不同：它们属于软件过程与生命周期模型的交叉内容，本章只要求区分“不是同一套分类”，细节回软件工程专题。这两张补充卡按 frontmatter 是 **P0**，但 P0 只来自 2026H1 公开回忆题信号；V 模型卡自己注明回忆题不是已核验官方原题，作答时仍按题干口径。

| 原子卡 | exam_priority | 什么时候做 |
| --- | --- | --- |
| [[敏捷开发方法]] | P0 | 第一轮：能区分 Scrum 与 XP 题眼，会复述迭代闭环 |
| [[V模型]] | P0 | 第一轮：会做左右配对，分清验证与确认；注意证据边界 |
| [[结构化方法]] | P2 | 第一轮只记“阶段 + 文档 + 自顶向下”入口，第二轮再补特点与边界 |
| [[原型法]] | P2 | 第一轮只记“可体验模型 + 用户反复评价”，第二轮再补适用边界 |
| [[面向对象方法]] | P2 | 第一轮只记“对象/类/状态/行为”，第二轮再补封装、继承、多态 |
| [[面向服务方法]] | P2 | 第一轮只记“接口与实现解耦、跨应用复用”，SOA 细节不在这里展开 |

**第一轮抓分顺序**：敏捷与 V 模型的题眼 → 四种方法的最小入口与互相区分。第二轮再补四张 P2 卡的机制细节。

## 二、30 秒主线

需求较稳定、要阶段控制和文档 → [[结构化方法]]；用户说不清需求、要靠可见模型反复确认 → [[原型法]]；要围绕对象、类、状态与行为组织问题域 → [[面向对象方法]]；要把能力做成稳定接口供跨应用复用 → [[面向服务方法]]。这四种都在“怎样组织开发活动”这一层，彼此可以结合使用。

敏捷补充的是“需求会变时怎样缩短反馈回路”，V 模型补充的是“开发产物与测试层次怎样对应”——它们不是第五、第六种信息系统开发方法，而是软件过程与生命周期模型口径。

## 三、题干关键词 → 第一反应

| 题干看到什么 | 第一反应与动作 |
| --- | --- |
| 自顶向下、逐层分解、阶段清楚、文档规范、阶段审查 | **结构化方法**；先答“阶段控制 + 结构分解”两个维度 |
| 先做可运行模型，请用户反复评价并修改 | **原型法**；先答反馈闭环，不是“开发快” |
| 对象、类、属性、行为、问题域模型 | **面向对象方法**；再看是否真正围绕对象组织分析与设计 |
| 服务契约、接口与实现解耦、跨应用互操作与复用 | **面向服务方法**；先答调用者依赖稳定契约 |
| Sprint、产品待办列表、产品负责人、Scrum Master | **Scrum**；不要与 XP 的工程实践混 |
| 测试驱动、结对编程、持续集成、重构、简单设计 | **XP**；题干若给指定教材清单，以题干口径为准 |
| 交付可用增量后评审反馈、再调整下一轮待办 | 敏捷迭代闭环；答“小批量交付 + 快速验证假设” |
| 需求—验收、概要/体系结构设计—集成测试、详细设计—单元测试 | **V 模型**的左右配对；对应的是测试依据 |
| “是否构造了正确的产品” / “产品是否被正确地构造” | 前者是**确认**（Validation），后者是**验证**（Verification） |

## 四、核心做题动作

**动作 A：三问定方法。** 一问需求清楚程度：稳定、能冻结规格 → 结构化；说不清、要边看边改 → 原型。二问建模单位：拆功能和处理过程 → 结构化视角；识别对象、类及其关系 → 面向对象。三问是否跨应用：把能力抽成服务供多个应用调用 → 面向服务。

**动作 B：结构化推进链。** 调查与规划 → 系统分析（要做什么）→ 系统设计（怎样实现）→ 实施与验收 → 运行与维护。关键不是背阶段名，而是前一阶段先留下可检查的文档，后一阶段才有稳定输入；发现错误允许**受控回退**，但要同步修订受影响的文档和后续成果。

**动作 C：原型闭环。** 取得基本需求 → 建立初始原型 → 交用户试用评价 → 修改补充 → 再次返回用户。没有用户评价，只有开发者自己反复改，就没有形成原型法闭环；原型也不能替代架构接口设计、非功能验证、文档与变更控制。

**动作 D：V 模型配对。** 左侧从上往下细化到编码，右侧从编码后的底部逐层向上：用户需求对验收测试，系统需求对系统测试，概要/体系结构设计对集成测试，详细设计对单元测试。这里“对应”指测试依据前置规划，**不等于左侧阶段已经执行了测试**。

**动作 E：敏捷迭代闭环。** 排序需求 → 选择本轮目标 → 设计开发测试 → 交付可用增量 → 评审与反馈 → 回到排序需求。Scrum 用产品待办列表、Sprint、评审与回顾组织这个过程；XP 用测试驱动、结对编程、持续集成等工程实践落地。

本模块没有需要保留的计算公式。

## 五、高频对比

### 四种教材内开发方法

| 方法 | 核心区分 | 典型例子 | 考试问法或陷阱 |
| --- | --- | --- | --- |
| [[结构化方法]] | 阶段控制 + 自顶向下分解 + 文档与审查 | 规则稳定的事务处理类系统，先建业务与数据模型再设计实现 | 误答“不需要用户参与”“进入下一阶段绝不能回退” |
| [[原型法]] | 可体验模型 + 用户反复试用评价 | 事项申报页面，用户走一遍才发现补交与进度提示 | 把“快速开发”当目的；原型代码直接当最终系统 |
| [[面向对象方法]] | 围绕对象、类、状态、行为与协作组织问题域 | 申请单、申请人、审核任务及其协作 | 认为“用了 UML”就能证明整个方法是面向对象 |
| [[面向服务方法]] | 能力封装为服务，调用者依赖稳定服务契约 | 查询客户、校验库存等能力被多个应用复用 | 与固定协议或产品绑定；忽略接口版本与数据语义治理 |

### 敏捷与 V 模型的口径对比

| 概念 | 核心区分 | 典型例子 | 考试问法或陷阱 |
| --- | --- | --- | --- |
| [[敏捷开发方法]] | 短周期交付与反馈应对需求变化 | Sprint 交付可用增量，评审后调整下一轮待办 | 认为“更重视可工作软件”就不要计划、文档与流程 |
| [[V模型]] | 开发产物与测试层次建立可追踪对应 | 详细设计对单元测试、概要设计对集成测试 | 把“尽早规划测试依据”说成“左侧阶段已执行测试” |

## 六、最容易丢分的地方

- **结构化方法不等于不用用户、不能回退。** 教材强调“用户第一”和阶段评审；真正的要求是回退时受控修订相互依赖的成果，把“文档多”当成它的全部设计思想也会丢分。
- **原型的目的是澄清需求，不是展示开发速度。** 原型法必须能持续获得真实用户反馈；原型不替代架构设计、安全与性能验证、文档和变更控制，反复修改也不等于可以无边界加需求。
- **“用了 UML”不能证明采用了面向对象方法。** UML 只是建模表达语言，还要看分析与设计是否真正围绕对象、类、状态、行为与协作展开；类和对象也不是同义词。
- **面向服务是开发与架构思想，不等于某一种协议或产品。** 它的稳定题眼是接口与实现解耦、跨应用互操作与复用，同时要治理接口版本、数据语义和调用可靠性。
- **V 模型的“对应”说的是测试依据。** 它强调在需求和设计阶段就规划对应层次的测试，既不等于左侧阶段已经运行测试，也不保证项目零缺陷。
- **敏捷的“更重视”不等于右侧不要。** 个体和互动、可工作软件、客户合作、响应变化是对比项，右侧的流程、文档、合同、计划仍有价值，只是用短周期反馈及时修正。
- **不要按行业机械判断方法。** “政府/银行必瀑布、互联网必敏捷”不成立；稳定或强监管项目也能采用敏捷实践，但要加强文档、追踪和合规控制。
- **敏捷、瀑布、V 模型与本章四种方法不是同一套分类。** 题干若按指定教材列举敏捷方法，以题干口径为准，不把现代实践全塞进官方清单。

## 八、闭卷自测

- [ ] 结构化方法为什么既要划分阶段，又要自顶向下分解系统？这两件事分别控制什么？
- [ ] 需求比较稳定、强调规范文档和阶段验收时，优先选哪种方法？给出两个题眼。
- [ ] 原型法的一轮闭环包含哪五步？没有用户评价时，闭环缺了什么？
- [ ] 原型能解决什么，又不能替代哪些工作？至少说出两项。
- [ ] 面向对象方法与结构化方法最先选择的建模单位有什么不同？
- [ ] “系统使用了 UML 图”是否足以证明采用了完整的面向对象方法？为什么？
- [ ] 面向服务方法中，调用者依赖的稳定对象是什么？这样做换来哪些好处、需要治理什么？
- [ ] Scrum 与 XP 各自的题眼是什么？各说两个。
- [ ] 一轮敏捷迭代的闭环步骤是什么？它为什么能应对需求变化？
- [ ] V 模型左右两侧的“对应”指什么？为什么不能理解为左侧阶段已在执行测试？
- [ ] 详细设计、概要/体系结构设计、系统需求、用户需求分别对应哪一层测试？
- [ ] “是否构造了正确的产品”和“产品是否被正确地构造”分别对应验证还是确认？
