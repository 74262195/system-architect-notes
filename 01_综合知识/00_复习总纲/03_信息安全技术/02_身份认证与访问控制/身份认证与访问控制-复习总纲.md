# 身份认证与访问控制 · 复习总纲

> [!tip] 用法（约 8 分钟）
> 先闭卷回答自测，卡住再点原子卡。本模块的核心只有一句话：**认证回答“你是谁”，访问控制回答“这次操作能不能做”。**

## 大纲要求到哪里

本模块对应大纲的**认证分类与访问控制技术**（SEC-A14～SEC-A16 与认证部分的落点见 [[信息安全技术-覆盖与减负审查-2026-09-09]]）。要求能区分：

- 身份认证的多种实现（口令、令牌、生物特征、证书、Kerberos、多因素）；
- 访问控制的主体、客体、策略，以及矩阵、ACL、能力表、授权关系表的落地方式；
- DAC / MAC / RBAC 三种策略依据的辨析。

**优先级**：
- 第一轮必抓 **P1**：[[身份认证]]、[[访问控制基础]]、[[Kerberos认证]]；
- 第二轮补 **P2**：[[DAC自主访问控制]]、[[MAC强制访问控制]]、[[RBAC基于角色访问控制]] 的“第一判断入口”；
- **P3**：[[单点登录SSO]] 时间紧可跳过，只需知道它是“一次认证、多系统复用身份结果”的能力。

## 30 秒主线

[[身份认证]] 先确认当前主体是谁（证书认证本来就是其中一种实现，不是它之后的额外步骤）→ [[访问控制基础]] 按主体、客体、策略作出允许/拒绝判决，并补齐执行与审计 → [[DAC自主访问控制]] / [[MAC强制访问控制]] / [[RBAC基于角色访问控制]] 回答“权限依据什么规则分配” → [[Kerberos认证]] 给出一个基于可信第三方与对称票据的网络认证实例 → [[单点登录SSO]] 是跨系统复用认证结果的工程扩展。

## 题干关键词 → 第一反应

| 题干看到什么 | 第一反应 |
| --- | --- |
| 口令 / PIN | 所知因素 |
| 硬件令牌 / 智能卡 / 设备私钥 | 所有因素 |
| 指纹 / 人脸 / 虹膜 | 所是因素 |
| 口令 + PIN 算不算双因素 | 不算，同属“所知”；多因素必须来自不同类别 |
| 认证通过后仍被拒绝读文件 | 认证 ≠ 授权，继续看访问控制 |
| 主体 / 客体 / 读、写、执行 | 访问控制矩阵 |
| 查“谁能访问这份文件” | ACL（按客体保存一列） |
| 查“这个用户能访问什么” | 能力表（按主体保存一行） |
| 属主自主授权、共享、权限转授 | DAC |
| 密级、安全标签、强制规则、BLP / Biba | MAC |
| 岗位、角色、用户—角色—权限、职责分离 | RBAC |
| KDC / AS / TGS / TGT / 服务票据 | Kerberos，对称密钥为核心的第三方认证 |
| 一次登录、多系统免重复认证 | SSO（先掌握身份认证与 Kerberos 再看） |
| OAuth 2.0 / OIDC / JWT | OAuth 2.0 是授权框架；OIDC 才是其上的身份认证层；JWT 只是令牌格式 |

## 核心做题动作

### 1. 一次认证先走四步

**声明身份 → 提交凭据或证明 → 系统验证 → 通过则建立认证结果/会话并交给访问控制**；失败则拒绝、限速或告警。

### 2. 认证之后必须再走访问控制四步（[[访问控制基础]]）

认证确认是谁 → 授权/策略判决能做什么 → **执行**真正放行或拒绝 → **审计**记录谁在何时做了什么。判决和执行必须配合：只算出“应该拒绝”却没拦住请求，访问控制仍然失败。

### 3. 一次访问请求按“主体 + 客体 + 动作 + 上下文”判决

上下文中可以包含时间、位置、设备状态等。做查询方向题时先看题干问的是“谁能访问它”（ACL）还是“它能访问什么”（能力表）。

### 4. Kerberos 只记三段（[[Kerberos认证]]）

1. 向 AS 认证，拿到 **TGT** 和“客户端—TGS 会话密钥”；
2. 用 TGT + 新鲜认证器向 TGS 换取**服务票据**；
3. 用服务票据 + 新认证器访问目标服务。

记忆口径：**外层票据给目标服务器解，客户端拿配套会话密钥证明自己**——TGT 给 TGS 解，服务票给具体服务解，客户端既不必要也不能解开票据本体。

### 5. 本模块没有必须背的公式

认证与访问控制考的是判定方向而不是计算；若题目给出角色层次，按题目给出的父子方向判断，不要死背“子继承父”。

## 高频对比

| 对比组 | 核心区分 | 典型例子 | 考试问法 / 陷阱 |
| --- | --- | --- | --- |
| 认证 vs 授权 vs 审计 | 你是谁 / 你能做什么 / 你做过什么 | 口令登录 → 读工资表被判权 → 记录操作 | 陷阱是“登录成功所以能访问”；或判决算了却没执行 |
| DAC vs MAC vs RBAC | 属主自主授权 / 系统按标签强制 / 按岗位角色授权 | 文件共享 / 密级标签 / 岗位角色 | 陷阱是 MAC 说成“绝对最安全”，或把 DAC 等同于 ACL |
| 访问矩阵三种落地 | 按列保存 / 按行保存 / 只存非空关系 | ACL / 能力表 / 授权关系表 | 陷阱是查询方向答反（“谁能访问”该用 ACL） |
| 证书认证 vs Kerberos | PKI 公钥体系 / 对称密钥 + 可信第三方票据 | HTTPS 服务器认证 / 域内访问文件服务 | 陷阱是把 Kerberos 说成 PKI 证书体系 |
| SSO 目标 vs 实现机制 | 能力/目标 / 具体协议 | SAML、OIDC、CAS、Kerberos | 陷阱是“用了 JWT 就是 SSO 协议”，或把 OAuth 2.0 当认证协议 |

## 最容易丢分的地方（为什么错）

- **把证书认证当成身份认证之后的另一道必经步骤。** 错在没看出“数字证书是身份认证可用的一种凭据/机制”；TLS 里验证证书 + 服务器证明持有私钥，就已经完成该场景的服务器身份认证。
- **口令 + PIN 当双因素。** 错在只数凭据个数，没检查因素类别是否不同。
- **认证通过就以为权限到手。** 认证只确认身份，读工资表还要按策略判权。
- **以为认证通过就不需要审计。** 策略难以约束所有滥用情形（尤其特权用户），审计是访问控制教材主线的一部分。
- **MAC 说成“绝对最安全”。** 错在忽略它仍依赖正确的标签、策略和管理员配置；它只保证普通属主不能自行越过强制规则。
- **MAC 口诀到处套。** “不上读、不下写”（BLP）与“不下读、不上写”（Biba）只在相应多级安全模型语境成立。
- **角色继承方向死背。** 不同教材或实现定义可能不同，应按题目给出的角色层次方向判断。
- **Kerberos 防重放只答“票据过期”。** 还要有认证器中的时间信息、短时间窗口和服务端重放检查；时钟偏差过大会导致认证失败。
- **票据通过就以为能读任意文件。** Kerberos 只证明身份与会话密钥持有关系，具体文件仍要应用授权判定。
- **拿 SSO 当协议。** SSO 是目标/能力；Kerberos、SAML、OIDC、CAS 是实现方式，JWT 只是令牌格式。
