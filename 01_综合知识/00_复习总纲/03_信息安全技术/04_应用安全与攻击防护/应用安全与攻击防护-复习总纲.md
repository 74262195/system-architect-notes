# 应用安全与攻击防护 · 复习总纲

> [!tip] 用法（约 10 分钟）
> 先闭卷回答自测，卡住再点原子卡。本模块只做一件事：**看清攻击者到底“做了什么动作”，而不是看到“网站打不开”就猜攻击名。**

## 大纲要求到哪里

本模块对应大纲的**攻击与防护**：DoS/DDoS、ARP/DNS/IP 欺骗、端口扫描分类、SYN/ICMP/SNMP 三类协议攻击，以及 Web 应用输入边界（SEC-A17～A19、A22 的落点见 [[信息安全技术-覆盖与减负审查-2026-09-09]]）。要求能做两段判断：

- **攻击识别段**：[[常见网络攻击]] → [[网络欺骗-ARP、DNS与IP欺骗]] → [[端口扫描-怎样用响应判断服务暴露]] → [[TCPIP协议攻击-SYN、ICMP与SNMP]]；
- **应用防护段**：[[SQL注入]] → [[XSS跨站脚本]] → [[CSRF跨站请求伪造]]。

**优先级**：第一轮必抓 **P1** 的 [[常见网络攻击]]（含 SYN Flood 与 DDoS、重放、中间人）；其余 6 张为 **P2**，第二轮补齐识别入口；本模块没有 P3。

## 30 秒主线

[[常见网络攻击]] 先用一句话把现象对到攻击名 → 欺骗类继续问“攻击者替换了哪一份对应关系” → [[端口扫描-怎样用响应判断服务暴露]] 是攻击前的信息收集 → [[TCPIP协议攻击-SYN、ICMP与SNMP]] 是即使没有业务漏洞也能滥用的协议能力 → 通道正常不代表应用安全，主线交到 [[SQL注入]]、[[XSS跨站脚本]]、[[CSRF跨站请求伪造]]。

## 题干关键词 → 第一反应

| 题干看到什么 | 第一反应 |
| --- | --- |
| 服务不可用、资源耗尽或异常崩溃 | DoS |
| 很多攻击源一起打、多源大量请求 | DDoS（说法是规模与来源） |
| SYN 很多、ACK 不回来、半连接堆积、SYN_RECV | SYN Flood（说法是具体手法） |
| 以前的合法报文又出现一次、重复执行 | 重放攻击；加密挡不住，要靠新鲜性检查 |
| 双方都以为在直接通信、证书校验有问题 | 中间人攻击 |
| IP-MAC 映射异常、局域网流量被转走 | ARP 欺骗 |
| 域名正确、却连到假地址，原网站未被入侵 | DNS 欺骗 |
| 外部报文却声称来自内部网段 | IP 欺骗；入口源地址过滤 |
| 逐个探测端口、收集开放服务与系统特征 | 端口扫描（信息收集，不等于已入侵） |
| 完整三次握手 | 全 TCP 连接扫描 |
| 收到 SYN+ACK 后立即发 RST | SYN（半开）扫描 |
| FIN、关闭端口回 RST、开放端口通常不回应 | FIN 扫描（教材识别模型） |
| 肉鸡 / 第三方代为探测 | 代理（第三方）扫描 |
| Ping、差错控制报文、ICMP 重定向 | ICMP 攻击 |
| 设备管理接口、改流向、改优先级、断连 | SNMP 攻击；收紧管理面 |
| 拼接 SQL、登录绕过、异常查询 | SQL 注入；参数化查询 |
| 评论区回显、浏览器执行脚本、DOM sink | XSS；按上下文输出编码 |
| 已登录、跨站诱导、自动带 Cookie、转账改密 | CSRF；Token / SameSite / 来源校验 |

## 核心做题动作

### 1. 三问定攻击名（[[常见网络攻击]]）

攻击者**做了什么动作** → 是**拒绝服务、伪造、重放还是插入** → 这个动作强迫目标处理什么资源。看到“网站打不开”不要直接选 DDoS，先看它是被什么动作打坏的。

### 2. 欺骗题三步（[[网络欺骗-ARP、DNS与IP欺骗]]）

**圈出被伪造的对象**（映射表 / DNS 应答 / IP 报头源地址）→ **对应层次**（局域网地址解析 → ARP；名称解析 → DNS；网络层源地址 → IP）→ **选同层防线**（ARP 绑定/检测、DNS 应答检查、边界源地址过滤）。

### 3. 端口扫描看“动作 → 响应 → 判断”（[[端口扫描-怎样用响应判断服务暴露]]）

先发什么报文，再看回什么。SYN 扫描走一遍：发 `SYN` → 开放端口通常回 `SYN+ACK` → 扫描方发 `RST` 终止，握手未完成 → 若直接回 `RST` 则判为关闭。它与 SYN Flood 都出现 SYN，但**一个是个别试探收集信息，一个是大量半连接耗尽资源**。

### 4. 协议攻击先问“被强迫处理什么”

连接状态 → SYN Flood；ICMP 控制报文 → ICMP 攻击；管理操作 → SNMP 攻击。防御也按对象对应：限制半连接与超时、过滤/限速控制报文、最小化管理暴露并强认证。

### 5. 三条 Web 输入边界的根因修复

| 考点 | 边界在哪里被越过 | 首位动作 |
| --- | --- | --- |
| [[SQL注入]] | 输入从“数据”变成 SQL 语法的一部分 | 参数化查询/安全 ORM 绑定，先固定 SQL 结构再单独传值 |
| [[XSS跨站脚本]] | 不可信内容进入 HTML/属性/URL/JS 等执行上下文 | 按输出上下文正确编码，优先用不解释为 HTML 的安全 DOM API |
| [[CSRF跨站请求伪造]] | 借浏览器自动携带的已有身份发请求 | 抗 CSRF Token + 合理 SameSite + Origin/Referer 校验，高风险操作再认证 |

SQL 注入的最小对照：把 `x' OR '1'='1` 直接拼进语句，单引号会提前结束字符串、`OR '1'='1'` 变成 SQL 条件；用参数绑定接口时，整段字符串只作为一个值来比较。注意 `?` 只是常见占位符示意，**必须通过驱动/ORM 单独传值**，不是先拼好整条 SQL 再执行。

### 6. 本模块没有必须背的公式

判定靠“动作、被伪造对象、被滥用的协议能力、输入进入的上下文”；没有需要套用的计算式。

## 高频对比

| 对比组 | 核心区分 | 典型例子 | 考试问法 / 陷阱 |
| --- | --- | --- | --- |
| SYN Flood vs DDoS vs 端口扫描 | 具体手法 / 组织规模与来源 / 信息收集 | 半连接堆积 / 多源同时打 / 逐个探端口 | 陷阱是三者混用；题干问“探测开放端口”答成拒绝服务 |
| 四类端口扫描 | 完整握手 / 半开 / FIN / 第三方代扫 | 全 TCP、SYN、FIN、代理 | 陷阱是 FIN 的 RST/无回应当成所有现实系统的绝对规律 |
| ARP vs DNS vs IP 欺骗 | 伪造 IP-MAC 映射 / 域名到 IP 应答 / 报文源地址 | 局域网流量被转走 / 连到假网站 / 外部包自称内网 | 陷阱是“都叫欺骗”就不分对象；IP 欺骗不是改目的地址 |
| SYN vs ICMP vs SNMP 攻击 | 滥用连接状态 / 控制报文 / 管理能力 | 半连接耗尽 / Ping 与重定向 / 改设备流向 | 陷阱是都写成“流量大”，防御只答扩容 |
| SQL 注入 vs XSS vs CSRF | 改数据库指令 / 浏览器执行脚本 / 借用已有身份发请求 | 登录绕过 / 评论区脚本 / 已登录转账 | 陷阱是答“过滤单引号”“过滤 `<script>`”当根治；XSS 可绕过许多 CSRF 防护 |

## 最容易丢分的地方（为什么错）

- **把 SYN Flood 与 DDoS 当同一层级。** SYN Flood 说手法，DDoS 说多少源一起打；“DDoS SYN Flood”完全成立。
- **以为加密了就不会被重放。** 攻击者不需要看懂密文，只要把以前合法的数据原样再发一次；要靠 Nonce、时间戳、序列号或一次性票据判断新鲜性。
- **把中间人等同于被动窃听。** 中间人会夹在双方之间分别冒充对方；防它不只需要加密，还需要身份认证和正确的证书校验。
- **ARP 欺骗与 DNS 欺骗混用。** 前者改局域网 IP-MAC 映射，后者改域名解析应答；DNS 欺骗不必攻破原网站。
- **把 DNS 教材检测方法当充分防线。** 多应答监听、主动探测、反向交叉查询都只能作为**告警线索**（各有依赖假设），合法的多地址与分流解析也会造成不一致。
- **把 DNSSEC 说成万能。** 它在域名区域已签名且解析器验证成功时，为 DNS 数据提供来源认证与完整性；不验证页面内容，也不替代传输加密与 HTTPS 服务身份校验。
- **IP 欺骗说成“改目的地址”。** 它伪造的是源地址；“伪造源 IP”是动作，能否完成连接仍受三次握手和序号确认限制。
- **端口当物理插槽。** 端口是主机的通信逻辑入口（套接字中的 `[IP: 端口]`）；扫描得到的是攻击面线索，不等于已经攻破主机。
- **“SYN 扫描不会被发现”。** 教材口径是“比完整连接扫描更不易被目标主机记录且较快”，属相对比较；SYN 报文仍经过网络设备，IDS/防火墙仍可能识别探测模式。
- **FIN 扫描当绝对规律。** RST/无回应的差异依赖具体 TCP/IP 实现和过滤策略，考试按教材识别模型判断即可。
- **拿黑名单过滤或 WAF 代替参数化查询。** 根因是数据与指令边界不清；白名单校验、最小权限、错误收敛、WAF 都是补充或纵深防线。
- **“统一 HTML 转义能覆盖所有上下文”。** 属性、URL、JavaScript、CSS 解析规则不同；`textContent` 也只适用于把纯文本放入元素内容，富文本需要可靠净化器。
- **HttpOnly 当 XSS 根治手段。** 它只限制脚本直接读取某些 Cookie，恶意脚本仍可篡改页面、诱导操作或利用已有会话发请求。
- **把“目标站完全不校验来源”当成 CSRF 必要定义。** 核心是服务器缺少能证明请求来自合法交互的抗伪造机制。

- 上游：[[TLS与HTTPS]] —— **通信通道安全 ≠ 应用代码安全**，HTTPS 正常也挡不住 SQL 注入、XSS、CSRF。
