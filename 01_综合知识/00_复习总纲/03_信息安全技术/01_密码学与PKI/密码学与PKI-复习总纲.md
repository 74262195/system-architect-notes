# 密码学与PKI · 复习总纲

> [!tip] 用法（约 10 分钟）
> 先闭卷回答每节末尾的自测，卡住再点对应原子卡；本页只做召回，不承担第一次教学。

## 大纲要求到哪里

本模块对应大纲的**加解密与密钥管理、认证与签名**部分（覆盖情况见 [[信息安全技术-覆盖与减负审查-2026-09-09]] 的 SEC-A09～SEC-A16）。要求能识别：

- 数据加密的作用与保密通信模型；
- 对称加密原理及 DES/IDEA/AES 的定位；
- 非对称加密原理及 RSA 的定位；
- 对称密钥分配与使用控制、公钥分配与证书/CA；
- 数字签名（含教材的对称密钥仲裁模型与公开密钥签名）；
- 密钥选择与生成因素。

**优先级**：本模块 6 张卡全部为 **P1（重点）**，没有可跳过的 P2/P3；第一轮就要把 [[对称加密]]、[[非对称加密]]、[[哈希算法]]、[[数字签名]]、[[数字证书与PKI]]、[[密钥管理]] 全部走通。

## 30 秒主线

[[对称加密]] 用共享密钥高效保护大量数据，但留下“密钥怎么安全送到对方”这一痛点 → [[非对称加密]] 用公私钥对补上密钥建立、身份与签名，但只做保密或签名方向的判断 → [[哈希算法]] 先把“内容变没变”压成摘要，为签名提供处理对象 → [[数字签名]] 用发送方私钥签、发送方公钥验，回答“是谁签的” → [[数字证书与PKI]] 再回答“验签用的公钥到底属于谁” → [[密钥管理]] 收口到密钥的生成、用途约束、分发、轮换与销毁。

## 题干关键词 → 第一反应

| 题干看到什么 | 第一反应 |
| --- | --- |
| AES / DES / 3DES / IDEA / RC4 | 先做“是不是对称算法”的归类 |
| AES-GCM / CBC / CTR / ECB | 这是**工作模式**，不要与算法名混为一类 |
| 共享密钥 + 大量数据 + 高效率 | 对称加密 |

| RSA / ECC、公钥 / 私钥 | 公钥密码，先判断问的是保密、签名还是协商 |
| DH / ECDH | 协商共享秘密，不是拿来直接加密大量业务数据 |
| A 给 B 发秘密 | 找 B 的密钥对：B 公钥保护、B 私钥处理 |
| 证明“这是我签的” | 找 A 的密钥对：A 私钥签名、A 公钥验证 |
| 摘要 / SHA / 碰撞 / 完整性 / HMAC | 哈希；HMAC 是“共享密钥 + 哈希” |
| 口令不能明文保存 | 带盐的口令 KDF / 慢哈希，不是普通快速哈希 |

| CRL / OCSP | 证书还没过期，是否已被提前撤销 |
| KDC、集中分发会话密钥 | 长期主密钥 + 短期会话密钥 |
| 密钥标签 / 控制矢量 | 约束密钥“只能做该做的事” |

## 核心做题动作与必要公式

### 1. 保密还是签名：先问“最终只想让谁打开 / 只想证明谁”

- 给 B 保密 → 用 **B 的公钥**保护，B 用自己的私钥处理；
- 验证 A 的签名 → A 用 **A 的私钥**签名，别人用 **A 的公钥**验证；
- 同时要求保密 + 来源验证 → 加密和签名是两个动作，可以组合，不是一件事。

### 2. 验签四步（[[数字签名]]）

1. B 对收到的消息重新计算 Hash，得到“收到消息的摘要”；
2. B 用 A 的公钥执行签名验证；
3. 验证算法检查签名与当前消息/摘要是否匹配；
4. 匹配则通过；改了消息而签名不变，就会失败。

### 3. 两两独立共享密钥的数量（[[对称加密]]、[[密钥管理]]）

**第一步：先判断题目在数“用户对”还是“每个人自己”。** 每对需要独立通信的用户共用一把密钥，不是每人一把。

**第二步：数不同用户对。**

$$
\text{不同共享密钥数}=\frac{N(N-1)}{2}
$$

- $N$：用户（主体）总数，单位“人/个”；
- 结果单位：**把**（每一对一把）；中文读作“N 乘 N 减 1 再除以 2”；
- 除以 2 的原因：AB 与 BA 是同一对，先按 $N(N-1)$ 数会把每一对数两遍。

**第三步：代数字。** 4 个用户为 $4\times3/2=6$ 把（AB、AC、AD、BC、BD、CD）；10 个用户为 $10\times9/2=45$ 把。

> [!warning] 适用条件
> 该式只在“每一对用户都预先维护一把独立共享密钥”的模型下成立。题目若改成 KDC 集中分发会话密钥，就不能机械套用；若问“每个用户自己要与其他人建立多少个共享关系”，答案是 $N-1$。

### 4. 证书验证不是只验一次签名（[[数字证书与PKI]]）

按清单逐项过：能否建链到可信根 → 每层签名是否正确 → 是否在有效期 → 身份/域名是否匹配（现代 HTTPS 主要看 SAN）→ 用途是否允许 → 策略要求时是否已撤销（CRL/OCSP）。

### 5. 密钥分发的三条线（[[密钥管理]]）

密钥空间 / 强密钥 / 随机性回答“**难不难猜**”；密钥标签 / 控制矢量回答“**允许拿去做什么**”；KDC、可信目录、证书回答“**怎样安全交给对方**”。三者不能互相替代。

## 高频对比

| 对比组 | 核心区分 | 典型例子 | 考试问法 / 陷阱 |
| --- | --- | --- | --- |
| 对称 vs 非对称 | 一把共享密钥 vs 一对公私钥；效率高 vs 解决密钥建立与签名 | AES vs RSA | “大量数据用哪种”“给 B 保密用谁的密钥”；陷阱是保密也用发送方公钥 |
| 加密算法 vs 工作模式 | 基本变换用什么 vs 长数据怎样连续调用分组算法 | AES vs ECB/CBC/CTR/GCM | “AES 和 GCM 是不是并列算法”；陷阱是答成两个算法 |
| 哈希 vs 签名 vs 证书 vs 加密 | 内容变没变 / 谁签的 / 公钥属于谁 / 别人能不能看懂 | SHA-256 / RSA 签名 / X.509 / AES | 四件事互相不替代；陷阱是“签名了所以内容保密” |
| 对称会话密钥撤销 vs 证书吊销 | KDC 撤销会话密钥 vs 公钥信任链的证书状态 | 会话密钥疑似泄露换钥 vs CRL/OCSP | 陷阱是拿吊销证书代替撤销对称会话密钥，或只把到期时间延后 |
| 自签名 vs 可信 | 描述“谁签了这张证书” vs 客户端是否把它当信任起点 | 根证书、自签证书告警 | 陷阱是答“根证书因为自签名所以可信” |

## 最容易丢分的地方（为什么错）

- **AES ≠ GCM。** 错在把“算法”和“规定怎样连续使用算法的模式”当成同一层次；AES-GCM 是“用 AES 做基本变换、按 GCM 规则完成加密和认证”。
- **保密看接收方，不是发送方。** 错在背了口诀却不想“这份秘密最终只想让谁打开”，于是误用 A 自己的公钥。
- **签名不保密。** 数字签名主要证明来源和完整性，原文仍可能被别人看到；要保密必须另外加密。
- **“私钥签名”不是“私钥加密整段原文”。** 实际签名通常先对消息求摘要，再对摘要及其规范化编码做签名运算。
- **哈希不是加密。** 安全哈希没有“用密钥还原原文”的解密过程；被问到加密/解密就不该答哈希。
- **单独公布 SHA-256 不抗主动攻击者。** 因为攻击者能同时替换文件和公开摘要；还要靠可信发布渠道、签名或带密钥的认证。
- **口令不能只做一次普通快速哈希。** Salt 降低预计算和“相同口令得到相同存储值”的风险，慢哈希/KDF 提高每次猜测成本，两者作用不同，Salt 不能替代“慢”。
- **验签成功 ≠ 公钥属于 A。** 攻击者用自己私钥签名、按自己的公钥验证，数学上一样通过；公钥归属要靠证书/PKI。
- **证书里没有主体私钥。** `.p12/.pfx` 能把证书、私钥、链打包，但那是文件打包方式，不能推出“证书本身包含私钥”。
- **根证书自签名 ≠ 天然可信。** 自签名只说明签名与自己的公钥匹配；可信是因为被放进客户端/管理员的**可信根证书库**。
- **CA 签名正确 ≠ 网站一定可信。** 证书只证明身份与公钥的绑定，不担保业务代码、安全运营和内容。
- **会话密钥疑似泄露：只延长到期时间不够。** 应停止并撤销旧钥、检查影响范围、经可信路径分发替代钥、验证旧钥被拒用、再按要求销毁或受控保全；换钥也不能自动证明旧密文从未被读取。
- **算法强不代表系统安全。** 密钥泄露、发错人、长期不换或错误使用，都会让加密失效。
