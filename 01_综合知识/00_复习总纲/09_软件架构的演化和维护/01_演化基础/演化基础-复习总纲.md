# 演化基础 · 复习总纲

## 用法

预计 5～8 分钟。先盖住下文，自问“这次变化落在组件、连接件还是约束上，还会波及谁”，卡住再点对应子卡。

本页只是复习路径与判据索引，不是新的知识事实源：只从已审核原子卡与章节索引提炼；与原子卡冲突时以原子卡为准。

## 大纲边界与优先级

大纲 9.1 的要求停在“架构为什么必须演化、演化到底改哪些元素”这一层，主教材第 10.1 节把它展开成架构定义与演化对象。本模块只有 2 张卡：

- 第一轮先抓 [[02_架构演化到底改变哪些元素]]（`exam_priority: P0`；2022 下半年综合知识第 38 题直接考构件演化）；
- 第一轮随后补 [[01_软件架构为什么必须持续演化]]（`exam_priority: P1`；2010 与 2018 论文有演化信号，无综合知识逐年题频）。

边界要分清：

- 本模块只回答“为什么变、变成哪几类元素、会波及什么”，不展开面向对象演化操作、演化时期与维护动作；
- `ABSD` 里也有一个叫“架构演化”的子过程，它归 06 章 [[05_ABSD：如何从架构需求逐步形成可交付架构]]；本章研究的是演化本身的对象、时期、方式、原则、评估和维护；
- 质量属性（性能、可靠性、可修改性等）是目标与观察维度，主事实源在 07 章 [[质量属性-复习总纲]]，本模块不复制定义。

## 30 秒主线

需求、业务、技术和运行环境持续变化 → 旧架构出现不适配 → **先识别架构级影响，而不是直接改代码** → 把变化落到 `SA = {components, connectors, constraints}` 三类元素上 → 区分直接变更、受波及和未受影响元素。

一句话：**变化先过架构层；演化就是对组件、连接件、约束的增删改，再加上它带出的波及。**

## 题干关键词 → 第一反应

| 题干信号 | 第一反应（先做的判断动作） |
| --- | --- |
| 新需求、业务规则、访问量、部署环境、技术替换 | 先判“架构是否需要演化”，不要直接答改代码 |
| “上线后发现错误才修复” | 判错：演化的驱动力不限于纠错 |
| 新增/删除/替换/拆分/合并模块或服务 | 组件（component）变化 |
| 增删调用、消息、接口，改变交互顺序或方向 | 连接件（connector）变化 |
| 拓扑、配置参数、超时重试、时序规则改变 | 约束（constraint）变化 |
| 题干只说“改了某个组件” | 不完整：继续追受波及元素 |
| 提到 ABSD 六步中的演化阶段 | 那是流程位置，不是本章的演化知识域 |
| 问性能、可靠性、可修改性“要守住什么” | 那是质量属性目标，回 07 章 |

## 核心做题动作：三步定位

1. **判层级**：这次变化是架构级（影响整体结构与质量能力），还是普通局部补丁？出现新需求、环境、技术或质量目标变化，先按架构级处理。
2. **映射元素**：把“改了架构”拆成具体对象——做事或存数据的是组件；组件之间怎样交互的是连接件；必须遵守的拓扑、配置或规则是约束。
3. **追波及**：找到第一处变化后，沿依赖、交互和约束继续追，把结果分成直接变更元素、受波及元素、未受影响元素。

常用对照：`SA = {components, connectors, constraints}`。

本模块没有需要代入计算的公式，考的是层级判断与元素归类，不必自造公式区。

## 高频对比

| 易混对 | 核心区分 | 典型例子 | 考试问法与陷阱 |
| --- | --- | --- | --- |
| 架构演化 vs 架构维护 | 前者回答“为什么变、改什么、何时/怎样变”；后者回答“怎样管理已有架构资产，让它可理解、可追踪、可继续修改” | 拆出库存服务 vs 记录决策、控制波及、保留基线 | 把架构维护等同于改代码 |
| 架构演化 vs 上线后纠错 | 驱动力还包括新需求、业务环境、运行环境与技术变化 | 多城市接入导致单库压力 | 题干写“修复缺陷”就排除演化 |
| 演化对象 vs 质量属性 | 组件—连接件—约束是“变什么”；性能、可靠性、可修改性是“要守住什么” | 新增调用 vs 响应时间目标 | 把质量属性当成演化元素 |
| 本章演化 vs ABSD 架构演化 | ABSD 的演化是开发流程中的一个子过程；本章是独立知识域 | 六步流程 vs 对象/时期/方式/原则/评估/维护 | 用 ABSD 六步回答本章题 |

## 最容易丢分的地方

- **把演化当成“设计失败的补救”**：架构演化的目的是维持架构自身的有用性，它贯穿需求、建模、文档、实现和维护多个阶段，不只是上线后返工。
- **看到一个组件变化就收工**：拆出一个服务通常同时带出新的连接件（调用、消息）和新的约束（超时、重试、一致性），必须继续追。
- **把三类元素当成三个互不相干的盒子**：组件变化常牵动连接件，连接件变化又可能触碰约束，这正是波及效应。
- **把质量属性和演化对象混成一层**：质量属性是目标和观察维度，组件/连接件/约束才是被改的对象。
- **误用 ABSD 边界**：ABSD 的“架构演化”只说明流程位置，本章要回答的是改哪些元素、何时改、怎样控制波及、怎样评估与长期维护。
