# 大型网站演化 · 复习总纲

## 用法

预计 5～8 分钟。先盖住下文，只看题干给的“当前瓶颈”，自问“该加哪种结构”，卡住再点唯一子卡。

本页只是复习路径与判据索引，不是新的知识事实源：只从已审核原子卡与章节索引提炼；与原子卡冲突时以原子卡为准。

## 大纲边界与优先级

大纲 9.6 要求到“能用大型网站案例说明架构演化过程”，主教材第 10.6 节展开。本模块只有 1 张卡 [[12_大型网站为什么一步步演化到分布式服务]]，`exam_priority` 为 **P0**、`review_level` 为**必读**（2010／2014／2017 案例分析考大型网站扩展，2023 回忆题仍出现 CDN 与 Redis 读写分离）。第一轮必须吃透演化因果，不能只背阶段编号。

边界要分清：

- 教材的十个阶段是**解释性路径**，不是所有网站必须照搬的技术采购清单；
- 本模块只讲“瓶颈 → 结构变化”的因果，不展开缓存、CDN、NoSQL 的产品选型与调优细节；性能、可伸缩性等质量属性的完整定义仍回 07 章 [[质量属性-复习总纲]]。

## 30 秒主线

十个阶段不是技术年表，而是一条连续的因果链：**当前瓶颈 → 加一种结构 → 解决当前问题 → 新瓶颈暴露 → 再演化**。前五步在单机资源上限内逐层拆：**单体 → 垂直拆分 → 缓存 → 应用集群+负载均衡 → 数据库读写分离**；后五步进入分布式组织：**CDN+反向代理 → 分布式文件/数据库 → NoSQL+搜索 → 业务拆分 → 分布式服务**。

一句话：**先找当前瓶颈，再选下一次结构变化。**

## 题干关键词 → 第一反应

| 题干信号（当前瓶颈） | 第一反应（下一次结构变化） |
| --- | --- |
| 所有资源挤在一台机器，容量/性能不够 | 垂直拆分（应用、文件、数据库分离） |
| 数据库访问慢、热点数据反复读库 | 缓存 |
| 单应用服务器连接/处理能力受限 | 应用集群 + 负载均衡 |
| 数据库仍有读压力（缓存未命中 + 全部写入） | 数据库读写分离（主库写、从库读） |
| 跨地域访问慢、入口压力大 | CDN / 反向代理 |
| 关系数据库不擅长的可伸缩存储与复杂检索 | NoSQL + 搜索引擎 |
| 业务复杂度上升，大应用按产品线耦合过重 | 业务拆分 |
| 共用业务能力重复、应用到数据库连接爆炸 | 分布式服务（抽出用户、商品等共用能力） |

## 核心流程：十个阶段的瓶颈链条

### 前五步：拆开一台机器上的资源瓶颈

1. **单体**：最小规模最省成本，问题是所有资源共同受一台机器上限约束。
2. **垂直拆分**：应用、文件、数据库分到不同服务器；随后数据库容易成为新瓶颈。
3. **缓存**：用热点数据减少数据库访问；随后单应用服务器的连接/处理能力暴露。
4. **应用集群**：横向增加应用服务器，用负载均衡分发；随后数据库仍承受缓存未命中和全部写入。
5. **读写分离**：主库写、从库读，降低数据库读负载；规模继续扩大后，单一中心和数据存储仍会遇到上限。

### 后五步：从“机器扩容”进入“分布式组织”

6. **CDN / 反向代理**：共同思想是让数据更早、更近地返回，并减轻后端压力。
7. **分布式文件 / 分布式数据库**：单机或简单主从承载不了数据规模时才继续拆；教材提醒分布式数据库不是越早用越好。
8. **NoSQL / 搜索引擎**：解决关系数据库不擅长的可伸缩存储和复杂检索。
9. **业务拆分**：业务复杂度上升后，按产品线把大应用拆成独立应用。
10. **分布式服务**：业务拆细后共用能力重复、应用到数据库连接爆炸，于是把用户、商品等共用业务抽成独立服务供应用调用。

**没有万能终局**：每次演化都在解决上一阶段的主要矛盾，但新结构会带来新的协调、数据一致性、运维和治理成本。架构演化是问题驱动的结构调整，不是技术越多越高级。

## 高频对比

| 易混对 | 核心区分 | 典型例子 | 考试问法与陷阱 |
| --- | --- | --- | --- |
| 缓存 vs 读写分离 | 用热点数据减少读库次数 vs 把读请求分到从库 | 热点商品缓存 vs 主写从读 | 题干已“有缓存仍读瓶颈”时仍答缓存 |
| 应用集群 vs 垂直拆分 | 同一应用横向加机器 vs 应用/文件/数据库按职责分机 | 加应用服务器+负载均衡 vs 应用与数据库分开部署 | 把“分成几台机器”一律当集群 |
| CDN/反向代理 vs 分布式文件/数据库 | 让数据更早更近返回、减轻后端压力 vs 突破单机存储上限 | 静态资源就近分发 vs 海量数据分片存储 | 用 CDN 回答“存储容量不够” |
| 业务拆分 vs 分布式服务 | 按产品线把大应用拆成独立应用 vs 抽出共用业务能力供各应用调用 | 拆成订单应用、商品应用 vs 抽独立用户服务 | 两者都叫“拆”，忽略共用能力重复与连接爆炸这一动因 |

## 最容易丢分的地方

- **死背十个阶段编号**：题目给的是当前瓶颈，应先按“瓶颈 → 结构变化”匹配，而不是回忆序号。
- **把缓存和读写分离混用**：缓存解决热点读；题干说“已经用了缓存和集群，数据库读请求仍是主要瓶颈”时，优先读写分离。
- **忽略新结构的成本**：每加一种结构都会引入新的协调、一致性、运维与治理成本，演化不是只有收益。
- **把教材路径当必经之路**：十阶段用于理解因果，实际网站按自身瓶颈选择，不必严格照搬。
