# 软件项目管理 · 复习总纲

## 用法

大模块，预计 **10～15 分钟**（含一道进度计算）。先合上卡片自问：WBS 和进度计划分别在回答什么？提交过版本是不是就等于建了基线？SQA 和软件测试差在哪？风险和"已经发生的问题"怎么分？哪一格答不出来，再点进对应原子卡看那一段，不要从第一篇重读。本页只是复习路线，不承担第一次教学。

## 大纲边界与优先级

大纲在本模块要求的是**项目怎样被管住**：管理范围、WBS 分解、活动依赖与进度计划、配置管理（含版本控制与基线）、软件质量保证和风险管理。

- **P0（第一轮必须拿下）**：[[活动依赖与进度计划]]、[[软件配置管理]]。
- **P1（正常第一轮一起完成）**：[[工作分解结构WBS]]、[[版本控制与基线]]、[[软件质量保证SQA]]、[[软件风险管理]]。
- **P2（第二轮补齐，仍在范围内）**：[[软件项目管理的范围]]。
- **P3**：本模块没有仅靠旧纲存活的卡，时间紧时不必额外取舍。

> [!note] 优先级口径
> 本模块只有 [[活动依赖与进度计划]]（P0）、[[软件配置管理]]（P0）、[[版本控制与基线]]（P1）三张卡在 frontmatter 里写了 `exam_priority`；其余卡按 [[软件工程基础知识-复习优先级]] 的原子级校准取值，总纲不另立一套。
> [[软件项目管理的范围]] 是 P2，却是本模块第一篇要读的坐标卡：**优先级不等于学习顺序**。

## 30 秒主线

[[软件项目管理的范围]] 先把视角从"把软件做出来"切到"把项目管住"：管理不是催进度，而是同时管范围、任务、人员资源、工作量、里程碑和风险，并且要在技术工作开始前介入、贯穿全过程。接着按一条连续链走：

**范围 → [[工作分解结构WBS]]（要做哪些工作和可交付成果）→ [[活动依赖与进度计划]]（谁先谁后、多久完成、总工期多长）→ [[软件配置管理]]（变化中的成果怎样可识别、可追踪、可控制）→ [[版本控制与基线]]（以哪一组成果为共同依据）→ [[软件质量保证SQA]]（过程是否真的按计划标准执行）→ [[软件风险管理]]（尚未必然发生但会影响目标的事）。**

一句话记整条链：**先拆清范围，再排时间和依赖，然后控住成果与版本，再检查过程遵循，最后把不确定因素盯住。**

## 题干关键词 → 第一反应

| 题干看到什么 | 第一反应（第一步动作） |
| --- | --- |
| 可交付成果、逐层定义完整工作范围、工作包 | WBS（范围分解，不表达先后） |
| 工作包越拆越细、"谁先谁后" | 判错：先后属于活动与进度计划，不属于 WBS |
| 前驱、并行、持续时间、总工期、里程碑 | 活动依赖与进度计划 |
| 关键路径怎么定 | 累计每条起点到终点路径的时间，最长的那条决定总工期 |
| 两条并行任务都完成才能联调 | 汇合点等最晚完成的前驱，不是把两路时间相加 |
| 同一个开发人员串行做两件事 | 依赖图不自动解决资源冲突，要按实际资源约束重排 |
| 配置项、产品配置由什么组成 | 受控成果集合：可包含文档、计算机程序、部件及数据 |
| 怎么恢复旧版本、比较差异、分支合并 | 版本控制 |
| 已评审批准、作为开发/测试/验收的共同依据 | 基线 |
| 代码已提交到仓库 / 已打标签 / 已发布 | 只形成受控版本，不等于建立基线 |
| 规定了必须评审和回归测试，实际为赶进度跳过 | SQA：查过程遵循、记不符合项并跟踪整改闭环 |
| 只发一次审计报告、不处理问题 | 不构成闭环，仍是丢分点 |
| 供应商可能延期、关键人员可能离开、性能目标可能达不到 | 风险（尚未必然发生，影响项目目标） |
| 接口已经延期、事故已经发生 | 已发生的问题，先处置并同步更新后续风险 |
| Boehm / Charette / CMU-SEI 的风险体系 | 风险估计与控制 / 分析与管理的两段式划分 |
| 质量体系认证、ISO 9000 系列与 ISO 9001 | 组织质量能力评价；认证不等于每个产品零缺陷 |

## 核心做题动作与必要公式

本模块固定四步，不需要先背流程名词表：

1. **先判在问哪一维**：是"要做哪些工作"（WBS）、"按什么先后、多久完成"（进度）、"成果和版本怎样受控"（配置）、"过程有没有按规则执行"（SQA），还是"还没发生但可能出事"（风险）？这一步定错，后面全错。
2. **进度题三步走**：读前驱关系 → 分别累计每条从起点到终点的完整路径时间 → 取最长者作为最早总工期；某个活动能拖多久、是否在关键路径上，要回到该活动的总时差判断。并行任务只有在**资源确实支持并行**时才取最长路径，否则按实际约束串行累计。
3. **配置题两问**：题目问的是"受控成果集合"（配置项、产品配置）还是"对成果的修改过程"（变更控制、版本控制）？集合题的答案是**文档、计算机程序、部件及数据**这类生命周期成果，不能只选源码或某类文档。
4. **风险题先分风险与问题**：尚未必然发生的是风险，按"识别 → 估计可能性与影响 → 排序 → 指定责任人、应对办法与监控条件 → 持续复查"处理；已经发生的是问题，先处置，再重新识别剩余风险，不能把记录一删了事。

关于公式：**本页不重抄三点估算和总时差的公式口径。** 进度计算题的这两节集中在 [[10_网络计划与关键路径]]，那里已写明用途、符号含义、单位、中文读法和适用条件，并标注了来源边界（这两节依据可追溯真题解析与辅导资料，主教材可搜索文本未定位到直接落点）。需要算总时差或三点估算时直接看那一篇，不要另造口径、也不要把它包装成主教材必背公式。

## 高频对比

| 对比 | 核心区分 | 典型例子 | 考试问法/陷阱 |
| --- | --- | --- | --- |
| WBS vs 活动依赖与进度计划 | 范围分解：要完成哪些可交付成果 vs 时间安排：活动按什么先后执行、持续多久 | 通知模块、验收报告、部署包 / 先完成接口再并行开发、最后联调 | 陷阱：把 WBS 的上下层关系当时间先后；WBS 不回答谁先谁后 |
| 版本控制 vs 基线 | 保存成果怎样演进、支持恢复与并行修改 vs 确定一组经批准、作为后续依据的成果 | 版本号、历史、差异、分支合并、回退 / 评审批准后成为开发与验收依据 | 常问"提交到仓库算不算基线"；提交只产生受控版本，基线需正式批准 |
| 软件配置管理 vs 版本控制/变更控制 | SCM 标识并控制全部受控成果的变化 vs 版本控制保存文件历史、变更控制批准是否实施 | 接口新增字段时同步接口定义、调用方代码、部署配置、文档、测试用例 / 只提交代码版本 | 陷阱：把配置管理等同于源码或配置文件；也把"Git"当成配置管理全部 |
| SQA vs 软件测试 | 检查产生产品的过程是否遵循约定并形成整改闭环 vs 检查产品结果的差异 | 检查需求评审与回归测试是否真的执行、证据是否完整 / 发布前跑一遍功能测试 | 问"质量保证就是测试吗"；只测产品不查过程，答不全 |
| 风险 vs 已发生的问题 | 尚未必然发生、可能影响范围成本进度质量的不确定因素 vs 已经触发、需要处置的事件 | 供应商"可能"延期、关键人员"可能"离开 / 接口已经延期 | 陷阱：把已发生的延期继续留在风险清单里"密切关注"而不行动 |
| 关键路径 vs 活动最多的路径 | 由最长的总持续时间决定 vs 与活动条数无关 | 两条路径中活动少但工期长的那条才是关键路径 | 陷阱：看到"串了四五个活动"就判关键路径；也可能存在多条并列关键路径 |

## 最容易丢分的地方

- **把 WBS 当进度图用。** 错在把"范围层级"读成"时间先后"。WBS 只回答要做哪些工作和可交付成果，先后与工期必须另外定义活动与依赖。
- **以为工作包越细越好。** 教材的经验原则是分解到**可控、可管理**为止，树通常不超过 6 层只是提醒不要无限细拆，不能替代工作包质量判断（可验收成果、完成标准、责任归口、可估算、可跟踪）。
- **把"唯一责任主体"读成"只能一个人干"。** 允许多人协作执行，关键是有一个明确的责任归口，避免"大家都负责，所以没人对结果负责"。
- **并行任务直接相加。** 汇合点要等最晚完成的前驱；只有资源允许并行时才按最长路径取总工期，资源不足时依赖图不会帮你解决冲突。
- **把关键路径等同于活动条数最多的路径。** 判据是总持续时间最长；也要记得关键路径可能不止一条。
- **把提交、打标签、发布版本当成基线。** 基线是一组经过评审批准、在特定范围内作为后续依据的配置项版本；三者都只说明产生了某个受控状态。
- **把"基线不能修改"当成绝对结论。** 准确说法是基线变更必须经过正式控制，同步修改相关配置项、验证一致性后再形成新基线，旧基线仍保留。
- **认为合并没有文本冲突就一定正确。** 工具只能发现它识别得了的内容冲突，接口含义、业务规则等语义冲突仍要靠评审和测试发现。
- **把配置管理收缩成"管源码/管配置文件"。** 受控成果还包括需求、设计、测试资料、部署配置等；产品配置可由文档、计算机程序、部件及数据组成。
- **把 SQA 当成测试的同义词。** 测试找产品结果差异；SQA 更强调过程遵循、预防、审计和管理可见性，而且只出报告不处理不符合项不构成闭环。
- **风险与问题不分。** 风险尚未必然发生，要提前识别、排序、备好应对和触发阈值；一旦发生就转为问题处置，并重新识别新的风险，不能只删原记录。
- **用单一级别机械排序或只写"密切关注"。** 高概率小影响与低概率大影响不能只看一个维度；阈值要写清观察对象、时间点和触发条件（如"检查点仍有缺口就升级"），否则无法检查是否履行。
- **以为模拟/备用方案通过就等于风险关闭。** 残余风险仍存在（如模拟端点与真实接口的行为差异），要等真实成果验收、关键集成测试通过、计划与相关方信息更新后才关闭。
