# 基于构件的软件工程 · 复习总纲

## 用法

小模块，预计 **5～8 分钟**。先合上卡片回答：构件模型和容器各管什么？顺序、层次、叠加组装怎么分？接口适配能解决什么、不能解决什么？答不全再点卡。

## 大纲边界与优先级

大纲要求掌握基于构件的软件工程（CBSE）的基本概念、开发过程、构件组装与接口适配。

- **P1（第一轮）**：[[构件模型与容器]]、[[构件组装方式]]、[[构件接口适配]]。
- **P2（第二轮）**：[[CBSE开发过程]]。
- **P0 / P3**：本模块没有。

## 30 秒主线

[[构件模型与容器]] 先解决"凭什么能复用"：构件是可复用、可组装的软件单元，通过**公开接口**协作；**构件模型**规定接口怎样描述、怎样被使用和部署；**容器**提供构件所需的支持服务与整合接口。[[CBSE开发过程]] 给出可反馈的复用链：需求概览 → 识别候选构件 → 核对能力差距并与用户协商可调整需求 → 设计架构、构件模型与平台 → 定制适配（必要时补自研）→ 组装与验证。[[构件组装方式]] 把镜头拉到连接处：顺序、层次、叠加三种组装。[[构件接口适配]] 处理最后一道连接问题：接口不兼容时用适配器转换。四站合起来是完整主线：**选得到 → 谈得拢 → 装得起来 → 接得上**。

## 题干关键词 → 第一反应

| 题干看到什么 | 第一反应（第一步动作） |
| --- | --- |
| 构件公开接口、元数据、配置、打包、环境要求 | 构件模型（规定怎样描述、使用和部署） |
| 身份认证、通信等支持服务与整合接口 | 容器（是运行容器概念，不等于 Docker） |
| 构件"独立部署" | 先看依赖是否明确声明且能被平台满足，不要读成零依赖 |
| 现成构件与原始需求不吻合 | CBSE 过程：先核对差距，再协商可调整需求或补实现 |
| 为了复用想直接删掉强制安全要求 | 判错：不可让步的业务/安全要求必须保留，换构件或补实现 |
| 前一个构件的输出喂给后一个 | 顺序组装（要保证输出输入兼容） |
| 一个构件请求另一个构件提供的服务 | 层次组装（要保证请求接口与提供接口相符） |
| 并列功能由新接口统一暴露，原构件互不调用 | 叠加组装 |
| 同名操作但参数类型或个数不同 | 参数不兼容 → 转换参数并明确默认值 |
| 相同目的用了不同操作名 | 操作不兼容 → 建立操作映射 |
| 一方需要撤销，另一方根本没有这个能力 | 操作不完备 → 补能力、换构件或协商需求 |
| 构件都各自通过了测试 | 仍需集成与系统验证 |

## 核心做题动作与必要公式

本模块不需要公式，固定三步：

1. **先判在问哪一站**：是"构件凭什么能被复用"（模型与容器）、"系统怎样靠复用做出来"（CBSE 过程）、"这组构件怎么连"（组装方式），还是"接口接不上怎么办"（接口适配）？
2. **组装方式看关系**：数据串接 → 顺序；服务调用 → 层次；功能并列合并成新接口 → 叠加。一个系统可以同时使用多种方式，不必对整个项目一刀切。
3. **适配先分类差异**：核对操作名、参数、返回与异常，判断属于参数不兼容、操作不兼容还是操作不完备；前两类可转换，第三类是**实际能力缺失**，只能补实现、换构件或协商需求。

## 高频对比

| 对比 | 核心区分 | 典型例子 | 考试问法/陷阱 |
| --- | --- | --- | --- |
| 构件组装模型 vs 基于构件的软件工程 | 过程模型视角：项目能不能主要靠复用和组装来做 vs 构件技术视角：构件特征、模型与容器、组装与适配 | "优先复用已有构件"的过程选择 / 公开接口、容器服务、适配器实现 | 都在说"复用"，先看题目问的是**过程组织**还是**技术细节** |
| 顺序 / 层次 / 叠加组装 | 前一个结果成为后一个输入 / 一个请求另一个提供的服务 / 并列功能经新接口合并暴露 | 格式转换后交给通知发送 / 告警处理调用通知构件 / 邮件与短信包装成统一通知入口 | 陷阱：把叠加组装说成原构件互相调用；叠加时原构件彼此不调用 |
| 参数不兼容 / 操作不兼容 / 操作不完备 | 同名操作参数不同 / 相同目的操作名不同 / 一方根本没有该能力 | 手机号字符串 vs 含国家码记录 / 不同命名约定 / 缺少"撤销通知" | 常问"改接口名能不能解决"；名字问题可映射，能力缺项不能靠改名解决 |
| 构件模型 vs 容器 | 规定构件怎样描述接口、被使用和部署 vs 提供构件运行所需的支持服务与整合接口 | 接口契约、元数据、配置、打包 / 身份认证、通信等支持服务 | 陷阱：把这里的容器直接等同于 Docker 容器 |
| 独立性 vs 零依赖 | 职责边界清楚、依赖可声明且可满足 vs 完全不依赖任何外部服务 | 声明需要认证服务并由容器提供 / 什么服务都不用 | 题干说"构件声明需要认证服务"时，不能直接判违反独立性 |
| 适配 vs 伪装成功 | 转换已有操作的调用方式 vs 把失败或未实现报成成功 | 参数映射并把异常映射为可识别的错误 / 构件返回已受理就当成真的完成 | 陷阱：返回"已受理"不等于业务已完成；失败路径必须一起验证 |

## 最容易丢分的地方

- **把"独立部署"读成"零依赖"。** 构件的独立是指职责边界清楚、依赖可以明确声明并在合适平台上被满足；声明需要认证服务本身不违反独立性。
- **把这里的容器等同于 Docker。** 教材讲的是构件运行容器的概念，提供构件所需的支持服务与整合接口，不要按某个具体产品去理解。
- **为了复用直接删需求。** 可协商的需求可以与用户协商调整，但**不可让步的业务或安全要求不能为了迁就候选构件而删除**，只能换构件或补实现。
- **把叠加组装说成构件之间互相调用。** 叠加是并列功能通过新接口组合暴露，原构件之间没有顺序传值或层次调用。
- **以为接口适配是万能补丁。** 参数不兼容、操作不兼容可以靠映射和转换解决；操作不完备是能力缺失，改名字不能凭空造出"撤销通知"这类业务能力。
- **把返回成功当成真的完成。** 适配器要能映射失败和异常并记录，不能把未实现的能力伪装成成功。
- **以为构件各自测过就可以直接交付。** 构件通过各自测试，仍需集成与系统验证。
- **把 CBSE 当成"找到构件 → 拼起来"两步。** 它是会反馈的链：能力与需求不匹配时要回到协商需求或补实现，架构与平台又会反过来限制候选构件范围。
