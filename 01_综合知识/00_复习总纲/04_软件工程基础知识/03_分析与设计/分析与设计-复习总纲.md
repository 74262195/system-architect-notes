# 分析与设计 · 复习总纲

## 用法

大模块，预计 **10～15 分钟**。本模块卡片多，不要平均用力：先做「题干关键词」表，凡是看到"图"的题先判它是哪一层表达、凡看到"模块"的题先判是在问内聚还是耦合；卡住的点再点对应原子卡。UML 五张子卡当前为 `待评估`，属于第二轮补强。

## 大纲边界与优先级

大纲在本模块要求：结构化分析与设计（DFD、数据字典、模块化与模块独立性、详细设计工具、概念数据模型）、面向对象方法（OOA/OOD/OOP）与 UML 建模表达，以及逆向工程、形式化方法等其他设计方法。

- **P0（第一轮必须拿下）**：[[数据流图DFD]]、[[模块耦合类型]]、[[模块内聚类型]]、[[UML总览]]。
- **P1（正常第一轮一起完成）**：[[数据字典]]、[[面向对象分析OOA]]、[[逆向工程]]。
- **P2（第二轮补齐）**：[[结构化分析与设计分工]]、[[模块信息隐藏]]、[[结构化详细设计工具]]、[[概念数据模型与实体联系]]、[[面向对象方法]]、[[面向对象设计OOD]]、[[实体类边界类与控制类]]、[[面向对象程序设计OOP]]、[[对象持久化与ORM]]、[[形式化方法]]。
- **`exam_priority: 待评估`（按第二轮处理）**：[[UML用例图]]、[[UML类图与基本关系]]、[[UML序列图与通信图]]、[[UML活动图与状态机图]]、[[UML构件图与部署图]]。时间紧时，至少把 [[UML总览]] 加"典型 UML 图识别"学完。

`结构化分析与设计分工`、`面向对象方法` 是 P2，但它们是各自小组的第一篇坐标卡：**优先级不等于学习顺序**。

## 30 秒主线

**结构化这条线**：[[结构化分析与设计分工]] 先分清四类表达对象（业务流图看业务流转、DFD 看数据加工、SC 看模块组织、程序流程图等看模块内部）。[[数据流图DFD]] 用外部项、加工、数据流、数据存储建立功能/数据流逻辑模型，靠父子图平衡保证分解一致；[[数据字典]] 再把图上的数据项、数据结构、数据流、数据存储、处理过程定义清楚。进入设计后，[[模块信息隐藏]] 建立模块边界，[[模块耦合类型]] 看模块之间依赖多深，[[模块内聚类型]] 看模块内部为什么放在一起，[[结构化详细设计工具]] 表达单个模块内部控制逻辑，[[概念数据模型与实体联系]] 补数据/实体角度。

**面向对象这条线**：[[面向对象方法]] 给出层级坐标，[[面向对象分析OOA]] 理解问题域，[[面向对象设计OOD]] 分配类职责并设计接口与协作，[[实体类边界类与控制类]] 细化职责分工，[[面向对象程序设计OOP]] 编码实现，[[对象持久化与ORM]] 解决对象状态长期保存。[[UML总览]] 说明 UML 是这套分析和设计的**统一表达语言**（不是 OOD 与 OOP 之间强制新增的阶段），随后六张图分别回答"谁来用、有哪些类、怎么发消息、流程怎么走、对象怎么换状态、软件怎么拆与部署在哪"。

**其他方法**：[[逆向工程]] 从已有实现恢复更高层知识；[[形式化方法]] 用严格语义的规格与推理减少歧义。

## 题干关键词 → 第一反应

| 题干看到什么 | 第一反应（第一步动作） |
| --- | --- |
| 业务活动、处理环节怎样前后衔接 | 业务流图（业务怎么办下去） |
| 数据从哪里来、经过什么加工、存到哪里 | DFD |
| 父图与子图边界输入输出对不上 | 父子图平衡被破坏 |
| 外部项直接连到数据存储 | DFD 合理性错误：应通过加工发生联系 |
| 图上只有名称，不知道组成、类型、取值范围 | 查数据字典 |
| 调用方必须了解另一个模块内部数据/算法 | 信息隐藏与模块独立性被破坏 |
| 只传"告警编号"这类简单数据 | 数据耦合 |
| 把整个"告警记录"结构传过去 | 标记耦合 |
| 传"处理模式"决定对方走哪个分支 | 控制耦合 |
| 多个模块读写同一张全局状态表 | 公共耦合 |
| 直接伸手改另一个模块内部 | 内容耦合（最强、最该避免） |
| 模块内所有步骤都为一个明确功能服务 | 功能内聚（最高） |
| 前一步的输出直接成为后一步输入 | 顺序内聚 |
| 几个处理围绕同一份数据 | 通信内聚 |
| 只是按执行流程先后放在一起 | 过程内聚 |
| 因为都在启动时执行 | 时间内聚 |
| 同类别操作、靠参数选一个执行 | 逻辑内聚 |
| 只是碰巧塞在一起 | 偶然内聚（最低） |
| 条件组合多、怕漏情况 | 判定表 |
| 实体、属性、1:1 / 1:N / M:N | 概念数据模型（E-R） |
| 识别业务对象及其关系、属性、服务 | OOA |
| 决定类职责、接口、对象协作 | OOD |
| 用语言创建实例、继承、多态、消息调用 | OOP |
| 长期保存业务信息 / 系统与外界交接 / 用例流程协调 | 实体类 / 边界类 / 控制类 |
| 对象与关系表怎样对应（ORM/JDBC/JDO） | 对象持久化与 ORM 层次辨析 |
| 组成、事物、关系、图、视图的层级归属 | UML 组成三大部分 |
| 外部角色能使用哪些功能 | 用例图（include 每次都要、extend 条件才加） |
| 类与类之间"临时用、本来连着、是一种、实现接口" | 类图（依赖/关联/泛化/实现） |
| 消息的时间先后 | 序列图 |
| 对象之间连不连、消息编号 | 通信图 |
| 一件业务流程怎么走、分支汇合 | 活动图 |
| 一个对象一生怎样换状态 | 状态机图 |
| 软件拆成哪些构件、彼此依赖 | 构件图 |
| 软件跑在哪些服务器/结点上 | 部署图 |
| 从旧代码和数据库结构恢复设计模型 | 逆向工程（按实现/结构/功能/领域判抽象层次） |
| 严格数学语义的规格与推理验证性质 | 形式化方法 |

## 核心做题动作与必要公式

本模块不需要公式，固定三步：

1. **先判表达层次**：题目是在问业务流转、数据怎么动、软件怎么分模块，还是模块内部怎么执行？分别对业务流图 / DFD / SC / 详细设计工具。
2. **再判模块独立性方向**：看的是**模块之间**就判耦合，看的是**模块内部**就判内聚；按"联系方式或聚合理由"判具体类型，再按教材顺序比高低。
3. **最后判阶段**：做到"识别问题域对象"是 OOA，"定职责、接口、协作"是 OOD，"写代码、创建实例、运行时多态"是 OOP；UML 只负责把前两者表达出来。

DFD 题另有固定动作：先明确系统范围 → 画顶层图 → 逐层分解 → 做父子图平衡与合理性检查。

## 高频对比

| 对比 | 核心区分 | 典型例子 | 考试问法/陷阱 |
| --- | --- | --- | --- |
| 数据耦合 / 标记耦合 / 控制耦合 | 传必要简单数据 / 传整个记录或数据结构 / 传控制信息去决定对方内部走哪条路 | 只传告警编号 / 传整个"告警记录对象" / 传"处理模式"参数 | 陷阱：按参数个数判断强弱；判据是**传的东西是什么性质**，不是传了几个 |
| 顺序内聚 vs 过程内聚 | 前一步的**输出直接成为后一步输入** vs 只是**按执行顺序**放在一起 | 解析报文→用字段结构做标准化 / 记录审计→刷新缓存→输出提示 | 常问"哪种内聚更高"：顺序高于通信，更高的是功能；"有顺序"不等于顺序内聚 |
| 公共耦合 vs 内容耦合 | 大家一起依赖同一个公共数据环境 vs 直接侵入另一个模块内部 | 多个模块读写全局告警状态表 / 直接改别的模块内部数据 | 判断题问"最低应避免哪种"→ 内容耦合最强 |
| 内聚高低顺序 | 教材由高到低：功能 → 顺序 → 通信 → 过程 → 时间 → 逻辑 → 偶然 | 功能内聚最典型，偶然内聚最低 | 常问"哪种内聚度最高/最低"；这个顺序是连续排列，不要自造档位 |
| 耦合高低顺序 | 教材由低到高：非直接 → 数据 → 标记 → 控制 → 通信 → 公共 → 内容 | 设计目标：低耦合 | 常问"哪种耦合最低"→ 非直接耦合；"最该避免"→ 内容耦合 |
| UML 图识别 | 用例图看"谁用、能干什么"，类图看静态关系，序列/通信图看消息，活动/状态机图看流程/对象状态，构件/部署图看拆分/运行位置 | "谁先调用谁"→序列图；"订单状态怎么变"→状态机图 | 陷阱：把序列图和通信图当两件事（它们可是同一次交互的两种侧重）；把部署工作流当部署图 |
| DFD / E-R / SC / 详细设计工具 | 数据加工 / 实体关系 / 模块调用 / 模块内部控制 | 数据经加工后入库 / 设备 1:N 告警 / 谁调用谁 / 条件分支 | 都可能有箭头，判据是"主角是谁"，不是图长相 |

## 最容易丢分的地方

- **给内聚排序时把顺序和过程弄反。** 错在只看到"都有先后"。顺序内聚的判据是**数据接力**（前一步输出成为后一步输入）；过程内聚只是**执行顺序相关**，数据未必传递。
- **按参数数量判耦合。** 参数少不一定低耦合：把整个结构传过去就是标记耦合；参数多但都是必要简单数据，仍可能只是数据耦合。判据是**传的信息性质**：业务数据 / 复杂结构 / 控制开关。
- **把标记耦合和控制耦合混成"传了个结构/参数"。** 关键看传的是**业务数据**（标记）还是**决定对方内部执行哪条路**的控制信息（控制）。
- **以为 DFD 能表达控制逻辑。** DFD 只描述数据从哪来、经什么加工、到哪去；判断分支和循环属于详细设计，塞进 DFD 就串层了。
- **忘了父子图平衡。** 分解可以更细，但该加工对外的边界输入输出必须保持一致，不能凭空多出或消失数据。
- **把 ER 当数据库表设计。** 概念数据模型抽象的是现实世界实体与联系，逻辑结构设计和物理设计是后续层次；联系数量必须**双向**确认（只知道"一台设备有多条告警"还不能断定 1:N）。
- **把 UML 当成 OOD 与 OOP 之间必须新增的开发阶段。** UML 是建模语言，OOA、OOD 过程中都可以用；它负责统一表达，不是阶段本身。
- **把 UML 五种视图塞进"三大组成"。** 三大组成是基本构造块、图、公用机制；视图是观察系统的角度，不是第四项，也不等于架构 4+1。
- **把用例图的 include 和 extend 反着用。** include 是基础用例每次都要包含的行为；extend 是特定条件下才附加的可选行为。
- **把逆向工程当成改系统。** 它重点是从已有实现恢复理解，本身不要求改变系统功能；恢复出的模型还受代码质量、缺失文档和工具能力限制。
