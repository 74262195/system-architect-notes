# 软件测试 · 复习总纲

## 用法

大模块，预计 **10～15 分钟**。本模块最大的风险不是不会背定义，而是把**不同分类维度摊成一排**。先用下面「一张坐标」把维度分清，再看「题干关键词」表自测；卡住时点进对应原子卡看那一段的判断依据。

## 大纲边界与优先级

大纲在本模块要求：测试的基本分类（静态/动态、黑盒/白盒/灰盒）、检验用例设计技术、测试层次（单元→集成→系统→验收）、专门的测试目的与场景，以及验证与确认、测试自动化等。

- **P0（第一轮必须拿下）**：[[静态测试与动态测试]]、[[黑盒白盒与灰盒测试]]、[[白盒覆盖的判断]]、[[单元测试与集成测试]]、[[系统测试与验收测试]]。
- **P1（正常第一轮一起完成）**：[[黑盒用例设计方法]]、[[性能负载与压力测试]]、[[回归测试]]。
- **P2（第二轮补齐，不是超纲）**：[[验证与确认V&V]]、[[测试自动化]]、[[Alpha与Beta测试]]、[[AB测试]]、[[Web链接与表单测试]]。
- **P3**：本模块没有。

`测试自动化` 和 `Web链接与表单测试` 属于"执行手段"和"教材补充场景"，不要与黑盒/白盒这类基本分类并列背诵。

## 30 秒主线

先立坐标：[[静态测试与动态测试]] 按**被测程序是否运行**分；[[黑盒白盒与灰盒测试]] 按**用例是否利用内部结构**分；用例怎么挑输入或覆盖代码，看 [[黑盒用例设计方法]]（等价类、边界值、错误推测）和 [[白盒覆盖的判断]]（语句、判定、路径覆盖）；测多大范围，走 [[单元测试与集成测试]] → [[系统测试与验收测试]]；为什么专门再测一次，看 [[性能负载与压力测试]]、[[回归测试]]、[[Alpha与Beta测试]]、[[AB测试]]、[[Web链接与表单测试]]；谁帮你重复执行，是 [[测试自动化]]；再往上一层，[[验证与确认V&V]] 问的是"按规格做对了"还是"做的正是用户要的"。

## 题干关键词 → 第一反应

| 题干看到什么 | 第一反应（第一步动作） |
| --- | --- |
| 桌面检查、审查、走查、静态分析，被测程序不运行 | 静态测试（判据是程序有没有运行，不是有没有工具） |
| 用实际输入数据运行程序观察结果 | 动态测试 |
| "不考虑内部结构和处理算法，只检查功能" | 黑盒测试（用例是否利用内部结构） |
| 语句、判定、路径覆盖 | 白盒测试 |
| 同时利用外部规格和部分内部信息 | 灰盒测试 |
| 输入域太大，要挑代表性输入 | 先划有效/无效等价类 |
| 只测了合法范围中间的值 | 漏了边界值及相邻值、非法输入 |
| 两个独立判定都取过真和假 | 只到判定覆盖，组合路径仍可能漏 |
| 问"覆盖强度最高" | 先看题目给的覆盖层级：路径覆盖最强 |
| 单模块内部逻辑/边界错误 | 单元测试 |
| 参数、调用、接口、状态传递错误 | 集成测试 |
| 完整系统对照系统规格 | 系统测试 |
| 用户/客户按合同与业务需求决定接收 | 验收测试 |
| 只给"支持五千请求" | 性能还缺请求类型、单位时间、响应与错误标准、环境条件 |
| 逐步增加正常工作量观察表现 | 负载测试 |
| 逼近或超过承受能力找瓶颈与不可接受点 | 压力测试 |
| 改了一处，担心影响别的功能 | 回归测试（可发生在多个层次，不是第五层） |
| 开发环境/受控模拟环境下的用户试用 | Alpha 测试 |
| 用户在真实使用环境中反馈问题 | Beta 测试 |
| 两个都能工作的方案比效果、随机分流量 | A/B 测试（不是 Alpha/Beta 的缩写） |
| 谁来重复执行测试动作 | 测试自动化（自动运行 ≠ 自动知道对错） |
| 按规格做对 / 做的是用户真正要的 | 验证 / 确认 |
| 链接、表单提交后看到成功提示 | 继续查后台数据与完整链条 |

## 核心做题动作与必要公式

本模块不需要公式，固定三步：

1. **先判维度**：题目在问"程序有没有运行"（静态/动态）、"用例有没有利用内部结构"（黑盒/白盒/灰盒）、"挑输入还是覆盖代码"（用例设计技术）、"测多大范围"（层次）、"为什么专门再测"（目的/场景），还是"谁在重复执行"（自动化）？维度不同，答案不能互相当选项。
2. **再判对象**：单模块内部逻辑 → 单元；模块之间参数、调用、接口与状态传递 → 集成；完整系统对系统规格 → 系统；用户/客户按合同与业务需求接收 → 验收。
3. **覆盖题单独处理**：先识别题目要求的覆盖对象（语句 / 判定出口 / 路径），再据此列测试用例；不要只凭用例数量推断覆盖程度。

## 高频对比

| 对比 | 核心区分 | 典型例子 | 考试问法/陷阱 |
| --- | --- | --- | --- |
| 静态测试 vs 动态测试 | 不运行被测程序（人工检查、静态分析） vs 运行程序观察结果 | 代码审查、走查 vs 用输入数据跑一遍看输出 | 陷阱：按"有没有用工具"判断；判据是**被测程序是否执行** |
| 黑盒 / 白盒 / 灰盒 | 依据外部规格 / 依据内部代码结构与逻辑 / 利用部分内部信息 | 功能是否符合需求 / 语句判定路径覆盖 / 兼顾接口与部分结构 | 陷阱：按测试阶段或"有没有源码"判断；判据是**用例是否利用内部结构** |
| 单元测试 vs 集成测试 | 模块自身逻辑与边界 vs 模块之间接口与协作 | 单模块内部判断错误 / 两模块组合后字段含义不一致 | 先看"问题发生在模块内还是模块间"，不要先看用了黑盒还是白盒 |
| 系统测试 vs 验收测试 | 完整系统对系统规格 vs 用户/合同角度是否可接收 | 开发测试团队对系统规格验证 / 客户按业务流程与合同验收 | 关键看**目的、依据和责任方**，不是"哪个更高级"；也不是重复无用 |
| 负载测试 vs 压力测试 | 不同正常工作量下观察表现 vs 逼近或超过承受能力找瓶颈与不可接受点 | 逐步加压看响应变化 / 加到系统失效找极限 | 性能测试是评价指标的总称，三者不要混成一件事 |
| 验证 vs 确认 | 是否按规格正确做出产品 vs 是否做出用户真正需要的产品 | 符合规格文档 / 客户觉得解决了真实问题 | 记法：验证＝把产品做对，确认＝做对的产品；两者都不是"不测试" |
| Alpha vs Beta | 开发方环境或受控模拟环境 vs 用户真实使用环境 | 请真实用户来开发环境试用 / 用户在自己环境长期使用 | 陷阱：只因参与者是真实用户就判 Beta |
| 回归测试 vs 测试层次 | 因软件被修改而重测受影响及原本正常的能力 vs 单元/集成/系统/验收这类层次 | 修完缺陷后补测旧功能 | 回归**不是第五层**，它可发生在多个层次 |

## 最容易丢分的地方

- **按测试阶段或"有没有源码"判黑盒白盒。** 判据只有一条：**用例设计有没有利用程序内部结构**。所以"集成测试就是黑盒、单元测试就是白盒"这类说法是错的。
- **只背语句/判定/路径三个名字，不会比较强度。** 要能解释：语句执行不代表分支全覆盖，分支全覆盖也不代表所有路径；两个判定都取过真和假，组合路径仍可能漏。**覆盖率不是正确率**——即使覆盖目标达到，也要检查输出与状态是否符合预期。
- **把静态测试理解成"不测代码"。** 静态测试的对象同样是代码，只是不运行它；桌面检查、审查、走查、静态分析都属此列。
- **把 V&V 当成又一种测试分类。** 它是"我们在确认什么"的质量保证视角，可以和多种检查、测试手段组合使用；验证与确认也不是"前者不测试、后者才测试"。
- **混淆系统测试与验收测试。** 二者不是重复：一个对系统规格，一个对用户需求与合同交付条件；判断依据是目的、依据和责任方。
- **把回归测试当固定第五层。** 它的触发条件是"软件发生了修改"，可以在不同层次上做；"原缺陷修好了"不等于回归完成，还要验证受影响的已有行为。
- **只凭"用户参与"判 Alpha/Beta。** 要看环境与参与方式：开发方环境或受控模拟环境偏 Alpha，用户真实环境才是 Beta。
- **把 A/B 测试与 Alpha/Beta 混为一谈。** A/B 是"两个都能工作的方案哪个效果更好"，要求相近人群同期比较同一指标；用不同月份的用户结果对照，时间、用户组成等变量也在变。
- **以为自动化等于自动判对错。** 脚本跑完没报错，可能只是没有有效断言；必须定义预期与可靠检查点。
- **看到成功提示就认为数据保存正确。** Web 表单要看提交到服务端存储和使用的完整链条；链接也要查导航可达性，不能只看"地址能打开"。
