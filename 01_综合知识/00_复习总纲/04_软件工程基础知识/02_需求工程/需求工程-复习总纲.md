# 需求工程 · 复习总纲

## 用法

大模块，预计 **10～15 分钟**。先看「30 秒主线」自述一遍"需求从哪来、怎么定下来、变了怎么办"，再对着「题干关键词」表自测；答不出时点进对应原子卡，看那一段的因果链，不要重读全篇。

## 大纲边界与优先级

大纲在本模块要求的是：需求层次与类型（业务/用户/功能、非功能）、需求开发与需求管理的分工、需求获取方法、需求规格与确认验证、需求变更控制、需求追踪。

- **P0（第一轮必须拿下）**：[[需求开发与需求管理]]、[[需求变更控制]]、[[需求双向追踪矩阵]]。
- **P1（正常第一轮一起完成）**：[[需求层次与非功能需求]]、[[需求获取方法]]、[[需求规格与确认验证]]。
- **P2、P3**：本模块没有。

本模块 6 张卡全在第一轮范围内，但阅读顺序仍从 [[需求层次与非功能需求]] 开始——它负责建立"需求不只是功能"的坐标。

## 30 秒主线

[[需求层次与非功能需求]] 先把"要什么"分层：业务需求问为什么做、用户需求问用户要完成什么、功能需求问系统必须做什么，非功能需求则是对系统行为与实现的约束（它不是第四层）。然后 [[需求开发与需求管理]] 把整个需求工程劈成两条线：**开发**＝获取→分析→规格→确认/验证，**管理**＝变更控制、版本控制、追踪、状态跟踪；两条线之间的桥是评审批准后形成的**需求基线**。

开发这条线逐站展开：[[需求获取方法]] 解决"从谁、用什么方法把需求挖出来"；[[需求规格与确认验证]] 把它写成可检查、可验收的正式依据。管理这条线由 [[需求变更控制]]（先影响分析、再由 CCB 决策）和 [[需求双向追踪矩阵]]（正向查漏实现、逆向查无依据实现）接力，追踪关系正是变更影响分析的依据。

## 题干关键词 → 第一反应

| 题干看到什么 | 第一反应（第一步动作） |
| --- | --- |
| "降低漏处理率""提高客户满意度"这类目标 | 业务需求（为什么做） |
| "值班人员能够确认、转派告警" | 用户需求（用户要完成什么任务） |
| "系统收到 P1 告警后提交短信通知请求" | 功能需求（系统必须做什么行为） |
| "10 秒内完成通知提交""可用性 99.9%" | 非功能需求（性能/质量要求） |
| "每人最多保存 3 个筛选器" | 先看语义：这仍是功能规则，**带数字不一定是非功能** |
| 必须遵循的标准、合同、外部接口、既有认证平台 | 约束类要求（也是需求规格的一部分） |
| 问"需求怎么形成" | 需求开发 |
| 问"需求形成以后怎么变、怎么追、怎么管版本" | 需求管理 |
| 评审批准后形成共同参照的版本 | 需求基线（桥；不是"永不再改"） |
| 需要深入追问一个人的工作原因 | 面谈 |
| 多方意见冲突、要集中形成共识 | 需求专题讨论会 |
| 人很多、只要统计倾向 | 问卷 |
| 用户说不清自己实际怎么操作 | 现场观察 |
| 界面/交互"看了才知道" | 原型 |
| 全新业务、连可能性都没想全 | 头脑风暴 |
| "系统响应要快""界面要友好" | 继续澄清：补环境、行为、可判断标准 |
| 需求是否完整、正确、一致、可行、可验证 | 需求确认/验证（不是只看签字） |
| 基线后收到新变更请求 | 先做影响分析与成本评估，不能直接实施 |
| "变更控制委员会" | CCB 是**决策机构**，不是技术方案设计与编码机构 |
| 变更已批准 | 还没结束：还要同步受影响成果、更新基线与状态、验证后关闭 |
| "编制需求与体系结构、设计、代码、测试的联系" | 需求双向追踪矩阵 |
| 从需求往后查设计/代码/测试 | 正向追踪（防漏实现） |
| 从代码/测试往回查需求来源 | 逆向追踪（防无依据实现） |

## 核心做题动作与必要公式

本模块不需要公式，固定三步：

1. **先判问题类型**：题干问"需求从哪来、怎么写清楚"→ 需求开发；问"需求形成之后怎么受控演进"→ 需求管理。
2. **再判需求层次/类型**：这句话是在说业务目标、用户任务、系统行为，还是对行为与实现的约束？只有能说清"将来怎样判断它满足与否"，才算可验证的需求。
3. **最后判流程动作**：基线之后出现变化，第一步永远是**明确变更 → 影响与成本分析 → 决策 → 实现 → 更新状态与关联成果**；影响分析靠的就是需求追踪关系。

## 高频对比

| 对比 | 核心区分 | 典型例子 | 考试问法/陷阱 |
| --- | --- | --- | --- |
| 需求开发 vs 需求管理 | 把需求弄清楚（获取/分析/规格/确认验证） vs 让已形成的需求受控演进（变更、版本、追踪、状态） | 访谈用户、写成规格 vs 收到变更请求后做影响分析 | 常问"某活动属于开发还是管理"；桥梁是需求基线 |
| 需求层次 vs 非功能需求 | 业务/用户/功能是纵向层次 vs 非功能是对行为、质量、约束的另一类要求 | "为什么建系统" / "用户要转派" / "系统发通知" vs "10 秒内提交通知" | 陷阱：把非功能当成"第四层"；或把带数字的功能规则判成非功能 |
| 正向追踪 vs 逆向追踪 | 需求→后续成果，查有没有真正做出来 vs 成果→需求来源，查为什么要做 | R1 是否都有设计/代码/测试 vs 代码里的"自动删除 7 天前告警"有没有需求依据 | 问"某条需求没有测试用例"→ 正向查漏；问"某功能找不到需求"→ 逆向查漏 |
| 需求基线 vs "永不再改" | 基线是当前正式认可版本、后续变更必须受控 vs 一字不能动 | 保留期 90 天改 365 天，仍可改但要走变更控制 | 陷阱：把"建立基线"理解成冻结需求 |
| 需求变更控制 vs 拒绝变更 | 让合理变化在影响可见后进入项目 vs 尽量不让用户改 | CCB 可以做"有条件批准"，条件关闭后再实施 | 陷阱：认为"批准＝变更结束"，忘了同步成果与关闭状态 |
| CCB vs 开发团队 | 对变更做接受/拒绝决策 vs 提出技术方案并实现 | 谁决定接不接受 vs 谁去改代码 | 常把 CCB 说成"负责设计并实施变更的机构" |

## 最容易丢分的地方

- **把非功能需求当成"第四层需求"。** 错在用"业务→用户→功能→非功能"的纵向顺序去理解它；非功能约束的是"做得怎么样、必须遵守什么"，可以作用于任何一层。
- **见数字就判非功能。** "每人最多保存 3 个筛选器"限定的是系统允许的行为，仍可能是功能规则。判断依据是语义，不是数字。
- **把需求管理往后放。** 它不是"项目后期才干的事"：初始需求产生时就能做管理规划，需求文档有初稿后管理活动已可开展。
- **把需求基线理解成冻结。** 基线的意义是"从这里开始必须走受控变更"，而不是禁止变更。
- **基线后收到变更就直接改代码。** 漏掉了影响与成本分析这一步；而影响分析要知道"这条需求连着哪些设计、代码、测试"，这又依赖需求追踪。
- **把 CCB 当作业机构。** CCB 是决策机构，负责决定接受哪些变更；说它"负责提出详细变更方案并实施编码"就把决策与作业混了。
- **认为"批准＝变更结束"。** 批准只是允许进入实施，之后还要同步需求、设计、测试、计划与状态，验证通过才算关闭。
- **以为敏捷就不需要变更控制。** 敏捷可以把批准的变化放进后续迭代，但仍然要识别、评估和管理变化，避免范围失控。
- **追踪矩阵建一次就不管。** 过时的矩阵会漏掉真实依赖甚至误导影响分析，必须随需求、设计、实现、测试变化持续维护。
- **凭印象填矩阵。** 关联必须有需求、设计、实现或测试资料作证据；空白可能代表遗漏、不适用或待核验，不能猜着填。

## 闭卷自测

- [ ] 业务需求、用户需求、功能需求分别在回答什么问题？为什么非功能需求不是"第四层"？
- [ ] "每人最多保存 3 个筛选器"是功能需求还是非功能需求？判断依据是什么？
- [ ] 需求开发和需求管理各自包含哪些活动？两者之间的桥梁是什么？
- [ ] 需求基线是不是"永远不能改"？它到底约束了什么？
- [ ] 需求获取之前要先做哪几件前置工作？为什么不能直接开会问"你要什么"？
- [ ] 面谈、专题讨论会、问卷、现场观察、原型、头脑风暴分别适合补什么信息缺口？
- [ ] "系统响应要快"为什么不是一条高质量需求？要补上什么才好验收？
- [ ] 需求确认/验证要检查哪些质量特性？
- [ ] 需求基线之后收到变更请求，完整处理链有哪几步？为什么第一步不是改代码？
- [ ] CCB 是决策机构还是作业机构？批准之后为什么还不算结束？
- [ ] 正向追踪和逆向追踪各能查出什么问题？为什么必须双向？
- [ ] 需求追踪矩阵为什么能支撑变更影响分析？它建立一次以后可以不管吗？
