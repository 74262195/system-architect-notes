# 软件过程 · 复习总纲

## 用法

大模块，预计 **10～15 分钟**。先合上卡片，用下面的「题干关键词」和「高频对比」自问一遍；哪一格答不出来，再点进对应的原子卡看那一段，不要从第一篇重读。本页只是复习路线，不承担第一次教学。

## 大纲边界与优先级

大纲在本模块要求的是**开发活动怎样被组织**：典型过程模型（瀑布、原型、螺旋、迭代增量、构件组装）、RUP 这一过程框架、一组敏捷方法，以及评估组织过程能力的 CMMI。

- **P0（第一轮必须拿下）**：[[瀑布模型]]、[[迭代与增量模型]]、[[螺旋模型]]、[[CMMI成熟度等级]]。
- **P1（正常第一轮一起完成）**：[[原型的去留与目标系统]]、[[构件组装模型]]、[[RUP]]、[[RUP九类工作流]]。
- **P2（第二轮补齐，仍在范围内）**：[[软件工程的定位]]、[[RUP四加一视图]]、[[极限编程XP]]、[[Scrum迭代管理]]、[[水晶系列方法]]、[[特征驱动开发FDD]]。
- **P3**：本模块没有仅靠旧纲存活的卡，时间紧时不必额外取舍。

`软件工程的定位` 虽然只是 P2，却是本模块第一篇要读的坐标卡：**优先级不等于学习顺序**。

## 30 秒主线

先分清三个概念：[[软件工程的定位]] 说清生命周期（软件一生有哪些阶段）、软件过程（要做哪些工作）、过程模型（这些工作怎么排）。需求稳定、希望阶段成果清楚，就用 [[瀑布模型]]；不想等到最后才看到可运行成果，就拆成多轮，进入 [[迭代与增量模型]]；如果每轮要先解决"最可能让项目失败的事"，就是风险驱动的 [[螺旋模型]]；用户自己都说不清要什么，用 [[原型的去留与目标系统]]；已有成熟能力可复用，转向 [[构件组装模型]]。

再往上收一层：[[RUP]] 把阶段与工作流组织成二维框架，[[RUP九类工作流]] 拆开纵向工作种类，[[RUP四加一视图]] 只是"以体系结构为中心"时的架构表达；变化更快时用敏捷方法 [[极限编程XP]]、[[Scrum迭代管理]]、[[水晶系列方法]]、[[特征驱动开发FDD]]。最后 [[CMMI成熟度等级]] 换一个视角：它不问这个项目怎么做，只问组织的过程能力成熟到什么程度。

## 题干关键词 → 第一反应

| 题干看到什么 | 第一反应（第一步动作） |
| --- | --- |
| 属于哪个阶段、开发之后是什么、可行性研究 | 先判"这是软件生命周期"，不是过程模型 |
| 需求稳定 + 严格阶段评审 + 晚期变更代价大 | 瀑布模型 |
| 用户说不清需求、先做样品让用户试用 | 原型模型 |
| 分批交付、较早得到可用系统和客户反馈 | 迭代/增量 |
| 已有功能被反复修正细化 | 迭代 |
| 系统比上一版"多会了一件事" | 增量 |
| 目标设定 → 风险分析 → 开发与有效性验证 → 评审 | 螺旋模型 |
| 每轮优先验证最可能失败的问题 | 螺旋模型（风险驱动） |
| 已有构件、构件库、复用、选择/适配/组装 | 构件组装模型 |
| 初始 / 细化 / 构造 / 移交 | RUP 四阶段（时间轴） |
| 需求、实现、测试等"正在做哪类工作" | RUP 九类工作流（纵向轴） |
| "九类工作流不包括哪一项" | 先排除成本管理（它不是独立核心工作流） |
| 用例驱动 / 以体系结构为中心 / 迭代增量 | RUP 的三个核心特点 |
| 同一架构换不同关注点描述 | 4+1 视图（属架构表达，去软件架构主源看细节） |
| Backlog、Sprint、可交付产品增量 | Scrum |
| 交流、朴素、反馈、勇气 | XP 的四项价值 |
| 方法家族、按项目环境选择成员 | 水晶系列 |
| 整体对象模型、特征列表、按特征计划/设计/构建 | FDD |
| 项目级可计划可监控 | CMMI 2 级 |
| 组织建立标准过程并制度化 | CMMI 3 级 |
| 定量目标、过程性能、可预测 | CMMI 4 级 |
| 持续（增量式/创新式）过程改进 | CMMI 5 级 |

## 核心做题动作与必要公式

本模块不需要公式，固定三步即可：

1. **先分层**：题干是在问"软件处在生命周期哪个阶段"，还是在问"开发工作怎样被组织"？后者才进入过程模型。
2. **再抓主动作**：需求稳不稳定？要不要早交付？风险是不是主要矛盾？需求说不说得清？有没有现成构件可复用？把题干里最突出的那个困难对应到一个模型。
3. **最后看层级**：如果题干说的是"整个组织的软件过程能力"，直接判 CMMI；说"这个项目怎么组织开发"，才在过程模型/敏捷/RUP 里选。

不要先背各模型的优缺点清单，再倒着猜题干。**先找题干强调的困难，再让模型去回答那个困难。**

## 高频对比

| 对比 | 核心区分 | 典型例子 | 考试问法/陷阱 |
| --- | --- | --- | --- |
| 瀑布 vs 迭代增量 | 一次把阶段顺序走完 vs 拆成多轮、逐步形成可用能力 | 需求稳定、评审驱动的项目 vs 每轮都能给用户看一部分 | 陷阱：把"分了多轮"直接判成螺旋；多轮只是迭代特征 |
| 迭代增量 vs 螺旋 | 改进已有结果、增加新能力、获取反馈 vs **每轮以风险分析为核心驱动力** | 告警平台第二轮加短信 vs 先验证设备协议能否稳定接入 | 问"每轮为什么这样做"；做过一次风险评估不算螺旋 |
| 迭代增量 vs 敏捷 | 迭代增量是常用的推进方式 vs 敏捷还包括适应型、以人为本、短周期反馈等主张 | 一个团队按轮次开发，不代表就用了某个具体敏捷方法 | 陷阱："用了迭代/增量就是敏捷"或"敏捷就是迭代增量全部" |
| RUP 四阶段 vs 四个瀑布阶段 | 里程碑/时间维度，阶段内仍可开展多类工作流并迭代 vs 需求→设计→编码→测试顺序推进 | 细化阶段可以写代码、做测试来验证架构 | 陷阱：说"细化阶段只做分析设计"；四阶段≠四个瀑布阶段 |
| 原型 vs 构件组装模型 | 需求模糊，用样品澄清要什么 vs 需求大体清楚，用已有实现少写代码 | 先做首页原型让用户试用 vs 评估公司已有认证、报表构件 | 都是"配置/复用"类题干，看困难是"说不清"还是"已有实现" |
| CMMI vs 过程模型 | 评组织的过程能力成熟度 vs 组织某个项目的开发活动 | 公司在三级/四级 vs 这个项目用瀑布还是迭代 | 陷阱：把 CMMI 当成"另一种开发流程"，与瀑布、敏捷并列 |

## 最容易丢分的地方

- **把"瀑布"读成"绝不回头"。** 错在把"严格阶段顺序"扩张成"物理上禁止回退"。卡片口径是：回退不是它擅长的正常节奏，**越晚回头，依赖旧成果的下游产物越多，返工越大**。
- **看到"一轮一轮"就判螺旋。** 错在只抓表面特征，漏掉判据：螺旋必须把**风险分析放进每一轮**，并据此决定本轮开发/验证方式和是否继续。
- **把迭代增量等同于敏捷的全部。** 错在把一种推进方式当成整个方法族；敏捷还有适应型、以人为本等主张，具体方法各有骨架。
- **把 RUP 四阶段当成瀑布的四个阶段。** 错在把"阶段目标划分"和"工程活动顺序"混为一谈；RUP 阶段内可同时出现需求、实现、测试等工作流，只是投入比例不同。
- **把 CMMI 当生命周期模型。** 错在"过程"一词被泛化；CMMI 评价的是组织过程能力，与"这个项目采用哪种模型"不是一个问题。
- **九类工作流当成九个顺序阶段，或把成本管理当作独立工作流。** 工作流是纵向工作种类，可以跨阶段反复出现；项目管理才是独立工作流。
- **把 4+1 当成 RUP 的第三维或第十类工作流。** 它属于"以体系结构为中心"的架构表达层；`部署工作流` 是工程活动，`物理视图` 是架构视角，二者不能互换。
- **原型能演示就等于能上线。** 原型首先是沟通与验证工具；只有演化型原型在补齐生产要求后才可能成为正式产品。
