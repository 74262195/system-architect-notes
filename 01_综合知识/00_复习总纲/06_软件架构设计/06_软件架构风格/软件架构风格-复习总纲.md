# 软件架构风格 · 复习总纲

## 用法

预计 10～15 分钟。先盖住下文，用“题干在用什么连接构件”自问一遍，卡住再点对应子卡。

- [[06_架构设计理论与实践/02_层次式架构/层次式架构：为什么要让上层只使用下层服务|层次式架构]]、[[06_架构设计理论与实践/03_云原生架构/事件驱动架构：不等下游响应时怎样让服务继续协作|事件驱动架构]]等完整机制在根级八域，这里只做一句承接；

## 30 秒主线

风格识别三动作：**找构件 → 找连接件在传什么 → 看组合约束**（入口：[[00_软件架构风格总览：如何用构件与连接件识别典型结构]]）。

五类是并列地图，下面箭头只表示阅读顺序，不表示演化关系：

[[01_数据流风格：批处理与管道过滤器为什么不同|数据流]] ／ [[02_调用返回风格：控制为什么沿明确调用关系传递|调用-返回]] ／ [[03_数据中心风格：仓库与黑板为什么都以共享数据为中心|数据中心]] ／ [[04_虚拟机风格：解释器与规则系统如何构造执行环境|虚拟机]] ／ [[05_独立构件风格：进程通信与事件系统如何实现松耦合协作|独立构件]]

一句话分类：**传数据 → 数据流；传控制/服务 → 调用-返回；读写共享中心 → 数据中心；构造解释环境 → 虚拟机；消息与事件 → 独立构件。**

## 题干关键词 → 第一反应

| 题干信号 | 第一反应（先做的判断动作） |
| --- | --- |
| 输出直接作为输入、管道、过滤器、边产生边处理 | 判管道-过滤器；先确认下一步是否等整批完成 |
| 整批数据、结果文件、后一步等前一步整批结束 | 判批处理；不要用“数据量大”代替“整批交付” |
| 主控程序、过程调用、子程序层层分解 | 判主程序/子程序；连接件是过程调用与返回 |
| 对象、封装、通过方法协作 | 判面向对象；先确认调用目标是否明确 |
| 表示层/业务层/数据层、上层使用下层服务、层间接口 | 判层次型；看传的是服务调用还是待加工数据 |
| 客户端请求、服务器提供数据或服务 | 判 C/S；再确认题干是否同时强调职责分层 |
| 中央数据库、共享仓库、多个构件共同读写 | 判仓库；看是否只是一般读写共享数据 |
| 知识源、部分解、问题状态、逐步求解 | 判黑板；看是否围绕部分解推进复杂求解 |
| 脚本、被解释程序、解释引擎、语言语义 | 判解释器；下一步由程序结构和语义决定 |
| 规则集、事实、工作内存、条件匹配 | 判规则系统；下一步由哪些规则被事实满足决定 |
| 独立进程、进程间消息、发送/接收 | 判进程通信；发送方可面向明确通信对象 |
| 注册/订阅、发布事件、触发者不知道响应者、隐式调用 | 判事件系统；发布者不必知道谁响应 |

> [!tip] 两个防误判动作
> 出现“消息”先问：调用目标明确吗？明确 → 面向对象；不明确 → 事件系统。
> 出现“共享数据”先问：是一般读写，还是多个知识源围绕部分解逐步求解？

## 核心做题动作：三步归类

1. **划范围**：题干描述的是整个系统，还是某一段局部链路？真实系统可以混合多种风格，先定观察范围再判主导机制。
2. **找连接件**：这一段靠什么连？传数据、传控制与服务、共享数据读写、解释环境、消息与事件。连接件是五类风格最稳的区分点。
3. **排干扰**：用下节对比表逐对排除，最后落到具体子风格。

本章**没有需要代入计算的公式**，考的是结构归类与顺序判断，不必自造公式区。

## 高频对比

| 核心区分 | 典型例子 | 考试问法 / 陷阱 |
| --- | --- | --- |
| **数据流**：数据被依次加工 | 批处理、管道-过滤器 | 用“数据量大”冒充批处理；判据是整批交付与阶段等待 |
| **调用-返回**：控制沿明确调用关系传递 | 主程序/子程序、面向对象、层次型、C/S | 出现“消息”就选事件系统；面向对象的方法请求也叫消息 |
| **数据中心**：多个构件围绕共享数据协作 | 仓库、黑板 | 只凭“主动/被动”区分仓库与黑板 |
| **虚拟机**：构造解释程序或规则的执行环境 | 解释器、规则系统 | 业务代码里有条件分支就算规则系统；用了虚拟机产品就算虚拟机风格 |
| **独立构件**：相对独立构件靠消息或事件协作 | 进程通信、事件系统 | 有消息就等于事件系统；要看发布者是否知道响应者 |

| 易混对 | 核心区分 | 典型例子 | 考试问法与陷阱 |
| --- | --- | --- | --- |
| 仓库 vs 黑板 | 一般读写共享数据 vs 围绕问题状态和部分解逐步求解 | 共享数据库 vs 语音识别、模式识别 | 只背“黑板更主动”；判据是知识源与部分解 |
| 批处理 vs 管道-过滤器 | 整批交付、阶段等待 vs 输出持续流入下一步 | 月底账单批处理 vs 实时日志链路 | 都“按步骤走”，忽略后一步是否等整批 |
| 管道-过滤器 vs 层次型 | 传待加工数据 vs 传服务调用与控制 | 日志清洗链 vs 三层应用 | 都“一层接一层”，只看图形不看连接内容 |
| 面向对象 vs 事件系统 | 调用目标明确 vs 发布者不必知道响应者 | 对象方法调用 vs 支付完成事件 | 见“消息”就判事件系统 |
| 解释器 vs 规则系统 | 下一步由程序语义决定 vs 由事实匹配到的规则决定 | 脚本引擎 vs 风控规则推理 | 把规则匹配误写成“按顺序解释执行程序” |
| 进程通信 vs 事件系统 | 可面向明确通信对象 vs 注册/订阅、隐式调用 | 独立进程交换消息 vs 响应者被自动通知 | 两者都靠消息，忽略“是否知道接收方” |

## 最容易丢分的地方

- **把并列关系读成演化关系**：01～05 只是阅读顺序，五类风格不存在“学完数据流才演化成调用-返回”的因果。
- **批处理 ≠ 数据量大**：直觉把“批”理解成“多”，但真正的判据是整批交付、后一步通常等前一步整批完成。
- **“消息”不是事件系统的充分条件**：面向对象的方法请求也能叫消息；只有发布者不必知道谁会响应时，才转向事件系统。
- **仓库 vs 黑板不能靠“主动/被动”一个词**：这个说法太粗，稳定判据是“在共享数据上一般读写”还是“多个知识源围绕部分解推进复杂求解”。
- **有 `if` 不等于规则系统**：规则要被组织成可匹配、可选择执行的集合；虚拟机风格的核心是人为构造解释程序或规则的执行环境。
- **连接件才是主判据**：只记住“都有多个构件”会全错，要先说清它们在传数据、传控制、共享数据、解释内容还是传事件。
- **真实系统可以混风格**：答题要按题干强调的粒度判断，不能给整个系统硬贴一个标签。
