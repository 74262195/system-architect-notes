# 可靠性管理 · 复习总纲

> **用法**：预计 5 分钟（1 张卡，P1）。先闭卷做末尾自测，卡住再点原子卡。本页只做复习索引，不是新的事实源；与卡片冲突时以卡片为准。

## 大纲边界与优先级

本模块对应大纲 8.3，只有一个考点：**软件可靠性管理为什么必须贯穿软件生命周期**。

- 唯一卡片 [[06_可靠性管理：为什么要贯穿软件生命周期]] 是 P1（2024 H1 直接考可靠性管理的阶段分工），属于第一轮要能答出的题眼。
- 大纲只要求「可靠性管理是软件工程管理的一部分、按生命周期各阶段分工」，不要求背具体管理模板或文档清单。

## 30 秒主线

「最后多测几轮」补不回需求阶段没定义的目标、设计阶段没考虑的故障处理 → 可靠性管理把可靠性目标、计划、活动、数据和纠正措施分散到**需求 → 设计 → 编码 → 测试 → 实施**全过程，保证它们之间不断链。

## 题干关键词 → 第一反应

| 题干看到什么 | 第一反应 |
| --- | --- |
| 软件可靠性管理属于什么 | 软件工程管理的一部分 |
| 何时开展可靠性活动 | 贯穿软件生命周期，不是交付前单点 |
| 各开发阶段怎样安排可靠性活动 | 先判断题干处于哪个阶段，再套该阶段侧重（见下方对比表） |
| 「等系统做完再要求达到很高可靠性」 | 典型反例：返工成本高，说明管理缺位 |

## 核心做题动作与必要公式

**动作 1：先给题干定位阶段。** 问「何时开展」直接答贯穿软件生命周期；问「某阶段重点」先判断是需求、设计、编码、测试还是实施，再套对应侧重，不要一律答「测试」。

**动作 2：用「不断链」解释为什么。** 可靠性管理的核心不是「每阶段都做同一件事」，而是保证目标、设计、测试、数据、评价之间接得起来。需求阶段没定目标、设计阶段没考虑故障处理，等完成后才提要求，往往只能付出更高返工成本。本模块不保留任何公式。

**动作 3：把管理对象说全。** 管理对象是贯穿生命周期的可靠性**目标、计划、活动、数据和纠正措施**；只答「加测试」不算答对「管理」。

## 高频对比

| 概念对 | 核心区分 | 考试问法 / 陷阱 |
| --- | --- | --- |
| 需求 / 设计 / 编码 / 测试 / 实施 | 需求定目标与验收标准；设计定度量并落实可靠性设计；编码做单元级发现与数据收集；测试同时做测试、建模、评价并调整计划；实施用真实运行数据再评价 | 问「某阶段重点」时不要一律答「测试」 |
| 可靠性管理 vs 交付前临时加测 | 管理贯穿生命周期、保证各环节衔接；末端加测只能暴露问题 | 「活动只放在交付前测试阶段，是否符合」→ 不符合 |
| 可靠性管理 vs 可靠性设计/测试/评价 | 管理是组织闭环（计划、数据、纠正措施）；设计/测试/评价是被管理的具体活动 | 题干问「属于什么、何时开展」答管理口径，别答技术手段 |
| 「每阶段做同一件事」 vs 「不断链」 | 前者是误解；后者才是管理目标 | 判断题出现「所有阶段做相同活动」要警惕 |

## 最容易丢分的地方

- 把可靠性管理归到测试人员或测试阶段。它是软件工程管理的一部分，不是交付前的末端活动；这正是「最后多测几轮」类选项的诱因。
- 只答「要加强管理」而不说管理对象。目标、计划、活动、数据、纠正措施才是得分点。
- 以为管理就是每阶段做同一件事。真正要求是目标、设计、测试、数据、评价之间不断链。
