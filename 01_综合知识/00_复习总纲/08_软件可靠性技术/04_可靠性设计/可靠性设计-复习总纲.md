## 题干关键词 → 第一反应

| 题干看到什么 | 第一反应 |
| --- | --- |
| 提高软件可靠性最有效、经济的重要阶段/手段 | 设计阶段的可靠性控制，不要条件反射选「增加测试」 |
| 验收测试失败后回退并改用后备块 | 恢复块（顺序尝试） |
| 多个独立版本同时运行后多数表决 | N 版本程序（并行表决） |
| 强调设计差异、不同人员/算法/语言 | N 版本的设计不相关性 |
| 准备差异化备用实现、替换、接管 | 冗余设计 |
| 返回值范围检查、超时检测、状态标志、自检、报警 | 检错设计 |
| 检测对象、检测延时、实现方式、处理方式 | 检错设计的四个分析要素 |
| 简化结构、优化数据流、降低模块耦合 | 降低复杂度设计 |
| 心跳、主备、Active/Standby、故障切换 | 双机热备 |
| 多节点组成统一系统、节点故障后其他节点接管 | 服务器集群 |
| 「同一份软件复制多份就是容错」 | 错：相同缺陷会同时出现，要靠设计差异 |

## 核心做题动作与必要公式

**动作 1：先看「串行切换」还是「并行表决」。** 恢复块是主实现先执行、验收测试不通过就回退并换备选块，关键词是顺序、逐块验收、失败回退、无备选时受控失败；N 版本是多版本并行算同一输入再表决，关键词是并行多版本、多数表决、设计差异。备选实现算出的结果同样必须过验收测试，不能直接交付。

**动作 2：容错与检错不要混。** 检错只保证「坏了能知道」，之后是停止、部分停止、报警还是交给别的恢复机制由处理方式决定；若题干强调「无人工干预仍继续运行」，只有检错通常不够。检错通常代价低于容错/冗余。

**动作 3：降低复杂度分两个方向看。** 模块复杂性指模块内部数据流、逻辑和程序规模；结构复杂性指模块之间关联程度。目标是减少不必要的复杂性，不是形式上压缩代码行数。

**动作 4：系统配置题先找「故障如何被检测」，再找「谁接管服务」。** 双机热备靠心跳等机制判断主机状态，故障后把资源/服务转移到备机；集群把多台服务器组成对外统一的系统，节点或应用故障时服务在其他节点重启或被接管。教材还区分热备、互备、双工等工作方式，本轮只抓共同核心：有冗余节点 + 能判断故障 + 能完成接管。本模块不保留公式。

## 高频对比

| 概念对 | 核心区分 | 考试问法 / 陷阱 |
| --- | --- | --- |
| 容错 vs 检错 | 容错要「故障后仍尽量完成服务」；检错要「尽快发现、定位/报警并进入处理」 | 「无人工干预仍继续运行」→ 仅检错不够；检错 ≠ 容错 |
| 恢复块 vs N 版本 vs 冗余 | 恢复块串行尝试并逐块验收；N 版本并行计算后多数表决；冗余准备差异化备用实现替换或接管 | 「验收测试 + 回退」→ 恢复块；「多数表决」→ N 版本 |
| 设计阶段 vs 测试阶段 | 设计阶段把单点、异常处理、耦合等结构性风险提前控制；测试能发现问题却不能替代设计 | 「提高可靠性最有效、经济的重要阶段」→ 设计阶段 |
| 做减法 vs 加冗余 | 降复杂度从源头减少缺陷机会；冗余/容错在故障发生后保住服务 | 选项说「为可靠性应无限增加冗余和功能」要警惕 |
| 双机热备 vs 集群 | 热备是一主一备 + 心跳判断 + 接管；集群是多节点组成统一系统、故障时节点间接管 | 「心跳 + Active/Standby」→ 双机热备；「多节点统一系统」→ 集群 |

## 最容易丢分的地方

- 把「简单复制同一份软件」当成软件容错。相同缺陷会同时出现，必须靠设计差异/不相关性。
- 以为备选程序跑完就能交付。恢复块的每个候选结果都要过验收测试；验收测试本身也可能漏检，通过只代表满足预先定义的验收条件。
- 把检错说成容错。检错解决「及时知道」，没有恢复动作时不能自动消掉故障。
- 认为可靠性只能靠加冗余。降复杂度是教材明确列出的设计方向，「代码越短越可靠」却是错的。
- 把双机/集群扩写成整章高可用。本模块只回答「系统配置层怎样用冗余和接管降低单点故障影响」；可用度定义与 MTTR 仍看 [[可靠性与可用性]]。
