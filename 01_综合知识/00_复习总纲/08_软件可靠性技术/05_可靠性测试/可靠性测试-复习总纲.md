## 题干关键词 → 第一反应

| 题干看到什么 | 第一反应 |
| --- | --- |
| 运行剖面、统计失效数据、后续可靠性评价 | 可靠性测试 |
| 覆盖率很高的测试数据能否直接评价可靠性 | 未必代表真实使用分布 |
| 用户类别、使用概率、状态转移、真实运行分布 | 运行剖面 |
| 哪种数据最适合确定运行概率 | 优先现有系统/历史版本的真实运行数据 |
| 「某关键功能概率低所以可以不测」 | 通常判错，低频关键路径要补充关键/边界测试 |
| 同一版本、失效时间/间隔、累计失效次数、可靠性数据记录 | 受控可靠性测试 |
| 测试中途修复并部署新版本，原统计能否直接续算 | 不能无条件合并，应开始新样本 |
| 合同/标准还要求覆盖测试 | 统计测试不排斥其他测试 |

## 核心做题动作与必要公式

**动作 1：先问数据能不能进模型。** 可靠性测试不仅要「找 bug」，还要在预期使用条件下取得能用于可靠性评估的失效数据。普通覆盖测试按结构或功能覆盖目标选用例，不天然代表真实使用概率，所以「发现了多少缺陷」不能直接等于「上线后失效概率」。

**动作 2：狭义与广义分开答。** 狭义指按预先确定的用例、在预期使用环境中、以接近真实用户的方式执行软件，核心目的是获取可靠性数据；广义把目标确定、运行剖面、用例设计、实施、数据分析、建模和评价串成完整验证过程。整条链是：**可靠性目标 → 运行剖面 → 测试用例 → 受控执行并记录失效 → 可靠性评价。**

**动作 3：建立运行剖面三步走。** 一是建立使用模型（用状态和转换描述用户如何操作）；二是分层使用者与用法（用户级分层关心「谁在激励系统」，用法级分层关心「哪些功能被怎样使用」）；三是给行为分配概率，优先用现有系统、原型或历史版本的真实数据，其次才用访谈、观察和领域专家判断。测试用例再按这些概率和关键程度从巨大输入域中抽样。

**动作 4：剖面决定主样本，风险补足长尾。** 运行剖面不是「只测最常用功能」。飞控起飞/降落占总运行时间很少却绝不能按低频忽略；对高安全系统，关键功能、边界和状态跃迁要建立专门剖面或补充非统计测试。

**动作 5：受控实施要记全数据。** 同一轮测试保持相同软件版本；新版本意味着新的测试开始，不能把新旧版本数据无条件混成一个样本。时间型数据包括失效发生时的累计时间、相邻失效间隔、某区间失效次数、到某时间点的累计失效次数；同时记录用例/说明、测试环境、结果、失效现象、测试人员。本模块不保留公式。

## 高频对比

| 概念对 | 核心区分 | 考试问法 / 陷阱 |
| --- | --- | --- |
| 可靠性测试 vs 普通软件测试 | 普通测试按覆盖目标暴露缺陷；可靠性测试按预期使用条件取得可统计的失效数据 | 「覆盖率很高就能评价可靠性吗」→ 未必，缺真实使用分布 |
| 狭义 vs 广义可靠性测试 | 狭义只指按用例在预期环境中执行并取数；广义还含目标、剖面、设计、分析、建模、评价 | 问「完整的可靠性验证过程」→ 答广义 |
| 统计主样本 vs 关键/边界补充 | 运行剖面按真实概率定常规比例；低频高风险路径另建专门剖面或非统计测试 | 「概率低所以不测」→ 判错 |
| 统计测试 vs 非统计测试 | 可靠性测试解决统计代表性；合同、标准、安全要求可能还要覆盖测试 | 两者不是互相取代，别答「其他测试都没用」 |
| 同一版本 vs 换版本 | 同一轮测试保持同一版本；版本变化意味着统计对象变化 | 「修复后换版本，原统计直接继续吗」→ 通常不能 |

## 最容易丢分的地方

- 把可靠性测试理解成「多跑几轮系统测试」。它是一条数据链，终点是能进入可靠性评价的失效数据。
- 用覆盖率代替使用分布。测试人员把三类功能各测 100 次，而真实用户几乎只在提交预约，样本就不代表未来使用。
- 平均分配用例。真实概率是 90% 浏览、9% 下单、1% 退款时，各测三分之一得到的失效比例会失真。
- 以「概率低」为由跳过关键路径。运行剖面给常规样本比例，低频关键/高风险路径要用专门剖面或非统计测试补足。
- 换版本后直接合并数据。前 100 个用例跑版本 A、后 100 个跑版本 B 再混算，统计对象已经变了。
