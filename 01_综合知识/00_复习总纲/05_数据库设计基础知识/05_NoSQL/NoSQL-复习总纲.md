## 30 秒主线

1. NoSQL 泛指一批不以传统关系表模型为唯一核心的数据管理方案，常被解释为 Non-Relational，也常理解为 Not Only SQL —— [[NoSQL分类与特点]]。
2. 大纲要求先能认四类：**键值、文档、列式/列族、图**，识别的入口是数据形态而不是产品名字。
3. 一套 NoSQL 系统可以按四层理解：**数据持久层 → 数据分布层 → 数据逻辑模型层 → 接口层**，记成“先存得下 → 再分得开 → 再组织成模型 → 最后给程序接口” —— [[NoSQL体系框架与适用场景]]；选型则回到需求：数据结构变化快、需要水平扩展、数据天然是文档/图/键值、对分布式高可用有强需求且业务允许相应一致性权衡时才评估，强依赖复杂关系查询、严格事务和成熟 SQL 生态时关系数据库仍可能更合适。

## 题干关键词 → 第一反应

| 题干看到什么 | 第一反应 |
| --- | --- |
| Key 直接找到 Value、缓存、会话、简单对象 | 键值数据库 |
| 一整个 JSON 对象、字段经常变化 | 文档数据库 |
| 按列或列族组织、大规模稀疏数据 | 列式/列族数据库 |
| 节点与边、社交关系、路径、关联网络 | 图数据库 |
| 问“NoSQL 四层框架从底到顶” | 持久层 → 分布层 → 逻辑模型层 → 接口层 |
| 问“直接面向应用程序的是哪一层” | 接口层 |
| 数据量大 + 复杂关系查询 + 严格事务 + 成熟 SQL 工具链 | 关系数据库仍可能更合适 |

## 核心流程（认类型 + 选型）

1. **先按数据形态认四类**：Key→Value 是键值，整体 JSON 文档是文档，节点与边是图，按列族组织是列式/列族。
2. **再按四层定位问题**：问数据最终怎么保存在介质上→持久层；问怎样跨节点分布、复制→分布层；问向应用呈现键值/文档/列/图哪种模型→逻辑模型层；问应用从哪里访问→接口层。
3. **最后做选型判断**：先看数据模型是否固定、是否需要水平扩展、数据天然是什么形态、对分布式高可用的要求，以及业务能接受哪种一致性/事务权衡。
4. **选型不是技术标签竞赛**：题干给出强关系查询、严格事务约束或成熟 SQL 生态时，反而应保留关系数据库。

## 高频对比

**四类 NoSQL 模型**

| 类型 | 心智模型 | 典型适合的数据 |
| --- | --- | --- |
| 键值数据库 | 用 Key 直接找到 Value | 缓存、会话、简单对象 |
| 文档数据库 | 以文档整体保存结构化/半结构化对象 | JSON 类业务对象 |
| 列式/列族数据库 | 按列或列族组织 | 大规模稀疏、分布式数据 |
| 图数据库 | 节点与边直接表达关系 | 社交关系、路径、关联网络 |

**四层框架的职责**

| 层次 | 回答什么 | 记法 |
| --- | --- | --- |
| 数据持久层 | 数据最终怎样保存在内存、磁盘或其他介质 | 先存得下 |
| 数据分布层 | 数据如何跨节点分布、复制或组织 | 再分得开 |
| 数据逻辑模型层 | 向上层呈现键值、文档、列、图等逻辑模型 | 再组织成模型 |
| 接口层 | 向应用提供访问入口 | 最后给程序接口 |

**NoSQL 与关系数据库的选型边界**

| 更可能考虑 NoSQL | 更可能保留关系数据库 |
| --- | --- |
| 数据结构变化快、不适合固定关系模式 | 业务强依赖复杂关系查询 |
| 数据规模与访问吞吐需要水平扩展 | 需要严格事务约束 |
| 数据天然是文档、图、键值等模型 | 依赖成熟 SQL 生态 |
| 对分布式、高可用有强需求，且业务允许一致性/事务权衡 | 一致性要求使权衡不可接受 |

## 最容易丢分的地方

- **把 NoSQL 当关系数据库的升级版**：它是针对不同数据模型、扩展和分布需求的一组方案，不是谁的替代品。
- **把“NoSQL”理解成“完全不用 SQL”**：这个名称本身常被理解为 Not Only SQL，别写成绝对定义。
- **把 ACID 差异绝对化**：教材用“不保证传统关系数据库的 ACID 特性”概括差异，应理解为总体设计取向，不能扩写成“任何 NoSQL 都绝不支持事务”。
- **只凭“数据量大”就选 NoSQL**：题干同时给出复杂关系查询、严格事务或成熟 SQL 工具链时，关系数据库仍可能更合适。
- **四层框架顺序记反**：教材从底往上列；应用读数据时从接口往下走、结果再返回，两条方向不要混。
- **以为所有 NoSQL 产品指标相同**：灵活模型、可扩展性、分布式高可用是总体优势方向，不代表每种产品在所有指标上都一样。
