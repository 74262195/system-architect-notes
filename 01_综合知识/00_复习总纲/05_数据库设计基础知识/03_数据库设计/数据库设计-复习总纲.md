# 数据库设计 · 复习总纲

## 用法

预计 10～12 分钟。本模块几乎都是“这道题在哪个阶段、这个产物属于哪一层”的定位题，先用「题干关键词」表自测定位，再回看「核心流程」里的转换规则；卡住就点对应原子卡。

## 大纲边界与优先级

大纲 5.3「数据库设计」要求覆盖需求分析、概念结构设计、逻辑结构设计、物理结构设计、实施与运行维护。按卡片 `exam_priority` 排：

- **P0 第一轮**：[[数据库设计六阶段]]（阶段总入口）、[[ER模型与概念结构设计]]、[[ER图合并与冲突]]、[[ER图转关系模式]]。
- **P1 第一轮**：[[数据需求分析]]、[[逻辑设计与完整性视图]]、[[反规范化设计]]、[[物理设计与索引]]、[[数据库运行维护与备份恢复]]。
- **P2 第二轮**：[[数据库实施与试运行]]——只要求会按产物和动作定位。

边界：备份与故障恢复由 [[数据库运行维护与备份恢复]] 承担；并发控制、日志与恢复只按 DBMS 运行管理职责识别，不在本模块展开。

## 30 秒主线

1. 设计是一条翻译链：**需求分析 → 概念结构设计 → 逻辑结构设计 → 物理结构设计 → 实施 → 运行维护**，每个阶段把上一层的问题变成下一层的方案 —— [[数据库设计六阶段]]。
2. 需求分析先和用户一起整理**信息、处理、系统**三类要求，交付物是数据流图、数据字典，而不是最终表 —— [[数据需求分析]]。
3. 概念结构设计用实体、属性、联系描述业务，先做局部 E-R 图再合并成全局概念模型 —— [[ER模型与概念结构设计]]；合并时必须处理属性、命名、结构三类冲突 —— [[ER图合并与冲突]]。
4. 全局 E-R 图按联系基数转成关系模式，再补范式检查、完整性约束和用户视图，才算逻辑设计收口 —— [[ER图转关系模式]]、[[逻辑设计与完整性视图]]。
5. 结构规范但读得慢时，先有实测瓶颈再做受控冗余 —— [[反规范化设计]]；然后决定数据分布、存储结构与访问路径 —— [[物理设计与索引]]；最后建库装载、联调试运行，上线后持续监测、备份恢复与重组重构 —— [[数据库实施与试运行]]、[[数据库运行维护与备份恢复]]。

## 核心公式与流程

### 1. 六阶段定位流程

1. 先圈出题目里的**产物或动作**，不要只看它提到“数据库”或“表”。
2. E-R 图、实体属性联系 → 概念结构设计。
3. 关系模式、E-R 转换、规范化、完整性约束、视图 → 逻辑结构设计。
4. 文件组织、索引、访问路径、数据分布 → 物理结构设计。
5. 建库、装载、调试、试运行 → 数据库实施。
6. 监测与改善、备份恢复、重组与重构、结构调整 → 运行和维护。

### 2. 局部 E-R 图合并的冲突判断

1. 先把两张图指向的**同一业务对象**对应起来。
2. 差异在类型、取值范围、单位 → 属性冲突（例：价格一处用元、一处用分）。
3. 同义异名或同名异义 → 命名冲突（例：“客户编号”与“会员号”同指一个标识）。
4. 同一对象被建成实体或属性、实体属性集合不同 → 结构冲突（例：“地址”在一处是属性、另一处是独立实体）。
5. 冲突解决后还要优化合成 E-R 图：可合并某些 1:1 或 1:* 联系，消除冗余属性和冗余联系。

### 3. E-R 图转关系模式的规则

实体先各自成表：实体名→模式名，实体属性→关系属性，实体标识符→关系的码。联系按基数落表，**联系自己的属性必须跟着联系走**：

| 联系基数 | 转换动作 | 关键约束 |
| --- | --- | --- |
| 1:1 | 通常不单建关系；可并入任一方，加入另一方的码和联系属性 | 外码加唯一约束，保证最多对应一条；哪一侧必须参与决定该侧外码是否非空 |
| 1:N | 并入 N 方，在 N 方加入 1 方的码和联系属性 | 每个 N 方记录只指向一个 1 方记录 |
| M:N | 必须新建独立关系，放入两端实体的码和联系属性 | 两端码共同构成该关系的码，不能把多值塞进一个字段 |

M:N 时联系关系的码是两端码的并集：

$$
\text{码}(\text{联系关系})=\text{码}(E_1)\cup\text{码}(E_2)
$$

**适用条件**：仅用于 M:N 联系；1:1、1:N 通常不新建关系。1:1 放在哪一侧不只看基数，还要看哪侧允许暂时没有关联对象、哪侧必须参与，以及联系属性放在哪边更自然；无论选哪边，外码都要唯一，非空只表达所放这一侧必须参与，不能单独强制另一侧也参与。

### 4. 逻辑设计四步与反规范化决策链

逻辑设计顺序：**确定目标数据模型并转换 → 检查依赖与范式 → 把业务规则写成完整性约束 → 按业务和用户建立视图**。约束落点：唯一学号用主码（实体完整性），选课的学号/课程号必须存在用外码（参照完整性），成绩 0～100 用检查条件（用户定义完整性）。

反规范化是一条受控链：**先规范化 → 再证明读瓶颈 → 只为这条访问增加数据 → 规定同步责任**；缺少同步设计就会出现明细合计 120 元、订单表仍显示 100 元的不一致。

### 5. 重组与重构的最小区分

只问一句：**表、约束、视图这些结构定义变了吗？** 没变、只清碎片和回收废弃空间是**重组**；增删列、改约束、分解合并表、修改视图是**重构**，重构后还要重新评价与验证安全性。

## 高频对比

**设计阶段三段**

| 阶段 | 回答什么 | 典型产物 |
| --- | --- | --- |
| 概念结构设计 | 业务世界里有什么对象和联系 | 局部/全局 E-R 图 |
| 逻辑结构设计 | 怎样变成 DBMS 支持的数据模型 | 关系模式、范式、约束、视图 |
| 物理结构设计 | 数据怎样分布、存储和访问 | 存储结构、索引、访问方式 |

**三类冲突**

| 冲突 | 先问什么 | 典型表现 | 处理方向 |
| --- | --- | --- | --- |
| 属性冲突 | 同一属性的取法是否一致 | 类型、取值范围、单位不同 | 统一为一种可存储的表示 |
| 命名冲突 | 名称与含义是否一一对应 | 同义异名；同名异义 | 统一命名，必要时拆开不同含义 |
| 结构冲突 | 同一对象被建成了什么 | 实体/属性身份不同；属性集合不同 | 统一抽象层次和模型结构 |

**成对概念**

| 对比组 | 关键区分 |
| --- | --- |
| 视图 vs 表 | 表保存数据的逻辑结构；视图是用户看数据的逻辑窗口，通常不复制物理数据；只建视图不等于权限控制完成 |
| 规范化 vs 反规范化 | 规范化先保证基本事实不重复；反规范化是按实测读瓶颈受控增加冗余，并要规定同步责任 |
| 重组 vs 重构 | 结构定义没变、只清碎片是重组；结构定义变了才是重构，重构后要重新评价安全性 |
| 需求分析 vs 概念设计 | 需求分析交付数据流图、数据字典；一旦开始画实体联系图就已进入概念结构设计 |

## 最容易丢分的地方

- **看到“表”就选逻辑设计**：先看产物。E-R 图属概念；关系模式、范式、约束、视图属逻辑；索引与存储属物理；建库装载属实施。
- **把 E-R 图当表结构**：E-R 只描述业务对象与联系；转成关系模式才进入逻辑设计。
- **只背三类冲突的名字**：题干给两个部门描述时，先对应同一业务对象，再判断差异落在属性表示、名字含义还是建模结构哪一层。
- **“有联系就新建一张表”**：只有 M:N 必须独立成关系；1:1、1:N 通常并入一方，但联系属性不能因此遗漏。
- **1:1 只看基数决定外码放哪边**：还要看参与约束；无论放哪边外码都要唯一，非空不能单独强制另一侧必须参与。
- **认为反规范化就是不规范化，或“只要慢就多建索引”**：前者是已规范化结构上按实测瓶颈做受控冗余；索引数量讨论的是访问路径与写入维护成本，属物理设计。
- **重组与重构互换**：判据是结构定义有没有变，不是数据量或碎片多少。
- **认为建了视图就安全了**：还要限制底层表权限，并把视图权限授给正确用户。
- **把需求分析写成表结构**：需求分析只能说“高峰期要快速查到结果”，不能直接拍板“给某列建 B 树索引”。
