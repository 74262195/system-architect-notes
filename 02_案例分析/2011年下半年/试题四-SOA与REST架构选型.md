# 2011 年下半年试题四：SOA 与 REST 架构选型

## 原题｜先独立作答

> [!warning] 先做题，再展开后面的解析
> 以下题面按仓库“资料版（来源待核验）”整理。问题 1 涉及原题表 4-1，当前案例页不臆造缺失表格版式。

某公司拟开发市场策略跟踪与分析系统。互联网访问数据来自两种第三方 Web 分析软件并生成不同格式报表；实际销售数据来自各分公司的电子表格或数据库。系统还要汇聚、分析这些数据，并通过浏览器展示市场策略效果。

王工主张采用面向服务架构：包装第三方软件和异构数据源，把数据访问功能通过标准 Web 服务接口暴露。李工认为核心是数据的定位、汇聚与转换，更适合面向资源架构：为数据元素确定地址，统一转换为 JSON，通过数据组合支持分析处理。架构评估后采用李工方案。

### 问题 1

分析系统的数据源特征和数据操作方式，完成原题表 4-1 的（1）～（3），并用 200 字以内说明李工方案的优点。

### 问题 2

从**数据获取方式、数据交互方式、数据访问的上下文无关性**三个方面比较两种方案，并用 500 字以内说明为什么没有采用王工方案。

### 问题 3

用 200 字以内解释 REST，并指出 REST 将哪 **3 种关注点**进行分离。

---


> [!summary]- 做完再看：这道题真正训练什么
> **第一动作**：不要看到“Web 服务”就直接选 SOA，先判断题目核心是在**调用业务功能**，还是在**定位、读取和组合资源**。
> **本题主链**：数据源特征 → 数据操作方式 → 服务/资源取向 → 比较交互代价 → REST 约束。
> **易错点**：把“用了 HTTP / JSON”直接等同于 REST，或者把 SOA 与 REST 当成互斥技术名词死背。

## 题目要求先拆成三个动作

题干给出市场策略跟踪与分析系统：数据来自第三方 Web 分析软件、分公司电子表格和数据库，需要汇聚、转换、分析并在浏览器展示。王工主张把异构数据源包装成 Web 服务，李工主张围绕数据资源定位、转换和组合，最终采用李工方案。

三问分别要求：

1. 从**数据源特征和数据操作方式**判断为什么资源取向更合适；
2. 从**数据获取、数据交互、上下文无关性**比较两种方案；
3. 解释 REST，并指出它分离的三个关注点。

## 第一问：先看数据，而不是先看技术名词

题干最关键的不是“Web”“JSON”这些名词，而是下面三类证据：

| 题干证据 | 先判断什么 | 对选型的影响 |
| --- | --- | --- |
| 电子表格、数据库、第三方报表 | 数据是可定位、可读取的持久资源 | 可以直接围绕资源组织访问 |
| 系统主要做采集、汇总、分析、展示 | 主要需求偏数据访问与组合 | 不一定需要先把每个数据源包装成业务服务 |
| 数据用于统计分析 | 读取远多于业务命令调用 | 资源取向可以减少额外服务封装 |

**作答骨架**：先写“数据是什么”，再写“主要怎样操作数据”，最后落到“因此哪种架构更贴合”。

可以压缩成：

> 数据源主要是文件、数据库和第三方报表等持久数据，当前场景以读取、汇聚和转换为主；因此直接标识并访问数据资源，比先把每个异构来源包装成服务再调用更直接。

这一步训练的是**需求证据 → 架构取向**，不是背“REST 比 SOA 好”。换一个需要复杂业务操作、事务协调或跨系统能力复用的题干，结论可能不同。

## 第二问：比较方案时固定三个维度

### 1. 数据获取方式

王工方案先把原有系统和数据源包装为服务，再通过服务接口取数据；李工方案先确定资源位置与标识，再直接取得资源表述。

因此本题场景下，前者多了一层服务封装，后者更贴近“找到数据 → 读取数据”。

### 2. 数据交互方式

SOA 方案更偏向通过服务调用完成交互；资源取向方案把资源本身作为交互中心，通过资源标识和表述进行访问。

考试作答不要只写“一个复杂、一个简单”，要说明**复杂在哪里**：是先封装功能再调用，还是直接围绕资源访问。

### 3. 上下文无关性

本题解析把李工方案的优势落在：客户端用 URI 标识资源，服务端不需要为每次资源访问保存特定客户端会话上下文。

这与 [[06_架构设计理论与实践/04_面向服务架构_SOA/REST：怎样把服务接口设计成围绕资源的交互|REST：怎样把服务接口设计成围绕资源的交互]] 中的资源中心、URI 与无状态约束相呼应。

> [!warning] 不要把旧题表述升级成绝对规律
> 不能由本题推出“SOA 数据访问一定低效”“REST 一定比 SOA 稳定”或“SOA 一定有状态”。本题结论只针对题干给出的以持久数据读取、汇聚和转换为核心的场景。

## 第三问：REST 要抓“资源—表述—动作”

本题解析的核心表述是：REST 从资源角度组织网络系统，资源由 URI 标识，客户端取得资源的表述，并通过交互使状态发生变化；同时把**资源、资源的表述、获取/操作资源的动作**分开。

回链理论主事实源：

- [[06_架构设计理论与实践/04_面向服务架构_SOA/REST：怎样把服务接口设计成围绕资源的交互|REST：怎样把服务接口设计成围绕资源的交互]]
- [[06_架构设计理论与实践/04_面向服务架构_SOA/SOA：怎样把跨系统能力组织成可组合的服务|SOA：怎样把跨系统能力组织成可组合的服务]]

因此看到 REST 案例题时，第一反应不是“HTTP + JSON”，而是检查：

> **有没有明确资源 → 有没有稳定标识 → 客户端交换的是不是资源表述 → 交互是否遵循 REST 约束。**

## 一张答题骨架

遇到“两个架构方案怎么选”的案例题，按下面顺序写：

1. **业务对象**：题目主要在处理能力、消息，还是资源/数据？
2. **主要动作**：调用业务功能、编排流程，还是读取/汇聚/转换数据？
3. **方案代价**：每个方案需要增加哪些封装、状态、转换或协调？
4. **约束匹配**：题干最在意简单访问、松耦合、实时性、可靠性还是其他质量属性？
5. **结论贴证据**：不能只写技术优缺点，必须说明为什么适合“这道题”。

## 容易丢分的地方

- 一看到“Web 服务”就默认 SOA 一定更先进；
- 一看到 JSON 就判定 REST；JSON 只是资源表述的一种可能格式；
- 比较方案时只背优缺点，不引用“持久数据、读取、汇聚、转换”等题干证据；
- 把本题的特定取舍写成现实工程中的绝对规律；
- 解释 REST 时只写 URI，不写资源、表述和交互约束。

## 本题形成的可复用动作

> **业务对象/数据特征 → 主要操作 → 服务还是资源 → 交互代价 → 约束匹配 → 贴题干作答。**

这补上了前面质量属性、安全架构和数据扩展案例之外的第四类动作：**面对两个可行架构方案时，怎样从题干需求反推选型，而不是背技术名词。**
