## 先把三问分层

题干背景是宇航装备软件规模增长，软件失效开始影响整个系统可靠性。三问实际从三个层次推进：

1. **问题 1：概念层**——什么叫可靠性，可靠性包含哪些子特性，可以采用哪些技术；
2. **问题 2：机理层**——为什么软件可靠性不能照搬硬件可靠性的思路；
3. **问题 3：设计层**——恢复块和 N 版本程序怎样通过不同方式实现软件容错。

## 第二问：软件不会像硬件一样“磨旧”

这是本题最值得复用的判断动作。

硬件可能因为材料老化、磨损等物理原因随时间发生退化；软件本身没有这种物理磨损。软件更典型的失效路径是：

> **程序中已有缺陷 → 某个输入/状态/执行路径触发缺陷 → 表现为软件失效。**

因此，题目让比较硬件和软件可靠性时，不要只背“软件不会老化”，而要先问：

1. 失效是否来自物理退化？
2. 不运行时是否还会因为自身材料老化而失效？
3. “维修”是在更换物理部件，还是修改代码并引入新版本？
4. 修改后是否可能引入新的缺陷？

解析资料给出的四个软件侧结论包括：不考虑软件演化时失效率统计上非增；软件不使用时不会因软件自身磨损而失效；软件维护会产生新的代码；软件失效前通常缺少硬件式物理退化预警。

原题表 3-1 的题面项目与资料解析对应如下。这里的“不使用时不失效”特指软件本身；答案原文明确排除存储介质老化等外部因素。

| 硬件可靠性特征 | 软件可靠性特征（资料解析） |
| --- | --- |
| 失效率服从浴缸曲线，随使用时间出现老化趋势 | 不考虑软件演化时，失效率在统计上非增 |
| 即使不使用，材料老化也可能导致失效 | 不使用时软件本身不会因物理磨损而失效，存储介质老化另论 |
| 维修可使硬件恢复原状态 | 软件维护会因修缺陷或需求变更而产生新代码 |
| 硬件失效前通常会出现退化或报警 | 软件失效前通常很少有类似物理退化预警 |

## 第三问：先看“串行回退”还是“并行表决”

问题 3 的资料 PDF 已核对：图 3-1 先运行主块并做验证测试；通过后输出结果，失败后进入异常处理并按图示尝试后备块。原表 3-2 对比运行环境、错误检测方法、恢复策略和实时性。以下按解析抽取列出的答案核对，不把其来源等级提升为官方标准答案。

但题干和解析足以核验两个核心机制：

- **恢复块**：主实现先运行，通过验收/验证测试判断；失败后回退，再尝试备选实现，属于反向恢复思路；
- **N 版本程序**：多个相互独立的版本针对相同输入运行，再通过表决决定结果，核心是并行多版本和表决。

## 一张可复用答题骨架

以后遇到可靠性案例，可以按下面顺序判断：

1. **先判问题层次**：定义/指标、失效机理，还是可靠性设计；
2. **再找故障来源**：物理退化、软件缺陷、节点单点还是运行环境；
3. **再看失败后动作**：检测、回退、切换、表决还是集群接管；
4. **最后匹配技术**：恢复块、N 版本、冗余、双机或集群；
5. **答案贴回题干**：说明该技术具体消除了哪个失效风险。

## 容易丢分的地方

- 把可靠性和可用性完全当成同一个概念；
- 直接把硬件“老化曲线”套到未修改的软件；
- 只背“冗余”二字，不说明故障后谁检测、谁接管或谁表决；
- 把恢复块和 N 版本都概括成“多份程序”，没有区分串行回退与并行表决；
- 把资料解析中的填空结论说成已核实的官方标准答案。

## 本题形成的可复用动作

> **先判可靠性问题层次 → 找失效来源 → 看故障后的处理动作 → 匹配容错技术 → 用题干证据解释为什么。**

这补上 G5 前四类案例动作之外的第五类：**可靠性案例不是先背方案，而是先从失效机理和故障处理路径识别技术。**
