## 先别看 SOA：题干真正的问题是什么

题干已经把集成难点写得很明显：

| 题干证据 | 说明什么 |
| --- | --- |
| 不同平台、数据库和中间件 | 实现环境异构 |
| 报文交换标准不同 | 数据格式/消息契约不统一 |
| 通信协议不同 | 传输方式不统一 |
| 希望最小改造旧系统 | 不能要求所有旧系统推倒重写 |
| 希望灵活交互和集成 | 不能继续大量两两硬编码连接 |

所以这题的第一判断不是：

> “SOA 很先进，所以选 SOA。”

而是：

> **旧系统能力仍然有价值，但它们的接口和通信方式彼此不统一；需要先把能力通过稳定契约暴露出来，再用统一集成基础设施处理差异。**

## 问题一：SOA 和 ESB 不要答成两个孤立定义

### 1. SOA 解决“能力怎样对外”

解析资料把 SOA 描述为：把应用的不同功能单元组织为**服务**，通过定义良好的接口和契约连接；接口采用尽量中立的方式描述，使服务不必依赖同一硬件平台、操作系统或编程语言。

放回题干就是：

> 分行旧系统内部怎么实现可以不同，但要把可复用业务能力通过稳定服务接口暴露出来。

所以答 SOA 时至少要落到三件事：

1. **能力服务化**：把业务功能组织成服务；
2. **接口/契约稳定**：调用方依赖契约，而不是依赖服务内部实现；
3. **跨异构环境交互**：降低平台和实现差异对调用方的影响。

### 2. ESB 解决“这些服务怎样接起来”

本题解析资料给出的 ESB 能力包括：

- 连接和整合服务；
- 服务描述/注册管理；
- 数据传递与转换；
- 路由、匹配和选择；
- 支持同步/异步等交互；
- 可进一步承载安全、服务质量、管理和负载等横切能力。

考试不要把它背成一串名词。先按“消除什么差异”分组：

| ESB 动作 | 消除/治理的问题 |
| --- | --- |
| 协议适配 | 系统 A 和 B 通信协议不同 |
| 消息/数据转换 | 报文格式、数据表示不同 |
| 路由与选择 | 请求应该发给哪个服务 |
| 服务发现/注册配合 | 调用方不必写死具体服务位置 |
| 安全、监控、QoS 等 | 通用治理不必散落到每个系统里 |

> [!warning] 边界
> 本题采用 ESB，是这道旧题给定的企业集成方案。不能把它扩展成“SOA 必须有 ESB”或“今天所有分布式系统都应该上 ESB”。

## 问题二：图缺失时，只训练能证实的架构角色

原题图 5-1 的六处填写如下：

| 图中空格 | 填入内容 | 图上的位置与职责 |
| --- | --- | --- |
| （1） | 业务层 | 位于应用层之下，业务 1、业务 2、业务 3 在这一层表达银行业务能力。 |
| （2） | UDDI | 服务注册中心；服务提供者登记服务，调用方通过它查找服务。 |
| （3） | publish | 服务发布者把服务信息发布到注册中心；图中与注册中心的发布关系相连。 |
| （4） | 企业服务总线 ESB | 位于服务与下层系统之间，负责连接、适配、转换与路由。 |
| （5） | 安全验证和质量管理 | 图右侧纵向贯穿多个层次，表示跨层服务治理。 |
| （6） | 组件层 | 位于服务层下方，封装并连接既有应用系统组件。 |

答案对应（c）、（i）、（h）、（e）、（g）、（j）。用图理解时，先看纵向层次，再看服务发现关系：

> 应用层使用业务层组织的能力；服务通过 publish 登记到 UDDI；调用关系由 ESB 承接并连接组件层中的既有系统；安全验证和质量管理贯穿这些层次。

注意把图里的三个角色分开：

- **UDDI** 是服务登记/查找位置；
- **publish** 是向注册中心登记服务的动作；
- **ESB** 承接运行时的服务连接和数据流转。

## 问题三：安全措施要先说“保护什么”

解析资料给出的三类措施可以压成三个目标：

1. **机密性**：使用 HTTPS/TLS 或其他加密机制保护传输内容；
2. **完整性**：使用哈希/消息摘要等机制发现数据被篡改；
3. **来源确认与抗抵赖**：对敏感交易使用数字签名等机制。

理论回链：

- [[01_综合知识/03_信息安全技术/03_网络与通信安全/TLS与HTTPS|TLS 与 HTTPS]]
- [[01_综合知识/03_信息安全技术/01_密码学与PKI/哈希算法|哈希算法]]
- [[01_综合知识/03_信息安全技术/01_密码学与PKI/数字签名|数字签名]]

这里的答题顺序最好是：

> **安全目标 → 机制 → 题干对象**

而不是只列“HTTPS、哈希、签名”三个名词。

## 一张可复用答题骨架

以后遇到“多个遗留系统需要整合”的案例题，按这个顺序：

1. **列异构证据**：平台、协议、格式、接口、数据源哪里不同；
2. **判断哪些资产不能推倒**：题干是否强调复用、最小改造、渐进集成；
3. **稳定能力边界**：把已有业务能力封装成服务/稳定接口；
4. **集中处理连接差异**：协议适配、数据转换、路由、发现；
5. **补横切治理**：安全、监控、QoS、管理；
6. **最后贴题干**：说明这些动作具体消除了题目里的哪种异构。

## 容易丢分的地方

- 只写“SOA 松耦合、可复用”，不解释题干中的平台/协议/报文异构；
- 把 ESB 简化成“消息队列”或“一个总线软件”；
- 把服务注册、协议转换、消息转换和路由写成互相重复的同一件事；
- 原图缺失时凭记忆给问题 2 填空位；
- 把旧题中的 ESB 方案写成现代系统的唯一正确集成方式；
- 问安全措施时只列产品，不说明机密性、完整性、来源确认等保护目标。

## 本题形成的可复用动作

> **异构现状 → 集成障碍 → 稳定服务契约 → ESB 转换/路由/解耦 → 安全横切保障。**

这是 G5 的第七类代表动作：面对企业系统整合题，先回答“**差异在哪里、谁负责吸收差异**”，再写 SOA / ESB 名词。
