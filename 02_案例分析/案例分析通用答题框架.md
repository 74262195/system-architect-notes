# 案例分析通用答题框架：从“我知道这个知识点”变成“我知道这题该答哪几句”

> [!summary]- 快速复习卡片（学完再看）
> **第一动作**：先看问题要求的是列举、判断、分析、策略、计算还是画图，不要先把脑子里的知识全部倒出来。
> **核心链路**：题目动作 → 题干证据 → 对应考点 → 结论 → 贴题理由/策略。
> **得分表达**：先写结论，再写与题干直接相关的理由；一问多点时分条，不用大段空泛描述。
> **易错点**：只背定义、不引用题干；把所有相关知识都写上；只写方案名却不解释为什么适合当前场景。

## 为什么综合知识学完了，案例题仍然可能不会答

综合知识常问“这个概念是什么、怎样区分、怎样计算”。案例题会换一种方式：先给一个项目背景，再问你**这个背景里的哪句话对应哪个知识点，以及针对这个具体约束应该采取什么动作**。

所以案例阶段不是重新造一套知识库，而是训练一层新的映射能力：

> **看到题干证据 → 识别它在考什么 → 调用已有知识 → 用题目要求的形式输出。**

例如题干写“交易请求必须在 1 秒内完成”，第一反应不是把所有质量属性定义背一遍，而是抓住 **响应时间约束**，先判断它指向性能，再按题目要求继续给出相应策略。

## 第一步：先识别问题要求你“做什么”

读完整个案例之前，可以先扫问题。不同动词决定答案长什么样。

| 问法 | 第一动作 | 答案最小形态 |
| --- | --- | --- |
| 列举 / 说明 | 数清要求几个点 | 名称 + 一句话解释 |
| 判断 / 指出 | 找题干证据并归类 | 结论 + 对应证据 |
| 分析原因 | 找“现象 → 机制”关系 | 原因 + 为什么导致该现象 |
| 给出策略 / 方案 | 先确定目标，再选措施 | 策略 + 为什么适合当前约束 |
| 比较 / 选择 | 先确定比较维度 | 方案差异 + 题干目标 + 选择理由 |
| 计算 | 先识别模型与已知量 | 步骤 + 中间结果 + 最终结果 |
| 绘图 / 补图 | 先确定图的规则与缺失对象 | 按题目规定的模型作图，不用文字替代 |

> [!tip] 考场第一动作
> **题目问几个点，就先给自己预留几个得分点位置。** 例如“指出 4 个要求对应的质量属性，并各给 2 个策略”，就应该立刻意识到答案至少有 4 组，每组都必须包含“属性 + 两个策略”。

## 第二步：圈出真正决定答案的题干证据

案例背景通常很长，但不是每句话权重都一样。优先圈下面几类信号：

- **数字指标**：1 秒、99.99%、10 秒恢复、6 小时内完成升级；
- **业务目标**：高并发、持续服务、保护隐私、快速迭代；
- **故障现象**：超时、单点故障、数据不一致、资源耗尽；
- **已有设计**：缓存、冗余节点、消息队列、分层、数据库复制；
- **限制条件**：不能停机、成本有限、旧系统不能修改、必须兼容某接口。

圈证据的目的不是摘抄，而是给下一步“归类”提供依据。

## 第三步：把证据映射到已经学过的模型

这一步才调用综合知识。

举几个最简单的映射：

- “响应时间必须小于某值” → 先想到**性能**；
- “故障后必须很快恢复” → 先想到**可用性 / 恢复能力**；
- “个人信息和交易信息不能泄露、篡改” → 先想到**安全性**；
- “经常增加功能，而且改动必须很快完成” → 先想到**可修改性**；
- “表结构、实体、关系、主外键” → 回到数据库设计；
- “不同候选架构哪个更适合” → 回到质量属性与架构权衡。

注意：**案例答案优先复用现有原子笔记的事实和术语。** 不为了案例题再写一份重复定义。

## 第四步：把答案写成“结论 + 贴题证据 + 动作”

最稳的表达不是万能套话，而是让阅卷者一眼看到你的结论和依据。

### 判断类

建议结构：

**结论：X。证据：题干出现 Y，因此对应 X。**

例如：

> 该要求对应性能，因为题干明确约束交易请求必须在规定响应时间内完成。

### 策略类

建议结构：

**目标属性 → 策略 → 为什么能改善题干中的指标。**

不要只写：

> “使用缓存、负载均衡。”

而要让策略和场景接上，例如：

> 可通过增加并行处理资源或降低单次请求资源需求来改善响应时间，从而直接针对题干中的性能约束。

具体策略名称以对应知识卡和真题资料为准，不能凭空扩写成所谓“标准答案”。

### 比较选择类

建议结构：

1. 题干最重要的目标是什么；
2. 方案 A 在该目标上的表现；
3. 方案 B 在该目标上的表现；
4. 给出选择并说明取舍。

不要先写“我认为 A 更好”，再补与题干无关的优缺点清单。

## 一道题如何做完而不是“看懂答案就算会了”

完成一道案例题后至少做一次反向复盘：

1. **遮住答案，只看题干**：能不能自己圈出决定性证据；
2. **只看证据**：能不能说出对应知识点；
3. **只看问题要求**：能不能先列出答案需要几个槽位；
4. **对照资料答案**：漏的是知识点，还是“知道但没写出来”；
5. **回链笔记**：若知识本身不会，回到综合知识；若知识会但答不出，则记录为案例表达问题。

这两类错误要分开：

- **知识缺口**：不知道什么是性能、可用性、某种架构策略；
- **案例能力缺口**：知道知识，但没有从题干证据识别出来，或者没有按得分点表达。

## 不使用“万能答题句”代替题干分析

像“提高系统性能”“增强可扩展性”“采用冗余机制”这类句子本身可能正确，但如果没有回答题目指定对象和约束，就可能只是泛泛而谈。

案例阶段真正要训练的是：

> **每一个答案点，都能指回题干中的某个要求、现象或限制。**

## 第一个训练样本为什么选 2009 下半年试题一

仓库中的该案例原始抽取当前标记为 `extract_status: 可解析`，其试题一给出在线交易平台的响应时间、安全、故障恢复和快速变更等约束，并要求识别质量属性和给出架构策略。

它非常适合练习今天这套动作：

> **数字/业务约束 → 质量属性 → 实现策略。**

下一批不会把解析资料直接当“官方标准答案”，而会同时保留题面来源与解析资料来源属性，再做真题拆解。

## 自测

1. 一道题要求“指出 4 个需求分别对应什么质量属性，并且每个属性给 2 个策略”，你读题后的第一动作是什么？

> [!answer]- 第 1 题答案与解析
> **答案**：先建立 4 组答案槽位，每组必须包含“质量属性 + 两个策略”，然后再回题干逐组找证据。
> **解析**：先解析题目要求，可以避免只答属性却漏掉策略等结构性失分。

2. 题干写“故障发生后 10 秒内恢复”，为什么不能只在答案里写“提高可靠性”？

> [!answer]- 第 2 题答案与解析
> **答案**：因为题干给的是具体故障恢复约束，需要先按现有知识体系判断对应属性，再给能直接作用于恢复/可用性的策略，并说明与该约束的关系。
> **解析**：案例答案要贴题，不能只给宽泛上位词。

3. 你知道缓存能改善部分性能场景，但题目问的是“如何保护客户交易信息”，为什么不能把缓存写进去凑点？

> [!answer]- 第 3 题答案与解析
> **答案**：因为策略必须服务于题目当前目标；保护交易信息首先是安全目标，缓存不是因为“也是架构技术”就自动成为有效答点。
> **解析**：案例题不是相关知识越多越好，而是答案点与题干目标越准确越好。
