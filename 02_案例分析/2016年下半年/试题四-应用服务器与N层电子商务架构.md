某电子产品制造公司原来只有一个企业网站，主要做宣传、产品介绍、客服和售后服务，技术上采用 Web 服务器和动态脚本语言。随着业务扩展，公司准备建设完整电子商务平台，新增订单、支付、库存等功能，而且未来要面向全球用户提供 **24 小时不间断服务**，在大负荷和长时间运行下仍要保持稳定。

张工主张直接扩展原网站；王工认为旧架构已难以承担新的业务规模和运行要求，建议采用应用服务器方式重新建设电子商务平台，例如题目语境中的 J2EE。

## 问题一：不要先比较 PHP 和 Java，先比较“旧系统任务”和“新系统任务”

旧系统主要承担：

> 企业宣传 → 产品介绍 → 客服 → 售后服务。

新系统增加了：

> 订单 → 支付 → 库存 → 全球访问 → 7×24 → 大负荷 → 长时间稳定运行。

真正发生变化的是**系统职责和质量属性**。

因此原系统不足可以先从三组问题作答：

### 1. 业务复杂度已经上升

展示型网站可以把大量处理直接放在 Web 应用中，但订单、支付、库存会带来更多业务规则、事务、数据访问和跨模块协作。

第一反应应是：

> **表示、业务逻辑和数据访问需要更清晰地分开。**

理论回链：

- [[06_架构设计理论与实践/02_层次式架构/层次式架构：为什么要让上层只使用下层服务|层次式架构]]
- [[06_架构设计理论与实践/02_层次式架构/业务逻辑层框架：怎样把业务代码组织得能改又不乱|业务逻辑层框架]]

### 2. 运行规模已经上升

题干明确要求全球服务、大负荷和长时间运行，因此系统不再只是“单机 Web 页面能打开”。

需要开始考虑：

- 多实例承载请求；
- 公共资源统一管理；
- 节点故障后的继续服务；
- 根据负载增加实例。

### 3. 公共技术能力不能散落在每个业务模块里

订单、支付、库存都会反复遇到事务、连接、并发和资源管理问题。如果每个模块自己处理，会增加重复代码和运行风险。

对应理论：

- [[06_架构设计理论与实践/02_层次式架构/事务处理：多步修改失败时怎样回到原状|事务处理]]
- [[06_架构设计理论与实践/02_层次式架构/数据库连接池：连接用完为什么通常要归还而不是关闭|数据库连接池]]

> [!warning] 不要这样答
> 不要把“PHP 是面向过程、Java 是面向对象”“PHP 天生不安全/不可靠”当成这题的核心规律。语言本身不是题干里 7×24、扩展性和故障接管的充分解释。考试复盘应把旧资料中的语言比较重新落回**架构和运行平台提供了什么能力**。

## 问题二：应用服务器不是“更大的 Web 服务器”

这道题要回答的核心是：

> **把通用的企业应用运行能力集中到一个受管理的运行环境里，让业务组件不必自己重复处理这些问题。**

在本题旧 J2EE 语境中，可以把应用服务器理解为承载业务逻辑、向客户端提供业务能力，并统一提供运行管理能力的平台。

做题时重点不是背产品，而是抓三类能力。

### 大负荷：多个实例一起承载

如果单台应用服务器无法承担请求，可以部署多个实例，让请求由多个节点共同处理。

这一步解决：

> **一台机器能力不够 → 增加节点共同承担。**

它与 [[01_综合知识/08_软件可靠性技术/04_可靠性设计/11_系统配置：双机热备与集群怎样服务可靠性目标|集群与系统级冗余]] 的共同思想是：不要让全部服务能力押在一个节点上。

### 可扩展：负载增长时可以增加处理节点

扩展性不是“服务器配置更高”这一条路。题目更希望你看到：

> **业务量继续增长时，可以增加应用服务器实例，而不是只能推翻整个程序。**

因此答题时可写成：

> 通过多实例/集群部署，把处理能力从单节点扩展为多节点；随着负载增长增加节点，提高整体处理能力。

### 稳定性：节点故障后仍有其他节点可接管

解析资料强调：一个应用服务器故障时，可由其他正常节点继续承载业务。

正确的考试动作是：

1. 先找有没有冗余节点；
2. 再找故障怎样被检测；
3. 最后找请求/业务怎样转移到健康节点。

这和“高可用”主线相同：

> **冗余 + 故障检测 + 切换/接管。**

可以回链：

- [[06_架构设计理论与实践/06_通信系统架构/网络高可用设计：怎样让故障少影响业务且更快恢复|网络高可用设计]]

但要注意，本题讲的是应用服务器层的运行可用性，不等于已经完成整个网络高可用设计。

## 问题三：N 层先看职责，不先背图中五个名字

题干已经给出最重要的信息：

> 不同逻辑功能封装到不同构件；不同层次的构件可以分别部署到不同机器。

这里先建立两个概念。

### “层”回答：谁负责什么

例如可以按逻辑理解为：

> 客户端/表示 → Web 交互 → 业务逻辑 → 数据/企业信息系统。

重点是**职责划分与依赖边界**。

### “部署到不同机器”回答：这些层跑在哪里

逻辑分层和物理部署不是一回事：

- 四层逻辑不代表必须四台机器；
- 同一层可以有多个实例；
- 不同层也可能合并部署。

这正是 [[06_架构设计理论与实践/02_层次式架构/层次式架构：为什么要让上层只使用下层服务|层次式架构]] 中的核心边界。

原题解析给出的 Applet、Servlet、EJB 等名称属于当时 J2EE 技术体系的识别内容。本页不要求把这些旧构件名扩展成现代 Web 架构的唯一实现方式。

## 一张可复用答题骨架

以后看到“旧网站升级为大型业务系统”的案例，按这个顺序：

1. **先比较业务职责**：展示型网站变成了哪些核心交易业务？
2. **再比较质量要求**：并发、7×24、稳定性、扩展性是否明显提高？
3. **找需要下沉的公共能力**：事务、连接、资源管理、运行管理；
4. **按职责分层**：表示、业务、数据访问/数据等不要混在一起；
5. **按负载扩节点**：单实例不够时增加实例共同承担；
6. **按故障设计接管**：有冗余还不够，还要检测和切换。

## 容易丢分的地方

- 把题目做成“PHP vs Java 哪个更好”的语言战争；
- 只写“J2EE 更稳定”，不说明稳定来自什么运行机制；
- 把“多层”理解成“必须多台服务器”；
- 把性能扩展和故障接管混为一件事；
- 图缺失时根据答案列表反推原图坐标；
- 把 2016 年题目的 J2EE 技术栈写成今天所有电商系统都必须采用的方案。

## 本题形成的可复用动作

> **业务增长/7×24 → 识别旧架构边界 → 公共运行能力下沉 → N 层职责拆分 → 多节点扩展 → 故障接管。**

这是 G5 的第八类代表动作：遇到“旧系统还能运行，但新业务规模和质量要求已经变了”的题，先判断**架构能力是否还匹配问题规模**，而不是先换技术名词。
