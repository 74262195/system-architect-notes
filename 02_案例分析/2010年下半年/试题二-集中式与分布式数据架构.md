# 2010 下半年试题二：业务要扩张时，怎样在集中式与分布式数据架构之间做选择

> [!summary]- 快速复习卡片
> **第一动作**：先圈业务增长、地域扩展、单点故障、读多写少等约束，再判断题目是在问“架构选择”“读写路径”还是“扩展方式”。
> **问题 1**：比较集中式与分布式数据架构，不只背定义，还要写控制位置、数据分布和代价。
> **问题 2**：先找单点，再把数据库、热备与缓存的职责分开；读与写分别走不同路径。
> **问题 3**：集中式主要向上扩展（Scale Up），分布式主要向外扩展（Scale Out）。
> **总判断**：题干给出全国扩张、客户增长和可扩展性要求，因此资料答案选择分布式数据架构。

## 题干先圈哪几句话

本题真正决定方案的不是“RMO 是运动服装公司”，而是下面四类约束：

- **5 年内从华南扩展到全国**：数据和访问会跨更多地域；
- **潜在客户数量大幅增加**：容量与并发需求持续增长；
- **要求避免单点故障**：不能只考虑性能，还要考虑可用性；
- **刘工提出局部数据库 + 缓存的读写分离**：后续问题会继续追问读、写、缓存失效和扩展方式。

所以第一动作是把题干翻译成：

> **业务规模和地域扩大 → 需要可扩展、可用的数据架构 → 比较集中式与分布式，并说明读写路径与扩展手段。**

## 问题 1：比较架构时不要只写“一个库 / 多个库”

资料答案的核心可以压成三个比较维度：

| 维度 | 集中式数据架构 | 分布式数据架构 |
| --- | --- | --- |
| 数据位置 | 数据集中在单个中心位置/数据库系统 | 数据分布在多个局部数据库或计算节点 |
| 管理方式 | 系统和数据管理集中控制 | 多个数据库系统协同，数据可跨节点访问与传送 |
| 典型取舍 | 结构简单、维护与成本较低，但易形成瓶颈和单点 | 容错和扩展能力更强，但同步、协作和维护更复杂 |

### 考场作答骨架

先各写一句定义，再各补一个“为什么适合/不适合本题”的取舍：

1. 集中式：数据与管理集中，简单、成本低，但单点和扩展能力受中心节点限制；
2. 分布式：多个节点/局部数据库共同承载数据与访问，利于地域扩展和容错，但同步协作更复杂；
3. 贴题干：RMO 将全国扩张、客户增长，所以资料答案选择分布式方案。

## 问题 2：先画清“谁负责读、谁负责写”，再答 CRUD

题目不是泛问数据库高可用，而是明确建立在“局部数据库 + 缓存”的读写分离方案上。资料答案增加热备数据库以降低单点故障风险，并把职责分成：

- **局部数据库**：持久化和写入；
- **热备数据库**：主数据库故障时提供备份/恢复能力；
- **缓存**：承载大量读取访问。

CRUD 的稳定作答顺序：

1. **读**：先查缓存；命中直接返回，未命中再读数据库并回填缓存；
2. **新增**：资料答案采用延迟加载，直接写数据库；
3. **修改**：修改数据库，并把对应缓存标记失效；
4. **删除**：删除数据库记录，并把对应缓存标记失效。

> [!important] 不要把旧题资料直接升级成现代系统的唯一最佳实践
> 真实工程中还会涉及复制延迟、缓存一致性、故障切换、事务边界等问题。本页只保留完成这道题所需的资料口径；不能因为一道 2010 年案例就扩写出一整套现代分布式数据库知识库。

## 问题 3：先判断扩展方向，再写手段

资料答案给出的核心对比是：

- **集中式 → Scale Up（向上扩展）**：增加 CPU、内存、磁盘等资源，或升级到更强的单机硬件；
- **分布式 → Scale Out（向外扩展）**：增加节点，并配合数据复制、垂直/水平切分、缓存等手段分担负载。

这里最容易丢分的是只写“扩容”。题目明确要求分别说明两种架构，因此先预留两个答案槽位：

> 集中式：向上扩展 → 单机资源增强。
>
> 分布式：向外扩展 → 增加节点并拆分/复制数据与负载。

## 本题形成的新答题能力

前两份样本分别训练“质量属性 → 策略”和“安全威胁 → 认证/抗抵赖”。本题增加第三种动作：

> **业务增长证据 → 数据架构选型 → 单点识别 → 读写路径 → Scale Up / Scale Out。**

以后看到“用户量持续增长、跨地域部署、数据库瓶颈、缓存、读写分离、扩展性”时，先判断题目到底要你回答：

- 为什么选集中式/分布式；
- 单点在哪里、怎样消除；
- 读写分别经过哪些组件；
- 是向上扩展还是向外扩展。

不要把四种问题混成一段“上缓存、做集群、加机器”的泛化答案。

## 最容易丢分的地方

1. 只背“集中式一个库、分布式多个库”，没有写控制方式与取舍；
2. 看到缓存就把所有 CRUD 都写成先访问缓存，忽略题目资料中的读写路径差异；
3. 问“避免单点故障”时只答缓存，没有处理数据库本身的故障；
4. 把 Scale Up 和 Scale Out 写反；
5. 不贴题干的全国扩张、客户增长，直接给通用技术清单；
6. 把解析资料中的旧实现细节写成今天所有系统都必须采用的绝对规则。

## 自测

1. 为什么“客户数量大幅增加”不能直接推出一定要使用缓存，却可以作为可扩展性需求的证据？
2. 为什么缓存可以分担读压力，但不能单独解决数据库单点故障？
3. 给单台数据库增加 CPU 和内存属于 Scale Up 还是 Scale Out？增加数据库节点并水平拆分数据呢？
