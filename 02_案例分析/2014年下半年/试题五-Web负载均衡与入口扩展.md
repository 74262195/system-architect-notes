# 2014 年下半年试题五：Web 负载均衡与入口扩展

## 原题｜先独立作答

> [!warning] 本批只训练问题 1
> 原题问题 2 的数据库分区/主从复制、问题 3 的缓存机制，与 [[2010年下半年/试题二-集中式与分布式数据架构|G5-03 数据架构与扩展]] 已形成的能力高度重叠。本页不复制第二套数据库答案。

某社交网站随着用户数量和访问量增长，Web 服务器负载和数据库磁盘 I/O 都出现明显瓶颈。项目组准备调整三层架构以提高并发处理能力。

针对 **Web 服务器负载过大**，项目组计划在客户端和 Web 服务器集群之间加入负载均衡机制。王工提出基于 DNS 的负载均衡，李工提出基于反向代理的负载均衡，最终采用后者。

### 问题 1

1. 简要说明基于 DNS 的负载均衡原理；
2. 简要说明基于反向代理的负载均衡原理；
3. 从执行效率、安全性、实现简易性等方面比较两种机制。

### 问题 2、3

原题后续还考查数据库水平分区、MySQL 主从复制和 Memcached。这里不展开，做完问题 1 后回到 [[2010年下半年/试题二-集中式与分布式数据架构|集中式与分布式数据架构案例]] 复习数据层扩展动作。

## 第一步：先问“瓶颈在哪里”

题干同时出现两个瓶颈：

- Web 服务器负载过大；
- 数据库磁盘 I/O 瓶颈。

问题 1 只问前者。

因此不能一看到“并发高”就把 CDN、缓存、分库、主从、消息队列全部写上去。第一动作应是：

> **入口 Web 处理能力不足 → 增加多个 Web 节点 → 再解决请求如何分配。**

这一步和 [[06_架构设计理论与实践/06_通信系统架构/网络高可用设计：怎样让故障少影响业务且更快恢复|网络高可用设计]] 有交集，但本题重点更偏**流量分担与节点选择**。

## DNS 负载均衡：在“域名解析”阶段分流

基于 DNS 的方案可以让同一个域名对应多个服务器地址。客户端查询域名时，DNS 返回其中一个地址，从而把不同客户端引向不同服务器。

先回忆 DNS 的本职工作：

- [[01_综合知识/01_计算机系统基础知识/03_计算机网络/07_应用层/01_名称与地址配置/DNS域名解析|DNS 域名解析]]

本题资料采用的典型思路是循环返回多个主机地址。

所以它的直观特点是：

> **分流发生得早，而且结构简单；但 DNS 本身通常并不知道某台 Web 服务器此刻到底忙不忙、是否刚刚故障。**

不要把“DNS 负载均衡”理解成 DNS 服务器在转发每一个 HTTP 请求；DNS 只是先帮客户端得到一个目标地址，后续请求通常直接去该目标。

## 反向代理负载均衡：请求先到一个统一入口再转发

反向代理方案中，客户端先连接代理/负载均衡入口，再由它把请求转发给后端多个 Web 服务器。

本题最值得抓住的关系是：

> **客户端 → 统一入口 → 后端 Web 节点。**

因为入口真正看到了请求，并且可以掌握后端节点状态，所以相较简单 DNS 轮询，它更容易：

- 根据不同节点能力或当前负载选择后端；
- 发现某节点异常后停止继续把新请求发给它；
- 隐藏真实后端地址；
- 在入口统一做部分安全、缓存或连接处理。

> [!warning] 边界
> “反向代理一定更安全”“一定更快”都不是绝对规律。增加统一入口本身也会引入容量和可用性设计问题。本题只按给定场景比较两种方案。

## 为什么“能看节点状态”很重要

假设有 3 台 Web 服务器：

- A：负载 30%；
- B：负载 95%；
- C：已经故障。

简单 DNS 轮询若仍把三个地址都视为可用，就可能把新客户端继续分给 B 或 C。

如果入口能够持续掌握后端状态，则可以把新请求优先发给健康且更空闲的节点。

这就是本题从“负载均衡”向“高可用”靠近的地方：

> **不仅要有多个节点，还要知道哪些节点当前可用。**

但完整高可用还应继续问：入口自己是不是单点、链路是否冗余、默认网关如何切换、故障检测多快、切换多快。这些由理论主事实源继续承担，本题不越界扩写。

## 三个维度怎么比较

### 1. 简易性

DNS 方案通常更直接：一个域名配置多个地址即可形成基础分流。

反向代理要增加入口组件，还要配置后端、转发和健康状态，因此架构更复杂。

### 2. 状态感知与分流能力

DNS 基础轮询主要依据地址轮换，并不天然等于实时感知后端负载。

反向代理因为处在请求路径上，更容易结合后端健康状态、负载和调度策略动态选节点。

### 3. 安全与暴露面

DNS 方案通常把后端服务器地址直接返回给客户端。

反向代理场景下，客户端只需要访问统一入口，真实后端可以隐藏在内部网络中；入口还可以集中承载一部分安全控制。

考试作答时最好写成：

> **机制差异 → 导致什么能力差异 → 为什么与题干有关。**

不要只背“DNS 简单、反向代理安全”两个结论。

## 它和 G5-08 有什么区别

[[2016年下半年/试题四-应用服务器与N层电子商务架构|G5-08]] 已经训练了：

> 业务增长 → 多节点扩展 → 故障接管。

本题进一步追问：

> **节点已经有多台了，那么入口怎样决定“这一次请求交给哪一台”？**

所以这不是重复，而是把“多节点”继续向前走一步到**流量分配机制**。

## 一张可复用答题骨架

以后遇到“Web 集群 + 负载均衡”的案例：

1. **找瓶颈层**：入口、应用、数据库还是存储？
2. **先扩处理节点**：单节点不足时是否已有多个后端？
3. **找流量分配位置**：DNS 阶段分，还是请求到统一入口后再分？
4. **看状态感知**：能否知道后端健康与当前负载？
5. **看故障行为**：节点挂了以后，新请求是否还能被送过去？
6. **看安全与复杂度**：是否暴露后端、是否增加新的入口组件和单点。

## 容易丢分的地方

- 题目问 Web 层，却把数据库缓存写成问题 1 的主体；
- 认为 DNS 会代理或转发每次 HTTP 请求；
- 只写“轮询”，没有说明是“同一域名对应多个服务器地址”；
- 只写“反向代理更好”，不解释它为什么更容易感知节点状态；
- 把负载均衡等同于完整高可用；
- 忽略负载均衡入口自身也需要容量和可用性设计；
- 把旧题资料中的比较结论写成所有现代系统的绝对规律。

## 本题形成的可复用动作

> **入口过载 → 横向扩 Web 节点 → 决定流量在哪里分 → 比较 DNS 与反向代理 → 检查状态感知、故障节点和暴露面。**

这是 G5 的第九类代表动作，也是通信系统架构案例的第一个子样本。
